高可用性クラスタリングにおける仮想IPアドレス（VIP）の仕組みとは？

高可用性クラスタにおける仮想IPアドレスとは何ですか？

  • **定義:仮想 IP (VIP) アドレスは、高可用性**で使用されるフローティング ネットワーク アドレスでアプリケーションへの継続的なアクセスを保証します。標準 IP とは異なり、VIP は特定の物理ハードウェア インターフェイスにバインドされず、クラスタ ノード間を移動して、クライアントに対して単一の永続的なエントリ ポイントを維持します。
  • ハードウェア不要： SafeKit **Gratuitous ARP（GARP）**を使用してソフトウェアレベルでVIPを管理するため、同一サブネット環境では外部ロードバランサーは不要です。
  • **アプリケーションの透過性:**ローカル VIP にバインドすることで、アプリケーションはフェイルオーバー イベントを認識せず、クライアントの送信元 IP アドレスと既存のセキュリティ構成を維持します。
  • **ディザスターリカバリー:**拡張 LAN を使用するとリモートデータセンター間で同じ VIP を使用できるため、複雑な DNS 再ルーティングや TTL キャッシュの遅延と比較して、サイト間のフェイルオーバーが簡素化されます。

SafeKitにおける仮想IPの実装

  • Mirrorクラスター: 、リアルタイムのレプリケーションとフェイルオーバーを容易にするために、プライマリ サーバーでのみアクティブなフローティング IP を備えています。
  • **Farmクラスター:**すべてのノード間で VIP を同時に維持することにより、ネットワーク負荷分散を有効にします。

主な利点： VIPは、 Gratuitous ARP（アドレス解決プロトコル）またはMACアドレステイクオーバーを利用することで、クライアントの手動再構成なしにシームレスなアプリケーションのフェイルオーバーを可能にし、24時間365日のビジネス継続性を保証します。

  • クラウドおよびマルチサブネット: 、外部ロードバランサーのヘルスチェック ( AWS 、 Azure 、 GCP ) を介して管理され、異なるサブネット間でトラフィックをリダイレクトします。

SafeKit VIP エイリアシングと MAC アドレス マッピング 標準的なSafeKit mirrorクラスタでは、両方のノードが同じローカル サブネットに存在するため、高可用性は**ソフトウェア定義の仮想 IP (VIP)**によって実現されます。ハードウェア ベースのソリューションとは異なり、 SafeKitこの VIP は OS ネットワーク スタック内で直接管理されます。この VIP は、クライアントの永続的な論理エントリ ポイントとして機能し、 IP エイリアシングを介してサーバー 1 とサーバー 2 の固有の物理 IP アドレスの上にレイヤー化されます。

SafeKitの高度な IP エイリアシングと複数の VIP のサポート

SafeKitソリューションの重要な利点は、ネットワークIDの管理における柔軟性です。VIPは、ノード間を「移動する」3番目のIPアドレスです。特に、 SafeKit 、単一のクラスタ内で複数の仮想IPアドレスを管理できます。これらは、同じプライマリイーサネットカードに割り当てることも、異なる物理カードに分散させることも可能で、異なるサービスを特定の仮想IDに紐付ける複雑な構成にも対応できます。

フェイルオーバーメカニズム：Gratuitous ARP (GARP)

SafeKit ハードウェア障害発生時に手動介入が一切ないことを保証します。通常動作時、VIPは以下のようにマッピングされます。 サーバー1のMACアドレス（mac1）。 もし SafeKit サーバー1でハートビート障害を検出すると、2段階の復旧手順を実行します。

  • アプリケーション復旧: SafeKitは、サーバー 2 上の重要なアプリケーション サービスを自動的に再起動します。
  • ネットワーク再ルーティング: SafeKitは、 **Gratuitous ARP (GARP)メッセージを即座にブロードキャストします。これにより、すべてのネットワークスイッチと接続されているクライアントの ARP キャッシュが強制的に更新され、VIP がサーバー 2 の MAC アドレス (mac2)**に再マッピングされます。

リモートデータセンターと拡張VLAN

SafeKitの同一サブネットアルゴリズムは、通常はローカルクラスタで使用されますが、拡張LANまたはストレッチVLANを介して接続されたリモートサイト全体での**災害復旧（DR）**には最適な選択肢です。この「ストレッチ」アーキテクチャにより、地理的な距離を超えて単一のサブネットを維持できるため、ネットワークトポロジが大幅に簡素化され、複雑なルーティングプロトコルのオーバーヘッドを回避できます。

⚠️ 注意: Gratuitous ARP によるレイヤ 2 ルーティングは、 最も透明性の高いソリューション アプリケーション向け。ロードバランサーを使用したレイヤー 3 ルーティングとは異なり、 **送信元/宛先 IP 変換 (SNAT/DNAT)**アプリケーションは元のクライアントIPアドレスで直接トラフィックを受信し、仮想IPアドレスはローカルで設定されます。 多くのアプリケーションは ローカルで仮想 IP を確認し、元のクライアント IP を直接受信します。この透明性がなければ、 期待どおりに動作しない可能性があります 複雑なネットワーク翻訳のため。

SafeKitヘルスチェックによる動的ルーティング

SafeKit 、各ノードに専用のヘルスチェックURLを提供することでトラフィックのルーティングを管理します。ロードバランサーはこれらのURLに問い合わせてクラスタの状態を判断します。

  • **プライマリノード (PRIM):**ヘルスチェックの結果、 HTTP 200 OKが返されました。ロードバランサーはすべてのトラフィックをここにルーティングします。
  • **セカンダリノード（セカンド）：**ヘルスチェックの結果、 HTTP 404 NOT FOUNDが返されました。ロードバランサーはこのノードにトラフィックを送信しません。

フェイルオーバーイベントが発生すると、 SafeKitヘルスチェック応答を即座に切り替え、ロードバランサーがクライアントトラフィックを新しいプライマリサーバーに再ルーティングするようにトリガーします。

⚠️ 注: SafeKitはヘルスチェックロジックを提供します。物理または仮想ロードバランサーは、ネットワークインフラストラクチャによって提供される必要があります。

Farmクラスタアーキテクチャ: WindowsまたはLinuxノード間での負荷分散

カーネルフィルタリングによる分散トラフィック処理 負荷クラスタでは、 farm IP（VIP）アドレス使用して、クライアント要求を複数のサーバーに同時に分散します。この例では2つのノードを使用していますが、このアーキテクチャはより大規模なサーバーファームをサポートするように拡張できます。同一サブネット構成では、IPエイリアシングを使用してクラスタ内のすべてのサーバーのカードにVIPが構成されます。

トラフィック分散：カーネルレベルフィルタ

単純なフェイルオーバークラスタとは異なり、 farmクラスタは、特殊なカーネルレベルフィルタを介してトラフィックを管理します。そのプロセスは次のとおりです。

  • **ARP マッピング:**クライアントの ARP キャッシュでは、VIP は最初に単一のハードウェア アドレス (サーバー 1 のmac1など) に関連付けられます。
  • パケット分割:サーバー 1 がトラフィックを受信すると、 SafeKitカーネルフィルタは、受信パケットの識別情報 ( クライアント IPまたはTCP ポートに基づく) を分析します。
  • **負荷分散:**フィルタは、どのパケットをローカルで処理し、どのパケットを他のノード (サーバー 2 など) にリダイレクトして処理するかを決定し、ワークロードのバランスを確保します。

プライマリノード（サーバー1）が故障した場合、クラスターは可用性を維持します。 無償ARP（GARP）. SafeKit クライアントのARPキャッシュを更新するためにGARPメッセージをブロードキャストします。 mac2 サーバー 2 の。これにより、プライマリ「エントリ ポイント」が失敗した場合でも、クライアントはすぐにサーバー 2 の残りのノードに再ルーティングされます。 farm.

インテリジェントなトラフィックルーティングと負荷分散ルール

ロードバランサーは、主に次の2つの要素に基づいてクライアントからのリクエストを分散します。

  • 分散ルール:トラフィックは、セッションアフィニティまたはロードバランシングアルゴリズム (例: クライアント IP アドレスまたはクライアント TCP ポートの分析) に従って分割されます。
  • **ノードの可用性:**トラフィックは、 SafeKitヘルスチェックによって正常と判断されたノードにのみルーティングされます。

⚠️ 注: SafeKitはヘルスチェックロジックを提供します。物理または仮想ロードバランサーは、ネットワークインフラストラクチャによって提供される必要があります。

SafeKitヘルスチェックメカニズム

SafeKit 、 farm内のすべてのサーバーにリアルタイムのヘルスチェック URLを提供し、その運用状況をロードバランサーに伝達します。

  • **ノードが稼働中:**ヘルスチェックの結果、 HTTP 200 OKが返されました。ロードバランサーはこのサーバーをアクティブローテーションに含めています。
  • **ノードダウン/フェイルオーバー:**サーバーまたはアプリケーションに障害が発生した場合、 SafeKit HTTP 404 NOT FOUNDを返します (またはサービスにアクセスできなくなります)。ロードバランサーは、障害が発生したノードへのトラフィックの送信を直ちに停止します。

仮想IPとDNSリダイレクト：DNSフェイルオーバーが失敗する理由

DNS伝播の落とし穴：VIPがDNSリダイレクトよりも優れている理由

高可用性アーキテクチャにおいて、フェイルオーバーにDNSを利用することは、しばしば誤った安心感を生み出します。DNSレコードを変更してバックアップサーバーを指すようにすることは、一見簡単な復旧方法のように思えますが、予測不可能な遅延という重大な問題を引き起こします。DNSベースのリダイレクトは、変更を認識して伝播するために、制御不能な中間リゾルバのエコシステムに依存するため、現代のエンタープライズサービスにおける「ダウンタイムゼロ」の要件とは根本的に相容れません。

技術的なシナリオ：DNS解決と「停止」したクライアント

標準的なネットワーク構成では、仮想名**（DNS名）** ユーザーにとって人間が読みやすいエントリポイントとして機能します。しかし、データがネットワークを介して送信されるためには、その名前が特定の物理IPアドレスに解決される必要があります。

高可用性クラスタにおける物理IP 1上のDNS解決と「スタック」したクライアント

現在の状態: 物理IP 1への解決

まず、 クライアント 1とクライアント 2は、DNS システムに仮想名を問い合わせます。システムは物理 IP 1を返します。その後、クライアントはその特定のハードウェア アドレスへの直接ネットワーク接続 (ソケット) を確立します。

フェイルオーバーの課題：物理IP 2への再ルーティング

物理IPアドレス1のサーバーが故障した場合、管理者はDNSレコードを更新して物理IPアドレス2を指すようにします。クライアントのルーティングを正常に行うには、以下の「完璧な」手順が必要です。

  • の有効期限 (TTL) 、すべての中間 ISP および企業リゾルバで期限切れになる必要があります。
  • クライアント1とクライアント2の両方のローカルDNSキャッシュをクリアする必要があります。
  • アプリケーションは既存のソケットを閉じ、新しいDNSルックアップを開始する必要があります。

これらの手順のいずれかが省略されると、 **クライアント 1 とクライアント 2 は、**無効な物理 IP 1 との通信を試み続ける「スタック」状態になり、DNS レコードが更新されてもサービスが停止します。

DNSリダイレクトの2つの「ブラックボックス」

  • **再帰的キャッシング:**多くのインターネット サービス プロバイダ (ISP) および企業の DNS リゾルバは、トラフィックを削減するために低い TTL 設定を無視し、要求された有効期限を超えて「古い」物理 IP 1 を数分または数時間キャッシュすることがよくあります。
  • **アプリケーションの永続性:**最新のアプリケーション (Java ベースのマイクロサービスや Web ブラウザなど) は、起動時に DNS ルックアップを一度だけ実行することがよくあります。DNS レコードが物理 IP 2 に更新された場合でも、アプリケーションは内部メモリに保存されている初期 IP を引き続き使用します。

結論

DNSリダイレクトは、高可用性ソリューションとしては一貫性に欠ける解決策です。ローカル環境またはリージョン環境内で瞬時にフェイルオーバーを実現するには、ソフトウェア定義のIP（VIP）を使用することが、ダウンゼロの永続性を保証する唯一の方法です。

仮想IP（VIP）とネットワーク

仮想IP（VIP）とは何ですか？また、物理IPとはどのように異なりますか？

物理IPアドレス****特定のネットワークインターフェースにバインドされますが、仮想IP（VIP） ****ハードウェアに依存しない「フローティング」アドレスです。 SafeKitでは、VIPは永続的なエントリポイントとして機能します。プライマリサーバーに障害が発生した場合、VIPは自動的に正常なセカンダリノードに移行するため、クライアントの再設定は不要です。

仮想IPを使用するには、ハードウェアロードバランサーが必要ですか？

いいえSafeKit高可用性ソフトウェアは、ソフトウェアレベルで仮想 IP を管理します。同一サブネットアーキテクチャでは、 IP エイリアシングと**Gratuitous ARP (GARP)**を利用してトラフィックをリダイレクトします。これにより、外部ハードウェアロードバランサーや専用プロキシサーバーのコストと複雑さが解消されます。

Gratuitous ARP（GARP）とは何ですか？また、なぜ使用されるのですか？

**Gratuitous ARP (GARP)**は、ネットワークスイッチとルーターの ARP テーブルを更新するネットワークブロードキャストです。フェイルオーバー中、新しいプライマリサーバーは GARP パケットを送信して、 仮想 IPがその MAC アドレスにマッピングされたことを通知し、ネットワークファブリック全体でトラフィックの再ルーティングを即座に実行します。

仮想IPアドレスにDNS名を関連付けることはできますか？

はい。標準の A レコードを作成することで、DNS 名を VIP に関連付けることができます。主な利点は、リダイレクトがVIP レベル (ARP またはネットワークリダイレクト経由) で管理され、 **DNS レベルでは管理されないことです。**これにより、DNS 伝播や TTL の期限切れに伴う遅延を回避することで、 アプリケーションの透過性が確保されます。

DNSルーティングと仮想IPアドレスの制限事項は何ですか？

DNSのリルーティングは**TTL（Time to Live）**とクライアント側のキャッシュによって制限されるため、復旧に数時間かかる場合があります。大きな欠点は、 DNS名を再解決できないクライアントが、障害が発生したサーバーへの接続を試み続けることです。これに対し、仮想IPは瞬時にレイヤー2フェイルオーバーを提供し、すべてのトラフィックを即座にリルーティングするため、クライアント側のDNSキャッシュの状態に関係なく接続が確保されます。

透明性とセキュリティ

アプリケーションの透過性にとって、ローカル仮想IPアドレスが重要なのはなぜですか？

ローカルIP (VIP) SafeKit が永続的な VIP にバインドできるようにすることで、アプリケーションの透過性確保します。カーネル レベルでリダイレクトを処理するため、バインドさた IP が変わる DNAT ソリューションとは異なり、アプリケーションはクラスタのフェイルオーバーを認識できませ 。

仮想IPアドレスを使用すると、クライアントの元のIPアドレスは維持されますか？

はい。 SafeKit ソースネットワークアドレス変換（SNAT）を回避します。VIPはアクティブサーバーにローカルであるため、アプリケーションは 元のクライアントIP これは、セキュリティ監査、セッションの永続性、および規制ログ記録にとって非常に重要です。
