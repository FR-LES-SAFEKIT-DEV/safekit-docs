# كيف يعمل عنوان IP الظاهري في مجموعة عالية التوافر؟ {#how-a-virtual-ip-address-vip-works-in-high-availability-clustering}

## ما هو عنوان IP الظاهري في مجموعة عالية التوافر؟ {#virtual-ip-definition}

**عنوان IP الظاهري** هو العنوان الوحيد الذي يستخدمه العملاء للاتصال بتطبيق في [مجموعة عالية التوفر](</ar/>). لا يرتبط عنوان IP الظاهري بخادم واحد. عند حدوث تجاوز الفشل، ينتقل إلى الخادم الذي يشغل التطبيق. لا يحتاج العملاء إلى تغيير تكوينهم.

**المبدأ الأساسي في SafeKit:** يتم **تكوين عنوان IP الظاهري محليًا على الخادم** الذي يشغل التطبيق. يبدأ التطبيق على عنوان IP الظاهري، ويتلقى عنوان IP العميل الأصلي. ولهذا السبب تعمل العديد من التطبيقات بشكل صحيح مع SafeKit دون أي تغيير. يوفر SafeKit نوعين من عناوين IP الظاهرية:

  * **عنوان IP الظاهري أساسي/ثانوي مع مجموعة mirror :** يكون عنوان IP الظاهري نشطًا فقط على الخادم الأساسي. عند تجاوز الفشل، ينتقل إلى الخادم الثانوي.
  * **موازنة تحميل الشبكة باستخدام عنوان IP ظاهري مع مجموعة <span class="notranslate farm-term" translate="no">farm</span> :** يكون عنوان IP الظاهري نشطًا على جميع الخوادم في نفس الوقت. ويتم مشاركة حركة المرور بينها.

## تطبيق عنوان IP الظاهري في SafeKit {#safekit-virtual-ip-implementation}

يشرح هذا المقال كيفية نقل عنوان IP الظاهري في كل بنية شبكة باستخدام SafeKit:

  * **نفس الشبكة الفرعية أو شبكة VLAN ممتدة (مجموعات [mirror](#virtual-ip-same-subnet-failover) [<span class="notranslate farm-term" translate="no">farm</span>](#virtual-ip-load-balancing-same-subnet)):** يقوم SafeKit بتهيئة عنوان IP الظاهري على الخادم وإرسال **ARP المجاني (GARP)**. لا يلزم وجود أجهزة خارجية. هذا هو الحل الأكثر شفافية (يتم تنفيذ كل شيء بواسطة منتج SafeKit).
  * **الشبكات الفرعية المختلفة ذات موازن التحميل (مجموعات [mirror](#virtual-ip-different-subnets-failover) [<span class="notranslate farm-term" translate="no">farm</span>](#virtual-ip-load-balancing-different-subnets)):** يستخدم موازن التحميل **فحص سلامة** SafeKit لإرسال حركة المرور إلى الخادم الصحيح (يتم تكوين موازن التحميل بواسطة المُدمِج).
  * **[الشبكات الفرعية المختلفة مع واجهات سطر الأوامر لمزود الخدمة السحابية](#virtual-ip-cloud-cli-failover) (مجموعة mirror):** يستدعي البرنامج النصي SafeKit `start_prim` واجهة سطر الأوامر السحابية لنقل عنوان IP الظاهري (برنامج نصي كتبه المُدمِج).
  * **[شبكات فرعية مختلفة باستخدام بروتوكول BGP](#virtual-ip-bgp-failover) (مجموعة mirror):** يعلن الخادم الأساسي عن عنوان IP الظاهري للموجهات (برنامج نصي كتبه المُدمِج).
  * **[الشبكات الفرعية المختلفة مع إعادة توجيه نظام أسماء النطاقات](#virtual-ip-vs-dns-redirection-failover) (مجموعة mirror):** يغير البرنامج النصي SafeKit `start_prim` سجل نظام أسماء النطاقات للاسم الظاهري إلى عنوان IP الفعلي للخادم الأساسي الجديد (برنامج نصي كتبه المُدمِج). لا يوجد عنوان IP ظاهري واحد، وهذه الطريقة ليست موثوقة لجميع العملاء.

## كيف يعمل عنوان IP الظاهري في نفس الشبكة الفرعية (مجموعة mirror) {#virtual-ip-same-subnet-failover}

- [اختبار عنوان IP الظاهري أساسي/ثانوي في مجموعة mirror SafeKit](/ar/best-practises/test-primary-backup-vip-mirror/)

### التحويل التلقائي في حالة الفشل وإعادة توجيه الشبكة في شبكة فرعية محلية {#automated-failover--network-rerouting-in-a-local-subnet}

في الشبكة المحلية، تدير **SafeKit** عنوان IP الظاهري وتجاوز الفشل للتطبيق تلقائيًا.

### مجموعة mirror المحلية: تجاوز الفشل بعقدتين على نظامي التشغيل Windows أو Linux {#local-mirror-cluster-seamless-2-node-windows-or-linux-failover}


![آلية تجاوز الفشل لعنوان IP الظاهري في SafeKit بين خادمين في نفس الشبكة الفرعية](/wp-content/uploads/2023/05/vip-mirror-same-subnet-1.png "w:256")

في **مجموعة mirror** ، توجد العقدتان في نفس الشبكة الفرعية. يستخدم التوافر العالي عنوان **IP ظاهريًا**. تدير SafeKit عنوان IP الظاهري في مكدس الشبكة لنظام التشغيل. لا يلزم وجود أجهزة خاصة. تتم إضافة عنوان IP الظاهري إلى عناوين IP المادية للخادم 1 والخادم 2 باستخدام **اسم مستعار لعنوان IP**. يتصل العملاء دائمًا بعنوان IP الظاهري.

#### الأسماء المستعارة لبروتوكول الإنترنت وعناوين IP الظاهرية المتعددة في SafeKit {#safekits-advanced-ip-aliasing--multiple-virtual-ip-support}

عنوان IP الظاهري هو عنوان IP ثالث يتنقل بين العُقد. يمكن لـ SafeKit إدارة **العديد من عناوين IP الظاهرية** في مجموعة واحدة. يمكنك وضعها على نفس بطاقة الشبكة أو على بطاقات شبكة مختلفة. وبهذه الطريقة، يمكن لكل خدمة استخدام عنوان IP الظاهري الخاص بها.

#### آلية تجاوز الفشل: ARP المجاني (GARP) {#the-failover-mechanism-gratuitous-arp-garp}

لا يتطلب تجاوز الفشل أي إجراء يدوي. في التشغيل العادي، يرتبط عنوان IP الظاهري **بعنوان MAC الخاص بالخادم 1 (mac1)**. إذا تعطل الخادم 1، يقوم SafeKit بثلاثة أشياء:

  * **إسناد اسم مستعار لعنوان IP الظاهري:** يقوم SafeKit بتهيئة عنوان IP الظاهري كاسم مستعار على بطاقة الشبكة الخاصة بالخادم 2، وهو الخادم الأساسي الجديد. ثم يرسل نظام التشغيل رسائل على الشبكة للإعلان عن عنوان IP الظاهري.
  * **GARP :** يرسل SafeKit أيضًا رسائل **ARP المجاني (GARP)**. تقوم محولات الشبكة والعملاء بتحديث ذاكرة التخزين المؤقت لـ ARP الخاصة بهم. يرتبط عنوان IP الظاهري الآن بعنوان **MAC الخاص بالخادم 2 (mac2)**.
  * **استعادة التطبيق:** يعيد SafeKit تشغيل خدمات التطبيق على الخادم 2.


#### مراكز البيانات البعيدة وشبكات VLAN الممتدة {#remote-data-centers--extended-vlans}

يعمل **الحل الخاص بالشبكة الفرعية نفسها الموضح أعلاه** أيضًا **لاستعادة البيانات بعد الكوارث** بين المواقع البعيدة. وغالبًا ما يكون هذا هو الخيار الأفضل عندما تكون المواقع متصلة بشبكة **VLAN ممتدة** (شبكة LAN موسعة). ويكون كلا الموقعين في شبكة فرعية واحدة. وتكون الشبكة أبسط، ولا تحتاج إلى بروتوكولات توجيه معقدة.

> **⚠️ ملاحظة:** إعادة التوجيه في الطبقة الثانية باستخدام ARP المجاني هو **الحل الأكثر شفافية** للتطبيقات. يتلقى التطبيق عنوان IP الأصلي للعميل، ويتم تكوين عنوان IP الظاهري محليًا. **تحتاج العديد من التطبيقات إلى عنوان IP ظاهري محلي**. بدون ذلك، **قد لا تعمل هذه التطبيقات بشكل صحيح**. في إعداد الشبكة الفرعية نفسها هذا، تنفذ SafeKit الآلية بأكملها، لذلك لا يلزم القيام بأي عمل تكامل خاص.

## كيف يعمل عنوان IP الظاهري عبر الشبكات الفرعية المختلفة باستخدام موازن تحميل (مجموعة mirror) {#virtual-ip-different-subnets-failover}

### موازن تحميل مع فحوصات سلامة SafeKit {#cloud-ready-traffic-orchestration-via-load-balancer-integration}

![رسم تخطيطي لعملية تجاوز فشل عنوان IP الظاهري باستخدام موازن تحميل عبر شبكتين فرعيتين مختلفتين.](/wp-content/uploads/2023/05/vip-mirror-different-subnet.png "w:256")

عندما تكون العُقد في **شبكات فرعية مختلفة** ، لا يمكن ARP المجاني نقل عنوان IP الظاهري. في هذه الحالة، يكون عنوان IP الظاهري على **موازن تحميل**. يرسل موازن التحميل حركة المرور إلى الخادم الأساسي.

يوفر SafeKit **عنوان URL لفحص السلامة** على كل عقدة:

  * **الأساسي (PRIM) :** يُرجع `HTTP 200 OK`. يرسل موازن التحميل حركة المرور إلى هذه العقدة.
  * **الثانوي (SECOND) :** يُرجع `HTTP 404 NOT FOUND`. لا يرسل موازن التحميل أي حركة مرور إلى هذه العقدة.

عند حدوث تجاوز الفشل، يغير SafeKit الاستجابات، ويرسل موازن التحميل حركة المرور إلى الخادم الأساسي الجديد. هذا هو الحل القياسي بين **مناطق التوفر** على [**AWS**](</ar/solutions/aws-high-availability-cluster-synchronous-replication-failover/>) و [**Azure**](</ar/solutions/azure-high-availability-cluster-synchronous-replication-failover/>) و [**Google Cloud**](</ar/solutions/gcp-high-availability-cluster-synchronous-replication-failover/>).

> **⚠️ ملاحظة:** يوفر SafeKit فحص السلامة. توفر شبكتك أو مزود الخدمة السحابية موازن التحميل.

### المشكلة: موازن التحميل يمتلك عنوان IP الظاهري {#the-load-balancer-pitfall-virtual-ip-on-the-frontend-nat-to-the-physical-ip}

مع وجود موازن تحميل فقط، يتصل العملاء بعنوان IP الظاهري. يقوم موازن التحميل بترجمة عنوان IP الظاهري (NAT) إلى عنوان **IP الفعلي** للخادم الأساسي. يستخدم العميل عنوان IP الظاهري، لكن الخادم يستخدم عنوان IP الفعلي الخاص به. لا يرى الخادم عنوان IP الظاهري.

### احتفظ بعنوان IP الظاهري الذي تم تكوينه محليًا على الخادم الأساسي {#why-the-virtual-ip-must-stay-configured-locally-on-the-primary-server}

تستخدم بعض التطبيقات عنوان IP الظاهري كعنوان للخادم. وتعمل بشكل صحيح فقط إذا تم **تكوين عنوان IP الظاهري محليًا على الخادم الأساسي**. عندئذ:

  * يمكن أن تبدأ الخدمات على عنوان IP الظاهري؛
  * يمكن للخادم الوصول إلى خدماته الخاصة باستخدام عنوان IP الظاهري؛
  * يعمل المصادقة مع عنوان IP الظاهري.

**أفضل الممارسات:** استخدم وضع موازن التحميل الذي يبقي عنوان IP الظاهري كعنوان وجهة (على سبيل المثال، Floating IP أو Direct Server Return). ثم قم بتكوين عنوان IP الظاهري محليًا على الخادم الأساسي. تعتمد الطريقة على الشبكة الفرعية لعنوان IP الظاهري:

  * **يقع عنوان IP الظاهري في نفس الشبكة الفرعية لعناوين IP المادية للخوادم:** احتفظ بالقسم `<vip>` في وحدة SafeKit. يقوم SafeKit تلقائيًا بتكوين عنوان IP الظاهري كاسم مستعار على بطاقة الشبكة لعنوان IP المادي.
  * **عنوان IP الظاهري موجود في شبكة فرعية مختلفة:** احتفظ بالقسم `<vip>` في وحدة SafeKit، مع تكوين محدد. يوضح المثال أدناه هذا التكوين على Azure.
  * **خيار آخر لشبكة فرعية مختلفة:** استخدم البرنامج النصي `start_prim` لتهيئة عنوان IP الظاهري على واجهة مخصصة، مثل واجهة loopback ، قبل بدء تشغيل التطبيق. استخدم البرنامج النصي `stop_prim` لإزالة عنوان IP الظاهري بعد توقف التطبيق. يكتب المُدمِج هذه الأوامر. لا يوفرها منتج SafeKit.

### مثال: موازن تحميل Azure مع عنوان IP ظاهري محلي (Milestone XProtect) {#azure-load-balancer-local-virtual-ip-example}

تُستخدم هذه البنية في بيئة الإنتاج على Azure **لخادم إدارة Milestone XProtect** ، مع وحدة SafeKit `videoos`. توجد العقدتان في منطقتي توفر. عنوان IP الظاهري هو عنوان IP الأمامي لموازن التحميل. يوجد عنوان IP الأمامي هذا في شبكة فرعية مخصصة.

**من جانب Azure** (يتم تكوينه بواسطة فريق البنية التحتية):

  1. أنشئ **موازن تحميل من الطبقة الرابعة** بعنوان IP أمامي في شبكة فرعية مخصصة.
  2. أضف عقدتي SafeKit إلى **مجمّع الواجهة الخلفية** لموازن التحميل.
  3. أضف **فحصًا صحيًا** على عنوان URL الخاص بفحص صحة SafeKit للوحدة: المسار `/var/modules/videoos/ready.txt` ، المنفذ `9010` (HTTP) أو المنفذ `9453` (HTTPS مع شهادات صالحة). بالنسبة لوحدة أخرى، استبدل `videoos` باسم الوحدة.
  4. أضف **قواعد موازنة التحميل** لجميع المنافذ التي يستخدمها العملاء على عنوان IP الظاهري: منافذ خدمات إدارة Milestone، وإذا لزم الأمر، منافذ الخدمات الأخرى.

**من جانب SafeKit:** في ملف `userconfig.xml` الخاص بالوحدة (`videoos/conf/userconfig.xml`)، استبدل قسم `<vip>` القياسي بهذا القسم:

```xml
<vip>
  <interface_list>
    <interface check="on" arpreroute="on" name="VM_INTERFACE_NAME">
      <real_interface>
        <virtual_addr addr="LB_FRONTEND_IP" netmask="LB_FRONTEND_NETMASK" where="one_side_alias" />
      </real_interface>
    </interface>
  </interface_list>
</vip>
```

استبدل `VM_INTERFACE_NAME` باسم واجهة الشبكة الخاصة بالجهاز الظاهري، `LB_FRONTEND_IP` بعنوان IP الأمامي لموازن التحميل، و `LB_FRONTEND_NETMASK` بقناع الشبكة للشبكة الفرعية الأمامية. يجب أن تحمل واجهة الشبكة الاسم نفسه على كلا العقدتين.

**على جانب التطبيق:** قم بتكوين جميع خدمات Milestone لاستخدام عنوان IP الظاهري، وليس عنوان IP الخاص بالخادم.

> **⚠️ ملاحظة:** استخدم شبكة فرعية أمامية **لا تتداخل** مع الشبكة الفرعية للأجهزة الافتراضية. على سبيل المثال، الأجهزة الافتراضية في `10.0.1.0/24` وعنوان IP الأمامي لموازن التحميل في `10.0.2.0/24`. يضيف SafeKit عنوان IP الأمامي مع قناع الشبكة الخاص به على واجهة الشبكة للجهاز الافتراضي. إذا تداخلت الشبكتان الفرعيتان، فإن هذا الاسم المستعار يغير توجيه الجهاز الافتراضي وقد تفشل حركة مرور الشبكة للأجهزة الافتراضية.


## كيف يعمل عنوان IP الظاهري عبر الشبكات الفرعية المختلفة باستخدام واجهات سطر الأوامر لمزود الخدمة السحابية (مجموعة mirror) {#virtual-ip-cloud-cli-failover}

### لماذا لا يعمل ARP المجاني في السحابة؟ {#why-gratuitous-arp-does-not-work-in-public-clouds}

**تتجاهل الشبكات السحابية (AWS، وAzure، وGoogle Cloud) ARP المجاني**. فهي ترسل حركة المرور فقط إلى عناوين IP المعينة في المنصة السحابية. يقوم SafeKit بتهيئة عنوان IP الظاهري على الخادم الأساسي، ولكن الشبكة السحابية لا ترسل حركة مرور IP الظاهرية إلى هذا الخادم.

### نقل عنوان IP الظاهري باستخدام واجهة سطر الأوامر السحابية (cloud CLI) {#moving-the-virtual-ip-through-the-cloud-api-in-safekit-failover-scripts}

بدون موازن تحميل، يمكن دمج واجهة سطر الأوامر (CLI) الخاصة بمزود الخدمة السحابية في **البرنامج النصي SafeKit `start_prim`** لتحديث تكوين الشبكة السحابية قبل بدء تشغيل التطبيق. يمكن لواجهة سطر الأوامر تعيين عنوان IP الظاهري للعقدة التي ستصبح أساسية أو تحديث المسار السحابي لتوجيه حركة مرور IP الظاهري إلى تلك العقدة.

**يبقى عنوان IP الظاهري محليًا** على الخادم الأساسي. **لا يوجد تحويل لعنوان الشبكة (NAT)** ، ولا يتغير عنوان IP الأصلي للعميل.

### القيود {#constraints-of-the-cli-approach}

  * يجب تثبيت واجهة سطر الأوامر السحابية (cloud CLI) على كلتا العقدتين. تحتاج كل عقدة إلى هوية سحابية مع أذونات للشبكة.
  * يجب أن تدير الشيفرة الأخطاء وإعادة المحاولة.
  * يُعدّ التبديل التلقائي **أبطأ بكثير** مما هو عليه مع موازن التحميل ومجسّ السلامة، لأن كل عملية تبديل تلقائي تنتظر استجابة واجهة برمجة تطبيقات السحابة.

> **⚠️ ملاحظة:** يجب **على المُدمِج** إضافة أوامر واجهة سطر الأوامر (CLI) الخاصة بالسحابة إلى البرنامج النصي `start_prim`. **لا يتم توفير هذه الأوامر بواسطة منتج SafeKit**. فهي تعتمد على مزود السحابة، وتصميم الشبكة، وقواعد الأمان الخاصة بالعميل. تحقق من صحة الحل مع فريق الشبكة الخاص بك قبل الإنتاج.

## كيف يعمل عنوان IP الظاهري عبر الشبكات الفرعية المختلفة باستخدام بروتوكول BGP (مجموعة mirror) {#virtual-ip-bgp-failover}

### إعادة توجيه عنوان IP الظاهري باستخدام بروتوكول BGP {#layer-3-virtual-ip-rerouting-with-bgp-route-advertisement}

باستخدام بروتوكول BGP (بروتوكول بوابة الحدود)، يتم عادةً تكوين عنوان IP الظاهري على واجهة loopback خاصة بالخادم الأساسي بواسطة البرنامج النصي `start_prim` قبل بدء تشغيل التطبيق. يعلن الخادم الأساسي عن عنوان IP الظاهري للموجهات كمسار /32.

عند تجاوز الفشل، يوقف البرنامج النصي `stop_prim` على الخادم الأساسي القديم التطبيق، ويزيل عنوان IP الظاهري من واجهة loopback ، ويسحب المسار /32 من أجهزة التوجيه. إذا تعطل الخادم الأساسي القديم، فلن يتم تشغيل `stop_prim` ، لكن أجهزة التوجيه تفقد جلسة BGP وتزيل المسار تلقائيًا.

### الفوائد والمتطلبات الأساسية {#benefits-and-prerequisites}

  * **يظل عنوان IP الظاهري محليًا، ولا يوجد تحويل لعنوان الشبكة (NAT)، ولا يتغير عنوان IP الخاص بالعميل.**
  * يعمل عبر الشبكات الفرعية والمواقع. لا تحتاج إلى شبكة VLAN ممتدة.
  * تحتاج إلى أجهزة توجيه BGP ومساعدة من فريق الشبكة لديك. في السحابة، تحتاج إلى خدمة خادم توجيه من مزود الخدمة السحابية.

> **⚠️ ملاحظة:** يستخدم تكامل BGP نصوص SafeKit البرمجية والبنية التحتية للتوجيه الخاصة بك. يجب **على المُدمِج** كتابة الأوامر في نصوص `start_prim` و `stop_prim` البرمجية. هذه النصوص البرمجية **غير متوفرة في منتج SafeKit**. تحقق من صحة الحل مع فريق الشبكة الخاص بك قبل الإنتاج.

## كيف تعمل إعادة توجيه نظام أسماء النطاقات (DNS) عبر الشبكات الفرعية المختلفة (مجموعة mirror) {#virtual-ip-vs-dns-redirection-failover}

### إعادة توجيه نظام أسماء النطاقات (DNS) باستخدام البرنامج النصي `start_prim` {#dns-rerouting-with-the-start-prim-script}

مع إعادة توجيه نظام أسماء النطاقات (DNS)، **لا يوجد عنوان IP ظاهري واحد**. يتصل العملاء **باسم ظاهري** (اسم نظام أسماء النطاقات). عند تجاوز الفشل، يبدأ البرنامج النصي `start_prim` على الخادم الأساسي الجديد التطبيق، ثم يغير سجل نظام أسماء النطاقات للاسم الظاهري إلى عنوان **IP الفعلي** للخادم الأساسي الجديد.

لا يحتاج البرنامج النصي `stop_prim` إلى القيام بأي شيء. إذا تعطل الخادم الأساسي القديم، فإن الخادم الأساسي الجديد يحل محله في سجل نظام أسماء النطاقات (DNS).

### مثال: تحليل DNS والعملاء الذين يحتفظون بعنوان IP القديم {#the-technical-scenario-dns-resolution-and-the-stuck-client}

![رسم تخطيطي يوضح حل اسم نظام أسماء النطاقات (DNS) إلى عنوان IP فعلي 1 في مجموعة عالية التوافر.](/wp-content/uploads/2025/12/dns-rerouting.png "w:256")

 تحليل DNS : لا يزال العملاء متصلين بعنوان IP الفعلي 1 في مجموعة عالية التوفر.

#### قبل تجاوز الفشل: يشير الاسم إلى عنوان IP الفعلي 1 {#current-state-resolution-to-physical-ip-1}

يطلب كل **من العميل 1** والعميل **2** من نظام DNS عنوان IP للاسم الظاهري. ويعيد نظام DNS **عنوان IP الفعلي 1.** ثم يفتح العميلان اتصال شبكة بهذا العنوان.

#### بعد تجاوز الفشل: يشير الاسم إلى عنوان IP الفعلي 2 {#the-failover-challenge-rerouting-to-physical-ip-2}

يفشل الخادم 1. يغير البرنامج النصي `start_prim` على الخادم 2 سجل DNS إلى **عنوان IP الفعلي 2.** يتصل العملاء بعنوان IP الفعلي 2 فقط إذا كانت جميع هذه الشروط صحيحة:

  * انتهت صلاحية **TTL (مدة البقاء)** على جميع خوادم DNS بين العميل وسجل DNS.
  * ذاكرة التخزين المؤقت المحلية لنظام أسماء النطاقات (DNS) لكل من العميل 1 والعميل 2 فارغة.
  * يُغلق التطبيق اتصاله ويُجري بحثًا *جديدًا* في نظام أسماء النطاقات (DNS).

إذا كان أحد الشرطين خاطئًا، يستمر **العميل 1 والعميل 2** في استخدام عنوان IP الفعلي 1. تكون الخدمة معطلة، حتى لو كان سجل DNS صحيحًا.

### القيود والمتطلبات الأساسية {#the-two-black-boxes-of-dns-redirection}

  * **ذاكرة التخزين المؤقت لنظام أسماء النطاقات (DNS):** يتجاهل العديد من مزودي خدمة الإنترنت وخوادم نظام أسماء النطاقات الخاصة بالشركات قيم TTL القصيرة. يمكنهم الاحتفاظ بعنوان IP الفعلي القديم 1 لدقائق أو ساعات.
  * **سلوك التطبيق:** تقوم العديد من التطبيقات (على سبيل المثال، خدمات جافا أو متصفحات الويب) بالبحث عن DNS مرة واحدة فقط، عندما تبدأ. وهي تستمر في استخدام عنوان IP الأول.
  * **يتغير عنوان IP في كل عملية تجاوز فشل:** لا يحتوي التطبيق على عنوان IP ظاهري محلي يظل كما هو. قد لا تعمل التطبيقات التي تسجل عنوان IP الخاص بها.
  * **المتطلبات الأساسية:** قيمة TTL قصيرة في سجل DNS (على سبيل المثال، من 30 إلى 60 ثانية)، وحقوق تحديث منطقة DNS من كلا الخادمين.

> **⚠️ ملاحظة:** يجب على **المُدمِج** كتابة أوامر تحديث نظام أسماء النطاقات (DNS) في البرنامج النصي `start_prim`. **لا يتم توفير هذه الأوامر بواسطة منتج SafeKit**. وتعتمد على خادم نظام أسماء النطاقات (DNS) (نظام أسماء النطاقات من Windows، أو BIND، أو نظام أسماء النطاقات السحابي).

### الخاتمة {#conclusion}

إعادة توجيه نظام أسماء النطاقات (DNS) ليس حلاً موثوقًا به لضمان التوافر العالي. استخدمه فقط إذا أجرت جميع الأجهزة العميلة بحثًا جديدًا لنظام أسماء النطاقات عند إعادة الاتصال. للحصول على تجاوز فوري وشفاف للأعطال، استخدم **عنوان IP ظاهريًا** : مع شبكة VLAN ممتدة، أو مع موازن تحميل، أو مع واجهات سطر الأوامر لمزود الخدمة السحابية، أو مع بروتوكول BGP.

## كيف يعمل موازن تحميل بروتوكول الإنترنت الظاهري في مجموعة <span class="notranslate farm-term" translate="no">farm</span> على نفس الشبكة الفرعية {#virtual-ip-load-balancing-same-subnet}

- [اختبار عنوان IP الظاهري لموازنة التحميل في مجموعة farm SafeKit](/ar/best-practises/test-load-balancing-vip-farm/)

### موازنة التحميل والتكرار على مستوى النواة {#scalable-performance-kernel-level-load-balancing--redundancy}

عندما يكون هناك الكثير من حركة المرور، يمكن لـ SafeKit مشاركة العمل بين عدة خوادم نشطة. إذا تعطل خادم واحد، تستمر الخوادم الأخرى في العمل.

### بنية مجموعة <span class="notranslate farm-term" translate="no">farm</span> : موازنة التحميل بين عُقد ويندوز أو لينكس {#farm-cluster-architecture-load-balancing-across-windows-or-linux-nodes}


![رسم تخطيطي لعنوان IP ظاهري متوازن الأحمال ضمن الشبكة الفرعية نفسها](/wp-content/uploads/2023/05/vip-farm-same-subnet.png "w:256")

في **مجموعة <span class="notranslate farm-term" translate="no">farm</span> موازنة التحميل** ، يتصل العملاء بعنوان IP ظاهري، ويتم مشاركة الطلبات بين عدة خوادم في نفس الوقت. يوضح هذا المثال عقدتين. يمكنك إضافة المزيد من العقد إلى المجموعة. في نفس الشبكة الفرعية، يتم تكوين عنوان IP الظاهري باستخدام اسم مستعار لعنوان IP على بطاقة الشبكة **لكل خادم** في المجموعة.

#### مشاركة حركة المرور: مرشح النواة {#traffic-distribution-the-kernel-level-filter}

في مجموعة <span class="notranslate farm-term" translate="no">farm</span> ، يشارك **مرشح SafeKit في النواة** حركة المرور. ويعمل على النحو التالي:

  * **تعيين ARP:** في ذاكرة التخزين المؤقت لبروتوكول تحليل العناوين (ARP) للعملاء، يرتبط عنوان IP الظاهري بعنوان MAC واحد (على سبيل المثال، `mac1` الخاص بالخادم 1).
  * **تحليل الحزم:** يستقبل الخادم 1 الحزم. يقرأ مرشح نواة SafeKit **عنوان IP الخاص بالعميل** أو **منفذ TCP** لكل حزمة.
  * **مشاركة التحميل:** يحدد المرشح الحزم التي يعالجها الخادم 1 والحزم التي تذهب إلى العقد الأخرى (على سبيل المثال، الخادم 2). لإرسال حزمة إلى عقدة أخرى، يعيد المرشح كتابة **عنوان MAC الوجهة** للحزمة بعنوان MAC لهذه العقدة. يبقى عنوان IP الوجهة هو عنوان IP الظاهري. يتم تقاسم العمل بين الخوادم.


#### التحويل التلقائي وإعادة التوجيه باستخدام ARP المجاني {#failover-and-rerouting-with-gratuitous-arp}

في حالة تعطل الخادم 1، يرسل SafeKit رسالة **ARP المجاني (GARP)**. يقوم العملاء بتحديث ذاكرة التخزين المؤقت لبروتوكول تحليل العناوين (ARP) الخاصة بهم باستخدام `mac2` الخاص بالخادم 2. ثم يتم توجيه العملاء على الفور إلى العقد الأخرى في farm.

#### النشر في المواقع النائية {#deployment-in-remote-sites}

يعمل حل موازنة التحميل هذا أيضًا بين **مراكز البيانات البعيدة** ، إذا كانت المواقع متصلة بواسطة **شبكة VLAN ممتدة**. تكون جميع المواقع بعد ذلك في نفس الشبكة الفرعية. هذا هو التكوين الأكثر كفاءة مجموعات <span class="notranslate farm-term" translate="no">farm</span> في عدة مواقع.

## كيف يعمل عنوان IP ظاهري متوازن الأحمال عبر الشبكات الفرعية المختلفة (مجموعة <span class="notranslate farm-term" translate="no">farm</span>) {#virtual-ip-load-balancing-different-subnets}

### حركة المرور عبر الشبكات الفرعية السحابية {#multi-zone-scaling-orchestrating-traffic-across-cloud-subnets}

يمكن مجموعة <span class="notranslate farm-term" translate="no">farm</span> مشاركة عمل التطبيق بين عدة مناطق توفر وشبكات فرعية.

### مجموعات <span class="notranslate farm-term" translate="no">farm</span> عبر الشبكات الفرعية: العديد من عُقد Windows أو Linux {#cross-subnet-farm-clusters-multi-node-windows--linux-scalability}


![رسم تخطيطي مجموعة farm متوازنة الأحمال تعمل عبر شبكتين فرعيتين مختلفتين.](/wp-content/uploads/2023/05/vip-farm-different-subnet.png "w:256")

عندما تكون عُقد <span class="notranslate farm-term" translate="no">farm</span> في **شبكات فرعية مختلفة** (على سبيل المثال، في عدة مناطق توفر سحابية)، يكون **عنوان IP الظاهري** على **موازن تحميل** خارجي. يرسل موازن التحميل حركة المرور إلى عناوين IP المادية للخوادم في كل شبكة فرعية.

#### قواعد توجيه حركة المرور وموازنة التحميل {#intelligent-traffic-routing--load-balancing-rules}

يوزع موازن التحميل طلبات العميل وفقًا لمعيارين:

  * **قواعد موازنة التحميل:** على سبيل المثال، **عنوان IP الخاص بالعميل** أو **منفذ TCP الخاص بالعميل**.
  * **إتاحة العقدة:** يرسل موازن التحميل حركة المرور فقط إلى العقد السليمة، بناءً على فحص سلامة SafeKit.


> **⚠️ ملاحظة:** يوفر SafeKit فحص السلامة. توفر شبكتك أو مزود الخدمة السحابية موازن التحميل.

#### فحص سلامة SafeKit {#safekit-health-check-mechanism}

يوفر SafeKit **عنوان URL لفحص السلامة** على كل خادم من الخوادم الموجودة في <span class="notranslate farm-term" translate="no">farm</span>. يقرأ موازن التحميل هذا العنوان لمعرفة حالة كل خادم:

  * **العقدة UP :** فحص السلامة يُرجع `HTTP 200 OK`. يرسل موازن التحميل حركة المرور إلى هذا الخادم.
  * **العقدة DOWN :** إذا تعطل خادم أو تطبيق، تُرجع SafeKit `HTTP 404 NOT FOUND`) (أو لا يستجيب الخادم). يتوقف موازن التحميل عن إرسال حركة المرور إلى هذه العقدة على الفور.


#### النشر السحابي: AWS وAzure وGCP {#cloud-deployment-standards-aws-azure-and-gcp}

هذه هي البنية القياسية **مجموعات <span class="notranslate farm-term" translate="no">farm</span> في السحابة**. إذا توقفت شبكة فرعية أو منطقة، تستمر العُقد الأخرى في معالجة حركة المرور. وهي مدعومة على [**Amazon AWS**](</ar/solutions/aws-load-balancing-cluster-failover/>) (Network Load Balancer AWS)، و [**Microsoft Azure**](</ar/solutions/azure-load-balancing-cluster-failover/>) (Azure Load Balancer)، و [**Google Cloud (GCP)**](</ar/solutions/gcp-load-balancing-cluster-failover/>) (Google Cloud Load Balancing).

## الأسئلة الشائعة حول عنوان IP الظاهري {#virtual-ip-faq}

### عنوان IP الظاهري والشبكات {#virtual-ip--networking}

ما هو عنوان IP الظاهري وما الفرق بينه وبين عنوان IP الفعلي؟

**عنوان IP الفعلي** مرتبط ببطاقة شبكة واحدة. أما **عنوان IP الظاهري** فلا يرتبط بالأجهزة. في مجموعة SafeKit، يستخدم العملاء دائمًا عنوان IP الظاهري. إذا تعطل الخادم الأساسي، ينتقل عنوان IP الظاهري تلقائيًا إلى عقدة سليمة. لا تحتاج إلى تغيير تكوين العميل.

هل أحتاج إلى موازن تحميل للأجهزة لاستخدام عنوان IP ظاهري؟

لا. تدير **SafeKit** عنوان IP الظاهري باستخدام البرامج. في الشبكة الفرعية نفسها، تستخدم SafeKit **أسماء IP المستعارة** وبروتوكول **ARP المجاني (GARP)** لإعادة توجيه حركة المرور. لا تحتاج إلى موازن تحميل خارجي أو خادم وكيل.

ما هو ARP المجاني (GARP) ولماذا يُستخدم؟

**ARP المجاني (GARP)** هو رسالة شبكة تُرسل إلى جميع الأجهزة. وتعمل على تحديث جداول بروتوكول تحليل العناوين (ARP) الخاصة بالمحولات والموجهات. عند حدوث تجاوز الفشل، يرسل الخادم الأساسي الجديد رسالة GARP. وتفيد الرسالة بأن **عنوان IP الظاهري** أصبح الآن مرتبطًا بعنوان MAC الخاص بالخادم الأساسي الجديد. ثم يُعاد توجيه حركة المرور على الفور.

هل يمكنني ربط اسم DNS بعنوان IP ظاهري؟

**نعم.** أنشئ سجل A قياسيًا لعنوان IP الظاهري. يتم إعادة التوجيه على **مستوى عنوان IP الظاهري** (باستخدام بروتوكول تحليل العناوين ARP أو إعادة توجيه الشبكة)، **وليس على مستوى نظام أسماء النطاقات (DNS**). لن تواجه تأخيرات في نظام أسماء النطاقات أو مشكلات في عمر الحزمة (TTL)، وستظل عملية تجاوز الفشل **شفافة للتطبيق**.

### الحوسبة السحابية والهياكل المتقدمة {#cloud--advanced-architectures}

كيف يعمل عنوان IP الظاهري في السحابة (AWS، Azure، GCP)؟

في السحابة، لا تتوفر رسائل GARP من الطبقة الثانية لإعادة توجيه عنوان IP ظاهري. يعمل SafeKit مع **موازنات تحميل السحابة** (AWS Elastic Load Balancing، أو Azure Load Balancer ، أو Google Cloud Load Balancing). يوفر SafeKit **عنوان URL لفحص السلامة**. يقرأ موازن التحميل هذا العنوان ويرسل حركة المرور إلى العقدة النشطة.

هل شبكة VLAN الممتدة أفضل من موازن التحميل لاستعادة البيانات بعد الكوارث؟

**نعم**. بين مراكز البيانات البعيدة، غالبًا ما يكون **شبكة VLAN الممتدة** أفضل لأن تجاوز الفشل يظل **شفافًا للتطبيق**. **لا يتغير عنوان IP الظاهري** ، لذلك يستمر التطبيق وعملاؤه في استخدام نفس العنوان بعد تجاوز الفشل بين مراكز البيانات.

ما هي حدود إعادة توجيه نظام أسماء النطاقات (DNS) مقارنةً بعنوان IP الظاهري؟

يعتمد **تحويل مسار DNS** على قيمة **TTL (مدة البقاء)** وعلى ذاكرة التخزين المؤقت لـ DNS لدى العميل. قد تستغرق عملية الاسترداد ساعات. أيضاً، يستمر **العملاء الذين لا يقومون بالبحث عن DNS جديد** في استخدام الخادم الفاشل. يتم إعادة توجيه **عنوان IP الظاهري** على الفور باستخدام رسائل GARP في الطبقة الثانية. لا يكون لذاكرة التخزين المؤقت لـ DNS لدى العميل أي تأثير.

### الشفافية والأمان {#transparency--security}

لماذا يُعد عنوان IP الظاهري المحلي مهمًا لشفافية التطبيق؟

باستخدام عنوان **IP ظاهري** محلي، يستخدم التطبيق عنوانًا لا يتغير. يقوم SafeKit بإعادة التوجيه في **النواة**. لا يرى التطبيق عملية تجاوز الفشل. مع DNAT، يتغير العنوان الذي يستخدمه التطبيق.

هل يحافظ عنوان IP الظاهري على عنوان IP الأصلي للعميل؟

نعم. لا يستخدم SafeKit خاصية ترجمة عنوان الشبكة المصدرية (SNAT). عنوان IP الظاهري محلي على الخادم النشط، لذا يتلقى التطبيق **عنوان IP الأصلي للعميل**. وهذا مهم لعمليات تدقيق الأمان، واستمرارية الجلسة، والسجلات التنظيمية.
