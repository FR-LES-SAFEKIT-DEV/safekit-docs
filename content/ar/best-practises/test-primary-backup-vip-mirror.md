# اختبار عنوان IP الظاهري لمجموعة mirror SafeKit في شبكتك

يصف هذا الدليل كيفية التحقق من أن عنوان IP الظاهري ( VIP ) لمجموعة mirror SafeKit (وحدة mirror ) يعمل بشكل صحيح في شبكتك: يتم الاحتفاظ بعنوان IP الظاهري ( VIP ) بواسطة الخادم الأساسي، ويتم إعادة توجيهه إلى الخادم الأساسي الجديد بعد تجاوز الفشل.

## 1. المبادئ الأساسية

**الشرط الأساسي:** يجب أن تكون كلتا عقدتي مجموعة mirror في نفس الشبكة الفرعية IP من الطبقة 2: LAN ، أو VLAN ممتدة بين المواقع البعيدة.

- يكون عنوان IP الظاهري ( VIP ) نشطًا فقط على **الخادم الأساسي** (حالات PRIM أو ALONE ): يتم تعيينه كاسم مستعار لعنوان IP الفعلي، على بطاقة الشبكة الخاصة بهذا العنوان، عندما تبدأ الوحدة كخادم أساسي على العقدة (تكوين `where="one_side_alias"` ).
- وبالتالي، فإن عنوان MAC الخاص بالخادم الرئيسي هو العنوان المرتبط بعنوان IP الظاهري ( VIP ) في جداول ARP (الموجه، البوابة، العملاء في نفس الشبكة الفرعية). ويتم توجيه جميع البيانات إلى عنوان IP الظاهري ( VIP ) إلى الخادم الرئيسي.
- أثناء عملية تجاوز الفشل (توقف أو تعطل الخادم الأساسي)، يتم إزالة IP الظاهري ( VIP ) من الخادم الأساسي السابق وتعيينه كاسم مستعار على الخادم الأساسي الجديد. ثم تسمح آليتان للشبكة بربط عنوان IP الظاهري ( VIP ) بعنوان MAC الخاص بالخادم الأساسي الجديد:
  - رسائل الشبكة التي يرسلها نظام التشغيل عند إضافة IP الظاهري ( VIP ) كاسم مستعار على بطاقة الشبكة؛
  - **GARPs** (بروتوكول ARP المجاني) المرسلة بواسطة SafeKit ، عندما يتم تكوين السمة `arpreroute="on"` في قسم `<vip>` .

لذا، ما تحتاج إلى اختباره هو:

1. يتم الاحتفاظ بعنوان IP الظاهري ( VIP ) بواسطة الخادم الرئيسي ويمكن الوصول إليه من العملاء؛
2. يتم إعادة توجيه عنوان MAC المرتبط بعنوان IP الظاهري ( VIP ) إلى الخادم الأساسي الجديد في الشبكة (الموجه، البوابة، المحاكاة الافتراضية) عند تغيير الخادم الأساسي.

## 2. المتطلبات الأساسية: تهيئة عنوان IP الظاهري ( VIP )

1. في ملف `userconfig.xml` الخاص بوحدة mirror ، قم بتكوين عنوان IP الظاهري ( VIP ) في قسم `<vip>` . تُفعّل السمة `arpreroute="on"` إرسال GARPs الخادم الأساسي الجديد بعد عملية تجاوز الفشل.

   ```xml
   <vip>
     <interface_list>
       <interface arpreroute="on">
         <real_interface>
           <virtual_addr addr="<VIP>" where="one_side_alias"/>
         </real_interface>
       </interface>
     </interface_list>
   </vip>
   ```

2. قم بتطبيق الإعدادات على كلا العقدتين.
3. ابدأ الوحدة: يجب أن تكون إحدى العقدتين **PRIM ( Ready )** والأخرى **SECOND ( Ready )** .

## 3. الاختبار 1 - IP افتراضي ( VIP ) يحتفظ به الخادم الرئيسي

**خطوات**

1. على الخادم الرئيسي، قم بتشغيل `ipconfig` ( Windows ) أو `ip addr show` ( Linux ).
   → **النتيجة المتوقعة:** يظهر IP الظاهري ( VIP ) كاسم مستعار على بطاقة الشبكة لعنوان IP الفعلي.
2. قم بتشغيل نفس الأمر على الخادم الثانوي.
   → **النتيجة المتوقعة:** لا يظهر عنوان IP الظاهري ( VIP ).
3. من محطة عمل العميل **خارج المجموعة** ، `ping` لكل من عناوين IP الفعلية وعنوان IP الظاهري ( VIP ).
   → **النتيجة المتوقعة:** استجابة جميع أوامر `ping` الثلاثة (إلا إذا تم تصفيتها بواسطة جدران الحماية).
4. تحقق من الوصول من خلال عنوان IP الظاهري ( VIP ) باستخدام SafeKit mosaic: من متصفح على العميل **الخارجي** ، اتصل بـ `http://<VIP>:9010/safekit/mosaic.html` (أو استخدم المنفذ 9453 إذا تم تحويل خادم الويب ووحدة التحكم SafeKit إلى HTTPS)، ثم أدخل **اسم وحدة** mirror وقم بتشغيل الاختبار.
   → **النتيجة المتوقعة:** تعرض جميع خلايا الفسيفساء اسم **الخادم الأساسي** بلون واحد: يتم خدمة جميع اتصالات TCP إلى عنوان IP الظاهري ( VIP ) بواسطة الخادم الأساسي.

## 4. الاختبار 2 - تجاوز الفشل اليدوي (إيقاف النظام الأساسي)

يتحقق هذا الاختبار من أن IP الظاهري ( VIP ) يتبع الخادم الأساسي أثناء عملية تجاوز الفشل، والتي يتم تشغيلها عن طريق إيقاف الوحدة النمطية على الخادم الأساسي.

**خطوات**

1. أوقف الوحدة النمطية على الجهاز الأساسي (العقدة 1) من وحدة تحكم SafeKit (أو من سطر الأوامر باستخدام `safekit stop -m <module>` ).
   **النتيجة المتوقعة:** ينتقل الجهاز 1 إلى STOP ( NotReady ) وينتقل الجهاز 2 إلى ALONE ( Ready ). في سجل الجهاز الأساسي الجديد، تظهر الرسالة " `Virtual IP <VIP> set` .
2. على الجهاز الأساسي الجديد، قم بتشغيل الأمر `ipconfig` أو `ip addr show` .
   → **النتيجة المتوقعة:** يظهر عنوان IP الظاهري ( VIP ) الآن كاسم مستعار على هذه العقدة، ولم يعد يظهر على العقدة الأساسية السابقة.
3. من محطة عمل العميل، كرر أوامر `ping` الثلاثة وقم بتشغيل الفسيفساء مرة أخرى على IP الظاهري ( VIP ).
   → **النتيجة المتوقعة:** كل شيء يستجيب، وجميع خلايا الفسيفساء تعرض الآن اسم **اللون الأساسي الجديد** ، بلون واحد.
4. أعد تشغيل الوحدة على العقدة 1: ستتم إعادة مزامنتها وتنتقل إلى SECOND ( Ready )، بينما تنتقل العقدة 2 إلى PRIM ( Ready ).

## 5. الاختبار 3 - التحقق من إعادة توجيه عناوين MAC باستخدام `arp -a`

تقوم بتدوين عنوان MAC المرتبط بعنوان IP الظاهري ( VIP ) قبل عملية تجاوز الفشل، ثم تتحقق من أنه قد تغير بعد ذلك.

لا يمكن إجراء هذا الاختبار إلا إذا كانت محطة عمل العميل موجودة في **نفس الشبكة الفرعية لعنوان IP** الخاصة بالمجموعة.

إذا كان هناك جهاز توجيه بين العميل والمجموعة، فلن يحتوي جدول ARP الخاص بالعميل على عنوان IP الظاهري ( VIP )، بل على عنوان البوابة المستخدمة للوصول إلى شبكة المجموعة. في هذه الحالة، يُرجى مراجعة جدول ARP الخاص بجهاز التوجيه أو البوابة مع فريق الشبكة.

**خطوات**

1. الوحدة هي PRIM ( Ready ) على العقدة 1 و SECOND ( Ready ) على العقدة 2.
2. على محطة عمل العميل، `ping` لكل من عناوين IP الفعلية وعنوان IP الظاهري ( VIP )، ثم قم بتشغيل `arp -a` .
   → **النتيجة المتوقعة:** يتم ربط IP الظاهري ( VIP ) بنفس **عنوان MAC الخاص بعنوان IP الفعلي للجهاز الأساسي** .
3. `stop` الوحدة النمطية على العقدة الأساسية (العقدة 1).
4. `ping` IP الظاهري ( VIP ) مرة أخرى، ثم قم بتشغيل `arp -a` مرة أخرى.
   → **النتيجة المتوقعة:** يتم الآن ربط IP الظاهري ( VIP ) بنفس **عنوان MAC الخاص بعنوان IP الفعلي للجهاز الأساسي الجديد** .

> `ping` لعنوان IP الظاهري ( VIP ) مرة أخرى قبل قراءة جدول ARP : قد يتم وضع علامة على الإدخال بأنه قديم ولا يتم تحديثه إلا بعد `ping` .

مثال على جدول ARP المتوقع، قبل وبعد إيقاف الخادم الرئيسي:

| عنوان | MAC قبل التوقف | MAC بعد التوقف |
|---|---|---|
| IP الفعلي للعقدة 1 | عنوان MAC للعقدة 1 | عنوان MAC للعقدة 1 |
| IP الفعلي للعقدة 2 | MAC للعقدة 2 | MAC للعقدة 2 |
| IP افتراضي ( VIP ) | **عنوان MAC للعقدة 1** | **MAC للعقدة 2** |

## 6. الاختبار 4 – فحص شامل باستخدام Wireshark ( Windows ) أو tcpdump ( Linux )

يمكنك تتبع اتصال TCP إلى عنوان IP الظاهري ( VIP ) عن طريق التقاط الحزم على العميل وعلى كلا العقدتين: باستخدام Wireshark على أجهزة Windows ، وباستخدام tcpdump على أجهزة Linux .

يجب عليك النظر إلى **رؤوس MAC (Ethernet) للحزم** : يظل عنوان IP الوجهة هو عنوان IP الظاهري ( VIP )، وعنوان MAC الوجهة هو الذي يوضح أي عقدة تستقبل حركة المرور.

**ما يجب عليك ملاحظته:**

| متى | أين يتم التقاط الصور | عناوين MAC المرصودة |
|---|---|---|
| قبل عملية تجاوز الفشل | عميل | MAC الخاص بالعميل → MAC الخاص **بالعقدة 1 (الأساسية)** |
| قبل عملية تجاوز الفشل | العقدة 1 | يتم استلام الحزم إلى عنوان IP الظاهري ( VIP )؛ ولا يستلم الجهاز 2 أي شيء |
| أثناء عملية تجاوز الفشل | شبكة | رسائل إعادة توجيه MAC المرسلة من العقدة 2 لعنوان IP الظاهري ( VIP ): الرسائل المرسلة من نظام التشغيل عند تعيينه كاسم مستعار، و GARPs المرسلة من SafeKit ( `arpreroute="on"` ). |
| بعد عملية تجاوز الفشل | عميل | MAC الخاص بالعميل → MAC الخاص **بالعقدة 2 (العقدة الأساسية الجديدة)** |

> إذا كانت محطة عمل العميل في شبكة فرعية مختلفة عن المجموعة، فإن " MAC الخاص بالعميل" الذي يظهر على العقد هو عنوان MAC الخاص **بالبوابة** (الموجه) الذي يربط الشبكتين الفرعيتين، وليس عنوان MAC الخاص بمحطة عمل العميل.

## 7. ما هي محطات العمل التي سيتم الاختبار منها؟

يعتمد السلوك على مسار الشبكة بين العميل والمجموعة. قم بتشغيل الاختبارين 1 و2 من كل نوع من أنواع العملاء ذوي الصلة ببنية نظامك:

| موقع العميل | ما الذي يفحصه الاختبار |
|---|---|
| العميل موجود في **نفس الشبكة الفرعية** مثل المجموعة | تحديث جداول ARP الخاصة بالعملاء (الاختبار 3 ممكن) |
| عميل في **شبكة فرعية مختلفة** (جهاز توجيه، بوابة، شبكة افتراضية للمشرف) | تحديث جداول ARP الخاصة بالعملاء في جهاز التوجيه أو البوابة |
| جهاز افتراضي للعميل **على برنامج إدارة الأجهزة الافتراضية الذي يستضيف أيضًا جهازًا افتراضيًا واحدًا من مجموعة mirror** | سلوك المحول الظاهري للمشرف، والذي يتولى أيضًا عمليات التبديل والتوجيه الداخلية. |

## 8. ملخص النتائج المتوقعة

| امتحان | فعل | النتيجة المتوقعة |
|---|---|---|
| 1 | PRIM / SECOND ، `ipconfig` ، `ping` و mosaic | عنوان IP افتراضي ( VIP ) كاسم مستعار على الجهاز الأساسي فقط؛ تستجيب أوامر `ping` الثلاثة (إلا إذا تم تصفيتها بواسطة جدران الحماية)؛ تعرض الفسيفساء الجهاز الأساسي فقط |
| 2 | توقف الأساسي | IP افتراضي ( VIP ) كاسم مستعار على العنوان الأساسي الجديد؛ رسالة `Virtual IP <VIP> set` ؛ يعرض المخطط الموازي العنوان الأساسي الجديد فقط |
| 3 | `arp -a` قبل وبعد إيقاف العملية الأساسية | ينتقل IP الظاهري ( VIP ) من عنوان MAC الخاص بالعقدة 1 إلى عنوان MAC الخاص بالعقدة 2 |
| 4 | التقاط بيانات Wireshark أو tcpdump قبل وبعد عملية تجاوز الفشل | يرسل العميل إلى عنوان MAC الخاص بالخادم الأساسي الجديد |

## 9. استكشاف الأخطاء وإصلاحها

- **لم يعد IP الظاهري ( VIP ) يستجيب بعد تجاوز الفشل:** لا يأخذ الجهاز الموجود على المسار (الموجه، البوابة، المحول الظاهري) رسائل إعادة توجيه MAC في الحسبان، ويستمر في إرسال البيانات إلى عنوان MAC الخاص بالعنوان الأساسي السابق. يُرجى مراجعة فريق الشبكة لديكم بشأن كيفية التعامل مع رسائل إعادة توجيه عناوين MAC .
- **إرسال GARPs :** تقوم السمة `arpreroute="on"` في قسم `<vip>` (مع `arpinterval` و `arpelapse` ) بإرسال GARPs بانتظام على عنوان IP الظاهري ( VIP ) بعد تجاوز الفشل. راجع دليل المستخدم، القسم 13.6.4 " [ صيغة `<vip>` ](https://safekit.eviden.com/resources/safekit-user-guide-82/#_%3Cvip%3E_Syntax) ".
- **تشخيص مشكلة حل عنوان IP الظاهري ( VIP ) ↔ MAC :** راجع دليل المستخدم، القسم 7.24 " [ استكشاف أخطاء حل عنوان IP الظاهري ( VIP ) ↔ MAC وإصلاحها ](https://safekit.eviden.com/resources/safekit-user-guide-82/#_Issue_with_VIP) "، والقسم 7.16 " [ مشكلة في عنوان IP الظاهري بعد تجاوز الفشل ](https://safekit.eviden.com/resources/safekit-user-guide-82/#_Problem_with_the_1) ".
