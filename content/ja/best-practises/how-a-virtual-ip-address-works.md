# 高可用性クラスタリングにおける仮想 IP アドレス (VIP) はどのように機能しますか? {#how-a-virtual-ip-address-vip-works-in-high-availability-clustering}

## 高可用性クラスターの仮想 IP アドレスとは何ですか? {#virtual-ip-definition}

  * **定義:** **仮想 IP (VIP) アドレス** は、アプリケーションへの継続的なアクセスを保証するために [高可用性クラスタリング](</ja/>) で使用されるフローティング ネットワーク アドレスです。標準 IP とは異なり、VIP は特定の物理ハードウェア インターフェイスにバインドされませんが、クラスター ノード間を移動して、クライアントの単一の永続的なエントリ ポイントを維持します。
  * **ハードウェアは不要:** SafeKit は **Gratuitous ARP (GARP)** を使用してソフトウェア レベルで VIP を管理し、同じサブネット環境での外部ロード バランサーの必要性を排除します。
  * **アプリケーションの透明性:** ローカル VIP にバインドすることにより、アプリケーションはフェイルオーバー イベントを認識せず、クライアントのソース IP と既存のセキュリティ構成を維持します。
  * **災害復旧:** **拡張 LAN** を使用すると、リモート データセンター間で同じ VIP を使用できるため、複雑な DNS 再ルーティングや TTL キャッシュの遅延と比較して、サイト間のフェイルオーバーが簡素化されます。


## SafeKit での仮想 IP の実装 {#safekit-vip-implementation}

  * **ミラー クラスター:** リアルタイムのレプリケーションとフェイルオーバーを容易にするために、プライマリ サーバー上でのみアクティブになるフローティング IP を備えています。
  * **ファーム クラスター:** すべてのノード間で VIP を同時に維持することで、ネットワークの負荷分散を有効にします。


**主な利点:** **Gratuitous ARP (アドレス解決プロトコル)** または **MAC アドレス テイクオーバー** を利用することで、VIP はクライアントを手動で再構成することなくシームレスなアプリケーション フェイルオーバーを可能にし、年中無休のビジネス継続性を確保します。

  * **クラウドとマルチサブネット:** 外部ロード バランサーのヘルス チェック (AWS、Azure、GCP) によって管理され、異なるサブネット間でトラフィックをリダイレクトします。

## 同一サブネット フェールオーバー (ミラー クラスター) での仮想 IP アドレス (VIP) の仕組み {#virtual-ip-same-subnet-failover}

### ローカルサブネットでの自動フェイルオーバーとネットワーク再ルーティング {#automated-failover--network-rerouting-in-a-local-subnet}

ローカル インフラストラクチャ内でシームレスなビジネス継続性を必要とする組織に、**SafeKit ローカル ネットワーク クラスター向けソフトウェア デファインド 高可用性** は、仮想 IP アドレスとリアルタイム アプリケーション フェイルオーバーを管理するための堅牢な自動ソリューションを提供します。 

### ローカル ミラー クラスター: シームレスな 2 ノード Windows または Linux フェイルオーバー {#local-mirror-cluster-seamless-2-node-windows-or-linux-failover}


![同じサブネット内の 2 つのサーバー間の SafeKit 仮想 IP (VIP) フェイルオーバー メカニズム](/wp-content/uploads/2023/05/vip-mirror-same-subnet-1.png "w:256")

 SafeKit VIP エイリアスと MAC アドレス マッピング 両方のノードが同じローカル サブネット内に存在する標準の **SafeKit ミラー クラスター**では、**ソフトウェア定義の仮想 IP (VIP)** を通じて高可用性が実現されます。ハードウェアベースのソリューションとは異なり、SafeKit はこの VIP を OS ネットワーク スタック内で直接管理します。この VIP は、**IP エイリアス** を介してサーバー 1 とサーバー 2 の一意の物理 IP アドレスの上に重ねられ、クライアントの永続的な論理エントリ ポイントとして機能します。 

#### SafeKit の高度な IP エイリアスと複数の VIP のサポート {#safekits-advanced-ip-aliasing--multiple-vip-support}

**SafeKit ソリューション**の主な利点は、ネットワーク ID の管理における柔軟性です。 VIP は、ノード間で「浮動」する 3 番目の IP アドレスです。特に、SafeKit は単一クラスター内で **複数の仮想 IP アドレス**を管理できます。これらは同じプライマリ イーサネット カードに割り当てることも、異なる物理カードに分散することもできるため、さまざまなサービスが特定の仮想 ID にバインドされる複雑な構成が可能になります。 

#### フェイルオーバーメカニズム: Gratuitous ARP (GARP) {#the-failover-mechanism-gratuitous-arp-garp}

SafeKit は、ハードウェア障害時の手動介入をゼロにします。通常の操作では、VIP は **サーバー 1 の MAC アドレス (mac1)** にマッピングされます。 SafeKit がサーバー 1 でハートビート障害を検出した場合、次の 2 段階の回復を実行します。 

  * **アプリケーションの回復:** SafeKit は、サーバー 2 上の重要なアプリケーション サービスを自動的に再起動します。
  * **ネットワーク再ルーティング:** SafeKit は、**Gratuitous ARP (GARP)** メッセージを即座にブロードキャストします。これにより、すべてのネットワーク スイッチと接続されているクライアントの ARP キャッシュが強制的に更新され、VIP が **サーバー 2 の MAC アドレス (mac2)** に再マッピングされます。


#### リモートデータセンターと拡張VLAN {#remote-data-centers--extended-vlans}

**SafeKit の同一サブネット アルゴリズム**は、通常はローカル クラスタに使用されますが、**拡張 LAN または拡張 VLAN** を介して接続されたリモート サイト全体での **災害復旧 (DR)** には推奨される選択肢です。この「拡張された」アーキテクチャにより、地理的な距離を超えて単一のサブネットを維持できるため、ネットワーク トポロジが大幅に簡素化され、複雑なルーティング プロトコルのオーバーヘッドが回避されます。 

> **⚠️ 注:** Gratuitous ARP を介したレイヤー 2 再ルーティングは、アプリケーションにとって **最も透明なソリューション** です。ロード バランサーを使用したレイヤー 3 の再ルーティングとは異なり、**送信元/宛先 IP 変換 (SNAT/DNAT)** を回避します。アプリケーションは元のクライアント IP でトラフィックを直接受信し、仮想 IP はローカルに構成されます。 **多くのアプリケーションは、仮想 IP をローカルで参照し、元のクライアント IP を直接受信することを好みます**。この透明性がないと、複雑なネットワーク変換により **期待どおりに動作しない可能性があります**。

## 仮想 IP (VIP) が異なるサブネット間でどのように動作するか (ミラー クラスター) {#virtual-ip-different-subnets-failover}

### ロードバランサ統合によるクラウド対応トラフィックオーケストレーション {#cloud-ready-traffic-orchestration-via-load-balancer-integration}

外部ネットワーク インフラストラクチャを活用することで、**SafeKit マルチ AZ およびクラウド クラスター向けソフトウェア デファインド 高可用性** は **ネットワーク ロード バランサー** とシームレスに統合し、別個のサブネットと可用性ゾーンにわたるトラフィック フェイルオーバーを調整します。 

### クロスサブネット ミラー クラスター: Windows および Linux の実装 {#cross-subnet-mirror-clusters-windows--linux-implementation}


![2 つの異なるサブネットにわたるロード バランサーを使用した仮想 IP フェイルオーバーの図](/wp-content/uploads/2023/05/vip-mirror-different-subnet.png "w:256")

 ロード バランサのヘルス チェックによるマルチサブネット トラフィック ルーティング クラスタ ノードが **異なるサブネット** に存在する場合、標準の ARP ベースのフェイルオーバーはできません。このシナリオでは、**仮想 IP (VIP)** は、サーバーのイーサネット カードではなく **ロード バランサー (LB)** でホストされます。ロード バランサーはゲートウェイとして機能し、リアルタイムの可用性に基づいてプライマリ ノードとセカンダリ ノードの物理 IP アドレスにトラフィックを送信します。 

#### SafeKit ヘルスチェックによる動的ルーティング {#dynamic-routing-via-safekit-health-checks}

SafeKit は、各ノードに専用の **ヘルス チェック URL** を提供することでトラフィック ステアリングを管理します。ロード バランサは、次の URL にクエリを実行して、クラスタの状態を判断します。 

  * **プライマリ ノード (PRIM):** ヘルス チェックは `HTTP 200 OK` を返します。ロード バランサーはすべてのトラフィックをここに転送します。
  * **セカンダリ ノード (SECOND):** ヘルス チェックは `HTTP 404 NOT FOUND` を返します。ロード バランサーは、このノードにトラフィックを送信しません。

**フェイルオーバー イベント**中、SafeKit はヘルス チェックの応答を即座に切り替え、ロード バランサーをトリガーしてクライアント トラフィックを新しいプライマリ サーバーに再ルーティングします。 

> **⚠️ 注:** SafeKit はヘルス チェック ロジックを提供します。物理または仮想ロード バランサーは、ネットワーク インフラストラクチャによって提供される必要があります。

#### クラウド統合: AWS、Azure、GCP {#cloud-integration-aws-azure-and-gcp}

この「ロード バランサー + ヘルス チェック」モデルは、**クラウド高可用性**の業界標準です。これは、次のような環境で SafeKit を実装するために不可欠です。 

  * 💡 [**Amazon AWS**](</solutions/aws-high-availability-cluster-synchronous-replication-failover/>) (AWS ネットワーク ロード バランサー)
  * 💡 [**Microsoft Azure**](</solutions/azure-high-availability-cluster-synchronous-replication-failover/>) (Azure ロード バランサー)
  * 💡 [**Google Cloud (GCP)**](</solutions/gcp-high-availability-cluster-synchronous-replication-failover/>) (Google Cloud 負荷分散)


#### ネットワークに関する考慮事項: ロード バランサーと拡張 LAN {#network-considerations-load-balancer-vs-extended-lan}

ロード バランサが不要な場合は、サブネット間の **拡張 LAN (VLAN ストレッチング)** の実装についてネットワーク チームに相談してください。これにより、より単純な「同一サブネット」VIP モデルに戻すことができます。 

> **⚠️ 注:** ロード バランサーを選択する場合は、アプリケーションが **送信元/宛先 IP 変換 (SNAT/DNAT)** と互換性があることを確認してください。ロード バランサーを使用すると、アプリケーションが元のユーザーの ID を追跡できなくなったり、アプリケーション自体のネットワーク インターフェイス上で直接構成された仮想 IP が認識されなくなるため、起動に失敗したりする可能性があります。

## 同じサブネット ファーム (ファーム クラスター) で負荷分散された仮想 IP がどのように動作するか {#vip-load-balancing-same-subnet}

### スケーラブルなパフォーマンス: カーネルレベルの負荷分散と冗長性 {#scalable-performance-kernel-level-load-balancing--redundancy}

高トラフィック環境については、**アーキテクチャ ガイド: マルチノード ファーム クラスターによるスケーラブルな高可用性**で、SafeKit が全体の冗長性を維持しながら複数のアクティブ サーバーにワークロードを分散する方法について説明しています。 

### ファーム クラスター アーキテクチャ: Windows または Linux ノード間の負荷分散 {#farm-cluster-architecture-load-balancing-across-windows-or-linux-nodes}


![同じサブネット ファーム クラスター内の負荷分散された仮想 IP (VIP) の図](/wp-content/uploads/2023/05/vip-farm-same-subnet.png "w:256")

 カーネル フィルタリングによる分散トラフィック処理 **負荷分散ファーム クラスタ** では、仮想 IP (VIP) アドレスを使用してクライアント要求を複数のサーバーに同時に分散します。この例には 2 つのノードがありますが、アーキテクチャは大規模なサーバー ファームをサポートするように拡張されます。同一サブネット構成では、VIP は IP エイリアスを介してクラスター内の **すべてのサーバー** のイーサネット カード上に構成されます。 

#### トラフィック分散: カーネルレベルのフィルター {#traffic-distribution-the-kernel-level-filter}

単純なフェールオーバー クラスターとは異なり、ファーム クラスターは特殊な **カーネル レベルのフィルター**を通じてトラフィックを管理します。プロセスは次のように機能します。 

  * **ARP マッピング:** クライアントの ARP キャッシュでは、VIP は最初に単一のハードウェア アドレス (例: サーバー 1 の `mac1`) に関連付けられます。
  * **パケット分割:** サーバー 1 がトラフィックを受信すると、SafeKit カーネル フィルターが受信パケットの ID を分析します (**クライアント IP** または **TCP ポート**に基づいて)。
  * **負荷共有:** フィルタは、どのパケットをローカルで処理する必要があり、どのパケットを他のノード (サーバー 2 など) にリダイレクトして処理するかを決定し、ワークロードのバランスを確保します。


#### Gratuitous ARP によるフェイルオーバーと再ルーティング {#failover-and-rerouting-with-gratuitous-arp}

プライマリ ノード (サーバー 1) に障害が発生した場合、クラスターは **Gratuitous ARP (GARP)** を通じて可用性を維持します。 SafeKit は、サーバー 2 の `mac2` でクライアント ARP キャッシュを更新するための GARP メッセージをブロードキャストします。これにより、プライマリの「エントリ ポイント」に障害が発生した場合でも、クライアントはファーム内の生き残ったノードに即座に再ルーティングされます。 

#### リモートサイトへの展開 {#deployment-in-remote-sites}

**リモート データ センター**全体で運用している組織の場合、サイトが **拡張 LAN または VLAN** 経由でリンクされていれば、この負荷分散アルゴリズムは機能し続けます。これにより、仮想の「同一サブネット」環境が作成されます。これは、地理的に分散されたファーム クラスターにとって最も効率的な構成です。 

## 負荷分散された仮想 IP が異なるサブネット間でどのように動作するか (ファーム クラスター) {#vip-load-balancing-different-subnets}

### マルチゾーン スケーリング: クラウド サブネット間のトラフィックのオーケストレーション {#multi-zone-scaling-orchestrating-traffic-across-cloud-subnets}

**アーキテクチャ ガイド: マルチゾーンおよびクラウド環境でのファーム クラスターのスケーリング** では、アプリケーションのワークロードを個別のアベイラビリティ ゾーンおよびサブネットに分散するための青写真が提供されます。 

### クロスサブネット ファーム クラスター: マルチノード Windows および Linux のスケーラビリティ {#cross-subnet-farm-clusters-multi-node-windows--linux-scalability}


![2 つの異なるサブネット間で動作する負荷分散されたファーム クラスターの図](/wp-content/uploads/2023/05/vip-farm-different-subnet.png "w:256")

 外部負荷分散によるグローバル トラフィック分散 ファーム ノードが **異なるサブネット**に分散されている場合 (マルチ AZ クラウド展開では一般的)、**仮想 IP (VIP)** は外部 **ロード バランサー (LB)** によって管理されます。 LB は VIP を保持し、受信トラフィックをそれぞれのサブネットにあるサーバーの物理 IP アドレスに送信します。 

#### インテリジェントなトラフィック ルーティングと負荷分散ルール {#intelligent-traffic-routing--load-balancing-rules}

ロード バランサーは、次の 2 つの主な要素に基づいてクライアント リクエストを分散します。 

  * **分散ルール:** トラフィックは、セッション アフィニティまたは負荷分散アルゴリズム (**クライアント IP アドレス** または **クライアント TCP ポート**の分析など) に従って分割されます。
  * **ノードの可用性:** トラフィックは、SafeKit ヘルスチェックによって決定された正常なノードにのみルーティングされます。


> **⚠️ 注:** SafeKit はヘルス チェック ロジックを提供します。物理または仮想ロード バランサーは、ネットワーク インフラストラクチャによって提供される必要があります。

#### SafeKit ヘルスチェックの仕組み {#safekit-health-check-mechanism}

SafeKit は、ファーム内のすべてのサーバーにリアルタイムの **ヘルス チェック URL** を提供し、その動作ステータスをロード バランサーに伝達します。 

  * **ノード UP:** ヘルスチェックは `HTTP 200 OK` を返します。ロード バランサーは、このサーバーをアクティブなローテーションに含めます。
  * **ノード ダウン/フェイルオーバー:** サーバーまたはアプリケーションに障害が発生した場合、SafeKit は `HTTP 404 NOT FOUND` を返します (またはサービスが到達不能になります)。ロード バランサーは、障害が発生したノードへのトラフィックの送信を直ちに停止します。


#### クラウド導入標準: AWS、Azure、GCP {#cloud-deployment-standards-aws-azure-and-gcp}

このアーキテクチャは **Cloud Farm クラスタ** の基本モデルであり、サブネットまたはゾーン全体がオフラインになった場合でも、残りのノードが負荷を処理し続けることが保証されます。これは以下によってネイティブにサポートされています。

## 仮想 IP と DNS リダイレクト: DNS フェイルオーバーが頻繁に失敗する理由 {#virtual-ip-vs-dns-redirection-failover}

### DNS 伝播トラップ: VIP が DNS リダイレクトよりも優れたパフォーマンスを発揮する理由 {#the-dns-propagation-trap-why-vips-outperform-dns-redirection}

フェイルオーバーを DNS に依存すると、高可用性アーキテクチャにおいて **誤ったセキュリティ感**が生じることがよくあります。バックアップ サーバーを指すように DNS レコードを変更することは簡単な回復パスのように見えますが、**予測不可能な遅延**という重要な変数が生じます。 DNS ベースのリダイレクトは、変更を認識して伝達するために中間再帰リゾルバーの制御されていないエコシステムに依存しているため、現代のエンタープライズ サービスの「ゼロ ダウンタイム」要件と根本的に互換性がありません。 

### 技術的なシナリオ: DNS 解決と「スタック」クライアント {#the-technical-scenario-dns-resolution-and-the-stuck-client}

標準的なネットワーク設定では、**仮想名** (DNS 名) は、ユーザーが判読できるエントリ ポイントとして機能します。ただし、データがネットワーク上を移動するには、その名前が特定の **物理 IP** アドレスに解決される必要があります。 

![高可用性クラスターにおける物理 IP 1 への DNS 名解決を示す図](/wp-content/uploads/2025/12/dns-rerouting.png "w:256")

 高可用性クラスター内の物理 IP 1 上の DNS 解決と「スタック」クライアント

#### 現在の状態: 物理 IP 1 への解決 {#current-state-resolution-to-physical-ip-1}

最初に、**クライアント 1** と **クライアント 2** が DNS システムに仮想名をクエリします。システムは **物理 IP 1** を返します。次に、クライアントは、その特定のハードウェア アドレスへの直接ネットワーク接続 (ソケット) を確立します。 

#### フェイルオーバーの課題: 物理 IP 2 への再ルーティング {#the-failover-challenge-rerouting-to-physical-ip-2}

物理 IP 1 のサーバーに障害が発生した場合、管理者は **物理 IP 2** を指すように DNS レコードを更新します。クライアントを正常に再ルーティングするには、「完璧な」シーケンスが発生する必要があります。 

  * **Time to Live (TTL)** は、すべての中間 ISP および企業リゾルバーで期限切れになる必要があります。
  * クライアント 1 とクライアント 2 の両方のローカル DNS キャッシュをフラッシュする必要があります。
  * アプリケーションは既存のソケットを閉じて、_新しい_ DNS ルックアップを開始する必要があります。

これらの手順のいずれかが行われていない場合、**クライアント 1 とクライアント 2 は無効な物理 IP 1 との通信を試みたまま「スタック」したまま**となり、DNS レコードが更新されているにもかかわらずサービスのダウンタイムが発生します。 

### DNS リダイレクトの 2 つの「ブラック ボックス」 {#the-two-black-boxes-of-dns-redirection}

  * **再帰的キャッシュ:** 多くのインターネット サービス プロバイダー (ISP) や企業の DNS リゾルバーは、トラフィックを削減するために低い TTL 設定を無視し、要求された有効期限を超えて数分から数時間にわたって「古い」物理 IP 1 をキャッシュすることがよくあります。
  * **アプリケーションの永続性:** 最近のアプリケーション (Java ベースのマイクロサービスや Web ブラウザなど) は、多くの場合、起動時に DNS ルックアップを 1 回だけ実行します。 DNS レコードが物理 IP 2 に更新されても、アプリケーションは内部メモリに保存されている初期 IP を引き続き使用します。


### 結論 {#conclusion}

DNS リダイレクトは、高可用性ソリューションとしては一貫性のないソリューションです。ローカル環境または地域環境内での即時フェイルオーバーの場合、ソフトウェア定義の **仮想 IP (VIP)** が、ゼロ ダウンタイムの永続性を保証する唯一の方法です。

## 仮想 IP (VIP) に関するよくある質問 {#virtual-ip-faq}

### 仮想 IP (VIP) とネットワーキング {#virtual-ip-vip--networking}

仮想 IP (VIP) とは何ですか?また、物理 IP との違いは何ですか?

**物理 IP アドレス**は特定のネットワーク インターフェイスにバインドされていますが、**仮想 IP (VIP)** はハードウェアから独立した「フローティング」アドレスです。 SafeKit クラスターでは、VIP は永続的なエントリー ポイントとして機能します。プライマリ サーバーに障害が発生した場合、VIP は正常なセカンダリ ノードに自動的に移行され、クライアントの再構成が不要になります。

仮想 IP を使用するにはハードウェア ロード バランサーが必要ですか?

いいえ。 **SafeKit 高可用性ソフトウェア** は、ソフトウェア レベルで仮想 IP を管理します。同一サブネット アーキテクチャでは、**IP エイリアシング** と **Gratuitous ARP (GARP)** を利用してトラフィックをリダイレクトします。これにより、外部ハードウェア ロード バランサーや専用プロキシ サーバーのコストと複雑さが解消されます。

Gratuitous ARP (GARP) とは何ですか? なぜ使用されるのですか?

**Gratuitous ARP (GARP)** は、ネットワーク スイッチおよびルーターの ARP テーブルを更新するネットワーク ブロードキャストです。フェイルオーバー中に、新しいプライマリ サーバーは GARP パケットを送信して、**仮想 IP** がその MAC アドレスにマッピングされたことを通知し、ネットワーク ファブリック全体でトラフィックの即時の再ルーティングを強制します。

DNS 名を仮想 IP に関連付けることはできますか?

**はい。** 標準の A レコードを作成することで、DNS 名を VIP に関連付けることができます。主な利点は、リダイレクトが **DNS レベル**ではなく、**VIP レベル** (ARP またはネットワーク リダイレクト経由) で管理されることです。これにより、DNS の伝播と TTL の有効期限に関連する遅延が回避され、**アプリケーションの透明性**が確保されます。

### クラウドと高度なアーキテクチャ {#cloud--advanced-architectures}

仮想 IP はクラウド (AWS、Azure、GCP) でどのように機能しますか?

レイヤ 2 (ARP) が制限されているクラウド環境では、SafeKit は **クラウド ロード バランサ** (AWS ELB、Azure LB、または Google GCLB) と統合します。 SafeKit は、SNAT/DNAT を使用してトラフィックをアクティブ ノードにルーティングするためにプラットフォームが監視する **ヘルス チェック URL** を提供します。

ディザスタリカバリには、ロードバランサよりも拡張 LAN の方が優れていますか?

**はい**。リモート データセンターの場合は、**拡張 LAN (拡張 VLAN)** がサイト全体で **アプリケーションの透過性**を維持するため、多くの場合優れています。 **同じ仮想 IP** を維持することで、アプリケーションとそのクライアントは同じ ID を使用して通信を継続し、データセンター間の移行を完全にシームレスにします。

DNS 再ルーティングと仮想 IP の制限は何ですか?

**DNS 再ルーティング**は **TTL (Time to Live)** とクライアント側のキャッシュによって制限されており、回復が数時間遅れる可能性があります。大きな欠点は、**DNS 名を再解決しないクライアントが、障害が発生したサーバーへの接続を試行したままになる**ことです。対照的に、**仮想 IP** は、すべてのトラフィックを即座に再ルーティングする瞬時のレイヤー 2 フェイルオーバーを提供し、クライアント側の DNS キャッシュのステータスに関係なく接続を確保します。

### 透明性とセキュリティ {#transparency--security}

アプリケーションの透明性にとってローカル仮想 IP が重要なのはなぜですか?

ローカル **仮想 IP (VIP)** は、ソフトウェアが永続 VIP にバインドできるようにすることで、**アプリケーションの透過性**を保証します。 SafeKit は、**カーネル レベル** でリダイレクトを処理し、バインドされた IP が変更される DNAT ソリューションとは異なり、アプリケーションがクラスターのフェイルオーバーを認識しないようにします。

仮想 IP を使用すると、クライアントの元の IP アドレスが保持されますか?

はい。 SafeKit は送信元ネットワーク アドレス変換 (SNAT) を回避します。 VIP はアクティブ サーバーに対してローカルであるため、アプリケーションは **元のクライアント IP** を受け取ります。これは、セキュリティ監査、セッションの永続性、および規制ログにとって重要です。
