# ネットワーク内のSafeKit mirrorクラスタの仮想IPアドレスをテストする

このガイドでは、 SafeKit mirrorクラスタ（ mirrorモジュール）の仮想IPアドレス（ VIP ）がネットワーク内で正しく機能していることを確認する方法について説明します。仮想IP （ VIP ）はプライマリサーバーによって保持され、フェイルオーバー後に新しいプライマリサーバーに再ルーティングされます。

## 1. 基本原則

**前提条件：** mirrorクラスタの両方のノードは、同じレイヤ2 IPサブネット（ LAN 、またはリモートサイト間で拡張されたVLANに属している必要があります。

- 仮想IP (VIP) は**プライマリ サーバー**(PRIMまたはALONE状態) でのみ有効です。モジュールがノード上でプライマリとして起動すると (`where="one_side_alias"`設定)、そのアドレスのネットワーク カード上の物理IPアドレスのエイリアスとして設定されます。
- したがって、プライマリサーバーのMACアドレスは、 ARPテーブル（ルーター、ゲートウェイ、同一サブネット内のクライアント）において仮想IP （ VIP ）に関連付けられているアドレスです。仮想IP （ VIP ）宛てのすべてのトラフィックはプライマリサーバーに送信されます。
- フェイルオーバー（プライマリの停止または障害）が発生すると、仮想IP （ VIP ）は以前のプライマリから削除され、新しいプライマリにエイリアスとして設定されます。その後、2つのメカニズムによって、ネットワークは仮想IP （ VIP ）を新しいプライマリのMACアドレスに関連付けることができます。
  - 仮想IP （ VIP ）がネットワークカードにエイリアスとして追加されたときに、オペレーティングシステムによって送信されるネットワークメッセージ。
  - `<vip>`セクションで`arpreroute="on"`属性が設定されている場合、 SafeKitによって送信される**GARPs** (gratuitous ARP)。

したがって、テストする必要があるのは以下のとおりです。

1. 仮想IP （ VIP ）はプライマリサーバーによって保持され、クライアントからアクセス可能です。
2. プライマリサーバーが変更されると、仮想IP （ VIP ）に関連付けられたMACアドレスは、ネットワーク内の新しいプライマリ（ルーター、ゲートウェイ、仮想化）に再ルーティングされます。

## 2. 前提条件：仮想IP （ VIP ）の設定

1. mirrorモジュールの`userconfig.xml`ファイルで、 `<vip>`セクションに仮想IP （ VIP ）を設定します。arpreroute `arpreroute="on"`属性を設定すると、フェイルオーバー後に新しいプライマリがGARPsを送信します。

   ```xml
   <vip>
     <interface_list>
       <interface arpreroute="on">
         <real_interface>
           <virtual_addr addr="<VIP>" where="one_side_alias"/>
         </real_interface>
       </interface>
     </interface_list>
   </vip>
   ```

2. 両方のノードに設定を適用してください。
3. モジュールを開始するには、一方のノードが<strong>PRIM （ Ready ）</strong>で、もう一方のノード<strong>がSECOND （ Ready ）</strong>である必要があります。

## 3. テスト1 – プライマリサーバーが保持する仮想IP （ VIP ）

**手順**

1. プライマリサーバーで、 `ipconfig` (Windows) または`ip addr show` (Linux) を実行します。
   →<strong>期待される結果:</strong>仮想IP (VIP) が、物理IPアドレスのネットワークカード上のエイリアスとして表示されます。
2. セカンダリーサーバーでも、同じコマンドを実行してください。
   →<strong>期待される結果：</strong>仮想IP （ VIP ）が表示されない。
3. <strong>クラスター外の</strong>クライアントワークステーションから、物理IPアドレスと仮想IP （ VIP ）の両方に`ping` 。
   →**期待される結果：** 3つの`ping`コマンドすべてが応答する（ファイアウォールによってフィルタリングされない限り）。
4. SafeKitモザイクを使用して仮想IP (VIP) 経由でのアクセスを確認します。<strong>外部</strong>クライアントのブラウザーから、 `http://<VIP>:9010/safekit/mosaic.html`に接続します (SafeKit Web サーバーとコンソールが HTTPS に切り替えられている場合は、ポート 9453 を使用します)。次に、 mirror<strong>モジュール名</strong>を入力してテストを実行します。
   →<strong>期待される結果:</strong>モザイクのすべてのセルに<strong>プライマリサーバー</strong>の名前が単一の色で表示されます。仮想IP (VIP) へのすべてのTCP接続はプライマリによって処理されます。

![モザイクを使用してSafeKit mirrorの仮想IPアドレスをテストします](/wp-content/uploads/2024/03/appli-20.png)

## 4. テスト2 – 手動フェイルオーバー（プライマリの停止）

このテストでは、プライマリサーバー上のモジュールを停止することによってトリガーされるフェイルオーバー中に、仮想IP （ VIP ）がプライマリサーバーに追従することを確認します。

**手順**

1. SafeKitコンソールから（またはコマンドラインから`safekit stop -m <module>`を使用して）プライマリ（ノード1）上のモジュールを停止します。
   →<strong>期待される結果：</strong>ノード 1 はSTOP (NotReady) 状態になり、ノード 2 はALONE (Ready) 状態になります。新しいプライマリのログに、 `Virtual IP <VIP> set`というメッセージが表示されます。
2. 新しいプライマリで、 `ipconfig`または`ip addr show`を実行します。
   →<strong>期待される結果:</strong>仮想IP (VIP) がこのノードのエイリアスとして表示され、以前のプライマリノードには表示されなくなります。
3. クライアントワークステーションから、3 つの`ping`コマンドを繰り返し実行し、仮想IP (VIP) でモザイクを再度実行します。
   →<strong>期待される結果：</strong>すべてが反応し、モザイクのすべてのセルに<strong>新しいプライマリ</strong>の名前が単一の色で表示されます。
4. ノード 1 のモジュールを再起動すると、同期が再行われSECOND (Ready) 状態になり、ノード 2 はPRIM (Ready) 状態になります。

## 5. テスト3 – `arp -a`を使用したMACリルーティングの確認

フェイルオーバー前に仮想IP （ VIP ）に関連付けられたMACアドレスを記録し、フェイルオーバー後にそれが変更されていることを確認します。

このテストは、クライアントワークステーションがクラスタと<strong>同じIPサブネット</strong>内にある場合にのみ可能です。

クライアントとクラスタの間にルーターが存在する場合、クライアントのARPテーブルには仮想IPアドレス（ VIP ）ではなく、クラスタのネットワークに到達するために使用されるゲートウェイのアドレスが含まれます。その場合は、ネットワークチームと協力してルーターまたはゲートウェイのARPテーブルを確認してください。

**手順**

1. 当該モジュールは、ノード1ではPRIM （ Ready ）状態、ノード2ではSECOND （ Ready ）状態です。
2. クライアントワークステーションで、物理IPアドレスと仮想IP （ VIP ）の両方に`ping` 、その後`arp -a`を実行します。
   →<strong>期待される結果:</strong>仮想IP (VIP) は<strong>、プライマリの物理IPアドレスと同じMACアドレス</strong>に関連付けられます。
3. プライマリ（ノード1）上のモジュールを`stop` 。
4. 仮想IP （ VIP ）に再度`ping` 、その後、再度`arp -a`を実行します。
   →<strong>期待される結果:</strong>仮想IP (VIP) が、<strong>新しいプライマリの物理IPアドレスと同じMACアドレス</strong>に関連付けられます。

> ARPテーブルを読み取る前に、仮想IP (VIP) に再度`ping` 。エントリが古いものとしてマークされ、 `ping`の後でのみ更新される場合があります。

プライマリが停止する前と後の、想定されるARPテーブルの例：

| 住所 | 停止前のMAC | 停止後のMAC |
|---|---|---|
| ノード1の物理IP | ノード1 MAC | ノード1 MAC |
| ノード2の物理IP | ノード2 MAC | ノード2 MAC |
| 仮想IP （ VIP ） | **ノード1 MAC** | **ノード2 MAC** |

## 6. テスト4 – Wireshark （ Windows ）またはtcpdump （ Linux ）を使用したエンドツーエンドチェック

クライアント側と両方のノードでパケットをキャプチャすることで、仮想IP （ VIP ）へのTCP接続を追跡できます。Windows WindowsではWiresharkを、 Linuxマシンではtcpdumpを使用します。

<strong>パケットのMAC （イーサネット）ヘッダー</strong>を確認する必要があります。宛先IPアドレスは仮想IP （ VIP ）のままであり、トラフィックを受信するノードを示すのは宛先MACアドレスです。

**観察すべき点：**

| いつ | パケットをキャプチャする場所 | 観測されたMACアドレス |
|---|---|---|
| フェイルオーバー前 | クライアント | クライアントMAC →<strong>ノード1（プライマリ）</strong>のMAC |
| フェイルオーバー前 | ノード1 | 仮想IP （ VIP ）宛のパケットは受信されるが、ノード2は何も受信しない。 |
| フェイルオーバー中 | ネットワーク | ノード 2 から仮想IP (VIP) に対して送信されるMACリルーティング メッセージ: OS がエイリアスとして設定されているときに送信されるメッセージ、およびSafeKit (`arpreroute="on"`) によって送信されるGARPs 。 |
| フェイルオーバー後 | クライアント | クライアントMAC → ノード2のMAC **（新しいプライマリ）** |

> クライアントワークステーションがクラスタとは異なるサブネットにある場合、ノードに表示される「クライアントMAC 」は、クライアントワークステーションのMACアドレスではなく、2つのサブネットを接続する**ゲートウェイ**（ルータ）のMACアドレスです。

## 7. どのワークステーションからテストを行うか

動作はクライアントとクラスタ間のネットワークパスに依存します。ご使用のアーキテクチャに関連する各タイプのクライアントから、テスト1とテスト2を実行してください。

| クライアントの所在地 | テストで確認する内容 |
|---|---|
| クラスターと<strong>同じサブネット</strong>内のクライアント | クライアントのARPテーブルの更新（テスト3回実施可能） |
| **別のサブネット**（ルーター、ゲートウェイ、ハイパーバイザー仮想ネットワーク）内のクライアント | ルーターまたはゲートウェイにおけるクライアントのARPテーブルの更新 |
| <strong>mirrorクラスタの仮想マシンも1台ホストしているハイパーバイザ上の</strong>クライアント仮想マシン | ハイパーバイザの仮想スイッチの動作。仮想スイッチは内部スイッチングとルーティングも処理する。 |

## 8．期待される結果の概要

| テスト | アクション | 期待される結果 |
|---|---|---|
| 1 | PRIM / SECOND 、 `ipconfig` 、 `ping` 、およびmosaic | 仮想IP （ VIP ）はプライマリのみのエイリアスとして使用されます。3つの`ping`コマンドは応答します（ファイアウォールでフィルタリングされない限り）。モザイクにはプライマリのみが表示されます。 |
| 2 | プライマリーの停止 | 新しいプライマリのエイリアスとして仮想IP （ VIP ）を設定します。 `Virtual IP <VIP> set` 、モザイクには新しいプライマリのみを表示します。 |
| 3 | プライマリが停止する前と後の`arp -a` | 仮想IP （ VIP ）は、ノード1のMACアドレスに移動する。 |
| 4 | フェイルオーバー前後のWiresharkまたはtcpdumpキャプチャ | クライアントは新しいプライマリのMACアドレスに送信します |

## 9. トラブルシューティング

- **フェイルオーバー後に仮想IP （ VIP ）が応答しなくなる原因は、** 経路上のデバイス（ルーター、ゲートウェイ、仮想スイッチなど）がMACリルーティングメッセージを考慮せず、以前のプライマリのMACアドレス宛てにトラフィックを送信し続けているためです。MACリルーティングメッセージの処理方法についてMACネットワークチームに確認してください。
- **GARPs送信:** `<vip>`セクションの`arpreroute="on"`属性 (`arpinterval`と`arpelapse`含む) は、フェイルオーバー後に仮想IP (VIP) 上で定期的にGARPs送信します。ユーザー ガイドのセクション 13.6.4 " [ `<vip>`構文](https://safekit.eviden.com/resources/safekit-user-guide-82/#_%3Cvip%3E_Syntax) " を参照してください。
- **仮想IP (VIP) ↔ MAC解決の診断:** ユーザー ガイドのセクション 7.24「 [仮想IP (VIP) ↔ MAC解決のトラブルシューティング](https://safekit.eviden.com/resources/safekit-user-guide-82/#_Issue_with_VIP) 」およびセクション 7.16「 [フェイルオーバー後の仮想IPの問題](https://safekit.eviden.com/resources/safekit-user-guide-82/#_Problem_with_the_1) 」を参照してください。

仮想IPアドレスを使用したロード バランシングについては、 [ SafeKit Farmクラスターでのロード バランシング仮想IPアドレスのテスト](/ja/best-practises/test-load-balancing-vip-farm/)を参照してください。
