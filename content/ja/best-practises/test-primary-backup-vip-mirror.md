# SafeKitミラークラスタにおけるプライマリ/バックアップ仮想IPアドレスのテスト

このガイドでは、SafeKitミラークラスタ（ミラーモジュール）の仮想IPアドレス（VIP）がネットワーク内で正しく機能していることを確認する方法について説明します。VIPはプライマリサーバーによって保持され、フェイルオーバー後に新しいプライマリサーバーに再ルーティングされます。

## 1. 基本原則

**前提条件：**ミラークラスタの両方のノードは、同じレイヤ2 IPサブネット（LAN、またはリモートサイト間で拡張されたVLAN）に属している必要があります。

- VIPは**プライマリサーバー**（PRIMまたはALONE状態）でのみアクティブになります。ノード上でモジュールがプライマリとして起動すると（ `where="one_side_alias"`構成）、そのアドレスのネットワークカード上の物理IPアドレスのエイリアスとして設定されます。
- したがって、プライマリサーバーのMACアドレスは、ARPテーブル（ルーター、ゲートウェイ、同一サブネット内のクライアント）においてVIPに関連付けられているMACアドレスです。VIP宛てのすべてのトラフィックはプライマリサーバーに送信されます。
- フェイルオーバー（プライマリの停止または障害）が発生すると、VIPは以前のプライマリから削除され、新しいプライマリにエイリアスとして設定されます。その後、2つのメカニズムによって、ネットワークはVIPを新しいプライマリのMACアドレスに関連付けることができます。
  - VIPがネットワークカードにエイリアスとして追加されたときに、オペレーティングシステムによって送信されるネットワークメッセージ。
  - `<vip>`セクションで`arpreroute="on"`属性が設定されている場合、SafeKit によって送信される**GARP** (gratuitous ARP)。

したがって、テストする必要があるのは以下のとおりです。

1. VIPはプライマリサーバーによって保持され、クライアントからアクセス可能であること。
2. ネットワーク（ルーター、ゲートウェイ、仮想化）が、プライマリサーバーが変更された際にGARPを考慮に入れること。

## 2. 前提条件：VIP構成

1. ミラーモジュールの`userconfig.xml`ファイルで、 `<vip>`セクションにVIPを設定します。arpreroute `arpreroute="on"`属性を設定すると、フェイルオーバー後に新しいプライマリがGARPを送信するようになります。

   ```xml
   <vip>
     <interface_list>
       <interface arpreroute="on">
         <real_interface>
           <virtual_addr addr="<VIP>" where="one_side_alias"/>
         </real_interface>
       </interface>
     </interface_list>
   </vip>
   ```

2. 両方のノードに設定を適用してください。
3. モジュールを開始するには、一方のノードが**PRIM（準備完了）**で、もう一方のノード**がSECOND（準備完了）**である必要があります。

## 3. テスト1 – VIPはプライマリサーバーによって保持される

**手順**

1. プライマリサーバーで、 `ipconfig` （Windows）または`ip addr show` （Linux）を実行します。
   →**期待される結果：** VIPが物理IPアドレスのネットワークカード上にエイリアスとして表示される。
2. セカンダリーサーバーでも、同じコマンドを実行してください。
   →**期待される結果：** VIPは表示されない。
3. **クラスタ外の**クライアントワークステーションから、物理IPアドレスとVIPの両方に`ping` 。
   →**期待される結果：** 3つの`ping`コマンドすべてが応答する（ファイアウォールによってフィルタリングされない限り）。
4. SafeKitモザイクを使用してVIP経由でのアクセスを確認します。クライアントワークステーションのブラウザから、 `http://<VIP>:9010/safekit/mosaic.html`に接続し、ミラー**モジュール名**を入力してテストを実行します。
   →**期待される結果:**モザイクのすべてのセルに**プライマリサーバー**の名前が単一の色で表示されます。VIP へのすべての TCP 接続はプライマリによって処理されます。

## 4. テスト2 – 手動フェイルオーバー（プライマリの停止）

このテストでは、プライマリサーバー上のモジュールを停止することで発生するフェイルオーバー中に、VIPがプライマリサーバーに追従することを確認します。

**手順**

1. SafeKitコンソールから（またはコマンドラインから`safekit stop -m <module>`を使用して）プライマリ（ノード1）上のモジュールを停止します。
   →**期待される結果：**ノード1はSTOP（NotReady）状態になり、ノード2はALONE（Ready）状態になります。新しいプライマリのログに`Virtual IP <VIP> set`というメッセージが表示されます。
2. 新しいプライマリで、 `ipconfig`または`ip addr show`を実行します。
   →**期待される結果：** VIPは、以前のプライマリノードではなく、このノードのエイリアスとして表示されるようになります。
3. クライアントワークステーションから、3つの`ping`コマンドを繰り返し実行し、VIP上でモザイク処理を再度実行します。
   →**期待される結果：**すべてが反応し、モザイクのすべてのセルに**新しいプライマリ**の名前が単一の色で表示されます。
4. ノード1でモジュールを再起動すると、同期が再行われ、SECOND（準備完了）状態になります。一方、ノード2はPRIM（準備完了）状態になります。

**このテストの制限事項：**ステップ3で正しい結果が得られたとしても、SafeKitが送信するGARPが正しく機能していることを証明できるわけではありません。VIPが新しいプライマリでエイリアスとして設定されると、オペレーティングシステム自体がネットワーク上にメッセージを送信し、仮想IPアドレスとMACアドレスの関連付けが既に再ルーティングされている可能性があります。この関連付けの再ルーティングを実際に確認できるのは、テスト3とテスト4のみです。

## 5. テスト3 – `arp -a`によるGARPリルーティングの確認

フェイルオーバー前にVIPに関連付けられているMACアドレスを記録し、フェイルオーバー後にそれが変更されていることを確認します。

このテストは、クライアントワークステーションがクラスタと**同じIPサブネット**内にある場合にのみ可能です。

クライアントとクラスタの間にルータが存在する場合、クライアントのARPテーブルにはVIPアドレスではなく、クラスタネットワークに到達するために使用されるゲートウェイのアドレスが含まれます。この場合、ネットワークチームと協力して、ルータまたはゲートウェイのARPテーブルでGARPを確認する必要があります。

**手順**

1. 当該モジュールは、ノード1ではPRIM（準備完了）状態、ノード2ではSECOND（準備完了）状態です。
2. クライアントワークステーションで、物理IPアドレスとVIPの両方に`ping` 、その後`arp -a`を実行します。
   →**期待される結果:** VIP は**プライマリの物理 IP アドレスと同じ MAC アドレス**に関連付けられます。
3. プライマリ（ノード1）上のモジュールを`stop` 。
4. VIPに再度`ping` 、その後再度`arp -a`を実行してください。
   →**期待される結果:** VIP は、**新しいプライマリの物理 IP アドレスと同じ MAC アドレス**に関連付けられます。

> ARP テーブルを読み取る前に VIP に再度`ping` 。エントリが古いものとしてマークされ、 `ping`後でのみ更新される可能性があります。

プライマリが停止する前と後の、想定されるARPテーブルの例：

|アドレス|停止前の MAC アドレス|停止後の MAC アドレス|
|---|---|---|
|ノード 1 の物理 IP アドレス|ノード 1 の MAC アドレス|ノード 1 の MAC アドレス|
|ノード 2 の物理 IP アドレス|ノード 2 の MAC アドレス|ノード 2 の MAC アドレス|
| VIP |**ノード 1 MAC** |**ノード 2 MAC** |

## 6. テスト4 – Wireshark（Windows）またはtcpdump（Linux）を使用したエンドツーエンドチェック

クライアント側と両方のノードでパケットをキャプチャすることで、VIPへのTCP接続を追跡できます。WindowsマシンではWiresharkを、Linuxマシンではtcpdumpを使用します。

**パケットのMAC（イーサネット）ヘッダー**を確認する必要があります。宛先IPアドレスはVIPのままですが、トラフィックを受信するノードを示すのは宛先MACアドレスです。

**観察すべき点：**

|いつ|どこで|観測された MAC アドレスをキャプチャするか|
|---|---|---|
|フェイルオーバー前|クライアント|クライアントMAC →**ノード1（プライマリ）**のMAC |
|フェイルオーバー前|ノード 1 | VIP 宛のパケットは受信されます。ノード 2 は何も受信しません|
|フェイルオーバー中|ネットワーク| VIP に対してノード 2 から GARP が送信されました|
|フェイルオーバー後|クライアント|クライアントMAC →**ノード2（新しいプライマリ）**のMAC |

クライアントワークステーションがクラスタとは異なるサブネットにある場合、ノードに表示される「クライアントMAC」は、クライアントワークステーションのMACアドレスではなく、2つのサブネットを接続する**ゲートウェイ**（ルータ）のMACアドレスになります。同様に、クライアントワークステーションでは、VIP宛てのパケットは、自身のゲートウェイのMACアドレスに送信されます。

## 7. どのワークステーションからテストを行うか

動作はクライアントとクラスタ間のネットワークパスに依存します。ご使用のアーキテクチャに関連する各タイプのクライアントから、テスト1とテスト2を実行してください。

|クライアントの所在地|テストで確認する内容|
|---|---|
|クラスターと**同じサブネット**内のクライアント| GARP によるクライアントの ARP テーブルの更新 (テスト 3 が可能) |
|**異なるサブネット**内のクライアント (ルーター、ゲートウェイ、ハイパーバイザー仮想ネットワーク) |ルーターまたはゲートウェイによる GARP 処理|
|**クラスター VM もホストするハイパーバイザー上のクライアント**VM |内部スイッチングとルーティングも処理するハイパーバイザーの仮想スイッチの動作|

## 8．期待される結果の概要

|テスト|アクション|期待される結果|
|---|---|---|
| 1 | PRIM / SECOND、 `ipconfig` 、 `ping` 、およびmosaic | VIPはプライマリのみのエイリアスとして使用されます。3つの`ping`コマンドは応答します（ファイアウォールによってフィルタリングされない限り）。mosaicにはプライマリのみが表示されます|
| 2 |プライマリの停止| VIP を新しいプライマリのエイリアスとして使用。 `Virtual IP <VIP> set`メッセージ。モザイクには新しいプライマリのみが表示されます|
| 3 |プライマリが停止する前と後の`arp -a` | VIP はノード 1 の MAC アドレスからノード 2 の MAC アドレスに移動します|
| 4 |フェイルオーバー前後の Wireshark または tcpdump キャプチャ|クライアントは新しいプライマリの MAC アドレスに送信します|

## 9. トラブルシューティング

- **フェイルオーバー後、VIPが応答しなくなります。**経路上のデバイス（ルーター、ゲートウェイ、仮想スイッチなど）がGARPを考慮していないため、以前のプライマリVIPのMACアドレス宛にトラフィックが送信され続けています。ネットワークチームにGARPの処理状況を確認してください。
- **GARP の送信:** `<vip>`セクションの`arpreroute="on"`属性 ( `arpinterval`および`arpelapse`を含む) は、フェイルオーバー後に VIP 上で定期的に GARP を送信します。ユーザー ガイドのセクション 13.6.4 " [`<vip>`構文](https://safekit.eviden.com/ja/resources/safekit-user-guide-82/#_%3Cvip%3E_Syntax)" を参照してください。
- **VIP ↔ MAC 解決の診断については、**ユーザーガイドのセクション 7.24「 [VIP ↔ MAC 解決のトラブルシューティング](https://safekit.eviden.com/ja/resources/safekit-user-guide-82/#_Issue_with_VIP)」およびセクション 7.16「[フェイルオーバー後の仮想 IP の問題](https://safekit.eviden.com/ja/resources/safekit-user-guide-82/#_Problem_with_the_1)」を参照してください。
