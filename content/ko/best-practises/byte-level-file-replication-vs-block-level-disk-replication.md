# 고가용성(HA)을 위한 바이트 수준 파일 복제와 블록 수준 디스크 복제 비교 {#byte-level-file-replication-vs-block-level-disk-replication-for-ha}

## 고가용성 클러스터에서 바이트 수준 파일 복제와 블록 수준 디스크 복제 비교 {#byte-level-file-replication-vs-block-level-disk-replication-in-a-high-availability-cluster}

### 개요 {#overview}

이 글에서는 고가용성 클러스터에서 바이트 수준 파일 복제와 블록 수준 디스크 복제의 장단점을 비교 분석합니다. 복제 데이터 용량, 애플리케이션 데이터 구성에 미치는 영향, 복구 시간, 구현 용이성 등을 중점적으로 살펴봅니다.

다음 비교표는 고가용성 소프트웨어 제품인 SafeKit 에서 구현된 바이트 수준 파일 복제에 대해 자세히 설명합니다.

### 바이트 수준 파일 복제란 무엇입니까? {#what-is-byte-level-file-replication}

바이트 수준 파일 복제(예: [ SafeKit ](</>) )는 파일 내부의 수정 사항만 복제한다는 의미입니다. 

고가용성 클러스터에서 장애 발생 시 데이터 손실이 전혀 발생하지 않도록 하려면 동기 복제 [ 와 비동기 복제 ](</ko/best-practises/synchronous-replication-vs-asynchronous-replication/>) 가 필요합니다. 비동기 복제는 백업 솔루션에 사용됩니다.

복제되는 데이터의 양은 애플리케이션이 파일 내에서 수정한 정보로 줄어듭니다. 불필요한 데이터는 복제되지 않습니다.

애플리케이션의 데이터 구성에는 아무런 영향이 없습니다. 예를 들어, 애플리케이션의 데이터가 시스템 디스크에 있는 경우 바이트 수준 파일 복제가 정상적으로 작동합니다.

장애 조치 발생 시 복구 시간(RTO)은 보조 서버의 복제된 파일에서 애플리케이션이 다시 시작되는 시간으로 단축됩니다.

마지막으로, 이 솔루션은 복제할 디렉터리의 경로만 구성하면 되므로 설정이 매우 간단합니다.

### 블록 레벨 디스크 복제란 무엇입니까? {#what-is-block-level-disk-replication}

블록 수준 디스크 복제(예: [ DRBD ](<https://linbit.com/drbd/>) )는 디스크 내부의 수정 사항만 복제한다는 의미입니다.

복제되는 데이터의 양은 애플리케이션에서 수정된 정보로만 한정되지 않습니다. 디스크 관리를 위한 메타데이터(사용 가능한 블록 목록, 파일 시스템 내부 정보)와 같은 추가 데이터도 복제됩니다.

이는 애플리케이션 데이터 구성에 상당한 영향을 미칩니다. 모든 데이터는 복제 디스크에 로컬로 저장되어야 합니다. 최소한 애플리케이션 재구성이 필요합니다. 그렇지 않으면 복제할 데이터 중 일부가 시스템 디스크에 있는 경우, 시스템 디스크는 각 서버마다 고유해야 하므로 복제가 불가능합니다.

장애 조치 후 복제된 디스크의 파일 시스템 복구 절차가 길어질수록 복구 시간(RTO)이 증가합니다.

마지막으로, 이 솔루션은 파일 시스템이 있는 특수 디스크를 구성하는 데 기술이 필요하기 때문에 설정이 쉽지 않습니다. 또한 복제된 디스크에 애플리케이션 데이터를 구성하려면 애플리케이션 관련 기술이 필요합니다.

## 바이트 수준 파일 복제와 블록 수준 디스크 복제의 장단점 {#pros-and-cons-of-byte-level-file-replication-vs-block-level-disk-replication}

---|---|---  
제품 | • [ SafeKit Windows 및 Linux ](/) | 에 적용됩니다. • 디스크 복제 제품(예: [ DRBD ](https://linbit.com/drbd/)   
애플리케이션 데이터 구성 | • SafeKit 사용해도 애플리케이션 데이터 구성에 영향 없음. <br> • [ 실시간 복제할 디렉터리만 정의하면 됨. ](/ko/architectures/file-replication-byte-level-with-failover-mirror-cluster/) <br> • 시스템 디스크 내부의 디렉터리도 복제 가능. | • 애플리케이션 데이터 구성에 영향 있음. <br> • 복제 디스크에 데이터를 저장하도록 애플리케이션을 특별히 구성해야 함. <br> • 시스템 디스크의 데이터는 복제할 수 없음.   
데이터 복제 | • 동기식 바이트 수준 파일 복제. <br> • 애플리케이션 활동으로 생성된 파일 수정 작업을 복제합니다. <br> • 메타데이터는 복제되지 않습니다. 파일 전체가 아닌 파일에서 수정된 데이터만 복제됩니다(바이트 수준 파일 복제). <br> • [ 장애 발생 시 데이터 손실을 방지하기 위한 동기식 복제 ](/ko/best-practises/synchronous-replication-vs-asynchronous-replication/) . | • 복제된 디스크 내에서 수정된 모든 데이터를 복제합니다. <br> • 애플리케이션 데이터와 메타데이터를 모두 복제합니다. <br> • 예를 들어 파일의 마지막 액세스 시간이 복제됩니다(파일을 읽을 때마다 마지막 액세스 시간이 수정됨).   
배포 복잡성 | • 아니요 - 2개의 서버에 소프트웨어 설치 | • 예 - 운영 체제 및 복제 디스크 구성에 특정 IT 기술 필요   
장애 조치 | • 두 번째 서버에서 애플리케이션을 다시 시작하십시오. | • 복제된 디스크에서 파일 시스템을 다시 마운트하십시오. <br> • 파일 시스템에서 복구 절차를 수행하십시오. <br> • 그런 다음 애플리케이션을 다시 시작하십시오.   
페일백 | • 자동 페일백. <br> • 기본 서버의 애플리케이션을 중지하지 않고 보조 서버에서 데이터를 재동기화합니다. <br> • 데이터 재동기화가 완료될 때까지 애플리케이션 페일오버가 수행되지 않습니다. | • 모든 제품의 기능 수준이 동일하지는 않습니다.   
쿼럼 및 스플릿 브레인 | • 네트워크 격리(스플릿 브레인) 후 단일 서버에서 애플리케이션 실행. <br> • 스플릿 브레인 후 데이터 일관성 유지. <br> • 스플릿 브레인을 위해 세 번째 머신, 쿼럼 디스크 또는 특수 하트비트 회선이 필요하지 않음. <br> • [ 하트비트, 페일오버 및 쿼럼에 대한 추가 정보 ](/best-practises/heartbeat-failover-quorum-windows-linux-cluster/) | • 스플릿 브레인 관리를 위해 특수 쿼럼 디스크 또는 세 번째 쿼럼 서버가 필요함.
