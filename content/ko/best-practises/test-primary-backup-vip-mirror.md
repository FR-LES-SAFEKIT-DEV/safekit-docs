# 네트워크에서 SafeKit 미러 클러스터의 가상 IP 주소를 테스트합니다.

이 가이드에서는 SafeKit 미러 클러스터(미러 모듈)의 가상 IP 주소(VIP)가 네트워크에서 올바르게 작동하는지 확인하는 방법을 설명합니다. VIP는 기본 서버에서 관리되며, 장애 조치 후 새 기본 서버로 재라우팅됩니다.

## 1. 핵심 원칙

**필수 조건:** 미러 클러스터의 두 노드 모두 동일한 레이어 2 IP 서브넷(LAN 또는 원격 사이트 간에 확장된 VLAN)에 있어야 합니다.

- VIP는 **기본 서버** (PRIM 또는 ALONE 상태)에서만 활성화됩니다. 모듈이 노드에서 기본으로 시작될 때( `where="one_side_alias"` 구성) 해당 주소의 네트워크 카드에서 물리적 IP 주소의 별칭으로 설정됩니다.
- 따라서 기본 서버의 MAC 주소는 ARP 테이블(동일 서브넷 내의 라우터, 게이트웨이, 클라이언트)에서 VIP와 연결된 주소입니다. VIP로 향하는 모든 트래픽은 기본 서버로 전송됩니다.
- 장애 조치(기본 서버의 중지 또는 장애)가 발생하면 VIP는 이전 기본 서버에서 제거되고 새 기본 서버에 별칭으로 설정됩니다. 그런 다음 두 가지 메커니즘을 통해 네트워크는 VIP를 새 기본 서버의 MAC 주소와 연결할 수 있습니다.
  - VIP를 네트워크 카드에 별칭으로 추가할 때 운영 체제에서 전송하는 네트워크 메시지;
  - `<vip>` 섹션에 `arpreroute="on"` 속성이 구성된 경우 SafeKit에서 전송하는 **GARP** (gratuitous ARP)입니다.

따라서 테스트해야 할 사항은 다음과 같습니다.

1. 해당 VIP는 기본 서버에 저장되어 있으며 클라이언트에서 접근할 수 있습니다.
2. VIP와 연결된 MAC 주소가 기본 서버가 변경될 때 네트워크(라우터, 게이트웨이, 가상화)의 새 기본 서버로 재라우팅된다는 것입니다.

## 2. 필수 조건: VIP 구성

1. 미러 모듈의 `userconfig.xml` 파일에서 `<vip>` 섹션에 VIP를 구성합니다. `arpreroute="on"` 속성은 페일오버 후 새 기본 서버가 GARP를 전송하도록 합니다.

   ```xml
   <vip>
     <interface_list>
       <interface arpreroute="on">
         <real_interface>
           <virtual_addr addr="<VIP>" where="one_side_alias"/>
         </real_interface>
       </interface>
     </interface_list>
   </vip>
   ```

2. 두 노드 모두에 설정을 적용하십시오.
3. 모듈을 시작하세요. 노드 하나는 **PRIM(준비됨)** 상태이고 다른 하나는 **SECOND(준비됨)** 상태여야 합니다.

## 3. 테스트 1 – VIP는 기본 서버에서 보유

**단계**

1. 기본 서버에서 `ipconfig` (Windows) 또는 `ip addr show` (Linux) 명령을 실행합니다.
   → **예상 결과:** VIP가 물리적 IP 주소의 네트워크 카드에 별칭으로 표시됩니다.
2. 보조 서버에서 동일한 명령을 실행합니다.
   → **예상 결과:** VIP가 나타나지 않습니다.
3. **클러스터 외부의** 클라이언트 워크스테이션에서 물리적 IP 주소와 VIP 모두에 `ping` .
   → **예상 결과:** 방화벽에 의해 차단되지 않는 한 세 가지 `ping` 명령 모두 응답합니다.
4. SafeKit mosaic을 사용하여 VIP를 통한 액세스를 확인하려면 **외부** 클라이언트의 브라우저에서 `http://<VIP>:9010/safekit/mosaic.html` 에 접속한 다음 미러 **모듈 이름을** 입력하고 테스트를 실행하십시오.
   → **예상 결과:** 모자이크의 모든 셀에 **기본 서버** 이름이 단일 색상으로 표시됩니다. 즉, VIP에 대한 모든 TCP 연결은 기본 서버에서 처리됩니다.

## 4. 테스트 2 – 수동 페일오버(기본 서버 중지)

이 테스트는 기본 서버에서 모듈을 중지하여 발생하는 장애 조치 중에 VIP가 기본 서버를 따라가는지 확인합니다.

**단계**

1. SafeKit 콘솔(또는 명령줄에서 `safekit stop -m <module>` )을 사용하여 기본 노드(노드 1)에서 해당 모듈을 중지합니다.
   → **예상 결과:** 노드 1은 STOP(NotReady) 상태로, 노드 2는 ALONE(Ready) 상태로 전환됩니다. 새 기본 노드의 로그에는 `Virtual IP <VIP> set` 메시지가 나타납니다.
2. 새로운 기본 서버에서 `ipconfig` 또는 `ip addr show` 실행하십시오.
   → **예상 결과:** VIP가 이제 이 노드에서 별칭으로 표시되고 이전 기본 노드에서는 더 이상 표시되지 않습니다.
3. 클라이언트 워크스테이션에서 세 가지 `ping` 명령을 반복 실행하고 VIP에서 mosaic을 다시 실행하십시오.
   → **예상 결과:** 모든 것이 정상적으로 작동하고, 모자이크의 모든 셀에 **새 기본 요소** 의 이름이 단일 색상으로 표시됩니다.
4. 노드 1에서 모듈을 재시작하면 노드 1은 다시 동기화되어 SECOND(준비) 상태가 되고, 노드 2는 PRIM(준비) 상태가 됩니다.

## 5. 테스트 3 – `arp -a` 를 이용한 MAC 재라우팅 확인

페일오버 전에 VIP와 연결된 MAC 주소를 기록해 둔 다음, 페일오버 후에 해당 주소가 변경되었는지 확인합니다.

이 테스트는 클라이언트 워크스테이션이 클러스터와 **동일한 IP 서브넷** 에 있는 경우에만 가능합니다.

클라이언트와 클러스터 사이에 라우터가 있는 경우, 클라이언트의 ARP 테이블에는 VIP 주소가 아닌 클러스터 네트워크에 도달하는 데 사용되는 게이트웨이 주소가 포함됩니다. 이 경우, 네트워크 팀과 협력하여 라우터 또는 게이트웨이의 ARP 테이블에서 MAC 재라우팅 설정을 확인해야 합니다.

**단계**

1. 해당 모듈은 노드 1에서는 PRIM(준비 완료) 상태이고, 노드 2에서는 SECOND(준비 완료) 상태입니다.
2. 클라이언트 워크스테이션에서 물리적 IP 주소와 VIP 모두에 `ping` 다음 `arp -a` 실행합니다.
   → **예상 결과:** VIP는 **기본 장치의 물리적 IP 주소와 동일한 MAC 주소** 와 연결됩니다.
3. 기본 노드(노드 1)에서 모듈을 `stop` .
4. VIP에 다시 `ping` , 그 다음 `arp -a` 다시 실행하세요.
   → **예상 결과:** 이제 VIP는 **새 기본 장치의 물리적 IP 주소와 동일한 MAC 주소** 와 연결됩니다.

ARP 테이블을 읽기 전에 VIP에 다시 `ping` 십시오. 항목이 오래된 것으로 표시되어 `ping` 후에만 갱신될 수 있습니다.

기본 서버가 중지되기 전과 후의 예상 ARP 테이블 예시:

| 주소 | 정류장 전 MAC 주소 | 정류장 후 MAC 주소 |
|---|---|---|
| 노드 1의 물리적 IP 주소 | 노드 1의 MAC 주소 | 노드 1의 MAC 주소 |
| 노드 2의 물리적 IP 주소 | 노드 2의 MAC 주소 | 노드 2의 MAC 주소 |
| VIP | **노드 1 MAC** | **노드 2 MAC** |

## 6. 테스트 4 – Wireshark(Windows) 또는 tcpdump(Linux)를 사용한 엔드투엔드 검사

클라이언트와 양쪽 노드에서 패킷을 캡처하여 VIP에 대한 TCP 연결을 추적할 수 있습니다. Windows 시스템에서는 Wireshark를, Linux 시스템에서는 tcpdump를 사용하면 됩니다.

**패킷의 MAC(이더넷) 헤더를** 확인해야 합니다. 목적지 IP 주소는 VIP로 유지되며, 어떤 노드가 트래픽을 수신하는지 보여주는 것은 목적지 MAC 주소입니다.

**주의해야 할 사항:**

| 언제 | 어디서 | 수집하는지 | 관찰된 MAC 주소 |
|---|---|---|
| 페일오버 전 | 클라이언트 | 클라이언트 MAC 주소 → **노드 1(기본)** 의 MAC 주소 |
| 페일오버 전 | 노드 1 | VIP로 전송되는 패킷은 수신되지만, 노드 2는 아무것도 수신하지 못함 |
| 페일오버 중 | 네트워크 | VIP에 대해 노드 2에서 전송되는 MAC 재라우팅 메시지: VIP가 별칭으로 설정된 경우 OS에서 전송되는 메시지 및 SafeKit( `arpreroute="on"` )에서 전송되는 GARP 메시지 |
| 페일오버 후 | 클라이언트 | 클라이언트 MAC 주소 → **노드 2(새로운 기본 노드)** 의 MAC 주소 |

클라이언트 워크스테이션이 클러스터와 다른 서브넷에 있는 경우 노드에서 보이는 "클라이언트 MAC"은 클라이언트 워크스테이션의 MAC 주소가 아니라 두 서브넷을 연결하는 **게이트웨이** (라우터)의 MAC 주소입니다.

## 7. 어떤 워크스테이션에서 테스트를 진행해야 할까요?

동작은 클라이언트와 클러스터 간의 네트워크 경로에 따라 달라집니다. 아키텍처에 맞는 각 클라이언트 유형별로 테스트 1과 2를 실행하십시오.

| 클라이언트 위치 | 테스트에서 확인하는 내용 |
|---|---|
| 클러스터와 **동일한 서브넷** 에 있는 클라이언트 | 클라이언트의 ARP 테이블 업데이트 (테스트 3 가능) |
클라이언트가 **다른 서브넷** (라우터, 게이트웨이, 하이퍼바이저 가상 네트워크)에 있는 | | 또는 게이트웨이에서 클라이언트의 ARP 테이블 업데이트 |
| **미러 클러스터의 VM 하나를 호스팅하는 하이퍼바이저 상의** 클라이언트 VM | 내부 스위칭 및 라우팅을 처리하는 하이퍼바이저의 가상 스위치 동작 |

## 8. 예상 결과 요약

| 테스트 | 조치 | 예상 결과 |
|---|---|---|
| 1 | 기본/보조, `ipconfig` , `ping` 및 mosaic | VIP는 기본 서버에서만 별칭으로 사용 가능; 3개의 `ping` 명령은 (방화벽에 의해 차단되지 않는 한) 응답함; mosaic에는 기본 서버만 표시됨 |
| 2 | 기본 서버 중지 | 새 기본 서버에 VIP를 별칭으로 사용; `Virtual IP <VIP> set` 메시지; 모자이크에는 새 기본 서버만 표시됨 |
| 3 | 기본 서버가 중지되기 전과 후의 `arp -a` | VIP가 노드 1의 MAC 주소에서 노드 2의 MAC 주소로 이동함 |
| 4 | 페일오버 전후의 Wireshark 또는 tcpdump 캡처 | 클라이언트가 새 기본 서버의 MAC 주소로 패킷을 전송합니다 |

## 9. 문제 해결

- **VIP가 페일오버 후 더 이상 응답하지 않습니다.** 경로상의 장치(라우터, 게이트웨이, 가상 스위치)가 MAC 재라우팅 메시지를 고려하지 않아 이전 기본 VIP의 MAC 주소로 계속 트래픽을 전송하고 있습니다. 네트워크 팀에 MAC 재라우팅 메시지 처리 방식을 확인하십시오.
- **GARP 전송:** `<vip>` 섹션의 `arpreroute="on"` 속성( `arpinterval` 및 `arpelapse` 포함)은 페일오버 후 VIP에서 정기적으로 GARP를 전송합니다. 사용자 가이드 13.6.4절 " [`<vip>` 구문](https://safekit.eviden.com/ko/resources/safekit-user-guide-82/#_%3Cvip%3E_Syntax) "을 참조하십시오.
- **VIP ↔ MAC 주소 확인 진단:** 사용자 가이드 7.24절 " [VIP ↔ MAC 주소 확인 문제 해결](https://safekit.eviden.com/ko/resources/safekit-user-guide-82/#_Issue_with_VIP) " 및 7.16절 " [페일오버 후 가상 IP 문제](https://safekit.eviden.com/ko/resources/safekit-user-guide-82/#_Problem_with_the_1) "를 참조하십시오.
