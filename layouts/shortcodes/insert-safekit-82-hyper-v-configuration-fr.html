Lisez attentivement la section « 1. Prérequis » pour l’**organisation des fichiers VM1**, sinon la récupération sur le nœud secondaire peut échouer avec des données incohérentes. * Vous devrez répéter cette configuration pour toutes les machines virtuelles que vous souhaitez répliquer et redémarrer. * Le système de fichiers dans lequel les fichiers de machine virtuelle répliqués par SafeKit sont stockés doit être NTFS ; **ReFS n’est pas pris en charge**. * SafeKit prend en charge la réplication des **points de contrôle de production {{ .Get "app" }}, mais pas des points de contrôle standard**. N’utilisez pas de points de contrôle standard, sinon la récupération sur le nœud secondaire peut échouer en raison de données incohérentes. ### 1. Prérequis {#prerequisite} Pour la réplication SafeKit, tous les fichiers de la machine virtuelle VM1 (fichier de configuration, disque dur virtuel, etc.) doivent être stockés dans le même dossier, même si ce n’est pas le comportement par défaut d’Hyper-V (par exemple, D:/Repli-{{ .Get "app" }}/VM1, où VM1 est le nom de la machine virtuelle). Si tous les fichiers de VM1 ne se trouvent pas dans le même dossier, utilisez le gestionnaire {{ .Get "app" }} : * Exportez VM1 dans un dossier, par exemple dans D:/Repli-{{ .Get "app" }} * Cette exportation créera un dossier D:/Repli-{{ .Get "app" }}/VM1 contenant tous les fichiers VM1 * Supprimer VM1 de l’inventaire du gestionnaire {{ .Get "app" }} * Importez VM1, précédemment exportée, dans le gestionnaire {{ .Get "app" }} ⚠️ Prenez un instantané de votre machine virtuelle avant de commencer la procédure. ⚠️ VM1 ne doit être créée que sur un seul nœud. La seule chose à créer sur l’autre nœud est le répertoire VM1 (D:/Repli-{{ .Get "app" }}/VM1). ⚠️ Assurez-vous que le ou les noms de commutateur virtuel référencés par la machine virtuelle existent sur les deux serveurs {{ .Get "app" }} et correspondent au même réseau physique. ⚠️ Le basculement du module Hyper-V ({{ .Get "mod" }}.safe) peut échouer si les conditions préalables à la migration de la machine virtuelle ne sont pas remplies. Pour détecter les problèmes de compatibilité entre les nœuds Hyper-V (matériel, réseau, configuration), consultez 🛠️ [KB SK-0088 dans ce document](https://github.com/FR-LES-SAFEKIT-DEV/safekit-packages/releases/download/v8.2/SafeKit_8.2_Knowledge_Base.pdf). ### 2. Lancez la console SafeKit {#2-launch-the-safekit-console} * Lancez la console web dans un navigateur sur un nœud du cluster en vous connectant à `http://localhost:9010`. * Saisissez `admin` comme nom d’utilisateur et le mot de passe défini lors de l’installation. Vous pouvez également exécuter la console dans un navigateur sur un poste de travail externe au cluster. ⚠️ La configuration de SafeKit s’effectue sur les deux nœuds à partir d’un seul navigateur. ℹ️ Pour sécuriser la console web, consultez 🛠️ [11. Sécuriser le service web SafeKit](/fr/resources/safekit-user-guide-82/#https) dans le Guide de l’utilisateur. ![Démarrez la console web SafeKit pour configurer le cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/01-login-large.png) ### 3. Configurer les adresses des nœuds {#3-configure-node-addresses} * Entrez les adresses IP des nœuds, appuyez sur la `Tab key` pour vérifier la connectivité et remplissez les noms des nœuds. Si node1 ou node2 est de couleur rouge, vérifiez la connectivité du navigateur aux deux nœuds et vérifiez le pare-feu sur les deux nœuds pour [le dépannage](/fr/resources/safekit-user-guide-82/#Troubleshooting) 🛠️. * Cliquez ensuite sur `Save and apply` pour sauvegarder la configuration. * Vérifiez le message `Success` ✅ sur les deux nœuds. * Si l’ `Failure` de configuration ❌ se produit sur un nœud, ouvrez l’accordéon ▼ pour ce nœud et consultez les messages. Notez que vous pouvez utiliser l’IA SafeKit 🤖 pour obtenir de l’aide. ℹ️ Si vous le souhaitez, vous pouvez ajouter un nouveau `LAN and nodes` (premier ➕) pour créer un deuxième heartbeat et un réseau de réplication dédié. ℹ️ Si vous cliquez sur `Advanced configuration`, le fichier `cluster.xml` s’affiche. Ce fichier est automatiquement renseigné par la console et déployé sur les nœuds. ![Saisissez les nœuds du cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/02-cluster-edit.png) ### 4. Sélectionnez un module {#4-select-a-module} * Dans `New module`, cliquez sur le module `{{ .Get "mod" }}.safe`. ℹ️ Dans la bannière bleue en haut, le nœud 🛜 `node1` représente le nœud de connexion de la console. Ce nœud relaie les requêtes vers le `node2` si nécessaire. ℹ️ La console recherche `xxx.safe` dans le répertoire `Application_Modules/generic/` sur le nœud de connexion (`node1`) si vous y avez placé un module lors de l’installation. ![Choisissez le module pour {{ .Get "app" }}](/wp-content/uploads/2024/03/04-module-new.png) ### 5. Configurer le module {#5-configure-the-module} * Choisissez le démarrage `Automatic` du module au démarrage sans délai. * Normalement, vous disposez d’un seul réseau `Heartbeat` sur lequel la réplication est effectuée. Cependant, vous pouvez définir un réseau privé si nécessaire (en ajoutant un LAN à l’étape 3). * Saisissez dans `VM_PATH` le chemin d’accès racine du répertoire répliqué (D:/Repli-{{ .Get "app" }}). * Saisissez `VM_NAME`, le nom de la machine virtuelle (VM1). Nous supposons que tous les fichiers VM1 se trouvent dans D:/Repli-{{ .Get "app" }}/VM1 (voir [les prérequis](#prerequisite)). Ce répertoire sera répliqué en temps réel par SafeKit. N’effectuez pas de réplication partielle, car le basculement ne fonctionnera pas. Les valeurs `NORMAL_STOP` et `FORCE_STOP` peuvent être « `stop` », « `save` » ou « `off` » : * « `stop` » arrête la machine virtuelle lorsque le module est arrêté. * « `save` » enregistre l’état actuel de la machine virtuelle (suspension) lorsque le module est arrêté. * « `off` » éteint la VM (mise hors tension) lorsque le module est arrêté. L’option « `stop` » est recommandée car elle provoque l’arrêt puis le redémarrage de la VM lorsque le module est arrêté et redémarré. Ainsi, si l’application à l’intérieur de la VM échoue, elle est redémarrée. Ce sera le cas, par exemple, lors du passage d’un rôle principal à un rôle secondaire. ℹ️ Vous n’avez pas besoin de configurer une adresse IP virtuelle. VM1 sera redémarrée sur l’ {{ .Get "app" }} secondaire avec son adresse IP physique, et cette adresse IP sera redirigée. ℹ️ Lorsque vous appliquez la configuration SafeKit, l’ `Automatic Start Action` de la machine virtuelle est définie sur `Nothing` dans {{ .Get "app" }}. Cela garantit que la machine virtuelle ne démarre pas automatiquement lorsque l’hôte Hyper-V démarre, mais qu’elle ne démarre que lorsque le module lui-même est démarré. ![Saisissez les paramètres {{ .Get "app" }}](/wp-content/uploads/2024/03/19-module-hyperv-edit-config-1.png) ### 6. Vérificateur personnalisé pour détecter les dysfonctionnements de la machine virtuelle {#vm-checker} Le vérificateur personnalisé envoie des messages de pulsation de l’hôte à la machine virtuelle à intervalles réguliers. Il incombe ensuite au service de pulsation {{ .Get "app" }} installé dans la machine virtuelle d’envoyer une réponse à chacun de ces messages de pulsation. Si le service {{ .Get "app" }} Heartbeat ne répond pas au message (VM bloquée, plantée ou ayant cessé de fonctionner), le vérificateur personnalisé exécute une action pour redémarrer la VM sur le même nœud {{ .Get "app" }} ou sur l’autre. * Cliquez sur `Checkers / Custom` (voir l’image). * Il suffit de définir un nom de votre choix dans `Resource name` (par exemple VM1). `Resource name` identifie la machine virtuelle avec un nom de ressource dans SafeKit : `custom.VM1`. * Avec `restart` en `Action`, la machine virtuelle est redémarrée sur le même nœud {{ .Get "app" }}. Après 3 redémarrages infructueux en 24 heures, le module SafeKit {{ .Get "mod" }} s’arrête sur le nœud principal et il y a un basculement de la machine virtuelle sur le nœud secondaire. * Si vous définissez `stopstart` dans `Action`, il y a un basculement direct sur l’autre nœud {{ .Get "app" }} dès que la machine virtuelle ne répond pas aux pulsations. ℹ️ Pour la maintenance, si vous souhaitez arrêter la machine virtuelle, le vérificateur personnalisé la redémarrera automatiquement. Pour éviter cela, vous pouvez [suspendre temporairement le vérificateur 🖼️](/wp-content/uploads/2024/04/safekit-disable-checkers.png). Ou vous pouvez le supprimer en supprimant la ligne de configuration dans la console. ℹ️ Il en va de même lorsque vous souhaitez restaurer un point de contrôle. {{ .Get "app" }} arrêtera la VM pour effectuer l’opération, et le vérificateur de VM peut réagir négativement en redémarrant automatiquement la VM. Pour éviter cela, [suspendez le vérificateur 🖼️](/wp-content/uploads/2024/04/safekit-disable-checkers.png) avant de procéder à l’opération. ℹ️ Par défaut, le vérificateur personnalisé accorde 50 secondes à la machine virtuelle pour démarrer avant de la considérer comme indisponible. Si votre machine virtuelle {{ .Get "app" }} nécessite plus de temps pour démarrer, vous pouvez augmenter ce délai en ajoutant -InitialGrace au vérificateur personnalisé vmcheck.ps1 dans userconfig.xml. La valeur est exprimée par incréments de 5 secondes. Par exemple, -InitialGrace 20 accorde un délai de grâce de 100 secondes : ``. ![Saisissez les paramètres du vérificateur personnalisé {{ .Get "app" }}](/wp-content/uploads/2024/04/safekit-custom-checker-hyperv.png) ### 7. Modifier les scripts (facultatif) {#7-edit-scripts-optional} * Ne modifiez pas les scripts. ### 8. Chiffrement des communications (facultatif) {#8-communication-encryption-optional} * Conservez le chiffrement des communications entre les nœuds. ![Chiffrement de la communication du module de l’ {{ .Get "app" }}](/wp-content/uploads/2024/03/07-module-encryption.png) ### 9. Enregistrer et appliquer {#9-save-and-apply} * `Save and apply` la configuration et les scripts sur les deux nœuds. ![Enregistrez et appliquez la configuration du module {{ .Get "app" }}](/wp-content/uploads/2024/03/08-module-save.png) ### 10. Vérifier la réussite de la configuration {#10-verify-successful-configuration} * Vérifiez le message `Success` ✅ sur les deux nœuds et cliquez sur `Monitor modules`. * Si l’ `Failure` de configuration ❌ se produit sur un nœud, ouvrez l’accordéon ▼ pour ce nœud et consultez les messages. Notez que vous pouvez utiliser l’IA SafeKit 🤖 pour obtenir de l’aide. ![Vérifier la réussite de la configuration du module {{ .Get "app" }}](/wp-content/uploads/2024/03/09-module-save-check.png) ### 11. Démarrer le nœud avec des données à jour {#11-start-the-node-with-up-to-date-data} * Si le nœud 1 possède le répertoire répliqué à jour pour `VM1/`, sélectionnez-le et ⋯ `Force start` ▶ `As primary`. Lorsque le nœud 2 sera démarré, toutes les données seront copiées du nœud 1 vers le nœud 2. ⚠️ Si vous faites le mauvais choix, vous risquez de synchroniser des données obsolètes sur les deux nœuds. ⚠️ Il est également supposé que `VM1` est arrêtée sur le nœud 1 afin que SafeKit installe les mécanismes de réplication, puis démarre `VM1` dans le script `start_prim`. ⚠️ Utilisez `Start` pour les démarrages suivants : SafeKit conserve le serveur le plus à jour. Démarrer `As primary` est un démarrage spécial la première fois ou lors d’opérations exceptionnelles. ![Démarrez le nœud {{ .Get "app" }} en tant que nœud principal avec les données à jour](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) ### 12. Attendez la transition vers ALONE (vert) {#12-wait-for-the-transition-to-alone-green} * Le nœud 1 doit atteindre l’état ALONE (vert), ce qui signifie que le script `start_prim` a été exécuté sur le nœud 1. ⚠️ Si ALONE (vert) n’est pas atteint ou si VM1 n’est pas démarré, analysez la raison avec le [journal du module 🖼️](/wp-content/uploads/2024/03/24-module-log-script.png) du nœud 1. * Cliquez sur l’icône **de journal** 🔍 du `node1` pour ouvrir le journal du module et recherchez les messages d’erreur, tels qu’un vérificateur détectant une erreur et arrêtant le module. * Cliquez sur `start_prim` dans le journal : les messages de sortie du script sont affichés à droite et les erreurs peuvent être détectées, comme le démarrage incorrect VM1. * Utilisez l’IA SafeKit 🤖 pour obtenir de l’aide concernant les messages du journal. ⚠️ Si le cluster est dans l’état `WAIT (red) not uptodate, STOP (red) not uptodate`, arrêtez le nœud WAIT et [forcez son démarrage en tant que primaire 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png). ![Le premier nœud {{ .Get "app" }} démarre en tant que primaire et devient ALONE](/wp-content/uploads/2024/03/12-monitoring-alone-stop.png) ### 13. Démarrer le nœud 2 {#13-start-node-2} * ⋯ `Start` le nœud 2 avec son menu contextuel. * Attendez le SECOND état (vert). ℹ️ Le nœud 2 reste dans le SECOND état (orange) pendant la resynchronisation des répertoires répliqués (copie du nœud 1 vers le nœud 2). * Cette opération peut prendre un certain temps en fonction de la taille des fichiers à resynchroniser dans les répertoires répliqués et de la bande passante du réseau. * Pour voir la progression de la copie, consultez le [journal du module 🖼️](/wp-content/uploads/2024/03/27-module-log-reintegration.png) et les [ressources de réplication 🖼️](/wp-content/uploads/2024/03/26-replication-resources-reintegration.png) du nœud 2. Utilisez l’IA SafeKit 🤖 pour obtenir de l’aide concernant les messages du journal. ℹ️ Lorsque vous utilisez des disques de différenciation {{ .Get "app" }}, seul le disque de différenciation doit être resynchronisé après la synchronisation initiale, ce qui permet de gagner du temps pour les disques durs virtuels volumineux. ![Démarrez le nœud 2 {{ .Get "app" }}](/wp-content/uploads/2024/03/13-monitoring-alone-stop-start.png) ### 14. Vérifiez que le cluster est opérationnel {#14-verify-that-the-cluster-is-operational} * Vérifiez que le cluster est vert/vert, que `VM1` s’exécute sur le nœud PRIM et qu’elle ne s’exécute pas sur le nœud SECOND. Dans cet état, seules les modifications apportées aux fichiers sont répliquées en temps réel. ![Le nœud {{ .Get "app" }} 2 est SECOND (vert)](/wp-content/uploads/2024/03/14-monitoring-prim-second.png) ### 15. Tests {#15-testing} * Arrêtez le nœud PRIM en faisant défiler son menu contextuel vers le bas et en cliquant sur `Stop`. * Vérifiez qu’il y a un basculement sur le SECOND nœud qui devrait devenir ALONE (vert). * Vérifiez auprès du gestionnaire {{ .Get "app" }} que `VM1` s’exécute sur le nœud 2. ⚠️ Si ALONE (vert) n’est pas atteint sur node2 ou si VM1 n’est pas démarrée, analysez la raison avec le [journal du module 🖼️](/wp-content/uploads/2024/03/38-module-log-script-second.png) du nœud 2. * Cliquez sur l’icône **de journal** 🔍 du `node2` pour ouvrir le journal du module et recherchez les messages d’erreur, tels qu’un vérificateur détectant une erreur et arrêtant le module. * Cliquez sur `start_prim` dans le journal : les messages de sortie du script sont affichés à droite et les erreurs peuvent être détectées, comme le démarrage incorrect VM1. * Utilisez l’IA SafeKit 🤖 pour obtenir de l’aide concernant les messages du journal. ⚠️ Étant donné que le script `start_prim` importe la machine virtuelle sur le nœud 2, le basculement peut échouer en raison des 🛠️ [paramètres {{ .Get "app" }} (voir la KB SK-0088 dans ce document)](https://github.com/FR-LES-SAFEKIT-DEV/safekit-packages/releases/download/v8.2/SafeKit_8.2_Knowledge_Base.pdf). ⚠️ Si tout est correct, lancez une initialisation sur node1, ce qui resynchronisera les répertoires répliqués à partir node2. Si les choses tournent mal, arrêtez node2 et [forcez le nœud 1 à démarrer en tant que primaire 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png), qui redémarrera avec ses données localement saines au moment de l’arrêt. ℹ️ Notez que vous disposez d’une 🕒 **[chronologie 🖼️](/wp-content/uploads/2026/05/safekit-console-timeline.png)** qui peut être utile pour comprendre ce qui se passe dans le cluster. ![Arrêtez le module {{ .Get "app" }} sur le serveur PRIM](/wp-content/uploads/2024/03/16-monitoring-prim-second-stop.png) ### 16. Si nécessaire, configurez un vérificateur de scission de cerveau {#16-if-necessary-configure-a-splitbrain-checker} * Consultez la [section « Quels sont les différents scénarios en cas d’isolement du réseau dans un cluster ? »](/fr/best-practises/power-outage-and-network-isolation-in-a-cluster/) pour savoir si vous devez configurer un vérificateur de scission de cerveau. * Accédez à la configuration du module et cliquez sur `Checkers / Splitbrain` (voir l’image) pour modifier les paramètres de splitbrain. * `Save and apply` la nouvelle configuration pour la redéployer sur les deux nœuds (le module doit être arrêté sur les deux nœuds pour l’enregistrer et l’appliquer). **Paramètres** : * `Resource name` identifie le témoin avec un nom de ressource : `splitbrain.witness`. Vous pouvez modifier cette valeur pour identifier le témoin. * `Witness address` est l’argument d’un ping lorsqu’un nœud passe de PRIM à ALONE ou de SECOND à ALONE. Modifiez cette valeur avec l’adresse IP du témoin (un élément robuste, généralement un routeur). * Remarque : vous pouvez définir plusieurs adresses IP séparées par des espaces. Notez que les adresses IP doivent être accessibles à partir d’un nœud, mais pas de l’autre en cas d’isolement du réseau. ![Saisissez les paramètres de la fonction de détection de cerveau divisé {{ .Get "app" }}](/wp-content/uploads/2024/04/safekit-split-brain-checker.png) ### 17. Redémarrage automatique en cas de défaillance d’un service critique dans la machine virtuelle {#17-automatic-restart-if-a-critical-service-fails-inside-the-vm} Si vous souhaitez un redémarrage automatique ou un basculement lorsqu’un service critique à l’intérieur de la machine virtuelle échoue, vous pouvez configurer les propriétés de récupération du service (voir l’image). Vous devez d’abord configurer le [vérificateur personnalisé de la machine virtuelle](#vm-checker) décrit précédemment. Ensuite, dans Microsoft Service Manager, à l’intérieur de la machine virtuelle, sélectionnez votre service critique et, dans la propriété de récupération du service, vous devez simplement configurer l’arrêt de la machine virtuelle lorsque le service critique échoue. Pour cela, dans les options de récupération de votre service critique, choisissez « **Exécuter un programme** » en cas d’échec et dans les options d’exécution du programme, définissez « **C:/Windows/System32/shutdown.exe** » et dans « Paramètres de la ligne de commande », définissez **/s /c « service fails »**. Bien sûr, vous pouvez mettre en œuvre une récupération plus subtile avec vos propres scripts. Mais sachez simplement que l’arrêt de la machine virtuelle activera le vérificateur personnalisé sur l’hôte. Le vérificateur personnalisé détectera que le signal vital {{ .Get "app" }} ne répond plus et redémarrera la machine virtuelle sur le même serveur {{ .Get "app" }} ou effectuera un basculement sur l’autre serveur {{ .Get "app" }} (selon sa configuration). Pour tester la fonctionnalité, utilisez le Gestionnaire des tâches et arrêtez le processus (Terminer la tâche) associé au service critique. Un arrêt propre du service via le Gestionnaire des services ou la commande « net stop » ne déclenche pas l’action de récupération dans le Gestionnaire des services Windows. ![Basculement des services critiques de la machine virtuelle de l’ {{ .Get "app" }} du module {{ .Get "app" }}](/wp-content/uploads/2023/11/hyperv-critical-service.png) ### 18.
