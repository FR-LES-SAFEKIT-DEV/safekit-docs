Leggere attentamente "1. Prerequisiti" per l’**organizzazione dei file VM1**. In caso contrario, il ripristino sul nodo secondario potrebbe non riuscire con dati incoerenti. * Dovrete ripetere questa configurazione per tutte le macchine virtuali che desiderate replicare e riavviare. * Il file system in cui sono archiviati i file delle macchine virtuali replicati da SafeKit deve essere NTFS; **ReFS non è supportato**. * SafeKit supporta la replica dei **checkpoint di produzione {{ .Get "app" }}, ma non dei checkpoint standard**. Non utilizzare i checkpoint standard, altrimenti il ripristino sul nodo secondario potrebbe fallire con dati incoerenti. ### 1. Prerequisiti {#prerequisite} Per la replica SafeKit, tutti i file della macchina virtuale VM1 (file di configurazione, disco rigido virtuale, ecc.) devono essere archiviati nella stessa cartella, anche se questo non è il comportamento predefinito di Hyper-V (ad esempio, D:/Repli-{{ .Get "app" }}/VM1, dove VM1 è il nome della macchina virtuale). Se tutti i file di VM1 non si trovano nella stessa cartella, utilizzare Gestione {{ .Get "app" }}: * Esportare VM1 in una cartella, ad esempio in D:/Repli-{{ .Get "app" }} * Questa esportazione creerà una cartella D:/Repli-{{ .Get "app" }}/VM1 contenente tutti i file VM1 * Rimuovere VM1 dall’inventario di {{ .Get "app" }} Manager * Importa VM1, precedentemente esportata, in {{ .Get "app" }} Manager ⚠️ Scatta un’istantanea della tua VM prima di iniziare la procedura. ⚠️ VM1 deve essere creata solo su un singolo nodo. L’unica cosa da creare sull’altro nodo è la directory VM1 (D:/Repli-{{ .Get "app" }}/VM1). ⚠️ Assicurarsi che il nome (o i nomi) dello switch virtuale a cui fa riferimento la macchina virtuale esista su entrambi i server {{ .Get "app" }} e corrisponda alla stessa rete fisica. ⚠️ Il failover del modulo Hyper-V ({{ .Get "mod" }}.safe) potrebbe non riuscire se i prerequisiti per la migrazione della VM non sono soddisfatti. Per rilevare problemi di compatibilità tra i nodi Hyper-V (hardware, rete, configurazione), consultare il documento 🛠️ [KB SK-0088 in questo documento](https://github.com/FR-LES-SAFEKIT-DEV/safekit-packages/releases/download/v8.2/SafeKit_8.2_Knowledge_Base.pdf). ### 2. Avviare la console SafeKit {#2-launch-the-safekit-console} * Avviare la console web in un browser su un nodo del cluster collegandosi a `http://localhost:9010`. * Inserire `admin` come nome utente e la password definita durante l’installazione. È inoltre possibile eseguire la console in un browser su una workstation esterna al cluster. ⚠️ La configurazione di SafeKit viene eseguita su entrambi i nodi da un unico browser. ℹ️ Per proteggere la console web, consultare 🛠️ [11. Protezione del servizio web SafeKit](/it/resources/safekit-user-guide-82/#https) nella Guida per l’utente. ![Avviare la console web SafeKit per configurare il cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/01-login-large.png) ### 3. Configurare gli indirizzi dei nodi {#3-configure-node-addresses} * Inserisci gli indirizzi IP dei nodi, premi il `Tab key` per verificare la connettività e compila i nomi dei nodi. Se node1 o node2 sono di colore rosso, controlla la connettività del browser con entrambi i nodi e controlla il firewall su entrambi i nodi per la 🛠️ [risoluzione dei problemi](/it/resources/safekit-user-guide-82/#Troubleshooting). * Quindi, fare clic su `Save and apply` per salvare la configurazione. * Controllare il messaggio `Success` ✅ su entrambi i nodi. * Se si verifica un `Failure` di configurazione ❌ su un nodo, aprire il ▼ fisco di quel nodo e rivedere i messaggi. Si noti che è possibile utilizzare SafeKit AI 🤖 per assistenza. ℹ️ Se lo desideri, puoi aggiungere una nuova `LAN and nodes` (prima ➕) per creare un secondo heartbeat e una rete di replica dedicata. ℹ️ Se si fa clic su `Advanced configuration`, viene visualizzato il file `cluster.xml`. Questo file viene popolato automaticamente dalla console e distribuito sui nodi. ![Inserisci i nodi del cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/02-cluster-edit.png) ### 4. Seleziona un modulo {#4-select-a-module} * Nel `New module`, fare clic sul modulo `{{ .Get "mod" }}.safe`. ℹ️ Nel banner blu in alto, 🛜 `node1` rappresenta il nodo di connessione della console. Questo nodo inoltra le richieste a `node2` quando necessario. ℹ️ La console cerca `xxx.safe` nella directory `Application_Modules/generic/` sul nodo di connessione (`node1`) se hai inserito un modulo lì durante l’installazione. ![Scegli il modulo per {{ .Get "app" }}](/wp-content/uploads/2024/03/04-module-new.png) ### 5. Configurare il modulo {#5-configure-the-module} * Scegliere l’avvio `Automatic` del modulo all’avvio senza ritardi. * Normalmente, si dispone di una singola rete `Heartbeat` su cui viene eseguita la replica. Tuttavia, è possibile definire una rete privata, se necessario (aggiungendo una LAN al passaggio 3). * In `VM_PATH`, inserire il percorso radice della directory replicata (D:/Repli-{{ .Get "app" }}). * In `VM_NAME`, inserire il nome della macchina virtuale (VM1). Si presuppone che tutti i file VM1 si trovino in D:/Repli-{{ .Get "app" }}/VM1 (vedere [i prerequisiti](#prerequisite)). Questa directory verrà replicata in tempo reale da SafeKit. Non eseguire la replica parziale, poiché il failover non funzionerà. I valori `NORMAL_STOP` e `FORCE_STOP` possono essere "`stop`", "`save`" o "`off`": * "`stop`" arresta la VM quando il modulo viene arrestato. * "`save`" salva lo stato corrente della VM (sospensione) quando il modulo viene arrestato. * "`off`" spegne la VM (power off) quando il modulo viene arrestato. Si consiglia di utilizzare "`stop`" perché spegne la VM e quindi la riavvia quando il modulo viene arrestato e riavviato. Pertanto, se l’applicazione all’interno della VM si arresta in modo anomalo, viene riavviata. Questo sarà il caso, ad esempio, quando si passa da un ruolo primario a uno secondario. ℹ️ Non è necessario configurare un indirizzo IP virtuale. VM1 verrà riavviata sul server {{ .Get "app" }} secondario con il suo indirizzo IP fisico e questo indirizzo IP verrà reindirizzato. ℹ️ Quando si applica la configurazione SafeKit, l’ `Automatic Start Action` della macchina virtuale è impostata su `Nothing` in {{ .Get "app" }}. Ciò garantisce che la VM non si avvii automaticamente all’avvio dell’host Hyper-V, ma venga avviata solo quando il modulo stesso viene avviato. ![Inserisci i parametri {{ .Get "app" }}](/wp-content/uploads/2024/03/19-module-hyperv-edit-config-1.png) ### 6. Controllo personalizzato per rilevare il malfunzionamento della VM {#vm-checker} Il checker personalizzato invia messaggi heartbeat dall’host alla VM a intervalli regolari. Spetta quindi al servizio {{ .Get "app" }} heartbeat installato nella VM inviare una risposta a ciascuno di questi messaggi heartbeat. Se il servizio {{ .Get "app" }} heartbeat non risponde al messaggio (VM bloccata, arrestata in modo anomalo o ha cessato di funzionare), il checker personalizzato esegue un’azione per riavviare la VM sullo stesso nodo {{ .Get "app" }} o sull’altro. * Fare clic su `Checkers / Custom` (vedere l’immagine). * Impostare un nome a scelta in `Resource name` (ad esempio VM1). `Resource name` identifica la macchina virtuale con un nome di risorsa in SafeKit: `custom.VM1`. * Con `restart` in `Action`, la VM viene riavviata sullo stesso nodo {{ .Get "app" }}. Dopo 3 riavvii non riusciti in 24 ore, il modulo SafeKit {{ .Get "mod" }} si arresta sul nodo primario e si verifica un failover della VM sul nodo secondario. * Se si imposta `stopstart` in `Action`, si verifica un failover diretto sull’altro nodo {{ .Get "app" }} non appena la VM non risponde agli heartbeat. ℹ️ Per la manutenzione, se si desidera arrestare la macchina virtuale, il checker personalizzato la riavvierà automaticamente. Per evitare ciò, è possibile [sospendere temporaneamente il checker 🖼️](/wp-content/uploads/2024/04/safekit-disable-checkers.png). Oppure è possibile rimuoverlo eliminando la riga di configurazione nella console. ℹ️ Lo stesso vale quando si desidera ripristinare un checkpoint. {{ .Get "app" }} interromperà la VM per eseguire l’operazione e il checker della VM potrebbe reagire negativamente riavviando automaticamente la VM. Per evitare ciò, [sospendi il checker 🖼️](/wp-content/uploads/2024/04/safekit-disable-checkers.png) prima di procedere con l’operazione. ℹ️ Per impostazione predefinita, il controllo personalizzato concede 50 secondi all’avvio della VM prima di considerarla non disponibile. Se la VM {{ .Get "app" }} richiede più tempo per l’avvio, è possibile aumentare questo ritardo aggiungendo -InitialGrace al controllo personalizzato vmcheck.ps1 in userconfig.xml. Il valore è espresso in incrementi di 5 secondi. Ad esempio, -InitialGrace 20 concede un periodo di tolleranza di 100 secondi: ``. ![Inserisci i parametri del checker personalizzato {{ .Get "app" }}](/wp-content/uploads/2024/04/safekit-custom-checker-hyperv.png) ### 7. Modifica gli script (facoltativo) {#7-edit-scripts-optional} * Non modificare gli script. ### 8. Crittografia della comunicazione (opzionale) {#8-communication-encryption-optional} * Mantenere la crittografia della comunicazione tra i nodi. ![Crittografia della comunicazione del modulo {{ .Get "app" }}](/wp-content/uploads/2024/03/07-module-encryption.png) ### 9. Salva e applica {#9-save-and-apply} * `Save and apply` la configurazione e gli script su entrambi i nodi. ![Salva e applica la configurazione del modulo {{ .Get "app" }}](/wp-content/uploads/2024/03/08-module-save.png) ### 10. Verificare la corretta configurazione {#10-verify-successful-configuration} * Controllare il messaggio `Success` ✅ su entrambi i nodi e fare clic su `Monitor modules`. * Se si verifica un `Failure` di configurazione ❌ su un nodo, aprire il ▼ fisco di quel nodo e rivedere i messaggi. Si noti che è possibile utilizzare SafeKit AI 🤖 per assistenza. ![Verifica l’esito della configurazione del modulo {{ .Get "app" }}](/wp-content/uploads/2024/03/09-module-save-check.png) ### 11. Avviare il nodo con i dati aggiornati {#11-start-the-node-with-up-to-date-data} * Se il nodo 1 dispone della directory replicata aggiornata per `VM1/`, selezionarla e ⋯ `Force start` ▶ `As primary`. Quando il nodo 2 viene avviato, tutti i dati verranno copiati dal nodo 1 al nodo 2. ⚠️ Se si effettua la scelta sbagliata, si corre il rischio di sincronizzare dati obsoleti su entrambi i nodi. ⚠️ Si presuppone inoltre che `VM1` sia arrestata sul nodo 1 in modo che SafeKit installi i meccanismi di replica e quindi avvii `VM1` nello script `start_prim`. ⚠️ Utilizzare `Start` per gli avvii successivi: SafeKit mantiene il server più aggiornato. L’avvio `As primary` è un avvio speciale la prima volta o durante operazioni eccezionali. ![Avviare come primario il nodo {{ .Get "app" }} con i dati aggiornati](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) ### 12. Attendere la transizione a ALONE (verde) {#12-wait-for-the-transition-to-alone-green} * Il nodo 1 dovrebbe raggiungere lo stato ALONE (verde), il che significa che lo script `start_prim` è stato eseguito sul nodo 1. ⚠️ Se ALONE (verde) non viene raggiunto o se VM1 non viene avviato, analizzare il motivo con il [registro del modulo 🖼️](/wp-content/uploads/2024/03/24-module-log-script.png) del nodo 1. * Fare clic sull’icona **del log** 🔍 del `node1` per aprire il log del modulo e cercare messaggi di errore, ad esempio un checker che rileva un errore e arresta il modulo. * Fare clic su `start_prim` nel log: i messaggi di output dello script vengono visualizzati a destra ed è possibile rilevare errori, ad esempio se VM1 non si è avviata correttamente. * Usa SafeKit AI 🤖 per ricevere assistenza con i messaggi di log. ⚠️ Se il cluster è in stato `WAIT (red) not uptodate, STOP (red) not uptodate`, arrestare il nodo WAIT e [forzarne l’avvio come primario 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png). ![Il primo nodo {{ .Get "app" }} si avvia come primario e diventa ALONE](/wp-content/uploads/2024/03/12-monitoring-alone-stop.png) ### 13. Avviare il nodo 2 {#13-start-node-2} * ⋯ `Start` il nodo 2 con il suo menu contestuale. * Attendere il SECOND stato (verde). ℹ️ Il nodo 2 rimane nel SECOND stato (arancione) durante la risincronizzazione delle directory replicate (copia dal nodo 1 al nodo 2). * Questa operazione potrebbe richiedere del tempo, a seconda delle dimensioni dei file da risincronizzare nelle directory replicate e della larghezza di banda della rete. * Per visualizzare l’avanzamento della copia, consultare il [registro del modulo 🖼️](/wp-content/uploads/2024/03/27-module-log-reintegration.png) e le [risorse di replica 🖼️](/wp-content/uploads/2024/03/26-replication-resources-reintegration.png) del nodo 2. Utilizzare SafeKit AI 🤖 per assistenza con i messaggi di registro. ℹ️ Quando si utilizzano i dischi differenziali {{ .Get "app" }}, solo il disco differenziale deve essere risincronizzato dopo la sincronizzazione iniziale, risparmiando tempo per i dischi rigidi virtuali di grandi dimensioni. ![Avviare il nodo 2 {{ .Get "app" }}](/wp-content/uploads/2024/03/13-monitoring-alone-stop-start.png) ### 14. Verificare che il cluster sia operativo {#14-verify-that-the-cluster-is-operational} * Verificare che il cluster sia verde/verde con `VM1` in esecuzione sul nodo PRIM e non sul nodo SECOND. In questo stato, solo le modifiche all’interno dei file vengono replicate in tempo reale. ![Il nodo {{ .Get "app" }} 2 è SECOND (verde)](/wp-content/uploads/2024/03/14-monitoring-prim-second.png) ### 15. Test {#15-testing} * Arrestare il nodo PRIM scorrendo il relativo menu contestuale e facendo clic su `Stop`. * Verificare che sia presente un failover sul SECOND nodo, che dovrebbe diventare ALONE (verde). * Verificare con il gestore {{ .Get "app" }} che `VM1` sia in esecuzione sul nodo 2. ⚠️ Se ALONE (verde) non viene raggiunto sul node2 o se VM1 non è avviata, analizzare il motivo con il [log del modulo 🖼️](/wp-content/uploads/2024/03/38-module-log-script-second.png) del nodo 2. * Fare clic sull’icona **del registro** 🔍 del `node2` per aprire il registro del modulo e cercare messaggi di errore, ad esempio un checker che rileva un errore e arresta il modulo. * Fare clic su `start_prim` nel log: i messaggi di output dello script vengono visualizzati a destra ed è possibile rilevare errori, ad esempio se VM1 non si è avviata correttamente. * Usa SafeKit AI 🤖 per ricevere assistenza con i messaggi di log. ⚠️ Poiché lo script `start_prim` importa la macchina virtuale sul nodo 2, il failover potrebbe non riuscire a causa delle 🛠️ [Impostazioni {{ .Get "app" }} (vedere KB SK-0088 in questo documento)](https://github.com/FR-LES-SAFEKIT-DEV/safekit-packages/releases/download/v8.2/SafeKit_8.2_Knowledge_Base.pdf). ⚠️ Se tutto è a posto, avviare node1. Node1 risincronizzerà quindi le directory replicate da node2. Se le cose vanno male, arrestare node2 e [forzare node 1 ad avviarsi come primario 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png), che si riavvierà con i suoi dati localmente integri al momento dell’arresto. ℹ️ Tieni presente che hai una 🕒 **[cronologia 🖼️](/wp-content/uploads/2026/05/safekit-console-timeline.png)** che può essere utile per capire cosa succede nel cluster. ![Arrestare il modulo {{ .Get "app" }} sul server PRIM](/wp-content/uploads/2024/03/16-monitoring-prim-second-stop.png) ### 16. Se necessario, configurare un checker split-brain {#16-if-necessary-configure-a-splitbrain-checker} * Per sapere se è necessario configurare un checker split-brain, consultare la sezione [Quali sono i diversi scenari in caso di isolamento della rete in un cluster?](/it/best-practises/power-outage-and-network-isolation-in-a-cluster/). * Andare alla configurazione del modulo e fare clic su `Checkers / Splitbrain` (vedere immagine) per modificare i parametri di splitbrain. * `Save and apply` la nuova configurazione per ridistribuirla su entrambi i nodi (il modulo deve essere arrestato su entrambi i nodi per salvare e applicare). **Parametri** : * `Resource name` identifica il witness con un nome di risorsa: `splitbrain.witness`. È possibile modificare questo valore per identificare il witness. * `Witness address` è l’argomento per un ping quando un nodo passa da PRIM a ALONE o da SECOND a ALONE. Modificare questo valore con l’IP del witness (un elemento robusto, in genere un router). * Nota: è possibile impostare più IP separati da spazi bianchi. Assicurarsi che gli indirizzi IP siano accessibili da un nodo ma non dall’altro in caso di isolamento della rete. ![Inserisci i parametri di splitbrain {{ .Get "app" }}](/wp-content/uploads/2024/04/safekit-split-brain-checker.png) ### 17. Riavvio automatico in caso di errore di un servizio critico all’interno della VM {#17-automatic-restart-if-a-critical-service-fails-inside-the-vm} Se si desidera un riavvio automatico o un failover quando un servizio critico all’interno della VM si arresta in modo anomalo, è possibile configurare le proprietà di ripristino del servizio (vedere l’immagine). Innanzitutto, è necessario configurare il [checker personalizzato della VM](#vm-checker) precedentemente descritto. Quindi, in Microsoft Service Manager all’interno della VM, selezionare il servizio critico e, nelle proprietà di ripristino del servizio, configurare lo spegnimento della VM in caso di errore del servizio critico. Per fare ciò, nelle Opzioni di ripristino del servizio critico, scegliere "**Esegui un programma**" in caso di errori. Nelle opzioni di esecuzione del programma, impostare `C:/Windows/System32/shutdown.exe` come programma e `/s /c "service fails"` come parametri della riga di comando. Naturalmente, è possibile implementare un ripristino più graduale con i propri script. Tuttavia, si tenga presente che l’arresto della VM abiliterà il checker personalizzato nell’host. Il checker personalizzato rileverà che l’heartbeat {{ .Get "app" }} non risponde più. Riavvierà quindi la VM sullo stesso server {{ .Get "app" }} o eseguirà il failover sull’altro server {{ .Get "app" }} (a seconda della sua configurazione). Per testare la funzionalità, utilizzare Task Manager e terminare il processo (Termina attività) associato al servizio critico. Un’interruzione pulita del servizio tramite Gestione servizi o il comando "net stop" non attiva l’azione di ripristino all’interno di Gestione servizi Windows. ![Failover della VM {{ .Get "app" }} in caso di errore di un servizio critico](/wp-content/uploads/2023/11/hyperv-critical-service.png) ### 18.
