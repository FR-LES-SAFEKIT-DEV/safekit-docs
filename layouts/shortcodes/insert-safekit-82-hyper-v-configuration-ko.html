녹색/녹색이고 `VM1`이 PRIM 노드에서 실행 중이며 SECOND 노드에서는 실행 중이 아닌지 확인합니다. 이 상태에서는 파일 내부의 변경 사항만 실시간으로 복제됩니다. ![{{ .Get "app" }} 노드 2는 SECOND (녹색)입니다](/wp-content/uploads/2024/03/14-monitoring-prim-second.png) ### 15. 테스트 {#15-testing} * PRIM 노드의 상황별 메뉴를 아래로 스크롤하여 `Stop` 클릭하여 노드를 중지합니다. * SECOND 노드에 장애 조치가 발생하여 ALONE 작동하는지(녹색) 확인합니다. * {{ .Get "app" }} 관리자에게 `VM1` 노드 2에서 실행 중인지 확인하세요. ⚠️ node2에서 ALONE (녹색)에 도달하지 못했거나 VM1 시작되지 않은 경우 노드 2의 [모듈 로그 🖼️](/wp-content/uploads/2024/03/38-module-log-script-second.png) 통해 원인을 분석하십시오. * `node2`의 🔍 **로그** 아이콘을 클릭하여 모듈 로그를 열고, 검사기가 오류를 감지하여 모듈을 중지시키는 등의 오류 메시지를 찾으십시오. * 로그에서 `start_prim`을 클릭하면 스크립트의 출력 메시지가 오른쪽에 표시되며, 예를 들어 VM1이 제대로 시작되지 않은 경우 오류를 감지할 수 있습니다. * 로그 메시지 관련 지원은 SafeKit AI 🤖 이용하세요. ⚠️ `start_prim` 스크립트가 노드 2에서 가상 머신을 가져오므로 🛠️ [{{ .Get "app" }} 설정으로 인해 장애 조치가 실패할 수 있습니다(이 문서의 KB SK-0088 참조)](https://github.com/FR-LES-SAFEKIT-DEV/safekit-packages/releases/download/v8.2/SafeKit_8.2_Knowledge_Base.pdf). ⚠️ 모든 것이 정상이라면 node1을 시작하십시오. 그러면 Node1이 node2로부터 복제된 디렉터리를 다시 동기화합니다. 문제가 발생하면 node2를 중지하고 [node1이 기본 노드로 시작되도록 강제하면 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) 중지 시점에 로컬에서 정상적인 데이터로 다시 시작됩니다. ℹ️ 클러스터에서 발생하는 상황을 이해하는 데 도움이 될 수 있는 🕒 **[타임라인 🖼️ 이](/wp-content/uploads/2026/05/safekit-console-timeline.png)** 있습니다. ![PRIM 서버에서 {{ .Get "app" }} 모듈을 중지합니다](/wp-content/uploads/2024/03/16-monitoring-prim-second-stop.png) ### 16. 필요한 경우 스플릿 브레인 체커를 구성합니다 {#16-if-necessary-configure-a-splitbrain-checker} * [클러스터에서 네트워크 격리가 발생하는 경우의 다양한 시나리오](/ko/best-practises/power-outage-and-network-isolation-in-a-cluster/)를 확인하여 스플릿 브레인 체커 구성해야 하는지 알아보십시오. * 모듈 구성으로 이동하여 `Checkers / Splitbrain` 클릭(이미지 참조)하여 분할 브레인 매개변수를 편집합니다. * 새 구성을 `Save and apply` 두 노드 모두에 재배포합니다(저장 및 적용하려면 두 노드 모두에서 모듈을 중지해야 합니다). **매개변수** : * `Resource name` 리소스 이름 `splitbrain.witness`로 감시자를 식별합니다. 이 값을 변경하여 감시자를 식별할 수 있습니다. * `Witness address`는 노드가 PRIM에서 ALONE으로 또는 SECOND에서 ALONE으로 전환될 때 ping에 대한 인수입니다. 이 값을 증인의 IP(일반적으로 라우터인 견고한 요소)로 변경하십시오. * 참고: 공백으로 구분된 여러 IP를 설정할 수 있습니다. 네트워크 격리 시 한 노드에서는 IP 주소에 액세스할 수 있지만 다른 노드에서는 액세스할 수 없는지 확인하십시오. ![{{ .Get "app" }} 분할 브레인 매개변수를 입력하세요](/wp-content/uploads/2024/04/safekit-split-brain-checker.png) ### 17. VM 내에서 중요 서비스가 실패할 경우 자동 재시작 {#17-automatic-restart-if-a-critical-service-fails-inside-the-vm} VM 내의 중요한 서비스에 장애가 발생할 때 자동 다시 시작 또는 장애 조치를 원하는 경우 서비스의 복구 속성을 구성할 수 있습니다(이미지 참조). 먼저 이전에 설명한 [VM 사용자 지정 검사기](#vm-checker)를 구성해야 합니다. 그런 다음 VM 내의 Microsoft 서비스 관리자에서 중요한 서비스를 선택하고 서비스의 복구 속성에서 중요한 서비스가 실패할 때 VM을 종료하도록 구성합니다. 이렇게 하려면 중요한 서비스의 복구 옵션에서 실패 시 "**프로그램 실행**"을 선택합니다. 프로그램 실행 옵션에서 `C:/Windows/System32/shutdown.exe`를 프로그램으로 설정하고 `/s /c "service fails"`를 명령줄 매개변수로 설정합니다. 물론, 자체 스크립트를 사용하여 더욱 미묘한 복구를 구현할 수 있습니다. 하지만 VM을 종료하면 호스트에서 사용자 지정 검사기가 활성화된다는 점에 유의하십시오. 사용자 지정 검사기는 {{ .Get "app" }} 하트비트가 더 이상 응답하지 않는다는 것을 감지합니다. 그런 다음 동일한 {{ .Get "app" }} 서버에서 VM을 다시 시작하거나 다른 {{ .Get "app" }} 서버로 장애 조치합니다(구성 방식에 따라 다름). 이 기능을 테스트하려면 작업 관리자를 사용하여 중요 서비스와 관련된 프로세스를 종료(작업 끝내기)하십시오. 서비스 관리자 또는 "net stop" 명령을 통해 서비스를 정상적으로 중지하면 Windows 서비스 관리자 내에서 복구 작업이 트리거되지 않습니다. ![중요 서비스 장애 시 {{ .Get "app" }} VM 장애 조치](/wp-content/uploads/2023/11/hyperv-critical-service.png) ### 18. 지원 {#18-support} * 지원을 받으려면 각 노드에 대해 SafeKit `Snapshots` 2개(.zip 파일 2개)를 찍으십시오. ℹ️ [지원에 대한 자세한 정보는 여기에서 확인하세요](/ko/resources/safekit-support/). ![지원을 위해 {{ .Get "app" }} 스냅샷을 찍으세요](/wp-content/uploads/2024/03/30-snapshots-mirror.png)
