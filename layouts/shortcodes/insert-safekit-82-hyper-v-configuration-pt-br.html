Pré-requisitos" para o **organização de arquivos VM1** , caso contrário, a recuperação no nó secundário poderá falhar com dados inconsistentes. * Você terá que repetir esta configuração para todas as VMs que deseja replicar e reiniciar. * O sistema de arquivos onde estão armazenados os arquivos da VM replicados por SafeKit deve ser NTFS; **ReFS não é compatível**. * SafeKit suporta replicação de **Pontos de verificação de produção {{ .Get "app" }}, mas não pontos de verificação padrão**. Não use pontos de verificação padrão; caso contrário, a recuperação no nó secundário poderá falhar com dados inconsistentes. ### 1. Pré-requisitos {#prerequisite} Para replicação SafeKit, todos os arquivos da máquina virtual VM1 (arquivo de configuração, disco rígido virtual, etc.) devem ser armazenados na mesma pasta, mesmo que esse não seja o comportamento padrão do Hyper-V (por exemplo, D:/Repli-{{ .Get "app" }}/VM1, onde VM1 é o nome da máquina virtual). Se todos os arquivos de VM1 não estiverem na mesma pasta, use o gerenciador {{ .Get "app" }}: * Exporte VM1 em uma pasta, por exemplo em D:/Repli-{{ .Get "app" }} * Esta exportação criará uma pasta D:/Repli-{{ .Get "app" }}/VM1 contendo todos os arquivos VM1 * Remova VM1 do inventário do gerente {{ .Get "app" }} * Importe VM1, previamente exportado, para o gerenciador {{ .Get "app" }} ⚠️ Tire um snapshot da sua VM antes de iniciar o procedimento. ⚠️ VM1 deve ser criado apenas em um único nó. A única coisa a ser criada no outro nó é o diretório VM1 (D:/Repli-{{ .Get "app" }}/VM1). ⚠️ Certifique-se de que os nomes dos switches virtuais referenciados pela máquina virtual existam em ambos os servidores {{ .Get "app" }} e correspondam à mesma rede física. ⚠️ O failover do módulo Hyper-V ({{ .Get "mod" }}.safe) poderá falhar se os pré-requisitos de migração da VM não forem atendidos. Para detectar problemas de compatibilidade entre nós do Hyper-V (hardware, rede, configuração), consulte🛠️ [KB SK-0088 neste documento](https://github.com/FR-LES-SAFEKIT-DEV/safekit-packages/releases/download/v8.2/SafeKit_8.2_Knowledge_Base.pdf). ### 2. Inicie o console SafeKit * Inicie o console da web em um navegador em um nó do cluster conectando-se a `http://localhost:9010`. * Entrar `admin` como nome de usuário e a senha definida durante a instalação. Também é possível executar o console em um navegador em uma estação de trabalho externa ao cluster. ⚠️ A configuração do SafeKit é feita em ambos os nós a partir de um único navegador. ℹ️ Para proteger o console da web, consulte 🛠️ [11\\. Protegendo o serviço da web SafeKit](/pt-br/resources/safekit-user-guide-82/#https) no Guia do usuário. ![Inicie o console da web SafeKit para configurar o cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/01-login-large.png) ### 3. Configure endereços de nós * Insira os endereços dos nós IP, pressione o botão `Tab key` para verificar a conectividade e preencher os nomes dos nós. Se o nó1 ou o nó2 tiver a cor vermelha, verifique a conectividade do navegador com ambos os nós e verifique o firewall em ambos os nós para 🛠️ [solução de problemas](/pt-br/resources/safekit-user-guide-82/#Troubleshooting). * Em seguida, clique em `Save and apply` para salvar a configuração. * Verifique o `Success` ✅ mensagem em ambos os nós. * Se a configuração `Failure` ❌ ocorre em um nó, abra o acordeão ▼ desse nó e revise as mensagens. Observe que você pode usar SafeKit AI 🤖 para obter assistência. ℹ️ Se desejar, você pode adicionar um novo `LAN and nodes` (primeiro ➕) para criar uma segunda pulsação e uma rede de replicação dedicada. ℹ️ Se você clicar em `Advanced configuration`, o `cluster.xml` arquivo é exibido. Este arquivo é preenchido automaticamente pelo console e implementado nos nós. ![Insira os nós do cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/02-cluster-edit.png) ### 4. Selecione um módulo * Em `New module`, clique no `{{ .Get "mod" }}.safe` módulo. ℹ️ No banner azul na parte superior, 🛜 `node1` representa o nó de conexão do console. Este nó retransmite solicitações para `node2` quando necessário. ℹ️ O console procura `xxx.safe` no `Application_Modules/generic/` diretório no nó de conexão (`node1`) se você colocou um módulo lá durante a instalação. ![Escolha o módulo para {{ .Get "app" }}](/wp-content/uploads/2024/03/04-module-new.png) ### 5. Configure o módulo * Escolha um `Automatic` início do módulo na inicialização sem demora. * Normalmente, você tem um único `Heartbeat` rede na qual a replicação é feita. Porém, você pode definir uma rede privada, se necessário (adicionando um LAN na etapa 3). * Colocar `VM_PATH`, o caminho raiz do diretório replicado (D:/Repli-{{ .Get "app" }}). * Entre `VM_NAME`, o nome da máquina virtual (VM1). Assumimos que todos os arquivos VM1 estão em D:/Repli-{{ .Get "app" }}/VM1 (veja [pré-requisitos](#prerequisite)). Este diretório será replicado em tempo real pelo SafeKit. Não execute replicação parcial, pois o failover não funcionará. O `NORMAL_STOP` e `FORCE_STOP` os valores podem ser "`stop`", "`save`"ou"`off`": * "`stop`" desliga a VM quando o módulo é interrompido. * "`save`" salva o estado atual da VM (suspender) quando o módulo é interrompido. * "`off`" desliga a VM (desliga) quando o módulo é parado. "`stop`" é recomendado porque causa o desligamento e depois a reinicialização da VM quando o módulo é parado e reiniciado. Assim, se a aplicação dentro da VM falhar, ela será reiniciada. Este será o caso, por exemplo, ao alternar entre funções primárias e secundárias. ℹ️ Você não precisa configurar um endereço IP virtual. VM1 será reinicializado no {{ .Get "app" }} secundário com seu endereço físico IP, e este endereço IP será redirecionado. ℹ️ Ao aplicar a configuração SafeKit, o `Automatic Start Action` da máquina virtual está configurada para `Nothing` em {{ .Get "app" }}. Isso garante que a VM não seja iniciada automaticamente quando o host Hyper-V for iniciado, mas apenas quando o próprio módulo for iniciado. ![Insira os parâmetros {{ .Get "app" }}](/wp-content/uploads/2024/03/19-module-hyperv-edit-config-1.png) ### 6. Verificador personalizado para detectar mau funcionamento da VM {#vm-checker} O verificador personalizado envia mensagens de pulsação do host para a VM em intervalos regulares. É então tarefa do serviço de pulsação {{ .Get "app" }} instalado na VM enviar uma resposta a cada uma dessas mensagens de pulsação. Se o {{ .Get "app" }} Heartbeat Service não responder à mensagem (VM travada, travada ou deixou de funcionar), o verificador customizado executa uma ação para reiniciar a VM no mesmo nó {{ .Get "app" }} ou em outro. * Clique em `Checkers / Custom` (ver imagem). * Basta definir um nome de sua escolha em `Resource name` (exemplo VM1). `Resource name` identifica a máquina virtual com um nome de recurso em SafeKit: `custom.VM1`. * Com `restart` em `Action`, a VM será reiniciada no mesmo nó {{ .Get "app" }}. Após três reinicializações malsucedidas em 24 horas, o módulo SafeKit {{ .Get "mod" }} para no nó primário e há um failover da VM no nó secundário. * Se você definir `stopstart` em `Action`, haverá um failover direto no outro nó {{ .Get "app" }} assim que a VM não responder às pulsações. ℹ️ Para manutenção, caso queira parar a máquina virtual, o verificador personalizado irá reiniciá-la automaticamente. Para evitar isso, você pode temporariamente [suspenda o verificador 🖼️](/wp-content/uploads/2024/04/safekit-disable-checkers.png). Ou você pode removê-lo excluindo a linha de configuração no console. ℹ️ O mesmo acontece quando você deseja restaurar um ponto de verificação. {{ .Get "app" }} interromperá a VM para executar a operação e o verificador de VM poderá reagir negativamente reiniciando automaticamente a VM. Para evitar isso, [suspenda o verificador 🖼️](/wp-content/uploads/2024/04/safekit-disable-checkers.png) antes de prosseguir com a operação. ℹ️ Por padrão, o verificador personalizado permite 50 segundos para a VM inicializar antes de considerá-la indisponível. Se sua VM {{ .Get "app" }} exigir mais tempo para iniciar, você poderá aumentar esse atraso adicionando -InitialGrace ao verificador customizado vmcheck.ps1 em userconfig.xml. O valor é expresso em incrementos de 5 segundos. Por exemplo, -InitialGrace 20 permite um período de carência de 100 segundos: ``. ![Insira os parâmetros do verificador personalizado {{ .Get "app" }}](/wp-content/uploads/2024/04/safekit-custom-checker-hyperv.png) ### 7. Edite scripts (opcional) * Não edite scripts. ### 8. Criptografia de comunicação (opcional) * Mantenha a criptografia da comunicação entre os nós. ![Criptografia de comunicação do módulo {{ .Get "app" }}](/wp-content/uploads/2024/03/07-module-encryption.png) ### 9. Salve e aplique * `Save and apply` a configuração e os scripts em ambos os nós. ![Salve e aplique a configuração do módulo {{ .Get "app" }}](/wp-content/uploads/2024/03/08-module-save.png) ### 10. Verifique a configuração bem-sucedida * Verifique o `Success` ✅ mensagem em ambos os nós e clique em `Monitor modules`. * Se a configuração `Failure` ❌ ocorre em um nó, abra o acordeão ▼ desse nó e revise as mensagens. Observe que você pode usar SafeKit AI 🤖 para obter assistência. ![Verifique o sucesso da configuração do módulo {{ .Get "app" }}](/wp-content/uploads/2024/03/09-module-save-check.png) ### 11. Inicie o nó com dados atualizados * Se o nó 1 tiver o diretório replicado atualizado para `VM1/`, selecione-o e ⋯ `Force start` ▶ `As primary`. Quando o nó 2 for iniciado, todos os dados serão copiados do nó 1 para o nó 2. ⚠️ Se você fizer a escolha errada, corre o risco de sincronizar dados desatualizados em ambos os nós. ⚠️ Supõe-se também que `VM1` é interrompido no nó 1 para que SafeKit instale os mecanismos de replicação e então inicie `VM1` no `start_prim` roteiro. ⚠️ Usar `Start` para inicializações subsequentes: SafeKit mantém o servidor mais atualizado. Começando `As primary` é uma inicialização especial na primeira vez ou durante operações excepcionais. ![Inicie como primário o nó {{ .Get "app" }} com os dados atualizados](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) ### 12. Aguarde a transição para ALONE (verde) * O nó 1 deve atingir o estado ALONE (verde), o que significa que o `start_prim` script foi executado no nó 1. ⚠️ Se ALONE (verde) não for alcançado ou se VM1 não for iniciado, analise o porquê com o [registro do módulo 🖼️](/wp-content/uploads/2024/03/24-module-log-script.png) do nó 1. * Clique no 🔍 **registro** ícone de `node1` para abrir o log do módulo e procurar mensagens de erro, como um verificador detectando um erro e parando o módulo. * Clique em `start_prim` no log: mensagens de saída do script são exibidas à direita e erros podem ser detectados, como VM1 iniciado incorretamente. * Use SafeKit AI 🤖 para obter assistência com mensagens de log. ⚠️ Se o cluster estiver em `WAIT (red) not uptodate, STOP (red) not uptodate` estado, pare o nó WAIT e [forçar seu início como primário 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png). ![O primeiro nó {{ .Get "app" }} começa como primário e se torna ALONE](/wp-content/uploads/2024/03/12-monitoring-alone-stop.png) ### 13. Iniciar nó 2 * ⋯ `Start` nó 2 com seu menu contextual. * Aguarde o estado SECOND (verde). ℹ️ O nó 2 permanece no estado SECOND (laranja) enquanto ressincroniza os diretórios replicados (copia do nó 1 para o nó 2). * Isso pode demorar um pouco, dependendo do tamanho dos arquivos a serem ressincronizados nos diretórios replicados e da largura de banda da rede. * Para ver o progresso da cópia, consulte o [registro do módulo 🖼️](/wp-content/uploads/2024/03/27-module-log-reintegration.png) e o [recursos de replicação 🖼️](/wp-content/uploads/2024/03/26-replication-resources-reintegration.png) do nó 2. Use SafeKit AI 🤖 para obter assistência com mensagens de log. ℹ️ Ao usar discos diferenciais {{ .Get "app" }}, apenas o disco diferencial precisa de ressincronização após a sincronização inicial, economizando tempo para discos rígidos virtuais grandes. ![Inicie o nó {{ .Get "app" }} 2](/wp-content/uploads/2024/03/13-monitoring-alone-stop-start.png) ### 14. Verifique se o cluster está operacional * Verifique se o cluster está verde/verde com `VM1` em execução no nó PRIM e não em execução no nó SECOND. Somente as alterações dentro dos arquivos são replicadas em tempo real neste estado. ![O nó {{ .Get "app" }} 2 é SECOND (verde)](/wp-content/uploads/2024/03/14-monitoring-prim-second.png) ### 15. Teste * Pare o nó PRIM rolando para baixo em seu menu contextual e clicando `Stop`. * Verifique se há um failover no nó SECOND que deve se tornar ALONE (verde). * Verifique com o gerente {{ .Get "app" }} se `VM1` está em execução no nó 2. ⚠️ Se ALONE (verde) não for alcançado no nó2 ou se VM1 não for iniciado, analise o porquê com o [registro do módulo 🖼️](/wp-content/uploads/2024/03/38-module-log-script-second.png) do nó 2. * Clique no 🔍 **registro** ícone de `node2` para abrir o log do módulo e procurar mensagens de erro, como um verificador detectando um erro e parando o módulo. * Clique em `start_prim` no log: mensagens de saída do script são exibidas à direita e erros podem ser detectados, como VM1 iniciado incorretamente. * Use SafeKit AI 🤖 para obter assistência com mensagens de log. ⚠️ Como o `start_prim` script importa a máquina virtual no nó 2, o failover pode falhar por causa de 🛠️ [Configurações {{ .Get "app" }} (consulte KB SK-0088 neste documento)](https://github.com/FR-LES-SAFEKIT-DEV/safekit-packages/releases/download/v8.2/SafeKit_8.2_Knowledge_Base.pdf). ⚠️ Se tudo estiver bem, inicie uma inicialização no node1, que irá ressincronizar os diretórios replicados do node2. Se as coisas derem errado, pare o node2 e [forçar o início como primário 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) do nó1, que será reiniciado com seus dados localmente íntegros no momento da parada. ℹ️ Observe que você tem um 🕒 **[linha do tempo 🖼️](/wp-content/uploads/2026/05/safekit-console-timeline.png)** isso pode ser útil para entender o que acontece no cluster. ![Pare o módulo {{ .Get "app" }} no servidor PRIM](/wp-content/uploads/2024/03/16-monitoring-prim-second-stop.png) ### 16. Se necessário, configure um verificador splitbrain * Veja [Quais são os diferentes cenários em caso de isolamento de rede num cluster?](/pt-br/best-practises/power-outage-and-network-isolation-in-a-cluster/) para saber se você precisa configurar um verificador splitbrain. * Acesse a configuração do módulo e clique em `Checkers / Splitbrain` (ver imagem) para editar os parâmetros do splitbrain. * `Save and apply` a nova configuração para reimplantá-la em ambos os nós (o módulo deve ser interrompido em ambos os nós para salvar e aplicar). **Parâmetros** : * `Resource name` identifica a testemunha com um nome de recurso: `splitbrain.witness`. Você pode alterar esse valor para identificar a testemunha. * `Witness address` é o argumento para um ping quando um nó vai de PRIM para ALONE ou de SECOND para ALONE. Altere esse valor com o IP da testemunha (um elemento robusto, normalmente um roteador). * Nota: você pode definir vários IPs separados por espaços em branco. Preste atenção que os endereços IP devem ser acessíveis a partir de um nó, mas não do outro em caso de isolamento da rede. ![Insira os parâmetros do splitbrain {{ .Get "app" }}](/wp-content/uploads/2024/04/safekit-split-brain-checker.png) ### 17. Reinicialização automática se um serviço crítico falhar dentro da VM Se desejar uma reinicialização ou failover automático quando um serviço crítico dentro da VM falhar, você pode configurar as propriedades de recuperação do serviço (veja a imagem). Primeiro você deve configurar o [Verificador personalizado de VM](#vm-checker) descrito anteriormente. E então no Microsoft Service Manager dentro da VM, selecione seu serviço crítico e na propriedade de recuperação do serviço, basta configurar o desligamento da VM quando o serviço crítico falhar. Para isso, nas opções de Recuperação do seu serviço crítico, escolha "**Execute um programa** "em caso de falhas e nas opções Executar programa, defina"**C:/Windows/System32/shutdown.exe** " e em "Parâmetros de linha de comando", defina **/s /c "serviço falha"**. Claro, você pode implementar uma recuperação mais sutil com seus próprios scripts. Mas esteja ciente de que desligar a VM ativará o verificador personalizado no host. O verificador personalizado detectará que a pulsação {{ .Get "app" }} não está mais respondendo e reiniciará a VM no mesmo servidor {{ .Get "app" }} ou fará um failover no outro servidor {{ .Get "app" }} (dependendo de sua configuração). Para testar o recurso, use o Gerenciador de Tarefas e elimine o processo (Finalizar tarefa) associado ao serviço crítico. Uma parada limpa do serviço por meio do Service Manager ou do comando "net stop" não aciona a ação de recuperação dentro do Windows Service Manager. ![Failover de serviços críticos da VM {{ .Get "app" }} do módulo {{ .Get "app" }}](/wp-content/uploads/2023/11/hyperv-critical-service.png) ### 18.
