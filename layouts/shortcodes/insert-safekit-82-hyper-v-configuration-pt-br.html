Leia atentamente "1. Pré-requisitos" para a **organização dos arquivos VM1**. Caso contrário, a recuperação no nó secundário pode falhar com dados inconsistentes. * Você terá que repetir essa configuração para todas as máquinas virtuais que deseja replicar e reiniciar. * O sistema de arquivos onde os arquivos da VM replicados pelo SafeKit são armazenados deve ser NTFS; **o ReFS não é suportado**. * SafeKit suporta a replicação de **pontos de verificação de produção {{ .Get "app" }}, mas não de pontos de verificação padrão**. Não use pontos de verificação padrão, caso contrário, a recuperação no nó secundário pode falhar com dados inconsistentes. ### 1. Pré-requisitos {#prerequisite} Para a replicação SafeKit, todos os arquivos da máquina virtual VM1 (arquivo de configuração, disco rígido virtual, etc.) devem ser armazenados na mesma pasta, embora esse não seja o comportamento padrão do Hyper-V (por exemplo, D:/Repli-{{ .Get "app" }}/VM1, onde VM1 é o nome da máquina virtual). Se todos os arquivos da VM1 não estiverem na mesma pasta, use o gerenciador {{ .Get "app" }}: * Exporte VM1 para uma pasta, por exemplo, em D:/Repli-{{ .Get "app" }} * Esta exportação criará uma pasta D:/Repli-{{ .Get "app" }}/VM1 contendo todos os arquivos VM1 * Remova VM1 do inventário do gerenciador de {{ .Get "app" }} * Importe VM1, previamente exportada, para o Gerenciador {{ .Get "app" }} ⚠️ Tire um instantâneo da sua máquina virtual antes de iniciar o procedimento. ⚠️ VM1 deve ser criada apenas em um único nó. A única coisa a ser criada no outro nó é o diretório VM1 (D:/Repli-{{ .Get "app" }}/VM1). ⚠️ Certifique-se de que o(s) nome(s) do(s) switch(es) virtual(is) referenciado(s) pela máquina virtual exista(m) em ambos os servidores {{ .Get "app" }} e corresponda(m) à mesma rede física. ⚠️ A migração do módulo Hyper-V ({{ .Get "mod" }}.safe) pode falhar se os pré-requisitos de migração da VM não forem atendidos. Para detectar problemas de compatibilidade entre os nós do Hyper-V (hardware, rede, configuração), consulte 🛠️ [KB SK-0088 neste documento](https://github.com/FR-LES-SAFEKIT-DEV/safekit-packages/releases/download/v8.2/SafeKit_8.2_Knowledge_Base.pdf). ### 2. Inicie o console SafeKit {#2-launch-the-safekit-console} * Inicie o console da web em um navegador em um nó do cluster, conectando-se a `http://localhost:9010`. * Insira `admin` como nome de usuário e a senha definida durante a instalação. Você também pode executar o console em um navegador em uma estação de trabalho externa ao cluster. ⚠️ A configuração do SafeKit é feita em ambos os nós a partir de um único navegador. ℹ️ Para proteger o console da web, consulte 🛠️ [11. Protegendo o serviço da web SafeKit](/pt-br/resources/safekit-user-guide-82/#https) no Guia do Usuário. ![Inicie o console web SafeKit para configurar o cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/01-login-large.png) ### 3. Configurar endereços de nós {#3-configure-node-addresses} * Insira os endereços IP do nó, pressione a `Tab key` para verificar a conectividade e preencha os nomes dos nós. Se node1 ou node2 estiverem em vermelho, verifique a conectividade do navegador com ambos os nós e verifique o firewall em ambos os nós para 🛠️ [solucionar problemas](/pt-br/resources/safekit-user-guide-82/#Troubleshooting). * Em seguida, clique em `Save and apply` para salvar a configuração. * Verifique a mensagem `Success` ✅ em ambos os nós. * Se ocorrer uma `Failure` de configuração ❌ em um nó, abra o acordeão ▼ desse nó e revise as mensagens. Observe que você pode usar a IA SafeKit 🤖 para obter assistência. ℹ️ Se desejar, você pode adicionar uma nova `LAN and nodes` (primeiro ➕) para criar um segundo heartbeat e uma rede de replicação dedicada. ℹ️ Se você clicar em `Advanced configuration`, o arquivo `cluster.xml` será exibido. Este arquivo é preenchido automaticamente pelo console e implantado nos nós. ![Insira os nós do cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/02-cluster-edit.png) ### 4. Selecione um módulo {#4-select-a-module} * No `New module`, clique no módulo `{{ .Get "mod" }}.safe`. ℹ️ No banner azul na parte superior, 🛜 `node1` representa o nó de conexão do console. Este nó retransmite solicitações para `node2` quando necessário. ℹ️ O console procura por `xxx.safe` no diretório `Application_Modules/generic/` no nó de conexão (`node1`) se você colocou um módulo lá durante a instalação. ![Escolha o módulo para {{ .Get "app" }}](/wp-content/uploads/2024/03/04-module-new.png) ### 5. Configure o módulo {#5-configure-the-module} * Escolha o início `Automatic` do módulo na inicialização sem atraso. * Normalmente, você tem uma única rede `Heartbeat` na qual a replicação é feita. No entanto, você pode definir uma rede privada, se necessário (adicionando uma LAN na etapa 3). * Em `VM_PATH`, insira o caminho raiz do diretório replicado (D:/Repli-{{ .Get "app" }}). * Em `VM_NAME`, insira o nome da máquina virtual (VM1). Assumimos que todos os arquivos VM1 estão em D:/Repli-{{ .Get "app" }}/VM1 (consulte [os pré-requisitos](#prerequisite)). Este diretório será replicado em tempo real pelo SafeKit. Não execute a replicação parcial, pois o failover não funcionará. Os valores `NORMAL_STOP` e `FORCE_STOP` podem ser "`stop`", "`save`" ou "`off`": * "`stop`" desliga a máquina virtual quando o módulo é parado. * "`save`" salva o estado atual da VM (suspender) quando o módulo é interrompido. * "`off`" desliga a VM (desliga a energia) quando o módulo é parado. A opção "`stop`" é recomendada porque desliga a VM e, em seguida, reinicia-a quando o módulo é parado e reiniciado. Assim, se o aplicativo dentro da VM falhar, ele é reiniciado. Isso acontecerá, por exemplo, ao alternar entre as funções primária e secundária. ℹ️ Você não precisa configurar um endereço IP virtual. VM1 será reiniciada no servidor {{ .Get "app" }} secundário com seu endereço IP físico, e esse endereço IP será redirecionado. ℹ️ Ao aplicar a configuração SafeKit, a `Automatic Start Action` da máquina virtual é definida como `Nothing` no {{ .Get "app" }}. Isso garante que a VM não seja iniciada automaticamente quando o host do Hyper-V for iniciado, mas sim apenas quando o próprio módulo for iniciado. ![Insira os parâmetros {{ .Get "app" }}](/wp-content/uploads/2024/03/19-module-hyperv-edit-config-1.png) ### 6. Verificador personalizado para detetar o mau funcionamento da máquina virtual {#vm-checker} O verificador personalizado envia mensagens heartbeat do host para a VM em intervalos regulares. É então trabalho do Serviço heartbeat {{ .Get "app" }} instalado na VM enviar uma resposta a cada uma dessas mensagens heartbeat. Se o Serviço heartbeat {{ .Get "app" }} não responder à mensagem (VM travada, travada ou parou de funcionar), o verificador personalizado executará uma ação para reiniciar a VM no mesmo nó {{ .Get "app" }} ou no outro. * Clique em `Checkers / Custom` (veja a imagem). * Defina um nome de sua escolha em `Resource name` (exemplo VM1). `Resource name` identifica a máquina virtual com um nome de recurso no SafeKit: `custom.VM1`. * Com `restart` em `Action`, a VM é reiniciada no mesmo nó {{ .Get "app" }}. Após 3 reinicializações malsucedidas em 24 horas, o módulo SafeKit {{ .Get "mod" }} para no nó primário e ocorre um failover da VM no nó secundário. * Se você definir `stopstart` em `Action`, haverá um failover direto no outro nó {{ .Get "app" }} assim que a VM não responder aos heartbeats. ℹ️ Para manutenção, se você quiser parar a máquina virtual, o verificador personalizado a reiniciará automaticamente. Para evitar isso, você pode [suspender temporariamente o verificador 🖼️](/wp-content/uploads/2024/04/safekit-disable-checkers.png). Ou você pode removê-lo excluindo a linha de configuração no console. ℹ️ O mesmo acontece quando você deseja restaurar um ponto de verificação. {{ .Get "app" }} interromperá a VM para executar a operação, e o verificador da VM poderá reagir negativamente reiniciando automaticamente a VM. Para evitar isso, [suspenda o verificador 🖼️](/wp-content/uploads/2024/04/safekit-disable-checkers.png) antes de prosseguir com a operação. ℹ️ Por padrão, o verificador personalizado permite 50 segundos para a VM inicializar antes de considerá-la indisponível. Se a sua VM {{ .Get "app" }} precisar de mais tempo para iniciar, você pode aumentar esse atraso adicionando -InitialGrace ao verificador personalizado vmcheck.ps1 em userconfig.xml. O valor é expresso em incrementos de 5 segundos. Por exemplo, -InitialGrace 20 permite um período de carência de 100 segundos: ``. ![Insira os parâmetros do verificador personalizado {{ .Get "app" }}](/wp-content/uploads/2024/04/safekit-custom-checker-hyperv.png) ### 7. Inicie o nó com dados atualizados {#11-start-the-node-with-up-to-date-data} * Se o nó 1 tiver o diretório replicado atualizado para `VM1/`, selecione-o e ⋯ `Force start` ▶ `As primary`. Quando o nó 2 for iniciado, todos os dados serão copiados do nó 1 para o nó 2. ⚠️ Se você fizer a escolha errada, corre o risco de sincronizar dados desatualizados em ambos os nós. ⚠️ Também se presume que `VM1` está parada no nó 1 para que SafeKit instale os mecanismos de replicação e, em seguida, inicie `VM1` no script `start_prim`. ⚠️ Use `Start` para inícios subsequentes: SafeKit mantém o servidor mais atualizado. Iniciar `As primary` é um início especial na primeira vez ou durante operações excepcionais. ![Inicie o nó {{ .Get "app" }} como primário com os dados atualizados](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) ### 12. Aguarde a transição para ALONE (verde) {#12-wait-for-the-transition-to-alone-green} * O nó 1 deve atingir o estado ALONE (verde), o que significa que o script `start_prim` foi executado no nó 1. ⚠️ Se ALONE (verde) não for atingido ou se VM1 não for iniciado, analise o motivo com o [log do módulo 🖼️](/wp-content/uploads/2024/03/24-module-log-script.png) do nó 1. * Clique no ícone **de log** 🔍 do `node1` para abrir o log do módulo e procure mensagens de erro, como um verificador que detecta um erro e interrompe o módulo. * Clique em `start_prim` no log: as mensagens de saída do script são exibidas à direita e você pode detectar erros, por exemplo, se VM1 não foi iniciada corretamente. * Use o SafeKit AI 🤖 para obter ajuda com as mensagens de log. ⚠️ Se o cluster estiver no estado `WAIT (red) not uptodate, STOP (red) not uptodate`, pare o nó WAIT e [force o seu início como primário 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png). ![O primeiro nó {{ .Get "app" }} inicia como primário e fica ALONE](/wp-content/uploads/2024/03/12-monitoring-alone-stop.png) ### 13. Iniciar o nó 2 {#13-start-node-2} * ⋯ `Start` o nó 2 com o seu menu contextual. * Aguarde o SECOND estado (verde). ℹ️ O nó 2 permanece no SECOND estado (laranja) enquanto resincroniza os diretórios replicados (cópia do nó 1 para o nó 2). * Isso pode levar algum tempo, dependendo do tamanho dos arquivos a serem resincronizados nos diretórios replicados e da largura de banda da rede. * Para ver o progresso da cópia, consulte o [log do módulo 🖼️](/wp-content/uploads/2024/03/27-module-log-reintegration.png) e os [recursos de replicação 🖼️](/wp-content/uploads/2024/03/26-replication-resources-reintegration.png) do nó 2. Use o SafeKit AI 🤖 para obter assistência com as mensagens de log. ℹ️ Ao usar discos de diferenciação {{ .Get "app" }}, apenas o disco de diferenciação precisa ser ressincronizado após a sincronização inicial, economizando tempo para discos rígidos virtuais grandes. ![Inicie o nó 2 {{ .Get "app" }}](/wp-content/uploads/2024/03/13-monitoring-alone-stop-start.png) ### 14. Verifique se o cluster está operacional {#14-verify-that-the-cluster-is-operational} * Verifique se o cluster está verde/verde com `VM1` em execução no nó PRIM e não em execução no nó SECOND. Apenas as alterações dentro dos arquivos são replicadas em tempo real neste estado. ![O nó {{ .Get "app" }} 2 é SECOND (verde)](/wp-content/uploads/2024/03/14-monitoring-prim-second.png) ### 15. Testes {#15-testing} * Pare o nó PRIM rolando para baixo no menu contextual e clicando em `Stop`. * Verifique se há um failover no SECOND nó, que deve ficar ALONE (verde). * Verifique com o gerenciador {{ .Get "app" }} se `VM1` está em execução no nó 2. ⚠️ Se ALONE (verde) não for atingido no node2 ou se VM1 não for iniciada, analise o motivo com o [log do módulo 🖼️](/wp-content/uploads/2024/03/38-module-log-script-second.png) do nó 2. * Clique no ícone **de log** 🔍 do `node2` para abrir o log do módulo e procure mensagens de erro, como um verificador detectando um erro e interrompendo o módulo. * Clique em `start_prim` no log: as mensagens de saída do script são exibidas à direita e você pode detectar erros, por exemplo, se VM1 não foi iniciada corretamente. * Use o SafeKit AI 🤖 para obter ajuda com as mensagens de log. ⚠️ Como o script `start_prim` importa a máquina virtual no nó 2, o failover pode falhar devido às 🛠️ [configurações {{ .Get "app" }} (consulte KB SK-0088 neste documento)](https://github.com/FR-LES-SAFEKIT-DEV/safekit-packages/releases/download/v8.2/SafeKit_8.2_Knowledge_Base.pdf). ⚠️ Se tudo estiver bem, inicie node1. Node1 então, resincroniza os diretórios replicados do node2. Se as coisas derem errado, pare node2 e [force o nó 1 a iniciar como primário 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png), que será reiniciado com seus dados localmente íntegros no momento da parada. ℹ️ Observe que você tem uma **[🖼️ linha do tempo](/wp-content/uploads/2026/05/safekit-console-timeline.png)** 🕒 que pode ser útil para entender o que acontece no cluster. ![Pare o módulo {{ .Get "app" }} no servidor PRIM](/wp-content/uploads/2024/03/16-monitoring-prim-second-stop.png) ### 16. Se necessário, configure um checker split-brain {#16-if-necessary-configure-a-splitbrain-checker} * Consulte ["Quais são os diferentes cenários em caso de isolamento de rede em um cluster?"](/pt-br/best-practises/power-outage-and-network-isolation-in-a-cluster/) para saber se você precisa configurar um checker split-brain. * Acesse a configuração do módulo e clique em `Checkers / Splitbrain` (veja a imagem) para editar os parâmetros do splitbrain. * `Save and apply` a nova configuração para reimplementá-la em ambos os nós (o módulo deve ser interrompido em ambos os nós para salvar e aplicar). **Parâmetros** : * `Resource name` identifica a testemunha com um nome de recurso: `splitbrain.witness`. Altere este valor com o IP da testemunha (um elemento robusto, normalmente um roteador). * Observação: você pode definir vários IPs separados por espaços em branco. Certifique-se de que os endereços IP sejam acessíveis de um nó, mas não do outro, em caso de isolamento de rede. ![Insira os parâmetros de divisão de rede {{ .Get "app" }}](/wp-content/uploads/2024/04/safekit-split-brain-checker.png) ### 17. Reinicialização automática caso um serviço essencial falhe dentro da máquina virtual {#17-automatic-restart-if-a-critical-service-fails-inside-the-vm} Se você deseja uma reinicialização automática ou failover quando um serviço crítico dentro da VM falhar, você pode configurar as propriedades de recuperação do serviço (veja a imagem). Primeiro, você deve configurar o [verificador personalizado da VM](#vm-checker), conforme descrito anteriormente. E então, no Microsoft Service Manager, dentro da VM, selecione seu serviço crítico e, na propriedade de recuperação do serviço, configure o desligamento da VM quando o serviço crítico falhar. Para fazer isso, nas opções de recuperação do seu serviço crítico, escolha "**Executar um programa**" em caso de falhas. Nas opções de execução do programa, defina `C:/Windows/System32/shutdown.exe` como o programa e defina `/s /c "service fails"` como os parâmetros da linha de comando. É claro que você pode implementar uma recuperação mais sutil com seus próprios scripts. No entanto, esteja ciente de que o desligamento da VM ativará o verificador personalizado no host. O verificador personalizado detectará que o heartbeat {{ .Get "app" }} não responde mais. Em seguida, ele reiniciará a VM no mesmo servidor {{ .Get "app" }} ou fará failover para o outro servidor {{ .Get "app" }} (dependendo de sua configuração). Para testar o recurso, use o Gerenciador de Tarefas e encerre o processo (Finalizar tarefa) associado ao serviço crítico. Uma parada limpa do serviço por meio do Gerenciador de Serviços ou do comando "net stop" não aciona a ação de recuperação dentro do Gerenciador de Serviços Windows. ![Failover da VM {{ .Get "app" }} quando um serviço crítico falha](/wp-content/uploads/2023/11/hyperv-critical-service.png) ### 18.
