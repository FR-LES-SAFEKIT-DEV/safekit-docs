Leia atentamente "1. Pré-requisitos" para a **organização dos ficheiros VM1**, caso contrário, a recuperação no nó secundário poderá falhar com dados inconsistentes. * Terá de repetir esta configuração para todas as máquinas virtuais que deseja replicar e reiniciar. * O sistema de ficheiros onde os ficheiros da VM replicados pelo SafeKit são armazenados deve ser NTFS; **o ReFS não é suportado**. * SafeKit suporta a replicação de **pontos de verificação de produção {{ .Get "app" }}, mas não de pontos de verificação padrão**. Pré-requisitos {#prerequisite} Para a replicação SafeKit, todos os ficheiros da máquina virtual VM1 (ficheiro de configuração, disco rígido virtual, etc.) devem ser armazenados na mesma pasta, embora este não seja o comportamento predefinido do Hyper-V (por exemplo, D:/Repli-{{ .Get "app" }}/VM1, onde VM1 é o nome da máquina virtual). Se todos os ficheiros da VM1 não estiverem na mesma pasta, utilize o Gestor {{ .Get "app" }}: * Exporte VM1 para uma pasta, por exemplo, em D:/Repli-{{ .Get "app" }} * Esta exportação criará uma pasta D:/Repli-{{ .Get "app" }}/VM1 contendo todos os ficheiros VM1 * Remova VM1 do inventário do gestor de {{ .Get "app" }} * Importar VM1, previamente exportada, para o Gestor {{ .Get "app" }} ⚠️ Faça uma cópia de segurança da sua máquina virtual antes de iniciar o procedimento. ⚠️ VM1 só deve ser criada num único nó. A única coisa a criar no outro nó é o diretório VM1 (D:/Repli-{{ .Get "app" }}/VM1). ⚠️ Certifique-se de que o(s) nome(s) do(s) comutador(es) virtual(is) referenciado(s) pela máquina virtual existe(m) em ambos os servidores {{ .Get "app" }} e corresponde(m) à mesma rede física. ⚠️ A comutação de falha do módulo Hyper-V ({{ .Get "mod" }}.safe) pode falhar se os pré-requisitos de migração da VM não forem cumpridos. Para detetar problemas de compatibilidade entre nós Hyper-V (hardware, rede, configuração), consulte 🛠️ [KB SK-0088 neste documento](https://github.com/FR-LES-SAFEKIT-DEV/safekit-packages/releases/download/v8.2/SafeKit_8.2_Knowledge_Base.pdf). ### 2. Inicie a consola SafeKit {#2-launch-the-safekit-console} * Inicie a consola web num navegador, num dos nós do cluster, ligando-se a `http://localhost:9010`. * Introduza `admin` como nome de utilizador e a palavra-passe definida durante a instalação. Também é possível executar a consola num navegador, numa estação de trabalho externa ao cluster. ⚠️ A configuração do SafeKit é feita em ambos os nós a partir de um único navegador. ℹ️ Para proteger a consola web, consulte 🛠️ [11. Proteção do serviço web SafeKit](/pt-pt/resources/safekit-user-guide-82/#https) no Guia do Utilizador. ![Inicie a consola web SafeKit para configurar o cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/01-login-large.png) ### 3. Configurar os endereços dos nós {#3-configure-node-addresses} * Introduza os endereços IP dos nós, prima a `Tab key` para verificar a conectividade e preencha os nomes dos nós. Se node1 ou node2 tiverem uma cor vermelha, verifique a conectividade do navegador a ambos os nós e verifique a firewall em ambos os nós para 🛠️ [resolução de problemas](/pt-pt/resources/safekit-user-guide-82/#Troubleshooting). * Em seguida, clique em `Save and apply` para guardar a configuração. * Verifique a mensagem `Success` ✅ em ambos os nós. * Se ocorrer uma `Failure` de configuração ❌ num nó, abra o acordeão ▼ desse nó e reveja as mensagens. Tenha em atenção que pode utilizar a IA SafeKit 🤖 para obter assistência. ℹ️ Se desejar, pode adicionar uma nova `LAN and nodes` (primeiro ➕) para criar um segundo heartbeat e uma rede de replicação dedicada. ℹ️ Se clicar em `Advanced configuration`, o ficheiro `cluster.xml` é apresentado. Este ficheiro é preenchido automaticamente pela consola e implementado nos nós. ![Introduza os nós do cluster da {{ .Get "app" }}](/wp-content/uploads/2024/03/02-cluster-edit.png) ### 4. Selecione um módulo {#4-select-a-module} * No `New module`, clique no módulo `{{ .Get "mod" }}.safe`. ℹ️ No banner azul no topo, `node1` 🛜 representa o nó de ligação da consola. Este nó reencaminha os pedidos para `node2` quando necessário. ℹ️ A consola procura por `xxx.safe` no diretório `Application_Modules/generic/` no nó de ligação (`node1`) se tiver colocado um módulo lá durante a instalação. ![Escolha o módulo para {{ .Get "app" }}](/wp-content/uploads/2024/03/04-module-new.png) ### 5. Configure o módulo {#5-configure-the-module} * Escolha o arranque `Automatic` do módulo no arranque, sem demora. * Normalmente, tem uma única rede `Heartbeat` na qual a replicação é feita. No entanto, pode definir uma rede privada, se necessário (adicionando uma LAN no passo 3). * Introduza em `VM_PATH` o caminho raiz do diretório replicado (D:/Repli-{{ .Get "app" }}). * Introduza em `VM_NAME` o nome da máquina virtual (VM1). Assumimos que todos os ficheiros VM1 estão em D:/Repli-{{ .Get "app" }}/VM1 (ver [pré-requisitos](#prerequisite)). Este diretório será replicado em tempo real pelo SafeKit. Não execute a replicação parcial, pois a recuperação de falhas não funcionará. Os valores `NORMAL_STOP` e `FORCE_STOP` podem ser " `stop` ", " `save` " ou " `off` ": * " `stop` " encerra a máquina virtual quando o módulo é parado. * " `save` " guarda o estado atual da VM (suspensão) quando o módulo é parado. * " `off` " desliga a máquina virtual (desliga a energia) quando o módulo é parado. A opção " `stop` " é recomendada porque causa o encerramento e, em seguida, o reinício da VM quando o módulo é parado e reiniciado. Assim, se a aplicação dentro da VM falhar, ela é reiniciada. Este será o caso, por exemplo, ao alternar entre funções primárias e secundárias. ℹ️ Não é necessário configurar um endereço IP virtual. VM1 será reiniciada na {{ .Get "app" }} secundária com o seu endereço IP físico e este endereço IP será redirecionado. ℹ️ Ao aplicar a configuração SafeKit, a `Automatic Start Action` da máquina virtual é definida como " `Nothing` na {{ .Get "app" }}. Isto garante que a máquina virtual não inicia automaticamente quando o anfitrião Hyper-V é iniciado, mas é iniciada apenas quando o próprio módulo é iniciado. ![Introduza os parâmetros {{ .Get "app" }}](/wp-content/uploads/2024/03/19-module-hyperv-edit-config-1.png) ### 6. Verificador personalizado para detetar avarias na máquina virtual {#vm-checker} O verificador personalizado envia mensagens de pulsação do anfitrião para a máquina virtual em intervalos regulares. É então da responsabilidade do Serviço de Pulsação {{ .Get "app" }}, instalado na máquina virtual, enviar uma resposta a cada uma destas mensagens de pulsação. Se o Serviço de Pulsação {{ .Get "app" }} não responder à mensagem (VM bloqueada, bloqueada ou deixou de funcionar), o verificador personalizado executa uma ação para reiniciar a VM no mesmo nó {{ .Get "app" }} ou no outro. * Clique em `Checkers / Custom` (ver imagem). * Basta definir um nome à sua escolha em `Resource name` (exemplo VM1). `Resource name` identifica a máquina virtual com um nome de recurso no SafeKit: `custom.VM1`. * Com `restart` em `Action`, a VM é reiniciada no mesmo nó {{ .Get "app" }}. Após 3 reinícios sem sucesso em 24 horas, o módulo SafeKit {{ .Get "mod" }} para no nó primário e ocorre uma comutação de contingência da VM para o nó secundário. * Se definir `stopstart` na `Action`, haverá uma comutação automática para o outro nó {{ .Get "app" }} assim que a máquina virtual deixar de responder aos sinais de pulsações. ℹ️ Para manutenção, se quiser parar a máquina virtual, o verificador personalizado irá reiniciá-la automaticamente. Para evitar isso, pode [suspender temporariamente o verificador 🖼️](/wp-content/uploads/2024/04/safekit-disable-checkers.png). Ou pode removê-lo, eliminando a linha de configuração na consola. ℹ️ O mesmo acontece quando se pretende restaurar um ponto de verificação. {{ .Get "app" }} irá parar a VM para executar a operação, e o verificador da VM poderá reagir negativamente reiniciando automaticamente a VM. Para evitar isso, [suspenda o verificador 🖼️](/wp-content/uploads/2024/04/safekit-disable-checkers.png) antes de prosseguir com a operação. ℹ️ Por predefinição, o verificador personalizado permite 50 segundos para a VM arrancar antes de a considerar indisponível. Se a sua VM {{ .Get "app" }} precisar de mais tempo para iniciar, pode aumentar este atraso adicionando -InitialGrace ao verificador personalizado vmcheck.ps1 em userconfig.xml. O valor é expresso em incrementos de 5 segundos. Por exemplo, -InitialGrace 20 permite um período de tolerância de 100 segundos: ``. ![Introduza os parâmetros do verificador personalizado {{ .Get "app" }}](/wp-content/uploads/2024/04/safekit-custom-checker-hyperv.png) ### 7. Inicie o nó com dados atualizados {#11-start-the-node-with-up-to-date-data} * Se o nó 1 tiver o diretório replicado atualizado para `VM1/`, selecione-o e ⋯ `Force start` ▶ `As primary`. Quando o nó 2 for iniciado, todos os dados serão copiados do nó 1 para o nó 2. ⚠️ Se fizer a escolha errada, corre o risco de sincronizar dados desatualizados em ambos os nós. ⚠️ Também se assume que `VM1` está parada no nó 1 para que SafeKit instale os mecanismos de replicação e, em seguida, inicie `VM1` no script `start_prim`. ⚠️ Utilize `Start` para arranques subsequentes: SafeKit mantém o servidor mais atualizado. Iniciar `As primary` é um arranque especial na primeira vez ou durante operações excecionais. ![Inicie como primário o nó {{ .Get "app" }} com os dados atualizados](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) ### 12. Aguarde a transição para ALONE (verde) {#12-wait-for-the-transition-to-alone-green} * O nó 1 deve atingir o estado ALONE (verde), o que significa que o script `start_prim` foi executado no nó 1. ⚠️ Se ALONE (verde) não for atingido ou se VM1 não for iniciado, analise o motivo com o [registo do módulo 🖼️](/wp-content/uploads/2024/03/24-module-log-script.png) do nó 1. * Clique no ícone **de registo** 🔍 do `node1` para abrir o registo do módulo e procure mensagens de erro, como um verificador que deteta um erro e para o módulo. * Clique em `start_prim` no registo: as mensagens de saída do script são apresentadas à direita e os erros podem ser detetados, como VM1 iniciado incorretamente. * Utilize o SafeKit AI 🤖 para obter assistência com as mensagens de registo. ⚠️ Se o cluster estiver no estado `WAIT (red) not uptodate, STOP (red) not uptodate`, pare o nó WAIT e [force o seu arranque como primário 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png). ![O primeiro nó {{ .Get "app" }} inicia como primário e fica ALONE](/wp-content/uploads/2024/03/12-monitoring-alone-stop.png) ### 13. Iniciar nó 2 {#13-start-node-2} * ⋯ `Start` o nó 2 com o seu menu contextual. * Aguarde o SECOND estado (verde). ℹ️ O nó 2 permanece no SECOND estado (laranja) enquanto resincroniza os diretórios replicados (cópia do nó 1 para o nó 2). * Isto pode demorar algum tempo, dependendo do tamanho dos ficheiros a resincronizar nos diretórios replicados e da largura de banda da rede. * Para ver o progresso da cópia, consulte o [registo do módulo 🖼️](/wp-content/uploads/2024/03/27-module-log-reintegration.png) e os [recursos de replicação 🖼️](/wp-content/uploads/2024/03/26-replication-resources-reintegration.png) do nó 2. Utilize a IA SafeKit 🤖 para obter assistência com as mensagens de registo. ℹ️ Ao utilizar discos de diferenciação {{ .Get "app" }}, apenas o disco de diferenciação precisa de ser resincronizado após a sincronização inicial, o que poupa tempo em discos rígidos virtuais de grande dimensão. ![Inicie o nó 2 {{ .Get "app" }}](/wp-content/uploads/2024/03/13-monitoring-alone-stop-start.png) ### 14. Verifique se o cluster está operacional {#14-verify-that-the-cluster-is-operational} * Verifique se o cluster está verde/verde com `VM1` a ser executada no nó PRIM e não no nó SECOND. Apenas as alterações dentro dos ficheiros são replicadas em tempo real neste estado. ![O nó {{ .Get "app" }} 2 é SECOND (verde)](/wp-content/uploads/2024/03/14-monitoring-prim-second.png) ### 15. Testes {#15-testing} * Pare o nó PRIM, percorrendo o menu contextual e clicando em `Stop`. * Verifique se existe um failover no SECOND nó, que deverá ficar ALONE (verde). * Verifique com o gestor {{ .Get "app" }} se `VM1` está a ser executada no nó 2. ⚠️ Se ALONE (verde) não for atingido no node2 ou se VM1 não for iniciada, analise o motivo com o [registo do módulo 🖼️](/wp-content/uploads/2024/03/38-module-log-script-second.png) do nó 2. * Clique no ícone **de registo** 🔍 do `node2` para abrir o registo do módulo e procure mensagens de erro, como um verificador que deteta um erro e para o módulo. * Clique em `start_prim` no registo: as mensagens de saída do script são apresentadas à direita e os erros podem ser detetados, como VM1 iniciado incorretamente. * Utilize o SafeKit AI 🤖 para obter assistência com as mensagens de registo. ⚠️ Como o script `start_prim` importa a máquina virtual no nó 2, a comutação de contingência pode falhar devido às 🛠️ [definições {{ .Get "app" }} (consulte a KB SK-0088 neste documento)](https://github.com/FR-LES-SAFEKIT-DEV/safekit-packages/releases/download/v8.2/SafeKit_8.2_Knowledge_Base.pdf). ⚠️ Se tudo estiver bem, inicie o node1, que irá ressincronizar os diretórios replicados do node2. Se as coisas correrem mal, pare node2 e [force o nó 1 a iniciar como primário 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png), que será reiniciado com os seus dados localmente íntegros no momento da paragem. ℹ️ Tenha em atenção que tem uma **[linha do 🖼️](/wp-content/uploads/2026/05/safekit-console-timeline.png)** 🕒 que pode ser útil para entender o que acontece no cluster. ![Parar o módulo {{ .Get "app" }} no servidor PRIM](/wp-content/uploads/2024/03/16-monitoring-prim-second-stop.png) ### 16. Se necessário, configure um verificador de divisão de rede {#16-if-necessary-configure-a-splitbrain-checker} * Consulte ["Quais são os diferentes cenários em caso de isolamento de rede num cluster?"](/pt-pt/best-practises/power-outage-and-network-isolation-in-a-cluster/) para saber se precisa de configurar um verificador de divisão de rede. * Vá para a configuração do módulo e clique em `Checkers / Splitbrain` (ver imagem) para editar os parâmetros do splitbrain. * `Save and apply` a nova configuração para a reimplantar em ambos os nós (o módulo deve estar parado em ambos os nós para guardar e aplicar). **Parâmetros** : * `Resource name` identifica a testemunha com um nome de recurso: `splitbrain.witness`. Pode alterar este valor para identificar a testemunha. * `Witness address` é o argumento para um ping quando um nó passa de PRIM para ALONE ou de SECOND para ALONE. Altere este valor para o IP do testemunha (um elemento robusto, normalmente um router). * Nota: pode definir vários IPs separados por espaços em branco. Tenha em atenção que os endereços IP devem ser acessíveis a partir de um nó, mas não do outro, em caso de isolamento de rede. ![Introduza os parâmetros de divisão de rede {{ .Get "app" }}](/wp-content/uploads/2024/04/safekit-split-brain-checker.png) ### 17. Reinicialização automática caso um serviço crítico falhe dentro da máquina virtual {#17-automatic-restart-if-a-critical-service-fails-inside-the-vm} Se pretender um reinício automático ou uma comutação de contingência quando um serviço crítico dentro da VM falhar, pode configurar as propriedades de Recuperação do serviço (ver imagem). Primeiro, deve configurar o [verificador personalizado da máquina virtual,](#vm-checker) conforme descrito anteriormente. E depois, no Microsoft Service Manager, dentro da VM, selecione o seu serviço crítico e, na propriedade de recuperação do serviço, só tem de configurar o encerramento da VM quando o serviço crítico falhar. Para isso, nas Opções de Recuperação do seu serviço crítico, escolha " **Executar um Programa** " em caso de falhas e, nas Opções de Execução do Programa, defina " **C:/Windows/System32/shutdown.exe** " e, em "Parâmetros da linha de comando", defina **/s /c "service fails"**. Claro que pode implementar uma recuperação mais subtil com os seus próprios scripts. Mas tenha em atenção que o encerramento da VM ativará o verificador personalizado no anfitrião. O verificador personalizado detetará que o "heartbeat" {{ .Get "app" }} deixou de responder e reiniciará a VM no mesmo servidor {{ .Get "app" }} ou fará um "failover" para o outro servidor {{ .Get "app" }} (dependendo da sua configuração). Para testar a funcionalidade, utilize o Gestor de Tarefas e encerre o processo (Terminar tarefa) associado ao serviço crítico. Uma paragem limpa do serviço através do Gestor de Serviços ou do comando "net stop" não aciona a ação de recuperação dentro do Gestor de Serviços Windows. ![Falha na migração de serviços críticos da VM {{ .Get "app" }} do módulo {{ .Get "app" }}](/wp-content/uploads/2023/11/hyperv-critical-service.png) ### 18.
