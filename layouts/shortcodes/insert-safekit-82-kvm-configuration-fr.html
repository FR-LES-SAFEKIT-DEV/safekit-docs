Prérequis {#prerequisite} L’image de la machine virtuelle VM1 se trouve dans le fichier `/var/lib/libvirt/images/vm1.qcow2`. Avant de configurer SafeKit, vous devez effectuer la configuration suivante pour placer la machine virtuelle dans un répertoire spécifique à vm1 qui sera répliqué par SafeKit. Sur le nœud 1 : * Arrêter vm1 : virsh shutdown vm1 * Créez un répertoire `vm1/` : mkdir -p /var/lib/libvirt/images/vm1/ * Copiez l’image vm1 vers le nouvel emplacement : cp -a /var/lib/libvirt/images/vm1.qcow2 /var/lib/libvirt/images/vm1/ L’image vm1 d’origine peut être supprimée dès que les tests avec le nouvel emplacement sont réussis. * Modifiez le fichier de configuration vm1 : EDITOR=vi virsh edit vm1 Et modifiez la ligne : par : * Définissez l’[option de cache sur « aucune »](/wp-content/uploads/2022/07/kvm-2.png) dans le même fichier, pour l’intégrité des données en cas de panne : * Fermer le fichier de configuration vm1 * Désactiver [le démarrage automatique de vm1](/wp-content/uploads/2022/07/kvm-3.png) : virsh autostart vm1 --disable * Créez un fichier de configuration `vm1.xml` pour vm1 : virsh dumpxml vm1 > vm1.xml Sur le nœud 2 : * Copiez le fichier de configuration `vm1.xml` du nœud 1. Remarque : chaque fois que la configuration vm1 est modifiée sur le nœud 1, vous devez réappliquer la nouvelle configuration sur le nœud 2. * Créez vm1, mais ne la démarrez pas : virsh define vm1.xml * Désactiver le démarrage automatique vm1 : virsh autostart vm1 --disable * Créez le répertoire pour l’emplacement de l’image : mkdir -p /var/lib/libvirt/images/vm1/ ### 2. Lancez la console SafeKit {#2-launch-the-safekit-console} * Lancez la console web dans un navigateur sur un nœud du cluster en vous connectant à `http://localhost:9010`. * Saisissez `admin` comme nom d’utilisateur et le mot de passe défini lors de l’installation. Vous pouvez également exécuter la console dans un navigateur sur un poste de travail externe au cluster. ⚠️ La configuration de SafeKit s’effectue sur les deux nœuds à partir d’un seul navigateur. ℹ️ Pour sécuriser la console web, consultez 🛠️ [11. Sécuriser le service web SafeKit](/fr/resources/safekit-user-guide-82/#https) dans le Guide de l’utilisateur. ![Démarrez la console web SafeKit pour configurer le cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/01-login-large.png) ### 3. Configurer les adresses des nœuds {#3-configure-node-addresses} * Entrez les adresses IP des nœuds, appuyez sur la `Tab key` pour vérifier la connectivité et remplissez les noms des nœuds. Si node1 ou node2 est de couleur rouge, vérifiez la connectivité du navigateur aux deux nœuds et vérifiez le pare-feu sur les deux nœuds pour [le dépannage](/fr/resources/safekit-user-guide-82/#Troubleshooting) 🛠️. * Cliquez ensuite sur `Save and apply` pour sauvegarder la configuration. * Vérifiez le message `Success` ✅ sur les deux nœuds. * Si l’ `Failure` de configuration ❌ se produit sur un nœud, ouvrez l’accordéon ▼ pour ce nœud et consultez les messages. Notez que vous pouvez utiliser l’IA SafeKit 🤖 pour obtenir de l’aide. ℹ️ Si vous le souhaitez, vous pouvez ajouter un nouveau `LAN and nodes` (premier ➕) pour créer un deuxième heartbeat et un réseau de réplication dédié. ℹ️ Si vous cliquez sur `Advanced configuration`, le fichier `cluster.xml` s’affiche. Ce fichier est automatiquement renseigné par la console et déployé sur les nœuds. ![Saisissez les nœuds du cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/02-cluster-edit.png) ### 4. Sélectionnez un module {#4-select-a-module} * Dans `New module`, cliquez sur le module `{{ .Get "mod" }}.safe`. ℹ️ Dans la bannière bleue en haut, le nœud 🛜 `node1` représente le nœud de connexion de la console. Ce nœud relaie les requêtes vers le `node2` si nécessaire. ℹ️ La console recherche `xxx.safe` dans le répertoire `Application_Modules/generic/` sur le nœud de connexion (`node1`) si vous y avez placé un module lors de l’installation. ![Choisissez le module pour {{ .Get "app" }}](/wp-content/uploads/2024/03/04-module-new.png) ### 5. Configurer le module {#5-configure-the-module} * Choisissez le démarrage `Automatic` du module au démarrage sans délai. * Normalement, vous disposez d’un seul réseau `Heartbeat` sur lequel la réplication est effectuée. Cependant, vous pouvez définir un réseau privé si nécessaire (en ajoutant un LAN à l’étape 3). * Indiquez dans `VM_PATH` le chemin d’accès racine du répertoire répliqué (`/var/lib/libvirt/images`). * Saisissez `VM_NAME`, le nom de la machine virtuelle (`vm1`). Nous supposons que les fichiers de la VM1 se trouvent dans `/var/lib/libvirt/images/vm1/` (voir [les prérequis](#prerequisite)). Ce répertoire sera répliqué en temps réel par SafeKit. ℹ️ Vous n’avez pas besoin de configurer une adresse IP virtuelle. VM1 sera redémarrée sur l’ {{ .Get "app" }} secondaire avec son adresse IP physique, et cette adresse IP sera redirigée. ![Saisissez les paramètres {{ .Get "app" }}](/wp-content/uploads/2024/03/21-module-kvm-edit-config-1.png) ### 6. Vérificateur personnalisé pour détecter les dysfonctionnements de la machine virtuelle {#6-custom-checker-to-detect-vm-malfunction} Le vérificateur personnalisé vérifie si la MV est en cours d’exécution (avec la commande ’virsh domstate’). Si la MV n’est pas en cours d’exécution, le vérificateur personnalisé redémarre automatiquement la MV sur le même nœud {{ .Get "app" }} ou sur l’autre. * Cliquez sur `Checkers / Custom` (voir l’image). * `Resource name` identifie la machine virtuelle avec un nom de ressource dans SafeKit : `custom.VM_NAME_check`. * Avec `restart` en `Action`, la machine virtuelle est redémarrée sur le même nœud {{ .Get "app" }}. Après 3 redémarrages infructueux en 24 heures, le module SafeKit {{ .Get "mod" }} s’arrête sur le nœud principal et il y a un basculement de la machine virtuelle sur le nœud secondaire. * Si vous définissez `stopstart` dans `Action`, un basculement direct s’effectue sur l’autre nœud {{ .Get "app" }} dès que la machine virtuelle n’est plus en cours d’exécution. ℹ️ Pour la maintenance, si vous souhaitez arrêter la machine virtuelle, le vérificateur personnalisé la redémarrera automatiquement. Pour éviter cela, vous pouvez [suspendre temporairement le vérificateur 🖼️](/wp-content/uploads/2024/04/safekit-disable-checkers.png). Ou vous pouvez le supprimer en supprimant la ligne de configuration dans la console. ![Saisissez les paramètres du vérificateur personnalisé {{ .Get "app" }}](/wp-content/uploads/2024/12/custom-kvm-checker-2.png) ### 7. Modifier les scripts (facultatif) {#7-edit-scripts-optional} * Ne modifiez pas les scripts. ### 8. Chiffrement des communications (facultatif) {#8-communication-encryption-optional} * Conservez le chiffrement des communications entre les nœuds. ![Chiffrement de la communication du module de l’ {{ .Get "app" }}](/wp-content/uploads/2024/03/07-module-encryption.png) ### 9. Enregistrer et appliquer {#9-save-and-apply} * `Save and apply` la configuration et les scripts sur les deux nœuds. ![Enregistrez et appliquez la configuration du module {{ .Get "app" }}](/wp-content/uploads/2024/03/08-module-save.png) ### 10. Vérifier la réussite de la configuration {#10-verify-successful-configuration} * Vérifiez le message `Success` ✅ sur les deux nœuds et cliquez sur `Monitor modules`. * Si l’ `Failure` de configuration ❌ se produit sur un nœud, ouvrez l’accordéon ▼ pour ce nœud et consultez les messages. Notez que vous pouvez utiliser l’IA SafeKit 🤖 pour obtenir de l’aide. ![Vérifier la réussite de la configuration du module {{ .Get "app" }}](/wp-content/uploads/2024/03/09-module-save-check.png) ### 11. Démarrer le nœud avec des données à jour {#11-start-the-node-with-up-to-date-data} * Si le nœud 1 possède le répertoire répliqué à jour pour `vm1/`, sélectionnez-le et ⋯ `Force start` ▶ `As primary`. Lorsque le nœud 2 sera démarré, toutes les données seront copiées du nœud 1 vers le nœud 2. ⚠️ Si vous faites le mauvais choix, vous risquez de synchroniser des données obsolètes sur les deux nœuds. ⚠️ Il est également supposé que `VM1` est arrêtée sur le nœud 1 afin que SafeKit installe les mécanismes de réplication, puis démarre `VM1` dans le script `start_prim`. ⚠️ Utilisez `Start` pour les démarrages suivants : SafeKit conserve le serveur le plus à jour. Démarrer `As primary` est un démarrage spécial la première fois ou lors d’opérations exceptionnelles. ![Démarrez le nœud {{ .Get "app" }} en tant que nœud principal avec les données à jour](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) ### 12. Attendez la transition vers ALONE (vert) {#12-wait-for-the-transition-to-alone-green} * Le nœud 1 doit atteindre l’état ALONE (vert), ce qui signifie que le script `start_prim` a été exécuté sur le nœud 1. ⚠️ Si ALONE (vert) n’est pas atteint ou si VM1 n’est pas démarré, analysez la raison avec le [journal du module 🖼️](/wp-content/uploads/2024/03/24-module-log-script.png) du nœud 1. * Cliquez sur l’icône **de journal** 🔍 du `node1` pour ouvrir le journal du module et recherchez les messages d’erreur, tels qu’un vérificateur détectant une erreur et arrêtant le module. * Cliquez sur `start_prim` dans le journal : les messages de sortie du script sont affichés à droite et les erreurs peuvent être détectées, comme le démarrage incorrect VM1. * Utilisez l’IA SafeKit 🤖 pour obtenir de l’aide concernant les messages du journal. ⚠️ Si le cluster est dans l’état `WAIT (red) not uptodate, STOP (red) not uptodate`, arrêtez le nœud WAIT et [forcez son démarrage en tant que primaire 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png). ![Le premier nœud {{ .Get "app" }} démarre en tant que primaire et devient ALONE](/wp-content/uploads/2024/03/12-monitoring-alone-stop.png) ### 13. Démarrer le nœud 2 {#13-start-node-2} * ⋯ `Start` le nœud 2 avec son menu contextuel. * Attendez le SECOND état (vert). ℹ️ * Le nœud 2 reste dans le SECOND état (orange) pendant la resynchronisation des répertoires répliqués (copie du nœud 1 vers le nœud 2). * Cette opération peut prendre un certain temps en fonction de la taille des fichiers à resynchroniser dans les répertoires répliqués et de la bande passante du réseau. * Pour voir la progression de la copie, consultez le [journal du module 🖼️](/wp-content/uploads/2024/03/27-module-log-reintegration.png) et les [ressources de réplication 🖼️](/wp-content/uploads/2024/03/26-replication-resources-reintegration.png) du nœud 2. Utilisez l’IA SafeKit 🤖 pour obtenir de l’aide concernant les messages du journal. ![Démarrez le nœud 2 {{ .Get "app" }}](/wp-content/uploads/2024/03/13-monitoring-alone-stop-start.png) ### 14. Vérifiez que le cluster est opérationnel {#14-verify-that-the-cluster-is-operational} * Vérifiez que le cluster est vert/vert, que `VM1` s’exécute sur le nœud PRIM et qu’elle ne s’exécute pas sur le nœud SECOND. Dans cet état, seules les modifications apportées aux fichiers sont répliquées en temps réel. ![Le nœud {{ .Get "app" }} 2 est SECOND (vert)](/wp-content/uploads/2024/03/14-monitoring-prim-second.png) ### 15. Tests {#15-testing} * Arrêtez le nœud PRIM en faisant défiler son menu contextuel vers le bas et en cliquant sur `Stop`. * Vérifiez qu’il y a un basculement sur le SECOND nœud qui devrait devenir ALONE (vert). * Vérifiez avec les outils {{ .Get "app" }} que `VM1` s’exécute sur le nœud 2. ⚠️ Si ALONE (vert) n’est pas atteint sur node2 ou si VM1 n’est pas démarrée, analysez la raison avec le [journal du module 🖼️](/wp-content/uploads/2024/03/38-module-log-script-second.png) du nœud 2. * Cliquez sur l’icône **de journal** 🔍 du `node2` pour ouvrir le journal du module et recherchez les messages d’erreur, tels qu’un vérificateur détectant une erreur et arrêtant le module. * Cliquez sur `start_prim` dans le journal : les messages de sortie du script sont affichés à droite et les erreurs peuvent être détectées, comme le démarrage incorrect VM1. * Utilisez l’IA SafeKit 🤖 pour obtenir de l’aide concernant les messages du journal. ⚠️ * Si tout est correct, lancez une synchronisation sur node1, ce qui resynchronisera les répertoires répliqués à partir node2. * Si les choses tournent mal, arrêtez node2 et [forcez le nœud 1 à démarrer en tant que primaire 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png), qui redémarrera avec ses données localement saines au moment de l’arrêt. ℹ️ Notez que vous disposez d’une 🕒 **[chronologie 🖼️](/wp-content/uploads/2026/05/safekit-console-timeline.png)** qui peut être utile pour comprendre ce qui se passe dans le cluster. ![Arrêtez le module {{ .Get "app" }} sur le serveur PRIM](/wp-content/uploads/2024/03/16-monitoring-prim-second-stop.png) ### 16. Si nécessaire, configurez un vérificateur de scission de cerveau {#16-if-necessary-configure-a-splitbrain-checker} * Consultez la [section « Quels sont les différents scénarios en cas d’isolement du réseau dans un cluster ? »](/fr/best-practises/power-outage-and-network-isolation-in-a-cluster/) pour savoir si vous devez configurer un vérificateur de scission de cerveau. * Accédez à la configuration du module et cliquez sur `Checkers / Splitbrain` (voir l’image) pour modifier les paramètres de splitbrain. * `Save and apply` la nouvelle configuration pour la redéployer sur les deux nœuds (le module doit être arrêté sur les deux nœuds pour l’enregistrer et l’appliquer). **Paramètres** : * `Resource name` identifie le témoin avec un nom de ressource : `splitbrain.witness`. Vous pouvez modifier cette valeur pour identifier le témoin. * `Witness address` est l’argument d’un ping lorsqu’un nœud passe de PRIM à ALONE ou de SECOND à ALONE. Modifiez cette valeur avec l’adresse IP du témoin (un élément robuste, généralement un routeur). * Remarque : vous pouvez définir plusieurs adresses IP séparées par des espaces. Notez que les adresses IP doivent être accessibles à partir d’un nœud, mais pas de l’autre en cas d’isolement du réseau. ![Saisissez les paramètres de la fonction de détection de cerveau divisé {{ .Get "app" }}](/wp-content/uploads/2024/04/safekit-split-brain-checker.png) ### 17.
