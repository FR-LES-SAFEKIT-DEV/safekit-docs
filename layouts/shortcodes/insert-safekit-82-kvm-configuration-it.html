{{/* Shortcode: insert-safekit-82-kvm-configuration-it */}} {{/* Parameters: app, mod */}} {{/* Source: content\quick-install\safekit-quick-installation-guide-with-kvm.md */}} ⚠️ La configurazione {{ .Get "app" }} viene presentata con una macchina virtuale denominata `VM1` e contenente l'applicazione per riavviare in caso di guasto. ⚠️ Dovrai ripetere questa configurazione per tutte le VM che desideri replicare e riavviare. ### 1. Prerequisiti {#prerequisite} L'immagine della macchina virtuale VM1 è nel file `/var/lib/libvirt/images/vm1.qcow2`. Prima di configurare SafeKit, è necessario eseguire la seguente configurazione per posizionare la macchina virtuale in una directory specifica di vm1 che verrà replicata da SafeKit. Sul nodo 1: * Ferma vm1: virsh shutdown vm1 * Crea un `vm1/` rubrica: mkdir -p /var/lib/libvirt/images/vm1/ * Copia l'immagine vm1 nella nuova posizione: cp -a /var/lib/libvirt/images/vm1.qcow2 /var/lib/libvirt/images/vm1/ L'immagine vm1 originale può essere eliminata non appena i test con la nuova posizione hanno esito positivo. * Modifica il file di configurazione vm1: EDITOR=vi virsh edit vm1 E cambia la riga: da: * Imposta il [opzione cache su "nessuno"](/wp-content/uploads/2022/07/kvm-2.png) nello stesso file, per l'integrità dei dati in caso di crash: * Chiudere il file di configurazione vm1 * Disabilita [vm1 avvio automatico](/wp-content/uploads/2022/07/kvm-3.png): virsh autostart vm1 --disable * Crea un `vm1.xml` file di configurazione per vm1: virsh dumpxml vm1 > vm1.xml Sul nodo 2: * Copia il `vm1.xml` file di configurazione dal nodo 1. Nota: ogni volta che la configurazione vm1 viene modificata sul nodo 1, è necessario riapplicare la nuova configurazione sul nodo 2. * Crea vm1 ma non avviarlo: virsh define vm1.xml * Disabilitare l'avvio automatico vm1: virsh autostart vm1 --disable * Crea la directory per la posizione dell'immagine: mkdir -p /var/lib/libvirt/images/vm1/ ### 2. Avvia la console SafeKit * Avvia la console Web in un browser su un nodo del cluster connettendoti a `http://localhost:9010`. * Entra `admin` come nome utente e la password definita durante l'installazione. È inoltre possibile eseguire la console in un browser su una workstation esterna al cluster. ⚠️ La configurazione di SafeKit viene effettuata su entrambi i nodi da un unico browser. ℹ️ Per proteggere la console web, vedere 🛠️ [11\. Protezione del servizio web SafeKit](/it/resources/safekit-user-guide-82/#https) nella Guida per l'utente. ![Avviare la console Web SafeKit per configurare il cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/01-login-large.png) ### 3. Configurare gli indirizzi dei nodi * Inserire gli indirizzi del nodo IP, premere il `Tab key` per verificare la connettività e inserire i nomi dei nodi. Se node1 o node2 ha un colore rosso, controlla la connettività del browser su entrambi i nodi e controlla il firewall su entrambi i nodi per 🛠️ [risoluzione dei problemi](/it/resources/safekit-user-guide-82/#Troubleshooting). * Quindi, fare clic su `Save and apply` per salvare la configurazione. * Controlla il `Success` Messaggio ✅ su entrambi i nodi. * Se la configurazione `Failure` ❌ si verifica su un nodo, apri la fisarmonica ▼ per quel nodo ed esamina i messaggi. Tieni presente che puoi utilizzare SafeKit AI 🤖 per assistenza. ℹ️ Se vuoi puoi aggiungerne uno nuovo `LAN and nodes` (primo ➕) per creare un secondo heartbeat e una rete di replica dedicata. ℹ️ Se si fa clic su `Advanced configuration`, il `cluster.xml` viene visualizzato il file. Questo file viene popolato automaticamente dalla console e distribuito sui nodi. ![Inserisci i nodi del cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/02-cluster-edit.png) ### 4. Selezionare un modulo * Dentro `New module`, fare clic su `{{ .Get "mod" }}.safe` modulo. ℹ️ Nello striscione blu in alto, 🛜 `node1` rappresenta il nodo di connessione della console. Questo nodo inoltra le richieste a `node2` quando richiesto. ℹ️ La console cerca `xxx.safe` nel `Application_Modules/generic/` directory sul nodo di connessione (`node1`) se hai posizionato un modulo lì durante l'installazione. ![Scegli il modulo per {{ .Get "app" }}](/wp-content/uploads/2024/03/04-module-new.png) ### 5. Configurare il modulo * Scegli un `Automatic` avvio del modulo all'avvio senza ritardo. * Normalmente, ne hai uno singolo `Heartbeat` rete su cui viene effettuata la replica. Tuttavia, se necessario, è possibile definire una rete privata (aggiungendo LAN al passaggio 3). * Metti dentro `VM_PATH`, il percorso root della directory replicata (`/var/lib/libvirt/images`). * Entra `VM_NAME`, il nome della macchina virtuale (`vm1`). Supponiamo che i file VM1 siano presenti `/var/lib/libvirt/image/vm1/` (vedi [prerequisiti](#prerequisite)). Questa directory verrà replicata in tempo reale da SafeKit. ℹ️ Non è necessario configurare un indirizzo IP virtuale. VM1 verrà riavviato sul {{ .Get "app" }} secondario con il suo indirizzo fisico IP e questo indirizzo IP verrà reindirizzato. ![Immettere i parametri {{ .Get "app" }}](/wp-content/uploads/2024/03/21-module-kvm-edit-config-1.png) ### 6. Controllo personalizzato per rilevare il malfunzionamento della VM Il controllo personalizzato controlla se la VM è in esecuzione (con il comando "virsh domstate"). Se la VM non è in esecuzione, il controllo personalizzato riavvia automaticamente la VM sullo stesso nodo {{ .Get "app" }} o sull'altro. * Fare clic su `Checkers / Custom` (vedi immagine). * `Resource name` identifica la macchina virtuale con un nome di risorsa in SafeKit: `custom.VM_NAME_check`. * Con `restart` dentro `Action`, la VM viene riavviata sullo stesso nodo {{ .Get "app" }}. Dopo 3 riavvii non riusciti in 24 ore, il modulo SafeKit {{ .Get "mod" }} si arresta sul nodo primario e si verifica un failover della VM sul nodo secondario. * Se imposti `stopstart` dentro `Action`, si verifica un failover diretto sull'altro nodo {{ .Get "app" }} non appena la VM non è in esecuzione. ℹ️ Per manutenzione, se desideri arrestare la macchina virtuale, il controllo personalizzato la riavvierà automaticamente. Per evitarlo, puoi temporaneamente [sospendere il controllore 🖼️](/wp-content/uploads/2024/04/safekit-disable-checkers.png). Oppure puoi rimuoverlo eliminando la riga di configurazione nella console. ![Inserisci i parametri del controllo personalizzato {{ .Get "app" }}](/wp-content/uploads/2024/12/custom-kvm-checker-2.png) ### 7. Modifica script (facoltativo) * Non modificare gli script. ### 8. Crittografia della comunicazione (opzionale) * Mantieni la crittografia della comunicazione tra i nodi. ![Crittografia della comunicazione del modulo {{ .Get "app" }}](/wp-content/uploads/2024/03/07-module-encryption.png) ### 9. Salva e applica * `Save and apply` la configurazione e gli script su entrambi i nodi. ![Salvare e applicare la configurazione del modulo {{ .Get "app" }}](/wp-content/uploads/2024/03/08-module-save.png) ### 10. Verificare la corretta configurazione * Controlla il `Success` Messaggio ✅ su entrambi i nodi e fare clic su `Monitor modules`. * Se la configurazione `Failure` ❌ si verifica su un nodo, apri la fisarmonica ▼ per quel nodo ed esamina i messaggi. Tieni presente che puoi utilizzare SafeKit AI 🤖 per assistenza. ![Verificare la riuscita della configurazione del modulo {{ .Get "app" }}](/wp-content/uploads/2024/03/09-module-save-check.png) ### 11. Avviare il nodo con dati aggiornati * Se il nodo 1 dispone della directory replicata aggiornata per `vm1/`, selezionalo e ⋯ `Force start` ▶ `As primary`. Quando verrà avviato il nodo 2, tutti i dati verranno copiati dal nodo 1 al nodo 2. ⚠️ Se fai la scelta sbagliata, corri il rischio di sincronizzare dati obsoleti su entrambi i nodi. ⚠️ Si presume anche questo `VM1` viene arrestato sul nodo 1 in modo che SafeKit installi i meccanismi di replica e quindi si avvii `VM1` nel `start_prim` sceneggiatura. ⚠️ Utilizzo `Start` per gli avvii successivi: SafeKit mantiene il server più aggiornato. Inizio `As primary` è un avviamento speciale al primo avvio o durante operazioni eccezionali. ![Avvia come primario il nodo {{ .Get "app" }} con i dati aggiornati](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) ### 12. Attendi il passaggio a ALONE (verde) * Il nodo 1 dovrebbe raggiungere lo stato ALONE (verde), il che significa che `start_prim` lo script è stato eseguito sul nodo 1. ⚠️ Se ALONE (verde) non viene raggiunto o se VM1 non viene avviato, analizzare il motivo con il [registro del modulo 🖼️](/wp-content/uploads/2024/03/24-module-log-script.png) del nodo 1. * Fare clic su 🔍 **registro** icona di `node1` per aprire il registro del modulo e cercare messaggi di errore come un controllo che rileva un errore e arresta il modulo. * Fare clic su `start_prim` nel registro: i messaggi di output dello script vengono visualizzati sulla destra e possono essere rilevati errori come VM1 avviato in modo errato. * Utilizzare SafeKit AI 🤖 per assistenza con i messaggi di registro. ⚠️ Se il quadro strumenti è presente `WAIT (red) not uptodate, STOP (red) not uptodate` stato, arresta il nodo WAIT e [forzarne l'avvio come 🖼️ primario](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png). ![Il primo nodo {{ .Get "app" }} inizia come primario e diventa ALONE](/wp-content/uploads/2024/03/12-monitoring-alone-stop.png) ### 13. Avviare il nodo 2 * ⋯ `Start` nodo 2 con il suo menu contestuale. * Attendi lo stato SECOND (verde). ℹ️ * Il nodo 2 rimane nello stato SECOND (arancione) durante la risincronizzazione delle directory replicate (copia dal nodo 1 al nodo 2). * Questa operazione potrebbe richiedere del tempo a seconda della dimensione dei file da risincronizzare nelle directory replicate e della larghezza di banda della rete. * Per vedere lo stato di avanzamento della copia, vedere il [registro del modulo 🖼️](/wp-content/uploads/2024/03/27-module-log-reintegration.png) e il [risorse di replica 🖼️](/wp-content/uploads/2024/03/26-replication-resources-reintegration.png) del nodo 2. Utilizzare SafeKit AI 🤖 per assistenza con i messaggi di registro. ![Avviare il nodo {{ .Get "app" }} 2](/wp-content/uploads/2024/03/13-monitoring-alone-stop-start.png) ### 14. Verificare che il cluster sia operativo * Controlla che il cluster sia verde/verde con `VM1` in esecuzione sul nodo PRIM e non in esecuzione sul nodo SECOND. Solo le modifiche all'interno dei file vengono replicate in tempo reale in questo stato. ![Il nodo 2 {{ .Get "app" }} è SECOND (verde)](/wp-content/uploads/2024/03/14-monitoring-prim-second.png) ### 15. Test * Arrestare il nodo PRIM scorrendo verso il basso il menu contestuale e facendo clic `Stop`. * Verificare che sia presente un failover sul nodo SECOND che dovrebbe diventare ALONE (verde). * Controllalo con gli strumenti {{ .Get "app" }} `VM1` è in esecuzione sul nodo 2. ⚠️ Se ALONE (verde) non viene raggiunto su node2 o se VM1 non viene avviato, analizzare il motivo con il [registro del modulo 🖼️](/wp-content/uploads/2024/03/38-module-log-script-second.png) del nodo 2. * Fare clic su 🔍 **registro** icona di `node2` per aprire il registro del modulo e cercare messaggi di errore come un controllo che rileva un errore e arresta il modulo. * Fare clic su `start_prim` nel registro: i messaggi di output dello script vengono visualizzati sulla destra e possono essere rilevati errori come VM1 avviato in modo errato. * Utilizzare SafeKit AI 🤖 per assistenza con i messaggi di registro. ⚠️ * Se tutto è a posto, avviare un avvio su node1, che risincronizzerà le directory replicate da node2. * Se le cose vanno male, ferma node2 e [forzare l'avvio come primario 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) di node1, che ripartirà con i dati locali integri al momento dell'arresto. ℹ️ Tieni presente che hai uno 🕒 **[sequenza temporale 🖼️](/wp-content/uploads/2026/05/safekit-console-timeline.png)** che può essere utile per capire cosa succede nel cluster. ![Arrestare il modulo {{ .Get "app" }} sul server PRIM](/wp-content/uploads/2024/03/16-monitoring-prim-second-stop.png) ### 16. Se necessario, configurare un controllo splitbrain * Vedi [Quali sono i diversi scenari in caso di isolamento della rete in un cluster?](/it/best-practises/power-outage-and-network-isolation-in-a-cluster/) per sapere se è necessario configurare un controllo splitbrain. * Vai alla configurazione del modulo e clicca su `Checkers / Splitbrain` (vedi immagine) per modificare i parametri di splitbrain. * `Save and apply` la nuova configurazione per ridistribuirla su entrambi i nodi (il modulo deve essere arrestato su entrambi i nodi per essere salvato e applicato). **Parametri** : * `Resource name` identifica il testimone con un nome di risorsa: `splitbrain.witness`. È possibile modificare questo valore per identificare il testimone. * `Witness address` è l'argomento per un ping quando un nodo va da PRIM a ALONE o da SECOND a ALONE. Cambia questo valore con lo IP del testimone (un elemento robusto, tipicamente un router). * Nota: è possibile impostare più IP separati da spazi bianchi. Fare attenzione che gli indirizzi IP devono essere accessibili da un nodo ma non dall'altro in caso di isolamento della rete. ![Inserisci i parametri dello splitbrain {{ .Get "app" }}](/wp-content/uploads/2024/04/safekit-split-brain-checker.png) ### 17. Replicare le istantanee La directory che contiene i file xml dello snapshot è: /var/lib/libvirt/qemu/snapshot/%VM_NAME% dove `VM_NAME` è il nome della macchina virtuale (vm1). Nota: se non è stata creata alcuna istantanea, crearne una per generare la directory (altrimenti la configurazione di SafeKit fallirà). Per replicarlo: * Nella configurazione del modulo, fare clic su `Advanced Configuration` (vedi immagine) da modificare `userconfig.xml`. * Inserisci le righe sottostanti nel file `` sezione di userconfig.xml: * `Save and apply` la nuova configurazione per ridistribuire il file userconfig.xml modificato su entrambi i nodi (il modulo deve essere arrestato su entrambi i nodi per essere salvato e applicato). * Crea istantanee sul nodo PRIM tramite virt-manager o una riga di comando: virsh snapshot-create-as vm1 snapshot-name Nota: quando si crea un'istantanea con una riga di comando, è necessario aggiornare la visualizzazione dell'istantanea in virt-manager. Gli snapshot creati sul nodo PRIM sono operativi sul nodo 2 dopo il failover, ma non sono elencati sul nodo 2. * Per importare uno snapshot sul nodo 2, devi eseguire il comando: virsh snapshot-create --redefine vm1 /var/lib/libvirt/qemu/snapshot/vm1/snapshot-name * La riga di comando per elencare tutte le istantanee di vm1 è: virsh snapshot-list vm1 ![Immettere i parametri {{ .Get "app" }}](/wp-content/uploads/2024/03/21-module-kvm-edit-config-1.png) ### 18. Supporto * Per ottenere supporto, prendi 2 SafeKit `Snapshots` (2 file .zip), uno per ciascun nodo. ℹ️ [Maggiori informazioni sul supporto qui](/it/resources/safekit-support/). ![Scatta le istantanee di {{ .Get "app" }} per supporto](/wp-content/uploads/2024/03/30-snapshots-mirror.png)
