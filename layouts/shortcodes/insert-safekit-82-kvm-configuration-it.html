Prerequisiti {#prerequisite} L’immagine della macchina virtuale VM1 si trova nel file `/var/lib/libvirt/images/vm1.qcow2`. Prima di configurare SafeKit, è necessario eseguire la seguente configurazione per posizionare la macchina virtuale in una directory specifica di vm1 che verrà replicata da SafeKit. Sul nodo 1: * Arresta vm1: virsh shutdown vm1 * Creare una directory `vm1/`: mkdir -p /var/lib/libvirt/images/vm1/ * Copia l’immagine vm1 nella nuova posizione: cp -a /var/lib/libvirt/images/vm1.qcow2 /var/lib/libvirt/images/vm1/ L’immagine vm1 originale può essere eliminata non appena i test con la nuova posizione avranno esito positivo. * Modificare il file di configurazione vm1: EDITOR=vi virsh edit vm1 E modifica la riga: di: * Impostare l’[opzione della cache su "nessuna"](/wp-content/uploads/2022/07/kvm-2.png) nello stesso file, per l’integrità dei dati in caso di arresto anomalo: * Chiudi il file di configurazione di vm1 * Disabilita [l’avvio automatico di vm1](/wp-content/uploads/2022/07/kvm-3.png): virsh autostart vm1 --disable * Creare un file di configurazione `vm1.xml` per vm1: virsh dumpxml vm1 > vm1.xml Sul nodo 2: * Copiare il file di configurazione `vm1.xml` dal nodo 1. Nota: ogni volta che la configurazione vm1 viene modificata sul nodo 1, è necessario riapplicare la nuova configurazione sul nodo 2. * Creare vm1 ma non avviarla: virsh define vm1.xml * Disabilita l’avvio automatico vm1: virsh autostart vm1 --disable * Creare la directory per la posizione dell’immagine: mkdir -p /var/lib/libvirt/images/vm1/ ### 2. Avviare la console SafeKit {#2-launch-the-safekit-console} * Avviare la console web in un browser su un nodo del cluster collegandosi a `http://localhost:9010`. * Inserire `admin` come nome utente e la password definita durante l’installazione. È inoltre possibile eseguire la console in un browser su una workstation esterna al cluster. ⚠️ La configurazione di SafeKit viene eseguita su entrambi i nodi da un unico browser. ℹ️ Per proteggere la console web, consultare 🛠️ [11. Protezione del servizio web SafeKit](/it/resources/safekit-user-guide-82/#https) nella Guida per l’utente. ![Avviare la console web SafeKit per configurare il cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/01-login-large.png) ### 3. Configurare gli indirizzi dei nodi {#3-configure-node-addresses} * Inserisci gli indirizzi IP dei nodi, premi il `Tab key` per verificare la connettività e compila i nomi dei nodi. Se node1 o node2 sono di colore rosso, controlla la connettività del browser con entrambi i nodi e controlla il firewall su entrambi i nodi per la 🛠️ [risoluzione dei problemi](/it/resources/safekit-user-guide-82/#Troubleshooting). * Quindi, fare clic su `Save and apply` per salvare la configurazione. * Controllare il messaggio `Success` ✅ su entrambi i nodi. * Se si verifica un `Failure` di configurazione ❌ su un nodo, aprire il ▼ fisco di quel nodo e rivedere i messaggi. Si noti che è possibile utilizzare SafeKit AI 🤖 per assistenza. ℹ️ Se lo desideri, puoi aggiungere una nuova `LAN and nodes` (prima ➕) per creare un secondo heartbeat e una rete di replica dedicata. ℹ️ Se si fa clic su `Advanced configuration`, viene visualizzato il file `cluster.xml`. Questo file viene popolato automaticamente dalla console e distribuito sui nodi. ![Inserisci i nodi del cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/02-cluster-edit.png) ### 4. Seleziona un modulo {#4-select-a-module} * Nel `New module`, fare clic sul modulo `{{ .Get "mod" }}.safe`. ℹ️ Nel banner blu in alto, 🛜 `node1` rappresenta il nodo di connessione della console. Questo nodo inoltra le richieste a `node2` quando necessario. ℹ️ La console cerca `xxx.safe` nella directory `Application_Modules/generic/` sul nodo di connessione (`node1`) se hai inserito un modulo lì durante l’installazione. ![Scegli il modulo per {{ .Get "app" }}](/wp-content/uploads/2024/03/04-module-new.png) ### 5. Configurare il modulo {#5-configure-the-module} * Scegliere l’avvio `Automatic` del modulo all’avvio senza ritardi. * Normalmente, si dispone di una singola rete `Heartbeat` su cui viene eseguita la replica. Tuttavia, è possibile definire una rete privata, se necessario (aggiungendo una LAN al passaggio 3). * Inserire in `VM_PATH` il percorso principale della directory replicata (`/var/lib/libvirt/images`). * Inserire in `VM_NAME` il nome della macchina virtuale (`vm1`). Si presuppone che i file VM1 si trovino in `/var/lib/libvirt/images/vm1/` (vedere [i prerequisiti](#prerequisite)). Questa directory verrà replicata in tempo reale da SafeKit. ℹ️ Non è necessario configurare un indirizzo IP virtuale. VM1 verrà riavviata {{ .Get "app" }} secondaria con il suo indirizzo IP fisico e questo indirizzo IP verrà reindirizzato. ![Inserisci i parametri {{ .Get "app" }}](/wp-content/uploads/2024/03/21-module-kvm-edit-config-1.png) ### 6. Controllo personalizzato per rilevare il malfunzionamento della VM {#6-custom-checker-to-detect-vm-malfunction} Il checker personalizzato controlla se la VM è in esecuzione (con il comando ’virsh domstate’). Se la VM non è in esecuzione, il checker personalizzato la riavvia automaticamente sullo stesso nodo {{ .Get "app" }} o sull’altro. * Fare clic su `Checkers / Custom` (vedere l’immagine). * `Resource name` identifica la macchina virtuale con un nome di risorsa in SafeKit: `custom.VM_NAME_check`. * Con `restart` in `Action`, la VM viene riavviata sullo stesso nodo {{ .Get "app" }}. Dopo 3 riavvii non riusciti in 24 ore, il modulo SafeKit {{ .Get "mod" }} si arresta sul nodo primario e si verifica un failover della VM sul nodo secondario. * Se si imposta `stopstart` in `Action`, si verifica un failover diretto sull’altro nodo {{ .Get "app" }} non appena la VM non è in esecuzione. ℹ️ Per la manutenzione, se si desidera arrestare la macchina virtuale, il checker personalizzato la riavvierà automaticamente. Per evitare ciò, è possibile [sospendere temporaneamente il checker 🖼️](/wp-content/uploads/2024/04/safekit-disable-checkers.png). Oppure è possibile rimuoverlo eliminando la riga di configurazione nella console. ![Inserisci i parametri del checker personalizzato {{ .Get "app" }}](/wp-content/uploads/2024/12/custom-kvm-checker-2.png) ### 7. Modifica gli script (facoltativo) {#7-edit-scripts-optional} * Non modificare gli script. ### 8. Salva e applica {#9-save-and-apply} * `Save and apply` la configurazione e gli script su entrambi i nodi. ![Salva e applica la configurazione del modulo {{ .Get "app" }}](/wp-content/uploads/2024/03/08-module-save.png) ### 10. Verificare la corretta configurazione {#10-verify-successful-configuration} * Controllare il messaggio `Success` ✅ su entrambi i nodi e fare clic su `Monitor modules`. * Se si verifica un `Failure` di configurazione ❌ su un nodo, aprire il ▼ fisco di quel nodo e rivedere i messaggi. Si noti che è possibile utilizzare SafeKit AI 🤖 per assistenza. ![Verifica l’esito della configurazione del modulo {{ .Get "app" }}](/wp-content/uploads/2024/03/09-module-save-check.png) ### 11. Avviare il nodo con i dati aggiornati {#11-start-the-node-with-up-to-date-data} * Se il nodo 1 dispone della directory replicata aggiornata per `vm1/`, selezionarlo e ⋯ `Force start` ▶ `As primary`. Quando il nodo 2 verrà avviato, tutti i dati verranno copiati dal nodo 1 al nodo 2. ⚠️ Se si effettua la scelta sbagliata, si corre il rischio di sincronizzare dati obsoleti su entrambi i nodi. ⚠️ Si presuppone inoltre che `VM1` sia arrestata sul nodo 1 in modo che SafeKit installi i meccanismi di replica e quindi avvii `VM1` nello script `start_prim`. ⚠️ Utilizzare `Start` per gli avvii successivi: SafeKit mantiene il server più aggiornato. L’avvio `As primary` è un avvio speciale la prima volta o durante operazioni eccezionali. ![Avviare come primario il nodo {{ .Get "app" }} con i dati aggiornati](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) ### 12. Attendere la transizione a ALONE (verde) {#12-wait-for-the-transition-to-alone-green} * Il nodo 1 dovrebbe raggiungere lo stato ALONE (verde), il che significa che lo script `start_prim` è stato eseguito sul nodo 1. ⚠️ Se ALONE (verde) non viene raggiunto o se VM1 non viene avviato, analizzare il motivo con il [registro del modulo 🖼️](/wp-content/uploads/2024/03/24-module-log-script.png) del nodo 1. * Fare clic sull’icona **del log** 🔍 del `node1` per aprire il log del modulo e cercare messaggi di errore, ad esempio un checker che rileva un errore e arresta il modulo. * Fare clic su `start_prim` nel log: i messaggi di output dello script vengono visualizzati a destra e possono essere rilevati errori come VM1 avviata in modo errato. * Usa SafeKit AI 🤖 per ricevere assistenza con i messaggi di log. ⚠️ Se il cluster è in stato `WAIT (red) not uptodate, STOP (red) not uptodate`, arrestare il nodo WAIT e [forzarne l’avvio come primario 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png). ![Il primo nodo {{ .Get "app" }} si avvia come primario e diventa ALONE](/wp-content/uploads/2024/03/12-monitoring-alone-stop.png) ### 13. Avviare il nodo 2 {#13-start-node-2} * ⋯ `Start` il nodo 2 con il suo menu contestuale. * Attendere il SECOND stato (verde). ℹ️ * Il nodo 2 rimane nel SECOND stato (arancione) durante la risincronizzazione delle directory replicate (copia dal nodo 1 al nodo 2). * Questa operazione potrebbe richiedere del tempo, a seconda delle dimensioni dei file da risincronizzare nelle directory replicate e della larghezza di banda della rete. * Per visualizzare l’avanzamento della copia, consultare il [registro del modulo 🖼️](/wp-content/uploads/2024/03/27-module-log-reintegration.png) e le [risorse di replica 🖼️](/wp-content/uploads/2024/03/26-replication-resources-reintegration.png) del nodo 2. Utilizzare SafeKit AI 🤖 per assistenza con i messaggi di registro. ![Avviare il nodo 2 {{ .Get "app" }}](/wp-content/uploads/2024/03/13-monitoring-alone-stop-start.png) ### 14. Verificare che il cluster sia operativo {#14-verify-that-the-cluster-is-operational} * Verificare che il cluster sia verde/verde con `VM1` in esecuzione sul nodo PRIM e non sul nodo SECOND. In questo stato, solo le modifiche all’interno dei file vengono replicate in tempo reale. ![Il nodo {{ .Get "app" }} 2 è SECOND (verde)](/wp-content/uploads/2024/03/14-monitoring-prim-second.png) ### 15. Test {#15-testing} * Arrestare il nodo PRIM scorrendo il relativo menu contestuale e facendo clic su `Stop`. * Verificare che sia presente un failover sul SECOND nodo, che dovrebbe diventare ALONE (verde). * Verificare con gli strumenti {{ .Get "app" }} che `VM1` sia in esecuzione sul nodo 2. ⚠️ Se ALONE (verde) non viene raggiunto sul node2 o se VM1 non è avviata, analizzare il motivo con il [log del modulo 🖼️](/wp-content/uploads/2024/03/38-module-log-script-second.png) del nodo 2. * Fare clic sull’icona **del registro** 🔍 del `node2` per aprire il registro del modulo e cercare messaggi di errore, ad esempio un checker che rileva un errore e arresta il modulo. * Fare clic su `start_prim` nel log: i messaggi di output dello script vengono visualizzati a destra e possono essere rilevati errori come VM1 avviata in modo errato. * Usa SafeKit AI 🤖 per ricevere assistenza con i messaggi di log. ⚠️ * Se tutto è a posto, avviare il node1, che risincronizzerà le directory replicate dal node2. * Se le cose vanno male, arrestare node2 e [forzare node 1 ad avviarsi come primario 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png), che si riavvierà con i suoi dati localmente integri al momento dell’arresto. ℹ️ Tieni presente che hai una 🕒 **[cronologia 🖼️](/wp-content/uploads/2026/05/safekit-console-timeline.png)** che può essere utile per capire cosa succede nel cluster. ![Arrestare il modulo {{ .Get "app" }} sul server PRIM](/wp-content/uploads/2024/03/16-monitoring-prim-second-stop.png) ### 16. Se necessario, configurare un verificatore di split-brain {#16-if-necessary-configure-a-splitbrain-checker} * Per sapere se è necessario configurare un verificatore di split-brain, consultare la sezione [Quali sono i diversi scenari in caso di isolamento della rete in un cluster?](/it/best-practises/power-outage-and-network-isolation-in-a-cluster/) * Andare alla configurazione del modulo e fare clic su `Checkers / Splitbrain` (vedere immagine) per modificare i parametri di splitbrain. * `Save and apply` la nuova configurazione per ridistribuirla su entrambi i nodi (il modulo deve essere arrestato su entrambi i nodi per salvare e applicare). **Parametri** : * `Resource name` identifica il witness con un nome di risorsa: `splitbrain.witness`. È possibile modificare questo valore per identificare il witness. * `Witness address` è l’argomento per un ping quando un nodo passa da PRIM a ALONE o da SECOND a ALONE. Modificare questo valore con l’IP del witness (un elemento robusto, in genere un router). * Nota: è possibile impostare più IP separati da spazi bianchi. Prestare attenzione al fatto che gli indirizzi IP devono essere accessibili da un nodo ma non dall’altro in caso di isolamento della rete. ![Inserisci i parametri di splitbrain {{ .Get "app" }}](/wp-content/uploads/2024/04/safekit-split-brain-checker.png) ### 17. Replicazione degli snapshot {#17-replicating-snapshots} La directory che contiene i file XML degli snapshot è: /var/lib/libvirt/qemu/snapshot/%VM_NAME% dove `VM_NAME` è il nome della macchina virtuale (vm1). Nota: se non è stato creato alcun snapshot, crearne uno per generare la directory (altrimenti la configurazione SafeKit non andrà a buon fine). Per replicarlo: * Nella configurazione del modulo, fare clic su `Advanced Configuration` (vedere l’immagine) per modificare `userconfig.xml`. * Inserisci le righe seguenti nella sezione `` di userconfig.xml: * `Save and apply` la nuova configurazione per ridistribuire il file userconfig.xml modificato su entrambi i nodi (il modulo deve essere arrestato su entrambi i nodi per salvare e applicare). * Creare snapshot sul nodo PRIM tramite virt-manager o una riga di comando: virsh snapshot-create-as vm1 snapshot-name Nota: quando si crea un’istantanea tramite riga di comando, è necessario aggiornare la vista delle istantanee in virt-manager.
