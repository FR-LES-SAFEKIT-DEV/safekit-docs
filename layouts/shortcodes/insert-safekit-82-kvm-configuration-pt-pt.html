Pré-requisitos {#prerequisite} A imagem da máquina virtual VM1 encontra-se no ficheiro `/var/lib/libvirt/images/vm1.qcow2`. Antes de configurar SafeKit, deve executar a seguinte configuração para colocar a máquina virtual num diretório específico da que será replicado pelo SafeKit. No nó 1: * Parar a vm1: virsh shutdown vm1 * Crie um diretório `vm1/`: mkdir -p /var/lib/libvirt/images/vm1/ * Copie a imagem da vm1 para o novo local: cp -a /var/lib/libvirt/images/vm1.qcow2 /var/lib/libvirt/images/vm1/ A imagem original vm1 pode ser eliminada assim que os testes com a nova localização forem bem-sucedidos. * Edite o ficheiro de configuração vm1: EDITOR=vi virsh edit vm1 E altere a linha: por: * Defina a [opção de cache como ’nenhuma’](/wp-content/uploads/2022/07/kvm-2.png) no mesmo ficheiro, para garantir a integridade dos dados em caso de falha: * Feche o ficheiro de configuração vm1 * Desativar [o arranque automático da vm1](/wp-content/uploads/2022/07/kvm-3.png): virsh autostart vm1 --disable * Crie um ficheiro de configuração `vm1.xml` para vm1: virsh dumpxml vm1 > vm1.xml No nó 2: * Copie o ficheiro de configuração `vm1.xml` do nó 1. Nota: sempre que a configuração vm1 for alterada no nó 1, deve reaplicar a nova configuração no nó 2. * Crie a vm1, mas não a inicie: virsh define vm1.xml * Desativar o arranque automático vm1: virsh autostart vm1 --disable * Crie o diretório para a localização da imagem: mkdir -p /var/lib/libvirt/images/vm1/ ### 2. Inicie a consola SafeKit {#2-launch-the-safekit-console} * Inicie a consola web num navegador, num dos nós do cluster, ligando-se a `http://localhost:9010`. * Introduza `admin` como nome de utilizador e a palavra-passe definida durante a instalação. Também é possível executar a consola num navegador, numa estação de trabalho externa ao cluster. ⚠️ A configuração do SafeKit é feita em ambos os nós a partir de um único navegador. ℹ️ Para proteger a consola web, consulte 🛠️ [11. Proteção do serviço web SafeKit](/pt-pt/resources/safekit-user-guide-82/#https) no Guia do Utilizador. ![Inicie a consola web SafeKit para configurar o cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/01-login-large.png) ### 3. Configurar os endereços dos nós {#3-configure-node-addresses} * Introduza os endereços IP dos nós, prima a `Tab key` para verificar a conectividade e preencha os nomes dos nós. Se node1 ou node2 tiverem uma cor vermelha, verifique a conectividade do navegador a ambos os nós e verifique a firewall em ambos os nós para 🛠️ [resolução de problemas](/pt-pt/resources/safekit-user-guide-82/#Troubleshooting). * Em seguida, clique em `Save and apply` para guardar a configuração. * Verifique a mensagem `Success` ✅ em ambos os nós. * Se ocorrer uma `Failure` de configuração ❌ num nó, abra o acordeão ▼ desse nó e reveja as mensagens. Tenha em atenção que pode utilizar a IA SafeKit 🤖 para obter assistência. ℹ️ Se desejar, pode adicionar uma nova `LAN and nodes` (primeiro ➕) para criar um segundo heartbeat e uma rede de replicação dedicada. ℹ️ Se clicar em `Advanced configuration`, o ficheiro `cluster.xml` é apresentado. Este ficheiro é preenchido automaticamente pela consola e implementado nos nós. ![Introduza os nós do cluster da {{ .Get "app" }}](/wp-content/uploads/2024/03/02-cluster-edit.png) ### 4. Selecione um módulo {#4-select-a-module} * No `New module`, clique no módulo `{{ .Get "mod" }}.safe`. ℹ️ No banner azul no topo, `node1` 🛜 representa o nó de ligação da consola. Este nó reencaminha os pedidos para `node2` quando necessário. ℹ️ A consola procura por `xxx.safe` no diretório `Application_Modules/generic/` no nó de ligação (`node1`) se tiver colocado um módulo lá durante a instalação. ![Escolha o módulo para {{ .Get "app" }}](/wp-content/uploads/2024/03/04-module-new.png) ### 5. Configure o módulo {#5-configure-the-module} * Escolha o arranque `Automatic` do módulo no arranque, sem demora. * Normalmente, tem uma única rede `Heartbeat` na qual a replicação é feita. No entanto, pode definir uma rede privada, se necessário (adicionando uma LAN no passo 3). * Introduza em `VM_PATH` o caminho raiz do diretório replicado (`/var/lib/libvirt/images`). * Introduza em `VM_NAME` o nome da máquina virtual (`vm1`). Assumimos que os ficheiros VM1 estão em `/var/lib/libvirt/images/vm1/` (ver [pré-requisitos](#prerequisite)). Este diretório será replicado em tempo real pelo SafeKit. ℹ️ Não é necessário configurar um endereço IP virtual. VM1 será reiniciada na {{ .Get "app" }} secundária com o seu endereço IP físico e este endereço IP será redirecionado. ![Introduza os parâmetros {{ .Get "app" }}](/wp-content/uploads/2024/03/21-module-kvm-edit-config-1.png) ### 6. Verificador personalizado para detetar avarias na máquina virtual {#6-custom-checker-to-detect-vm-malfunction} O verificador personalizado verifica se a VM está em execução (com o comando ’virsh domstate’). Se a VM não estiver em execução, o verificador personalizado reinicia automaticamente a VM no mesmo nó {{ .Get "app" }} ou noutro. * Clique em `Checkers / Custom` (ver imagem). * `Resource name` identifica a máquina virtual com um nome de recurso no SafeKit: `custom.VM_NAME_check`. * Com `restart` em `Action`, a VM é reiniciada no mesmo nó {{ .Get "app" }}. Após 3 reinícios sem sucesso em 24 horas, o módulo SafeKit {{ .Get "mod" }} para no nó primário e ocorre uma comutação de contingência da VM para o nó secundário. * Se definir `stopstart` em `Action`, haverá uma comutação automática para o outro nó {{ .Get "app" }} assim que a máquina virtual não estiver em execução. ℹ️ Para manutenção, se quiser parar a máquina virtual, o verificador personalizado irá reiniciá-la automaticamente. Para evitar isso, pode [suspender temporariamente o verificador 🖼️](/wp-content/uploads/2024/04/safekit-disable-checkers.png). Ou pode removê-lo, eliminando a linha de configuração na consola. ![Introduza os parâmetros do verificador personalizado {{ .Get "app" }}](/wp-content/uploads/2024/12/custom-kvm-checker-2.png) ### 7. Editar os scripts (opcional) {#7-edit-scripts-optional} * Não edite os scripts. ### 8. Criptografia da comunicação (opcional) {#8-communication-encryption-optional} * Mantenha a encriptação da comunicação entre os nós. ![Criptografia de comunicação do módulo {{ .Get "app" }}](/wp-content/uploads/2024/03/07-module-encryption.png) ### 9. Guardar e aplicar {#9-save-and-apply} * `Save and apply` a configuração e os scripts em ambos os nós. ![Guarde e aplique a configuração do módulo {{ .Get "app" }}](/wp-content/uploads/2024/03/08-module-save.png) ### 10. Verifique se a configuração foi bem-sucedida {#10-verify-successful-configuration} * Verifique a mensagem `Success` ✅ em ambos os nós e clique em `Monitor modules`. * Se ocorrer uma `Failure` de configuração ❌ num nó, abra o acordeão ▼ desse nó e reveja as mensagens. Tenha em atenção que pode utilizar a IA SafeKit 🤖 para obter assistência. ![Verifique o sucesso da configuração do módulo {{ .Get "app" }}](/wp-content/uploads/2024/03/09-module-save-check.png) ### 11. Inicie o nó com dados atualizados {#11-start-the-node-with-up-to-date-data} * Se o nó 1 tiver o diretório replicado atualizado para `vm1/`, selecione-o e ⋯ `Force start` ▶ `As primary`. Quando o nó 2 for iniciado, todos os dados serão copiados do nó 1 para o nó 2. ⚠️ Se fizer a escolha errada, corre o risco de sincronizar dados desatualizados em ambos os nós. ⚠️ Também se assume que `VM1` está parada no nó 1 para que SafeKit instale os mecanismos de replicação e, em seguida, inicie `VM1` no script `start_prim`. ⚠️ Utilize `Start` para arranques subsequentes: SafeKit mantém o servidor mais atualizado. Iniciar `As primary` é um arranque especial na primeira vez ou durante operações excecionais. ![Inicie como primário o nó {{ .Get "app" }} com os dados atualizados](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) ### 12. Aguarde a transição para ALONE (verde) {#12-wait-for-the-transition-to-alone-green} * O nó 1 deve atingir o estado ALONE (verde), o que significa que o script `start_prim` foi executado no nó 1. ⚠️ Se ALONE (verde) não for atingido ou se VM1 não for iniciado, analise o motivo com o [registo do módulo 🖼️](/wp-content/uploads/2024/03/24-module-log-script.png) do nó 1. * Clique no ícone **de registo** 🔍 do `node1` para abrir o registo do módulo e procure mensagens de erro, como um verificador que deteta um erro e para o módulo. * Clique em `start_prim` no registo: as mensagens de saída do script são apresentadas à direita e os erros podem ser detetados, como VM1 iniciado incorretamente. * Utilize o SafeKit AI 🤖 para obter assistência com as mensagens de registo. ⚠️ Se o cluster estiver no estado `WAIT (red) not uptodate, STOP (red) not uptodate`, pare o nó WAIT e [force o seu arranque como primário 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png). ![O primeiro nó {{ .Get "app" }} inicia como primário e fica ALONE](/wp-content/uploads/2024/03/12-monitoring-alone-stop.png) ### 13. Iniciar nó 2 {#13-start-node-2} * ⋯ `Start` o nó 2 com o seu menu contextual. * Aguarde o SECOND estado (verde). ℹ️ * O nó 2 permanece no SECOND estado (laranja) enquanto resincroniza os diretórios replicados (cópia do nó 1 para o nó 2). * Isto pode demorar algum tempo, dependendo do tamanho dos ficheiros a resincronizar nos diretórios replicados e da largura de banda da rede. * Para ver o progresso da cópia, consulte o [registo do módulo 🖼️](/wp-content/uploads/2024/03/27-module-log-reintegration.png) e os [recursos de replicação 🖼️](/wp-content/uploads/2024/03/26-replication-resources-reintegration.png) do nó 2. Utilize a IA SafeKit 🤖 para obter assistência com as mensagens de registo. ![Inicie o nó 2 {{ .Get "app" }}](/wp-content/uploads/2024/03/13-monitoring-alone-stop-start.png) ### 14. Verifique se o cluster está operacional {#14-verify-that-the-cluster-is-operational} * Verifique se o cluster está verde/verde com `VM1` a ser executada no nó PRIM e não no nó SECOND. Apenas as alterações dentro dos ficheiros são replicadas em tempo real neste estado. ![O nó {{ .Get "app" }} 2 é SECOND (verde)](/wp-content/uploads/2024/03/14-monitoring-prim-second.png) ### 15. Testes {#15-testing} * Pare o nó PRIM, percorrendo o menu contextual e clicando em `Stop`. * Verifique se existe um failover no SECOND nó, que deverá ficar ALONE (verde). * Verifique com as ferramentas {{ .Get "app" }} se `VM1` está a ser executada no nó 2. ⚠️ Se ALONE (verde) não for atingido no node2 ou se VM1 não for iniciada, analise o motivo com o [registo do módulo 🖼️](/wp-content/uploads/2024/03/38-module-log-script-second.png) do nó 2. * Clique no ícone **de registo** 🔍 do `node2` para abrir o registo do módulo e procure mensagens de erro, como um verificador que deteta um erro e para o módulo. * Clique em `start_prim` no registo: as mensagens de saída do script são apresentadas à direita e os erros podem ser detetados, como VM1 iniciado incorretamente. * Utilize o SafeKit AI 🤖 para obter assistência com as mensagens de registo. ⚠️ * Se tudo estiver bem, inicie o node1, que irá ressincronizar os diretórios replicados do node2. * Se as coisas correrem mal, pare node2 e [force o nó 1 a iniciar como primário 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png), que será reiniciado com os seus dados localmente íntegros no momento da paragem. ℹ️ Tenha em atenção que tem uma **[linha do 🖼️](/wp-content/uploads/2026/05/safekit-console-timeline.png)** 🕒 que pode ser útil para entender o que acontece no cluster. ![Parar o módulo {{ .Get "app" }} no servidor PRIM](/wp-content/uploads/2024/03/16-monitoring-prim-second-stop.png) ### 16. Se necessário, configure um verificador de divisão de rede {#16-if-necessary-configure-a-splitbrain-checker} * Consulte ["Quais são os diferentes cenários em caso de isolamento de rede num cluster?"](/pt-pt/best-practises/power-outage-and-network-isolation-in-a-cluster/) para saber se precisa de configurar um verificador de divisão de rede. * Vá para a configuração do módulo e clique em `Checkers / Splitbrain` (ver imagem) para editar os parâmetros do splitbrain. * `Save and apply` a nova configuração para a reimplantar em ambos os nós (o módulo deve estar parado em ambos os nós para guardar e aplicar). **Parâmetros** : * `Resource name` identifica a testemunha com um nome de recurso: `splitbrain.witness`. Altere este valor para o IP do testemunha (um elemento robusto, normalmente um router). * Nota: pode definir vários IPs separados por espaços em branco. Tenha em atenção que os endereços IP devem ser acessíveis a partir de um nó, mas não do outro, em caso de isolamento de rede. ![Introduza os parâmetros de divisão de rede {{ .Get "app" }}](/wp-content/uploads/2024/04/safekit-split-brain-checker.png) ### 17.
