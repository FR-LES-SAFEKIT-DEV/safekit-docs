Per le versioni precedenti, 🛠️ [consultare questo articolo](/it/quick-install/safekit-quick-installation-guide-old-milestone-configuration/). ### 1. Avviare la console SafeKit {#1-launch-the-safekit-console} * Avviare la console web in un browser su un nodo del cluster collegandosi a `http://localhost:9010`. * Inserire `admin` come nome utente e la password definita durante l’installazione. È inoltre possibile eseguire la console in un browser su una workstation esterna al cluster. ⚠️ La configurazione di SafeKit viene eseguita su entrambi i nodi da un unico browser. ℹ️ Per proteggere la console web, consultare 🛠️ [11. Protezione del servizio web SafeKit](/it/resources/safekit-user-guide-82/#https) nella Guida per l’utente. ![Avviare la console web SafeKit per configurare il cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/01-login-large.png) ### 2. Configurare gli indirizzi dei nodi {#2-configure-node-addresses} * Inserisci gli indirizzi IP dei nodi, premi il `Tab key` per verificare la connettività e compila i nomi dei nodi. Se node1 o node2 sono di colore rosso, controlla la connettività del browser con entrambi i nodi e controlla il firewall su entrambi i nodi per la 🛠️ [risoluzione dei problemi](/it/resources/safekit-user-guide-82/#Troubleshooting). * Quindi, fare clic su `Save and apply` per salvare la configurazione. * Controllare il messaggio `Success` ✅ su entrambi i nodi. * Se si verifica un `Failure` di configurazione ❌ su un nodo, aprire il ▼ fisco di quel nodo e rivedere i messaggi. Si noti che è possibile utilizzare SafeKit AI 🤖 per assistenza. ℹ️ Se lo desideri, puoi aggiungere una nuova `LAN and nodes` (prima ➕) per creare un secondo heartbeat e una rete di replica dedicata. ℹ️ Se si fa clic su `Advanced configuration`, viene visualizzato il file `cluster.xml`. Questo file viene popolato automaticamente dalla console e distribuito sui nodi. ![Inserisci i nodi del cluster {{ .Get "app" }}](/wp-content/uploads/2024/03/02-cluster-edit.png) ### 3. Seleziona un modulo {#3-select-a-module} * Nel `New module`, fare clic sul modulo `{{ .Get "mod" }}.safe`. ℹ️ Nel banner blu in alto, 🛜 `node1` rappresenta il nodo di connessione della console. Questo nodo inoltra le richieste a `node2` quando necessario. ℹ️ La console cerca `xxx.safe` nella directory `Application_Modules/generic/` sul nodo di connessione (`node1`) se hai inserito un modulo lì durante l’installazione. ![Scegli il modulo per {{ .Get "app" }}](/wp-content/uploads/2024/03/04-module-new.png) ### 4. Configurare il modulo {#4-configure-the-module} * In `Module startup at boot`, scegliere un avvio automatico del modulo all’avvio senza ritardo. * In `Macros`/`SERVICES`, inserisci i nomi dei servizi della tua applicazione, nell’ordine di avvio, separati da virgole. Consulta questo screenshot per un esempio visivo dei [servizi Milestone XProtect 🖼️](/wp-content/uploads/2025/05/milestone-services.png). * Nelle `Heartbeat networks`, è necessario disporre di una singola rete heartbeat su cui viene eseguita la replica. Se è stata aggiunta una LAN privata al passaggio 2, è possibile configurare due heartbeat con il flusso di replica sulla LAN privata. * In `Virtual IP addresses`, inserire un indirizzo IP virtuale. Un indirizzo IP virtuale è un indirizzo IP standard nella stessa rete IP (stessa sottorete) degli indirizzi IP di entrambi i nodi. I client dell’applicazione devono essere configurati con l’indirizzo IP virtuale (o il nome DNS associato all’indirizzo IP virtuale). L’indirizzo IP virtuale viene commutato automaticamente in caso di guasto. * In `Replicated directories`, impostare i percorsi delle directory da replicare. Verificare che esistano su entrambi i nodi e che contengano i dati dell’applicazione. La replica dei dati e dei log è essenziale per un database. È possibile creare ulteriori directory replicate in base alle esigenze. Per un esempio visivo della [replica SQL Milestone XProtect consultare questa schermata 🖼️](/wp-content/uploads/2025/05/milestone-replication.png). * In `Checkers`, sarà possibile configurare i checker, se necessario, come il monitoraggio dei processi, i checker personalizzati, TCP, ping o i checker split-brain. Ad esempio, se un nome di processo viene visualizzato in `Monitored processes/services`, verrà monitorato con un’azione di riavvio in caso di errore. La configurazione di un nome di processo errato farà sì che il modulo si arresti subito dopo l’avvio. ⚠️ Se SQL si trova sul server di gestione: * I [database di sistema SQL](https://learn.microsoft.com/en-us/sql/relational-databases/databases/system-databases) (come master.mdf e mastlog.ldf) devono trovarsi nelle stesse directory su entrambi i nodi. Le directory devono essere configurate come replicate. * SQL deve essere installato anche nella stessa posizione nel file system su entrambi i nodi, perché il [database delle risorse SQL](https://learn.microsoft.com/en-us/sql/relational-databases/databases/resource-database) di sola lettura si trova nel binario ed è necessario per il failover. Questo database non deve essere replicato. * I database SQL Milestone (.mdf e .ldf) devono trovarsi nelle stesse directory su entrambi i nodi. Le directory devono essere configurate come replicate. I database Milestone sono i seguenti, secondo questo [articolo](https://doc.milestonesys.com/xprotect/xprotect-management-client/2026r1/en/change-the-location-and-name-of-a-sql-server-database.html). ℹ️ Se si fa clic su `Advanced configuration`, viene visualizzato il file `userconfig.xml`. Questo file viene popolato automaticamente dalla console e distribuito sui nodi con gli script di riavvio. ℹ️ Quando si applica la configurazione SafeKit, il `startup type` dei servizi viene automaticamente impostato su `Manual` in Servizi Windows. Ciò garantisce che i servizi non si avviino automaticamente all’avvio del sistema, ma vengano avviati solo quando il modulo stesso viene avviato. ![Accedi alle impostazioni del modulo {{ .Get "app" }}](/wp-content/uploads/2025/05/05-module-mirror-edit-config-3.png) ### 5. Modifica gli script (facoltativo) {#5-edit-scripts-optional} * Questo passaggio è facoltativo e può essere saltato nella maggior parte dei casi, poiché gli script di riavvio sono già preconfigurati per riavviare i servizi definiti nel passaggio precedente. * Quindi, fai clic direttamente su `Next step`. * `start_prim.ps1` avvia tutti i servizi nell’ordine specificato nell’elenco `SERVICES` e avvia i `IIS application pools` utilizzati da Milestone. `stop_prim.ps1` arresta tutti i servizi nell’ordine inverso. * Inoltre, `start_prim.ps1` controlla l’avvio di ciascun servizio e arresta il modulo se un servizio non si avvia correttamente. ![Accedi alle impostazioni del modulo {{ .Get "app" }}](/wp-content/uploads/2026/09/28-module-edit-script.png) ### 6. Crittografia della comunicazione (opzionale) {#6-communication-encryption-optional} * Mantenere la crittografia della comunicazione tra i nodi. ![Crittografia della comunicazione del modulo {{ .Get "app" }}](/wp-content/uploads/2025/05/07-module-encryption-1.png) ### 7. Salva e applica {#7-save-and-apply} * `Save and apply` la configurazione e gli script su entrambi i nodi. ![Salva e applica la configurazione del modulo {{ .Get "app" }}](/wp-content/uploads/2025/05/08-module-save-1.png) ### 8. Verifica della corretta configurazione {#8-verify-successful-configuration} * Controllare il messaggio `Success` ✅ su entrambi i nodi e fare clic su `Monitor modules`. * Se si verifica un `Failure` di configurazione ❌ su un nodo, aprire il ▼ fisco di quel nodo e rivedere i messaggi. Si noti che è possibile utilizzare SafeKit AI 🤖 per assistenza. ![Verifica l’esito della configurazione del modulo {{ .Get "app" }}](/wp-content/uploads/2025/05/09-module-save-check-1.png) ### 9. Avviare il nodo con i dati aggiornati {#9-start-the-node-with-up-to-date-data} * Se il nodo 1 dispone delle directory replicate aggiornate, selezionarlo e ⋯ `Force start` ▶ `As primary`. Quando il nodo 2 verrà avviato, tutti i dati verranno copiati dal nodo 1 al nodo 2. ⚠️ Se si effettua la scelta sbagliata, si corre il rischio di sincronizzare dati obsoleti su entrambi i nodi. ⚠️ Si presuppone inoltre che l’applicazione {{ .Get "app" }} sia arrestata sul nodo 1 in modo che SafeKit installi i meccanismi di replica e quindi avvii l’applicazione nello script `start_prim`. ⚠️ Utilizzare `Start` per gli avvii successivi: SafeKit mantiene il server più aggiornato. L’avvio `As primary` è un avvio speciale la prima volta o durante operazioni eccezionali. ![Avviare come primario il nodo {{ .Get "app" }} con i dati aggiornati](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) ### 10. Attendere la transizione a ALONE (verde) {#10-wait-for-the-transition-to-alone-green} * Il nodo 1 dovrebbe raggiungere lo stato ALONE (verde), il che significa che l’IP virtuale è impostato e che lo script `start_prim` è stato eseguito sul nodo 1. ⚠️ Se ALONE (verde) non viene raggiunto o se l’applicazione non viene avviata, analizzare il motivo con il [log del modulo 🖼️](/wp-content/uploads/2024/03/24-module-log-script.png) del nodo 1. * Fare clic sull’icona **del log** 🔍 del `node1` per aprire il log del modulo e cercare messaggi di errore, ad esempio un checker che rileva un errore e arresta il modulo. * Fare clic su `start_prim` nel log: i messaggi di output dello script vengono visualizzati a destra e possono essere rilevati errori, ad esempio un servizio avviato in modo errato. * Usa SafeKit AI 🤖 per ricevere assistenza con i messaggi di log. ⚠️ Se il cluster è in stato `WAIT (red) not uptodate, STOP (red) not uptodate`, arrestare il nodo WAIT e [forzarne l’avvio come primario 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png). ![Il primo nodo {{ .Get "app" }} si avvia come primario e diventa ALONE](/wp-content/uploads/2024/03/12-monitoring-alone-stop.png) ### 11. Risolvere il problema di autenticazione Windows in caso di failover {#role} Quando si avvia Milestone XProtect Management Client, è necessario eseguire l’autenticazione utilizzando uno dei seguenti metodi. A seconda della scelta, sono necessari passaggi specifici per garantire che l’accesso funzioni dopo un failover SafeKit. Riferimento: [Visualizza schermata di accesso 🖼️](/wp-content/uploads/2022/07/milestone-management-server-connect.png). #### Autenticazione Windows con Active Directory (AD) {#windows-authentication-with-active-directory-ad} **Configurazione:** non è richiesta alcuna configurazione speciale. Se l’autenticazione Windows Milestone è configurata con un Active Directory, le informazioni su utente e password vengono recuperate dall’AD esterno. Dopo un failover, il nodo secondario si connette allo stesso AD, quindi l’autenticazione funziona automaticamente. #### Autenticazione Windows in gruppo di lavoro {#windows-authentication-in-workgroup} **Configurazione:** è necessario aggiungere il gruppo **BUILTIN/Administrators** in "Sicurezza/Ruoli". **Avvertenza:** in un gruppo di lavoro, gli utenti locali hanno identificatori di sicurezza (SID) diversi su ciascun nodo, anche se i nomi sono identici. Solo il gruppo BUILTIN/Administrators ha lo stesso SID su entrambi i nodi. * Aggiungendo questo gruppo, è possibile eseguire l’autenticazione sul nodo secondario con qualsiasi account amministratore locale dopo un failover. * In caso contrario, l’autenticazione locale Windows sul nodo secondario non andrà a buon fine perché i SID non corrisponderanno. #### Autenticazione di base con database SQL {#basic-authentication-with-sql-database} **Configurazione:** creare un utente con "Autenticazione di base" (ad esempio, " Admin "). Per l’"Autenticazione di base", le credenziali utente sono archiviate direttamente nel database SQL. Poiché SafeKit replica il database SQL sul nodo secondario in tempo reale, questi utenti sono sempre disponibili immediatamente dopo un failover. ![Impostare i ruoli nel Management Client Milestone](/wp-content/uploads/2022/07/milestone-management-server-roles.png) ### 14. Avviare il nodo 2 {#14-start-node-2} * ⋯ `Start` il nodo 2 con il suo menu contestuale. * Attendere il SECOND stato (verde). ℹ️ * Il nodo 2 rimane nel SECOND stato (arancione) durante la risincronizzazione delle directory replicate (copia dal nodo 1 al nodo 2). * Questa operazione potrebbe richiedere del tempo, a seconda delle dimensioni dei file da risincronizzare nelle directory replicate e della larghezza di banda della rete. * Per visualizzare l’avanzamento della copia, consultare il [registro del modulo 🖼️](/wp-content/uploads/2024/03/27-module-log-reintegration.png) e le [risorse di replica 🖼️](/wp-content/uploads/2024/03/26-replication-resources-reintegration.png) del nodo 2. Utilizzare SafeKit AI 🤖 per assistenza con i messaggi di registro. ![Avviare il nodo 2 {{ .Get "app" }}](/wp-content/uploads/2024/03/13-monitoring-alone-stop-start.png) ### 15. Verificare che il cluster sia operativo {#15-verify-that-the-cluster-is-operational} * Verificare che il cluster sia verde/verde con i servizi {{ .Get "app" }} in esecuzione sul nodo PRIM e non in esecuzione sul nodo SECOND. * In questo stato, solo le modifiche all’interno dei file vengono replicate in tempo reale. ⚠️ * Registrare i **server di registrazione** con l’indirizzo IP virtuale. * Connettere il **Milestone Management Client** e il **Milestone Smart Client** all’indirizzo IP virtuale. * I componenti che sono client dei servizi {{ .Get "app" }} devono essere configurati con l’indirizzo IP virtuale. La configurazione può essere eseguita con un nome DNS (se è stato creato un nome DNS e associato all’indirizzo IP virtuale). ![Il nodo {{ .Get "app" }} 2 è SECOND (verde)](/wp-content/uploads/2024/03/14-monitoring-prim-second.png) ### 16. Test {#16-testing} * Arrestare il nodo PRIM scorrendo il relativo menu contestuale e facendo clic su `Stop`. * Verificare che sia presente un failover sul SECOND nodo, che dovrebbe diventare ALONE (verde). * E con Microsoft Management Console (MMC) su Windows o con le righe di comando su Linux, controllare il failover dei servizi {{ .Get "app" }} (arrestati sul nodo 1 nello script `stop_prim` e avviati sul nodo 2 nello script `start_prim`). ⚠️ Se ALONE (verde) non viene raggiunto sul node2 o se l’applicazione non viene avviata, analizzare il motivo con il [log del modulo 🖼️](/wp-content/uploads/2024/03/38-module-log-script-second.png) del nodo 2. * Fare clic sull’icona **del registro** 🔍 del `node2` per aprire il registro del modulo e cercare messaggi di errore, ad esempio un checker che rileva un errore e arresta il modulo. * Fare clic su `start_prim` nel log: i messaggi di output dello script vengono visualizzati a destra e possono essere rilevati errori, ad esempio un servizio avviato in modo errato. * Usa SafeKit AI 🤖 per ricevere assistenza con i messaggi di log. ⚠️ * Se tutto è a posto, avviare il node1, che risincronizzerà le directory replicate dal node2. * Se le cose vanno male, arrestare node2 e [forzare l’avvio come primario 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) di node1, che si riavvierà con i suoi dati localmente integri al momento dell’arresto. ℹ️ Tieni presente che hai una 🕒 **[cronologia 🖼️](/wp-content/uploads/2026/05/safekit-console-timeline.png)** che può essere utile per capire cosa succede nel cluster. ℹ️ Trova maggiori dettagli, insieme ai video, nella [formazione online SafeKit](/it/resources/safekit-on-line-training/). ![Arrestare il modulo {{ .Get "app" }} sul server PRIM](/wp-content/uploads/2024/03/16-monitoring-prim-second-stop.png) ### 17.
