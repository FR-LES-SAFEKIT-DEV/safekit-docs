IP 주소(또는 DNS 가상과 관련된 이름 IP 주소). 가상 IP 장애 발생 시 주소가 자동으로 전환됩니다. * `Replicated directories`에서 복제할 디렉터리의 경로를 설정합니다. 두 노드 모두에 존재하고 애플리케이션 데이터를 포함하는지 확인하십시오. 데이터베이스에는 데이터 및 로그 복제가 필수적입니다. 필요에 따라 추가 복제 디렉터리를 생성할 수 있습니다. [Milestone XProtect SQL 복제 🖼️](/wp-content/uploads/2025/05/milestone-replication.png)의 시각적 예를 보려면 이 스크린샷을 참조하세요. * `Checkers`에서는 필요한 경우 프로세스 모니터링, 사용자 정의 검사기, TCP, 핑 또는 분할 브레인 검사기와 같은 검사기를 구성할 수 있습니다. 예를 들어 `Monitored processes/services`에 프로세스 이름이 표시되어 있으면 장애 발생 시 다시 시작 동작으로 모니터링됩니다. 잘못된 프로세스 이름을 구성하면 모듈이 시작 직후 중지됩니다. ⚠️ SQL이 관리 서버에 있는 경우: * [SQL 시스템 데이터베이스](https://learn.microsoft.com/en-us/sql/relational-databases/databases/system-databases)(master.mdf 및 mastlog.ldf 등)는 두 노드의 동일한 디렉터리에 있어야 합니다. 디렉터리는 복제되도록 구성해야 합니다. * 읽기 전용 [SQL 리소스 데이터베이스](https://learn.microsoft.com/en-us/sql/relational-databases/databases/resource-database)가 바이너리에 있으며 장애 조치에 필요하므로 SQL도 두 노드의 파일 시스템에서 동일한 위치에 설치해야 합니다. 이 데이터베이스는 복제할 필요가 없습니다. * Milestone SQL 데이터베이스(.mdf 및 .ldf)는 두 노드의 동일한 디렉터리에 있어야 합니다. 디렉터리는 복제되도록 구성해야 합니다. Milestone 데이터베이스 목록은 이 [문서](https://doc.milestonesys.com/xprotect/xprotect-management-client/2026r1/en/change-the-location-and-name-of-a-sql-server-database.html)를 참조하세요. ℹ️ `Advanced configuration`를 클릭하면 `userconfig.xml` 파일이 표시됩니다. 이 파일은 콘솔에 의해 자동으로 채워지고 다시 시작 스크립트를 사용하여 노드에 배포됩니다. ℹ️ SafeKit 구성을 적용하면 Windows 서비스의 `startup type`이 자동으로 `Manual`로 설정됩니다. 따라서 시스템 부팅 시 서비스가 자동으로 시작되지 않고 모듈 자체가 시작될 때만 시작됩니다. ![{{ .Get "app" }} 모듈 설정을 입력하세요.](/wp-content/uploads/2025/05/05-module-mirror-edit-config-3.png) ### 5. 스크립트 편집(선택 사항) * 이 단계는 선택 사항이며 대부분의 경우 건너뛸 수 있습니다. 이전 단계에서 정의한 서비스를 다시 시작하도록 다시 시작 스크립트가 이미 사전 구성되어 있기 때문입니다. * 따라서 `Next step`를 직접 클릭하세요. * `start_prim.ps1`는 `SERVICES` 목록에 지정된 순서대로 모든 서비스를 시작하고 Milestone이 사용하는 `IIS application pools`를 시작합니다. `stop_prim.ps1`는 역순으로 모든 서비스를 중지합니다. * 또한 `start_prim.ps1`는 각 서비스의 시작을 확인하고 서비스가 올바르게 시작되지 않으면 모듈을 중지합니다. ![{{ .Get "app" }} 모듈 설정을 입력하세요.](/wp-content/uploads/2026/09/28-module-edit-script.png) ### 6. 통신 암호화(선택) * 노드 간 통신 암호화를 유지합니다. ![{{ .Get "app" }} 모듈의 통신 암호화](/wp-content/uploads/2025/05/07-module-encryption-1.png) ### 7. 저장 및 적용 * `Save and apply` 두 노드의 구성 및 스크립트. ![{{ .Get "app" }} 모듈 구성 저장 및 적용](/wp-content/uploads/2025/05/08-module-save-1.png) ### 8. 성공적인 구성 확인 * 두 노드 모두에서 `Success` ✅ 메시지를 확인하고 `Monitor modules`를 클릭하세요. * 한 노드에서 `Failure` ❌ 구성이 발생하면 해당 노드에 대한 ▼ 아코디언을 열고 메시지를 검토합니다. Milestone의 "Windows authentication"이 Active Directory로 구성된 경우 사용자 및 암호 정보는 외부 AD에서 검색됩니다. 장애 조치 후 보조 노드가 동일한 AD에 연결하므로 인증이 자동으로 작동합니다. #### 작업 그룹의 Windows 인증 **구성:** "Security / Roles"에 **BUILTIN/Administrators** 그룹을 추가해야 합니다. **경고:** 작업 그룹에서는 이름이 같아도 각 노드의 로컬 사용자 보안 식별자(SID)가 다릅니다. BUILTIN/Administrators 그룹만 두 노드에서 동일한 SID를 갖습니다. * 이 그룹을 추가하면 장애 조치 후 모든 로컬 관리자 계정으로 보조 노드에서 인증할 수 있습니다. * 추가하지 않으면 SID가 일치하지 않아 보조 노드에서 로컬 Windows 인증이 실패합니다. #### SQL 데이터베이스를 사용한 기본 인증 **구성:** "Basic authentication"을 사용하는 사용자(예: "Admin")를 만듭니다. "Basic authentication"에서는 사용자 자격 증명이 SQL 데이터베이스에 직접 저장됩니다. SafeKit이 SQL 데이터베이스를 보조 노드에 실시간으로 복제하므로 이러한 사용자는 장애 조치 직후 항상 사용 가능합니다. ![Milestone Management Client에서 역할 설정](/wp-content/uploads/2022/07/milestone-management-server-roles.png) ### 14. 노드 2 시작 * ⋯ 상황에 맞는 메뉴가 있는 `Start` 노드 2. * SECOND(녹색) 상태를 기다립니다. ℹ️ * 노드 2는 복제된 디렉터리를 다시 동기화하는 동안(노드 1에서 노드 2로 복사) SECOND(주황색) 상태를 유지합니다. * 복제된 디렉터리에서 다시 동기화할 파일 크기와 네트워크 대역폭에 따라 시간이 걸릴 수 있습니다. * 복사 진행 상황을 보려면 노드 2의 [ 모듈 로그 🖼️](/wp-content/uploads/2024/03/27-module-log-reintegration.png) 및 [복제 리소스 🖼️](/wp-content/uploads/2024/03/26-replication-resources-reintegration.png)를 참조하세요. 로그 메시지에 대한 지원을 받으려면 SafeKit AI 🤖를 사용하세요. ![{{ .Get "app" }} 노드 2를 시작합니다.](/wp-content/uploads/2024/03/13-monitoring-alone-stop-start.png) ### 15. 클러스터가 작동하는지 확인합니다. * 클러스터가 녹색/녹색인지 확인합니다. {{ .Get "app" }} 에서 실행되는 서비스 PRIM 노드에서 실행되고 있지 않습니다. SECOND 노드. * 이 상태에서는 파일 내부의 변경 사항만 실시간으로 복제됩니다. ⚠️ * **녹화 서버**를 가상 IP 주소로 등록합니다. * **Milestone Management Client** 및 **Milestone Smart Client**를 가상 IP 주소에 연결합니다. * {{ .Get "app" }} 서비스의 클라이언트인 구성 요소는 가상 IP 주소로 구성되어야 합니다. 구성은 DNS 이름으로 수행할 수 있습니다(DNS 이름이 생성되어 가상 IP 주소와 연결된 경우). ![{{ .Get "app" }} 노드 2는 SECOND(녹색)입니다.](/wp-content/uploads/2024/03/14-monitoring-prim-second.png) ### 16. 테스트 * 그만해 PRIM 상황에 맞는 메뉴를 아래로 스크롤하고 클릭하여 노드 `Stop`. * 장애 조치(failover)가 있는지 확인합니다. [모듈 로그 🖼️](/wp-content/uploads/2024/03/38-module-log-script-second.png) 노드 2의 * 🔍를 클릭하세요. **로그** 아이콘 `node2` 모듈 로그를 열고 검사기가 오류를 감지하고 모듈을 중지하는 등의 오류 메시지를 찾습니다. * 로그에서 `start_prim`를 클릭하면 스크립트의 출력 메시지가 오른쪽에 표시되고 서비스가 잘못 시작되는 등의 오류가 감지될 수 있습니다. * 로그 메시지에 대한 도움을 받으려면 SafeKit AI 🤖를 사용하세요. ⚠️ * 모든 것이 정상이면 node1에서 시작을 시작합니다. 그러면 node2에서 복제된 디렉터리가 다시 동기화됩니다. * 일이 잘못되면 멈춰라 node2 그리고 [시작을 기본으로 강제 실행 🖼️](/wp-content/uploads/2024/03/10-monitoring-mirror-stop-stop-prim.png) 의 node1, 중지 시점의 로컬 정상 데이터로 다시 시작됩니다. ℹ️ 클러스터에서 발생하는 상황을 이해하는 데 도움이 되는 🕒 **[타임라인 🖼️](/wp-content/uploads/2026/05/safekit-console-timeline.png)**을 사용할 수 있습니다. ℹ️ [SafeKit 온라인 교육](/ko/resources/safekit-on-line-training/)에서 동영상과 함께 자세한 내용을 찾아보세요. ![그만해 {{ .Get "app" }} 모듈 PRIM 서버](/wp-content/uploads/2024/03/16-monitoring-prim-second-stop.png) ### 17. 지원 * 지원을 받으려면 각 노드당 하나씩 2개의 SafeKit `Snapshots`(2개의 .zip 파일)를 가져가세요. ℹ️ [지원에 대한 자세한 내용은 여기에서 확인하세요.](/ko/resources/safekit-support/). ![지원을 위해 {{ .Get "app" }} 스냅샷 가져오기](/wp-content/uploads/2024/03/30-snapshots-mirror.png)
