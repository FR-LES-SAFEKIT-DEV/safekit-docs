Die Benutzer sind mit einer virtuellen IP-Adresse verbunden. Die [virtuelle IP-Adresse](/de/best-practises/how-a-virtual-ip-address-works/) wird lokal auf jedem Server im farm-Mode-Cluster konfiguriert. Der eingehende Datenverkehr an die virtuelle IP-Adresse wird von allen Servern empfangen und von einem Netzwerkfilter im Kernel jedes Servers unter ihnen aufgeteilt. SafeKit erkennt Hardware- und Softwarefehler, konfiguriert Netzwerkfilter im Fehlerfall neu und bietet konfigurierbare Anwendungsprüfer und Wiederherstellungsskripte. ### Lastverteilung in einem Netzwerkfilter {#network-load-balancing} Der Algorithmus für den Netzwerklastenausgleich innerhalb des Netzwerkfilters basiert auf der Identität der Client-Pakete (Client-IP-Adresse, Client-TCP-Port). Abhängig von der Identität des Client-Paket-Eingangs akzeptiert nur ein Filter in einem Server das Paket; die anderen Filter in anderen Servern lehnen es ab. Sobald ein Paket vom Filter auf einem Server akzeptiert wird, werden nur die CPU und der Arbeitsspeicher dieses Servers von der {{ .Get "app" }} Anwendung verwendet, die auf die Anfrage des Clients antwortet. Die Ausgabemeldungen werden direkt vom Anwendungsserver an den Client gesendet. Wenn ein Server ausfällt, konfiguriert das farm Heartbeat-Protokoll die Filter im Netzwerk-Lastenausgleichscluster neu, um den Datenverkehr auf den verbleibenden verfügbaren Servern neu auszubalancieren. ### Zustandsbehaftete oder zustandslose Anwendungen {#stateful-stateless} Bei einer zustandsbehafteten {{ .Get "app" }} Anwendung besteht eine Sitzungsaffinität. Derselbe Client muss über mehrere TCP-Sitzungen mit demselben Server verbunden sein, um seinen Kontext auf dem Server abzurufen. In diesem Fall wird die SafeKit Lastverteilungsregel auf der Client-IP-Adresse konfiguriert. Somit ist derselbe Client immer über mehrere TCP-Sitzungen mit demselben Server verbunden. Und verschiedene Clients werden auf verschiedene Server in der farm verteilt. Bei einer zustandslosen {{ .Get "app" }} Anwendung gibt es keine Sitzungsaffinität. Derselbe Client kann über mehrere TCP-Sitzungen mit verschiedenen Servern in der farm verbunden sein. Es wird kein Kontext lokal auf einem Server von einer Sitzung zur nächsten gespeichert. In diesem Fall wird die SafeKit Lastverteilungsregel auf der TCP-Client-Sitzungsidentität konfiguriert. Diese Konfiguration ist die beste für die Verteilung von Sitzungen zwischen Servern, erfordert jedoch einen TCP-Dienst ohne Sitzungsaffinität. ### Wie konfiguriert man einen SafeKit Cluster im farm-Modus für {{ .Get "app" }} ? {#safekit-farm-cluster-configuration} ![SafeKit Web Console: Cluster-Konfiguration für das Lastausgleichsverfahren im {{ .Get "app" }} und die Verwaltung virtueller IPs.](/wp-content/uploads/2026/01/safekit-farm-cluster-config.png "w:966") Das **SafeKit Cluster im farm Modus** ist für eine hohe Verfügbarkeit und Skalierbarkeit von Diensten ausgelegt. Die Konfiguration konzentriert sich auf die gleichzeitige Verteilung des eingehenden Datenverkehrs auf beide Knoten: * **Lastverteilungsdienste (Registerkarte „Makros“):** Definieren Sie die spezifischen Anwendungsdienste (z. B. Apache, IIS, Nginx), die auf allen Knoten aktiv bleiben sollen. * **Heartbeat-Netzwerk(e):** Kommunikationspfad(e), die verwendet werden, um zu erkennen, ob ein Knoten die farm verlassen hat, wodurch eine sofortige Umverteilung der Last ausgelöst wird. * **Virtuelle IP (Farm VIP):** Im Gegensatz zu einem Mirror-Cluster wird die Farm VIP zwischen den Knoten unter Verwendung eines Kernel-Filteralgorithmus zur Verteilung des Netzwerkverkehrs gemeinsam genutzt. * **Lastausgleichsregeln:** Definieren Sie die Richtlinie für die Datenverkehrsverteilung basierend auf der Quell-IP-Adresse oder dem Port. * **Checkers:** Überwachen Sie den Zustand der Anwendung und lösen Sie einen automatischen Neustart aus, wenn ein Prozessfehler erkannt wird. ### Wie überwacht man einen SafeKit Cluster im farm-Modus für {{ .Get "app" }} ? {#safekit-farm-cluster-monitoring} ![SafeKit Console: Überwachung eines Cluster-Systems im Farm-Modus mit 2 Knoten, das beide {{ .Get "app" }} Knoten im UP Zustand mit aktiver Lastverteilung anzeigt.](/wp-content/uploads/2026/01/safekit-farm-cluster-monitor.png "w:473") Die Überwachung eines Clusters im farm Modus bietet Transparenz über den **Active-Active-** Charakter der Infrastruktur, bei dem alle Knoten zur Leistung der Anwendung beitragen (in diesem Beispiel werden 2 Knoten angezeigt): * **UP Status (50 % auf 2 Knoten):** In einer gesunden farm befinden sich beide Knoten im Status „ UP “ (50 %), was bedeutet, dass beide aktiv Client-Anfragen über die gemeinsam genutzte virtuelle IP-Adresse empfangen und verarbeiten. * **Automatische Neuausrichtung:** Wenn ein Knoten ausfällt, zeigt die Konsole visuell an, dass der verbleibende Knoten 100 % des Datenverkehrs übernimmt. Es gibt keine „Failover“-Verzögerung, da der überlebende Knoten bereits aktiv ist (abgesehen von einer Erkennungszeit von einigen Sekunden). * **Knoteneinfügung:** Wenn ein reparierter Knoten neu gestartet wird, wechselt er von „ STOP “ zu „ UP “ und beginnt automatisch, ohne Eingreifen des Administrators, mit dem Empfang seines Teils der Last. * **Keine Datensynchronisierung:** Beachten Sie, dass in einem Cluster farm-Modus kein „orangener“ Resynchronisierungsstatus vorhanden ist, da die Knoten zustandslos sein oder eine Backend-Datenbank gemeinsam nutzen sollen (die in einem Mirror-Cluster separat geschützt werden kann). Über einfache Status-Symbole hinaus bietet die Benutzeroberfläche eine Ein-Klick-Knotenverwaltung, mit der Sie einen Knoten für geplante Wartungsarbeiten manuell stoppen oder starten können, während die gemeinsam genutzte virtuelle IP-Adresse den Datenverkehr automatisch neu verteilt, ohne die Benutzeraktivität zu unterbrechen.
