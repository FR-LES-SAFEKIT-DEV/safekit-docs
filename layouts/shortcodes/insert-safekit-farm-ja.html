{{ .Get "app" }}ネットワーク負荷分散とフェイルオーバーの実装方法](/wp-content/uploads/2023/02/safekit-up-up-up-300.png "w:300") 前の図では、{{ .Get "app" }} アプリケーションが 3 台のサーバーで実行されています（3 は例であり、2 台以上でもかまいません）。ユーザーは仮想 IP アドレスに接続されています。 [仮想 IP アドレスは](/ja/best-practises/how-a-virtual-ip-address-works/)、farm モードクラスター内の各サーバーにローカルに設定されます。 仮想 IP アドレスへの入力トラフィックは、すべてのサーバーによって受信され、各サーバーのカーネル内のネットワークフィルターによってサーバー間で分割されます。 SafeKit は、ハードウェアおよびソフトウェアの障害を検出し、障害発生時にネットワークフィルタを再構成し、設定可能なアプリケーションチェッカーとリカバリスクリプトを提供します。 ### ネットワークフィルタにおける負荷分散 {#network-load-balancing} ネットワークフィルタ内のネットワーク負荷分散アルゴリズムは、クライアントパケットの ID（クライアント IP アドレス、クライアント TCP ポート）に基づいています。クライアントパケット入力の ID に応じて、サーバー内の 1 つのフィルタのみがパケットを受け入れ、他のサーバー内の他のフィルタはそれを拒否します。 サーバー上のフィルターによってパケットが受け入れられると、クライアントの要求に応答する {{ .Get "app" }} アプリケーションによって、このサーバーの CPU とメモリのみが使用されます。出力メッセージは、アプリケーションサーバーからクライアントに直接送信されます。 サーバーに障害が発生した場合、farm ハートビートプロトコルはネットワーク負荷分散クラスター内のフィルターを再構成し、残りの使用可能なサーバーへのトラフィックを再調整します。 ### ステートフルアプリケーションまたはステートレスアプリケーション {#stateful-stateless} ステートフルな {{ .Get "app" }} では、セッションアフィニティが適用されます。同じクライアントは、サーバー上のコンテキストを取得するために、複数の TCP セッションで同じサーバーに接続する必要があります。この場合、SafeKit ロードバランシングルールはクライアントの IP アドレスに設定されます。したがって、同じクライアントは常に複数の TCP セッションで同じサーバーに接続されます。そして、異なるクライアントは farm 内の異なるサーバーに分散されます。 ステートレスな {{ .Get "app" }} アプリケーションでは、セッションアフィニティはありません。同じクライアントが、複数の TCP セッションで farm 内の異なるサーバーに接続される可能性があります。あるセッションから別のセッションへのコンテキストは、サーバー上にローカルに保存されません。この場合、SafeKit ロードバランシングルールは、TCP クライアントセッション ID で構成されます。この構成は、サーバー間でセッションを分散するのに最適ですが、セッションアフィニティのない TCP サービスが必要です。 ### {{ .Get "app" }} 向けに farm モードで SafeKit クラスターを構成する方法 {#safekit-farm-cluster-configuration} ![SafeKit Web Console: {{ .Get "app" }}ネットワーク負荷分散と仮想 IP 管理のためのクラスター構成。](/wp-content/uploads/2026/01/safekit-farm-cluster-config.png "w:966") **farm モードの SafeKit クラスターは**、サービスの高可用性とスケーラビリティを目的として設計されています。この構成では、両方のノードに同時に着信するトラフィックを分散することに重点を置いています * **ロードバランシングサービス（マクロタブ）：** すべてのノードでアクティブに保つ特定のアプリケーションサービス（例：Apache、IIS、Nginx）を定義します。 * **ハートビートネットワーク：** ノードが farm から離脱したかどうかを検出するために使用される通信パスで、負荷の即時再分配をトリガーします。 * **仮想 IP（Farm VIP）：** mirror クラスターとは異なり、Farm VIP はカーネルフィルタリングアルゴリズムを使用してネットワークトラフィックを分散し、ノード間で共有されます。 * **ロードバランシングルール：** 送信元 IP アドレスまたはポートに基づいてトラフィック分散ポリシーを定義します。 * **チェッカー：** アプリケーションの正常性を監視し、プロセスの障害が検出された場合は自動再起動をトリガーします。 ### {{ .Get "app" }} の farm モードで SafeKit クラスターを監視する方法は？ {#safekit-farm-cluster-monitoring} ![SafeKit コンソール：2 ノードのファームモードクラスターを監視。両方の {{ .Get "app" }} ノードが UP 状態で、アクティブなロードバランシングが有効になっていることを示しています。](/wp-content/uploads/2026/01/safekit-farm-cluster-monitor.png "w:473") farm モードでクラスターを監視すると、インフラストラクチャの**アクティブ/アクティブな**性質を可視化できます。このモードでは、すべてのノードがアプリケーションのパフォーマンスに貢献します（この例では 2 つのノードが表示されます） * **UP 状態 (2 ノードで 50%):** 正常な farm では、両方のノードが「UP」(50%)状態にあり、共有仮想 IP を介してクライアント要求をアクティブに受信および処理していることを意味します。 * **自動リバランス：** 1 つのノードに障害が発生した場合、コンソールには残りのノードがトラフィックの 100% を引き受けていることが視覚的に表示されます。生き残ったノードはすでにアクティブであるため、「フェイルオーバー」による遅延はありません（数秒の検出時間を除く）。 * **ノード挿入：** 修復されたノードが再起動すると、「STOP」から「UP」に移行し、管理者の介入なしに自動的に負荷の一部を受信し始めます。 * **データ同期なし：**farm モードクラスターでは、ノードはステートレスであるか、バックエンドデータベースを共有することが想定されているため、「オレンジ」の再同期状態はありません (バックエンドデータベースは mirror クラスターで個別に保護できます)。 シンプルなステータスアイコンに加え、このインターフェースはワンクリックのノード管理を提供します。計画的なメンテナンスのためにノードを手動で停止または開始できる一方で、共有仮想 IP はユーザーの活動を中断することなく自動的にトラフィックを再分配します。
