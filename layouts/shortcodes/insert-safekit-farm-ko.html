{{/* Shortcode: insert-safekit-farm-ko — 1 instance in 1 file */}} {{/* Parameters: app */}} {{/* Source: content\ko\_index.md */}} ## farm 모드에서 SafeKit 클러스터는 {{ .Get "app" }}와 어떻게 작동하나요? {#safekit-farm-cluster} ### farm 모드 클러스터의 가상 IP 주소 {#virtual-ip-address-farm} ![SafeKit 클러스터가 {{ .Get "app" }} 네트워크 부하 분산 및 장애 조치를 구현하는 방식](/wp-content/uploads/2023/02/safekit-up-up-up-300.png "w:300") 위 그림에서 {{ .Get "app" }} 애플리케이션은 3대의 서버에서 실행됩니다(3대는 예시일 뿐이며, 2대 이상으로 구성할 수 있습니다). 사용자는 가상 IP 주소로 연결됩니다. [가상 IP 주소](/ko/best-practises/how-a-virtual-ip-address-works/)는 farm 모드 클러스터의 각 서버에 로컬로 구성됩니다.\ 가상 IP 주소로 들어오는 트래픽은 모든 서버가 수신하며, 각 서버 커널 내부의 네트워크 필터에 의해 서버 간에 분산됩니다. SafeKit은 하드웨어 및 소프트웨어 장애를 감지하고, 장애 발생 시 네트워크 필터를 재구성하며, 구성 가능한 애플리케이션 검사기와 복구 스크립트를 제공합니다. ### 네트워크 필터에서의 부하 분산 {#network-load-balancing} 네트워크 필터 내부의 부하 분산 알고리즘은 클라이언트 패킷의 식별 정보(클라이언트 IP 주소, TCP 포트)를 기반으로 합니다. 입력된 클라이언트 패킷의 식별 정보에 따라 한 서버의 필터만 패킷을 수용하고, 다른 서버의 필터들은 이를 거부합니다. 패킷이 특정 서버의 필터에 의해 수용되면, 클라이언트 요청에 응답하는 {{ .Get "app" }} 애플리케이션은 해당 서버의 CPU와 메모리만 사용합니다. 출력 메시지는 애플리케이션 서버에서 클라이언트로 직접 전송됩니다. 서버 장애가 발생하면 farm 하트비트 프로토콜이 네트워크 부하 분산 클러스터의 필터를 재구성하여 남아 있는 가용 서버로 트래픽을 다시 분산합니다. ### 스테이트풀 또는 스테이트리스 애플리케이션 {#stateful-stateless} 스테이트풀 {{ .Get "app" }} 애플리케이션의 경우 세션 어피니티가 존재합니다. 동일한 클라이언트가 서버의 컨텍스트를 가져오려면 여러 TCP 세션에 걸쳐 동일한 서버에 연결되어야 합니다. 이 경우 SafeKit 부하 분산 규칙은 클라이언트 IP 주소를 기반으로 구성됩니다. 따라서 동일한 클라이언트는 여러 TCP 세션에서도 항상 동일한 서버로 연결되고, 서로 다른 클라이언트는 farm 내의 여러 서버로 분산됩니다. 스테이트리스 {{ .Get "app" }} 애플리케이션의 경우 세션 어피니티가 없습니다. 동일한 클라이언트가 여러 TCP 세션에서 farm 내의 서로 다른 서버로 연결될 수 있습니다. 세션 간에 서버 로컬에 저장되는 컨텍스트는 없습니다. 이 경우 SafeKit 부하 분산 규칙은 TCP 클라이언트 세션 식별 정보를 기반으로 구성됩니다. 이 구성은 서버 간 세션 분산에 가장 적합하지만, 세션 어피니티가 필요하지 않은 TCP 서비스여야 합니다. ### {{ .Get "app" }}용 farm 모드 SafeKit 클러스터를 구성하는 방법 {#safekit-farm-cluster-configuration} ![SafeKit 웹 콘솔: {{ .Get "app" }} 네트워크 부하 분산 및 가상 IP 관리를 위한 farm 모드 클러스터 구성](/wp-content/uploads/2026/01/safekit-farm-cluster-config.png "w:966") **farm 모드 SafeKit 클러스터**는 서비스의 고가용성과 확장성을 위해 설계되었습니다. 구성은 동시에 두 노드 모두로 유입되는 트래픽을 분산하는 데 중점을 둡니다. * **부하 분산 서비스(Macros 탭):** 모든 노드에서 활성 상태를 유지할 특정 애플리케이션 서비스(예: Apache, IIS, Nginx)를 정의합니다. * **하트비트 네트워크:** 노드가 farm을 이탈했는지 감지하는 데 사용되는 통신 경로로, 이탈 감지 시 즉각적인 부하 재분배를 시작합니다. * **가상 IP (Farm VIP):** `Mirror` 클러스터와 달리, Farm VIP는 네트워크 트래픽을 분산하기 위해 커널 필터링 알고리즘을 사용하여 노드 간에 공유됩니다. * **부하 분산 규칙:** 소스 IP 주소 또는 포트를 기반으로 트래픽 분산 정책을 정의합니다. * **검사기:** 애플리케이션 상태를 모니터링하고 프로세스 장애가 감지되면 자동 재시작을 시작합니다. ### {{ .Get "app" }}용 farm 모드 SafeKit 클러스터를 모니터링하는 방법 {#safekit-farm-cluster-monitoring} ![SafeKit 콘솔: 부하 분산이 활성화되고 두 {{ .Get "app" }} 노드가 UP 상태인 2노드 farm 모드 클러스터 모니터링](/wp-content/uploads/2026/01/safekit-farm-cluster-monitor.png "w:473") farm 모드에서 클러스터를 모니터링하면 모든 노드가 애플리케이션 성능에 기여하는 인프라의 **액티브-액티브** 특성을 확인할 수 있습니다(이 예시에서는 2개의 노드가 표시됨). * **UP 상태(노드 2대에서 각각 50%):** 정상적인 farm에서는 두 노드가 모두 "UP"(50%) 상태로, 공유 가상 IP를 통해 클라이언트 요청을 능동적으로 수신하고 처리합니다. * **자동 재분배:** 한 노드에 장애가 발생하면 콘솔에서 나머지 노드가 트래픽의 100%를 처리하는 모습을 확인할 수 있습니다. 잔존 노드가 이미 활성 상태이므로 몇 초간의 장애 감지 시간을 제외하면 장애 조치 지연이 없습니다. * **노드 추가:** 복구된 노드가 다시 시작되면 "STOP"에서 "UP" 상태로 전환되고, 관리자의 개입 없이 자동으로 할당된 트래픽을 수신하기 시작합니다. * **데이터 동기화 없음:** farm 모드 클러스터에서는 노드가 스테이트리스이거나 백엔드 데이터베이스를 공유하는 것으로 간주하므로 "주황색" 재동기화 상태가 없습니다(해당 데이터베이스는 `Mirror` 클러스터에서 별도로 보호할 수 있습니다). 단순한 상태 아이콘 확인을 넘어, 인터페이스에서 클릭 한 번으로 노드를 관리할 수 있습니다. 이를 통해 계획된 유지보수를 위해 노드를 수동으로 중지하거나 시작할 수 있으며, 그동안 공유 가상 IP는 사용자 활동을 중단시키지 않고 트래픽을 자동으로 재분배합니다.
