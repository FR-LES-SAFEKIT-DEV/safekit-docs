Gebruikers zijn verbonden met een virtueel IP-adres. Het [virtuele IP-adres](/nl/best-practises/how-a-virtual-ip-address-works/) wordt lokaal geconfigureerd op elke server in het cluster in de farm. Het inkomende verkeer naar het virtuele IP-adres wordt ontvangen door alle servers en over hen verdeeld door een netwerkfilter in de kernel van elke server. SafeKit detecteert hardware- en softwarefouten, reconfigureert netwerkfilters in geval van een storing en biedt configureerbare applicatiecontroleprogramma's en herstelscripts. ### Taakverdeling in een netwerkfilter {#network-load-balancing} Het netwerkbelastingverdelingsalgoritme in het netwerkfilter is gebaseerd op de identiteit van de clientpakketten (client-IP-adres, client-TCP-poort). Afhankelijk van de identiteit van de clientpakketinvoer accepteert slechts één filter op een server het pakket; de andere filters op andere servers weigeren het. Zodra een pakket door het filter op een server is geaccepteerd, worden alleen de CPU en het geheugen van deze server gebruikt door de {{ .Get "app" }} applicatie die reageert op het verzoek van de client. De uitvoerberichten worden rechtstreeks van de applicatieserver naar de client verzonden. Als een server uitvalt, reconfigureert het farm heartbeatprotocol de filters in het netwerkloadbalancingcluster om het verkeer opnieuw te verdelen over de resterende beschikbare servers. ### Toepassingen met of zonder status {#stateful-stateless} Bij een stateful {{ .Get "app" }} applicatie is er sprake van sessieaffiniteit. Dezelfde client moet verbonden zijn met dezelfde server via meerdere TCP-sessies om de context op de server op te halen. In dit geval wordt de SafeKit taakverdelingsregel geconfigureerd op het IP-adres van de client. Zo is dezelfde client altijd verbonden met dezelfde server via meerdere TCP-sessies. En verschillende clients worden verdeeld over verschillende servers in de farm. Bij een stateless {{ .Get "app" }} applicatie is er geen sessieaffiniteit. Dezelfde client kan op meerdere TCP-sessies verbonden zijn met verschillende servers in de farm. Er wordt geen context lokaal opgeslagen op een server van de ene sessie naar de andere. In dit geval wordt de SafeKit taakverdelingsregel geconfigureerd op de TCP-clientsessie-identiteit. Deze configuratie is de beste voor het verdelen van sessies tussen servers, maar vereist een TCP-service zonder sessieaffiniteit. ### Hoe configureer ik een SafeKit cluster in farm voor {{ .Get "app" }} ? {#safekit-farm-cluster-configuration} ![SafeKit Web Console: Clusterconfiguratie voor netwerklastverdeling {{ .Get "app" }} en virtueel IP-beheer.](/wp-content/uploads/2026/01/safekit-farm-cluster-config.png "w:966") Het **SafeKit cluster in farm** is ontworpen voor hoge beschikbaarheid en schaalbaarheid van services. De configuratie richt zich op het distribueren van inkomend verkeer over beide knooppunten tegelijkertijd: * **Load Balanced Services (tabblad Macro's):** Definieer de specifieke applicatieservices (bijv. Apache, IIS, Nginx) die op alle knooppunten actief moeten blijven. * **Heartbeat-netwerk(en):** Communicatiepad(en) die worden gebruikt om te detecteren of een knooppunt de farm heeft verlaten, waardoor een onmiddellijke herverdeling van de belasting wordt geactiveerd. * **Virtueel IP (Farm VIP):** In tegenstelling tot een mirror-cluster wordt de Farm VIP gedeeld tussen knooppunten met behulp van een kernel-filteralgoritme om het netwerkverkeer te verdelen. * **Taakverdelingsregels:** definieer het verkeersdistributiebeleid op basis van het bron-IP-adres of de poort. * **Checkers:** controleer de status van de toepassing en start deze automatisch opnieuw op als er een procesfout wordt gedetecteerd. ### Hoe monitor je een SafeKit cluster in farm voor {{ .Get "app" }} ? {#safekit-farm-cluster-monitoring} ![SafeKit Console: Monitoring van een cluster in farmmodus met 2 knooppunten, waarbij beide {{ .Get "app" }} knooppunten in UP status staan met actieve taakverdeling.](/wp-content/uploads/2026/01/safekit-farm-cluster-monitor.png "w:473") Het monitoren van een cluster in farm modus biedt inzicht in de **Active-Active-** aard van de infrastructuur, waarbij alle knooppunten bijdragen aan de prestaties van de toepassing (in dit voorbeeld worden 2 knooppunten weergegeven): * **UP status (50% op 2 knooppunten):** In een gezonde farm bevinden beide knooppunten zich in de " UP "-status (50%), wat betekent dat ze beide actief clientverzoeken ontvangen en verwerken via het gedeelde virtuele IP-adres. * **Automatische herverdeling:** Als één knooppunt uitvalt, toont de console visueel dat het resterende knooppunt 100% van het verkeer verwerkt. Er is geen "failover"-vertraging, aangezien het overgebleven knooppunt al actief is (afgezien van een detectietijd van een paar seconden). * **Knooppuntinvoeging:** Wanneer een hersteld knooppunt opnieuw wordt gestart, gaat het van " STOP " naar " UP " en begint het automatisch met het ontvangen van zijn deel van de belasting zonder tussenkomst van de beheerder. * **Geen gegevenssynchronisatie:** Merk op dat er in een cluster in farm geen "oranje" resynchronisatiestatus is, aangezien knooppunten stateless zijn of een backend-database delen (die afzonderlijk kan worden beschermd in een mirror-cluster). Naast eenvoudige statuspictogrammen biedt de interface nodebeheer met één klik, waarmee u een node handmatig kunt stoppen of starten voor gepland onderhoud, terwijl het gedeelde virtuele IP-adres het verkeer automatisch opnieuw verdeelt zonder de gebruikersactiviteit te onderbreken.
