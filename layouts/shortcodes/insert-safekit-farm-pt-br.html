Os usuários estão conectados a um endereço IP virtual. O [endereço IP virtual](/pt-br/best-practises/how-a-virtual-ip-address-works/) é configurado localmente em cada servidor no cluster em modo farm. O tráfego de entrada para o endereço IP virtual é recebido por todos os servidores e dividido entre eles por um filtro de rede dentro do kernel de cada servidor. SafeKit detecta falhas de hardware e software, reconfigura os filtros de rede em caso de falha e oferece verificadores de aplicativos configuráveis e scripts de recuperação. ### Balanceamento de carga em um filtro de rede {#network-load-balancing} O algoritmo de balanceamento de carga da rede dentro do filtro de rede é baseado na identidade dos pacotes do cliente (endereço IP do cliente, porta TCP do cliente). Dependendo da identidade da entrada do pacote do cliente, apenas um filtro em um servidor aceita o pacote; os outros filtros em outros servidores o rejeitam. Uma vez que um pacote é aceito pelo filtro em um servidor, apenas a CPU e a memória desse servidor são usadas pelo {{ .Get "app" }} que responde à solicitação do cliente. As mensagens de saída são enviadas diretamente do servidor de aplicativos para o cliente. Se um servidor falhar, o protocolo de pulsação farm reconfigura os filtros no cluster de balanceamento de carga da rede para reequilibrar o tráfego nos servidores disponíveis restantes. ### Aplicações com ou sem estado {#stateful-stateless} Com um {{ .Get "app" }} estado, há afinidade de sessão. O mesmo cliente deve estar conectado ao mesmo servidor em várias sessões TCP para recuperar seu contexto no servidor. Nesse caso, a regra de balanceamento de carga SafeKit é configurada no endereço IP do cliente. Assim, o mesmo cliente está sempre conectado ao mesmo servidor em várias sessões TCP. E diferentes clientes são distribuídos entre diferentes servidores no farm. Com um aplicativo {{ .Get "app" }} sem estado, não há afinidade de sessão. O mesmo cliente pode estar conectado a diferentes servidores no farm em várias sessões TCP. Não há contexto armazenado localmente em um servidor de uma sessão para outra. Nesse caso, a regra de balanceamento de carga SafeKit é configurada na identidade da sessão do cliente TCP. Essa configuração é a melhor para distribuir sessões entre servidores, mas requer um serviço TCP sem afinidade de sessão. ### Como configurar um cluster SafeKit no modo farm para {{ .Get "app" }} ? {#safekit-farm-cluster-configuration} ![Console Web SafeKit: configuração de cluster para balanceamento de carga de rede {{ .Get "app" }} e gerenciamento de IP virtual.](/wp-content/uploads/2026/01/safekit-farm-cluster-config.png "w:966") O **cluster SafeKit no modo farm** foi projetado para alta disponibilidade e escalabilidade de serviços. A configuração se concentra em distribuir o tráfego de entrada em ambos os nós simultaneamente: * **Serviços com balanceamento de carga (guia Macros):** defina os serviços de aplicativos específicos (por exemplo, Apache, IIS, Nginx) a serem mantidos ativos em todos os nós. * **Rede(s) de pulsações:** Caminho(s) de comunicação usado(s) para detectar se um nó saiu da farm, acionando uma redistribuição imediata da carga. * **IP Virtual (VIP Farm):** Ao contrário de um cluster mirror, o VIP Farm é compartilhado entre os nós usando um algoritmo de filtragem do kernel para distribuir o tráfego de rede. * **Regras de balanceamento de carga:** defina a política de distribuição de tráfego com base no endereço IP de origem ou na porta. * **Verificadores:** Monitore a integridade do aplicativo e acione a reinicialização automática se for detectada uma falha no processo. ### Como monitorar um cluster SafeKit em modo farm para {{ .Get "app" }} ? {#safekit-farm-cluster-monitoring} ![Console SafeKit: Monitoramento de um cluster em modo farm de 2 nós, mostrando ambos os nós {{ .Get "app" }} no estado UP com balanceamento de carga ativo.](/wp-content/uploads/2026/01/safekit-farm-cluster-monitor.png "w:473") O monitoramento de um cluster no modo farm fornece visibilidade sobre a natureza **Ativo-Ativo** da infraestrutura, onde todos os nós contribuem para o desempenho do aplicativo (mostrando 2 nós neste exemplo): * **Estado UP (50% em 2 nós):** Em uma farm íntegra, ambos os nós estão no estado " UP " (50%), o que significa que ambos estão recebendo e processando ativamente as solicitações do cliente por meio do IP virtual compartilhado. * **Rebalanceamento automático:** se um nó falhar, o console mostra visualmente o nó restante recebendo 100% do tráfego. Não há atraso de "failover", pois o nó sobrevivente já está ativo (além de um tempo de detecção de alguns segundos). * **Inserção de nó:** quando um nó reparado é reiniciado, ele transita de " STOP " para " UP " e começa automaticamente a receber sua parte da carga sem intervenção do administrador. * **Sem sincronização de dados:** observe que, em um cluster no modo farm, não há estado de resincronização "Laranja", pois espera-se que os nós sejam sem estado ou compartilhem um banco de dados de backend (que pode ser protegido separadamente em um cluster mirror). Além de simples ícones de status, a interface fornece gerenciamento de nó com um clique, permitindo que você pare ou inicie manualmente um nó para manutenção planejada, enquanto o IP virtual compartilhado redistribui automaticamente o tráfego sem interromper a atividade do usuário.
