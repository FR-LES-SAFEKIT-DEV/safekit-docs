Os utilizadores estão ligados a um endereço IP virtual. O [endereço IP virtual](/pt-pt/best-practises/how-a-virtual-ip-address-works/) é configurado localmente em cada servidor do cluster em modo de farm. O tráfego de entrada para o endereço IP virtual é recebido por todos os servidores e distribuído entre eles por um filtro de rede dentro do kernel de cada servidor. SafeKit deteta falhas de hardware e software, reconfigura os filtros de rede em caso de falha e oferece verificadores de aplicações configuráveis e scripts de recuperação. ### Balanceamento de carga num filtro de rede {#network-load-balancing} O algoritmo de balanceamento de carga da rede, dentro do filtro de rede, baseia-se na identidade dos pacotes do cliente (endereço IP do cliente, porta TCP do cliente). Dependendo da identidade da entrada do pacote do cliente, apenas um filtro num servidor aceita o pacote; os outros filtros noutros servidores rejeitam-no. Uma vez que um pacote é aceite pelo filtro num servidor, apenas a CPU e a memória desse servidor são utilizadas pela {{ .Get "app" }} que responde ao pedido do cliente. As mensagens de saída são enviadas diretamente do servidor de aplicações para o cliente. Se um servidor falhar, o protocolo de pulsações farm reconfigura os filtros no cluster de balanceamento de carga da rede para reequilibrar o tráfego nos servidores disponíveis restantes. ### Aplicações com ou sem estado {#stateful-stateless} Com uma aplicação {{ .Get "app" }} persistente, existe afinidade de sessão. O mesmo cliente deve estar ligado ao mesmo servidor em várias sessões TCP para recuperar o seu contexto no servidor. Neste caso, a regra de balanceamento de carga SafeKit é configurada no endereço IP do cliente. Assim, o mesmo cliente está sempre ligado ao mesmo servidor em várias sessões TCP. E diferentes clientes são distribuídos por diferentes servidores no farm. Com uma {{ .Get "app" }} stateless, não existe afinidade de sessão. O mesmo cliente pode estar ligado a diferentes servidores no farm em múltiplas sessões TCP. Não existe contexto armazenado localmente num servidor de uma sessão para outra. Neste caso, a regra de balanceamento de carga SafeKit é configurada na identidade da sessão do cliente TCP. Esta configuração é a que melhor distribui as sessões entre os servidores, mas requer um serviço TCP sem afinidade de sessão. ### Como configurar um cluster SafeKit em modo farm para {{ .Get "app" }} ? {#safekit-farm-cluster-configuration} ![Consola Web SafeKit: Configuração de cluster para balanceamento de carga da rede {{ .Get "app" }} e gestão de IP virtual.](/wp-content/uploads/2026/01/safekit-farm-cluster-config.png "w:966") O **cluster SafeKit em modo farm** foi concebido para alta disponibilidade e escalabilidade de serviços. A configuração foca-se na distribuição do tráfego de entrada por ambos os nós em simultâneo: * **Serviços com Balanceamento de Carga (separador Macros):** Defina os serviços de aplicação específicos (por exemplo, Apache, IIS, Nginx) a serem mantidos ativos em todos os nós. * **Rede(s) de pulsações:** Caminho(s) de comunicação utilizado(s) para detetar se um nó saiu da farm, acionando uma redistribuição imediata da carga. * **IP Virtual (VIP Farm):** Ao contrário de um cluster mirror, o VIP Farm é partilhado entre os nós, utilizando um algoritmo de filtragem do kernel para distribuir o tráfego de rede. * **Regras de Balanceamento de Carga:** Defina a política de distribuição de tráfego com base no endereço IP de origem ou na porta. * **Verificadores:** Monitorize o estado da aplicação e acione o reinício automático se for detetado um erro de processo. ### Como monitorizar um cluster SafeKit em modo farm para {{ .Get "app" }} ? {#safekit-farm-cluster-monitoring} ![Consola SafeKit: Monitorização de um cluster em modo farm de 2 nós, mostrando ambos os nós {{ .Get "app" }} no estado UP com balanceamento de carga ativo.](/wp-content/uploads/2026/01/safekit-farm-cluster-monitor.png "w:473") A monitorização de um cluster em modo farm proporciona visibilidade sobre a natureza **Ativo-Ativo** da infraestrutura, onde todos os nós contribuem para o desempenho da aplicação (mostrando 2 nós neste exemplo): * **Estado UP (50% em 2 nós):** Numa farm saudável, ambos os nós estão no estado " UP " (50%), o que significa que estão ambos a receber e a processar ativamente pedidos de clientes através do IP Virtual partilhado. * **Reequilíbrio Automático:** Se um nó falhar, a consola mostra visualmente o nó restante a receber 100% do tráfego. Não há atraso de "failover", pois o nó sobrevivente já está ativo (além de um tempo de deteção de alguns segundos). * **Inserção de Nó:** Quando um nó reparado é reiniciado, ele transita de " STOP " para " UP " e começa automaticamente a receber a sua parte da carga sem intervenção do administrador. * **Sem Sincronização de Dados:** Tenha em atenção que, num cluster em modo de farm, não existe o estado de resincronização "Laranja", uma vez que os nós são esperados como sem estado ou partilhando uma base de dados de backend (que pode ser protegida separadamente num cluster mirror). Além de simples ícones de estado, a interface oferece gestão de nós com um clique, permitindo-lhe parar ou iniciar manualmente um nó para manutenção planeada, enquanto o IP Virtual partilhado redistribui automaticamente o tráfego sem interromper a atividade do utilizador.
