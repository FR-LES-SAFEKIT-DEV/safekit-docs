{{/* Shortcode: insert-safekit-farm-pt-pt — 1 instance in 1 file */}} {{/* Parameters: app */}} {{/* Source: content\pt-pt\_index.md */}} ## Como funciona o cluster SafeKit em modo farm com {{ .Get "app" }}? {#safekit-farm-cluster} ### Endereço IP virtual num cluster em modo farm {#virtual-ip-address-farm} ![Como o cluster SafeKit implementa o equilíbrio de carga de rede e o failover de {{ .Get "app" }} em modo farm](/wp-content/uploads/2023/02/safekit-up-up-up-300.png "w:300") Na figura anterior, a aplicação {{ .Get "app" }} está a ser executada em 3 servidores (3 é um exemplo, podem ser 2 ou mais). Os utilizadores estão ligados a um endereço IP virtual. O [endereço IP virtual](/pt-pt/best-practises/how-a-virtual-ip-address-works/) está configurado localmente em cada servidor no cluster em modo farm.\ Todos os servidores recebem o tráfego de entrada destinado ao endereço IP virtual, que é distribuído entre eles por um filtro de rede no kernel de cada servidor. O SafeKit deteta falhas de hardware e software, reconfigura os filtros de rede em caso de falha e disponibiliza verificadores de aplicações e scripts de recuperação configuráveis. ### Equilíbrio de carga num filtro de rede {#network-load-balancing} O algoritmo de equilíbrio de carga de rede no filtro de rede baseia-se na identidade dos pacotes do cliente (endereço IP e porta TCP do cliente). Dependendo da identidade do pacote de entrada do cliente, apenas um filtro num servidor aceita o pacote; os outros filtros nos restantes servidores rejeitam-no. Assim que um pacote é aceite pelo filtro num servidor, apenas a CPU e a memória desse servidor são utilizadas pela aplicação {{ .Get "app" }} que responde ao pedido do cliente. As mensagens de saída são enviadas diretamente do servidor da aplicação para o cliente. Se um servidor falhar, o protocolo de heartbeat de farm reconfigura os filtros no cluster de equilíbrio de carga de rede para redistribuir o tráfego pelos servidores restantes disponíveis. ### Aplicações com ou sem estado {#stateful-stateless} Com uma aplicação {{ .Get "app" }} com estado, existe afinidade de sessão. O mesmo cliente deve estar ligado ao mesmo servidor em múltiplas sessões TCP para recuperar o seu contexto no servidor. Neste caso, a regra de equilíbrio de carga do SafeKit é configurada com base no endereço IP do cliente. Assim, o mesmo cliente está sempre ligado ao mesmo servidor em múltiplas sessões TCP, enquanto clientes diferentes são distribuídos por servidores diferentes na farm. Com uma aplicação {{ .Get "app" }} sem estado, não existe afinidade de sessão. O mesmo cliente pode estar ligado a diferentes servidores da farm em múltiplas sessões TCP. Não há contexto armazenado localmente num servidor de uma sessão para outra. Neste caso, a regra de equilíbrio de carga do SafeKit é configurada com base na identidade da sessão TCP do cliente. Esta configuração é a melhor para distribuir sessões entre servidores, mas requer um serviço TCP sem afinidade de sessão. ### Como configurar um cluster SafeKit em modo farm para {{ .Get "app" }}? {#safekit-farm-cluster-configuration} ![Consola Web SafeKit: configuração do cluster em modo farm para o equilíbrio de carga de rede de {{ .Get "app" }} e a gestão do IP virtual.](/wp-content/uploads/2026/01/safekit-farm-cluster-config.png "w:966") O **cluster SafeKit em modo farm** foi concebido para a alta disponibilidade e escalabilidade de serviços. A configuração foca-se na distribuição simultânea do tráfego de entrada pelos dois nós: * **Serviços com equilíbrio de carga (separador Macros):** Defina os serviços de aplicação específicos (por exemplo, Apache, IIS, Nginx) que devem ser mantidos ativos em todos os nós. * **Rede(s) de heartbeat:** Caminho(s) de comunicação utilizado(s) para detetar se um nó saiu da farm, acionando uma redistribuição imediata da carga. * **IP virtual (Farm VIP):** Ao contrário de um cluster `Mirror`, o Farm VIP é partilhado entre os nós através de um algoritmo de filtragem do kernel para distribuir o tráfego de rede. * **Regras de equilíbrio de carga:** Defina a política de distribuição de tráfego com base no endereço IP de origem ou na porta. * **Verificadores:** Monitorizam o estado de saúde da aplicação e acionam o reinício automático se for detetada uma falha num processo. ### Como monitorizar um cluster SafeKit em modo farm para {{ .Get "app" }}? {#safekit-farm-cluster-monitoring} ![Consola SafeKit: monitorização de um cluster de 2 nós em modo farm, com ambos os nós de {{ .Get "app" }} no estado UP e o equilíbrio de carga ativo.](/wp-content/uploads/2026/01/safekit-farm-cluster-monitor.png "w:473") A monitorização de um cluster em modo farm oferece visibilidade sobre a natureza **Ativo-Ativo** da infraestrutura, onde todos os nós contribuem para o desempenho da aplicação (neste exemplo são apresentados 2 nós): * **Estado UP (50% em 2 nós):** Numa farm saudável, ambos os nós estão no estado "UP" (50%), o que significa que recebem e processam ativamente os pedidos dos clientes através do IP virtual partilhado. * **Reequilíbrio automático:** Se um nó falhar, a consola mostra visualmente o nó restante a assumir 100% do tráfego. Não existe atraso de failover, uma vez que o nó sobrevivente já está ativo (além de alguns segundos para a deteção). * **Adição de um nó:** Quando um nó reparado é reiniciado, passa do estado "STOP" para "UP" e começa automaticamente a receber a sua parte da carga, sem intervenção do administrador. * **Sem sincronização de dados:** Note que, num cluster em modo farm, não existe o estado de ressincronização "Laranja", uma vez que se pressupõe que os nós não têm estado ou partilham uma base de dados de backend (que pode ser protegida separadamente num cluster `Mirror`). Para além dos ícones de estado simples, a interface disponibiliza a gestão de nós com um único clique, permitindo-lhe parar ou iniciar manualmente um nó para manutenção planeada, enquanto o IP virtual partilhado redistribui automaticamente o tráfego sem interromper a atividade dos utilizadores.
