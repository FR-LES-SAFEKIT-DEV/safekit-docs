Mentre l’HA a livello di VM è più facile da configurare, l’HA a livello di applicazione è indipendente dall’hypervisor e può essere eseguito in ambienti fisici, virtuali o cloud. ### Quali sono i vantaggi distintivi di SafeKit per l’alta disponibilità di Hyper-V rispetto ai prodotti della concorrenza? {#what-are-the-distinctive-advantages-of-safekit-for-hyper-v-high-availability-compared-to-competitors} SafeKit si differenzia dalle tradizionali soluzioni di clustering Hyper-V grazie alla sua **architettura "shared-nothing"** e alla gestione semplificata. Ogni macchina virtuale replicata viene eseguita in un modulo mirror indipendente (con un massimo di 32 macchine virtuali) con un server primario che può essere il server Hyper-V 1 o il server Hyper-V 2. ### 1. Come funziona la replica in tempo reale per {{ .Get "app" }} ? {#1-how-does-real-time-replication-work-for--get-app-} Il server 1 (PRIM) esegue l’ {{ .Get "app" }} VM (macchina virtuale). SafeKit replica in tempo reale i file della VM (disco rigido virtuale, configurazione della VM). Solo le modifiche apportate ai file vengono replicate sulla rete. ![Replica di file a livello di byte in un cluster {{ .Get "app" }} mirror](/wp-content/uploads/2023/02/safekit-prim-second-300.png "w:300") La replica è [sincrona](/it/best-practises/synchronous-replication-vs-asynchronous-replication/) e non comporta alcuna perdita di dati in caso di errore, a differenza della replica asincrona. È sufficiente configurare il nome della directory della VM in SafeKit. Non ci sono prerequisiti sull’organizzazione del disco. La directory può essere situata nel disco di sistema. ### 2. Cosa succede durante un failover automatico {{ .Get "app" }} ? {#2-what-happens-during-an-automatic--get-app--failover} Quando il Server 1 si guasta, il Server 2 subentra. SafeKit riavvia la VM {{ .Get "app" }} sul Server 2. Hyper-V trova i file replicati da SafeKit aggiornati sul Server 2. La VM continua a essere eseguita sul Server 2 modificando localmente i suoi file, che non vengono più replicati sul Server 1. ![Failover {{ .Get "app" }} in un cluster mirror](/wp-content/uploads/2023/02/safekit-stop-alone-300.png "w:300") Il tempo di failover è pari al tempo di rilevamento dei guasti (impostato su 30 secondi per impostazione predefinita) più il tempo di riavvio della VM. ### 3. Come vengono sincronizzati i dati dopo un errore {{ .Get "app" }} ? {#3-how-is-data-synchronized-after-a--get-app--failure} Il failback prevede il riavvio del Server 1 dopo aver risolto il problema che ne ha causato il guasto. SafeKit risincronizza automaticamente i file della VM. ![Failback in un cluster {{ .Get "app" }} mirror](/wp-content/uploads/2023/02/safekit-resynchro-alone-300.png "w:300") Il failback avviene senza interrompere la VM {{ .Get "app" }}, che può continuare a essere eseguita sul server 2. ### 4. Come si ripristina il normale funzionamento {{ .Get "app" }} ? {#4-how-is-normal--get-app--operation-restored} Dopo la reintegrazione, i file della VM sono nuovamente in modalità mirror, come nel passaggio 1. Il sistema è tornato in modalità ad alta disponibilità, con la VM {{ .Get "app" }} in esecuzione su Server 2 e SafeKit che replica gli aggiornamenti dei file su Server 1. ![Ritorno al normale funzionamento in un cluster {{ .Get "app" }} mirror](/wp-content/uploads/2023/02/safekit-second-prim-300.png "w:300") Se l’amministratore desidera che la VM venga eseguita sul Server 1, ciò può essere fatto manualmente tramite la console web al momento opportuno, o automaticamente tramite la configurazione. ### Come configurare un cluster {{ .Get "app" }} SafeKit ? {#safekit-mirror-cluster-configure} ![SafeKit Web Console: dashboard del cluster {{ .Get "app" }} a 2 nodi per la replica di macchine virtuali e il failover automatico.](/wp-content/uploads/2024/03/19-module-hyperv-edit-config-1.png "w:694") La **console web SafeKit** fornisce un’interfaccia intuitiva per configurare l’alta disponibilità delle applicazioni critiche. In pochi passaggi, è possibile configurare un **cluster {{ .Get "app" }} SafeKit** per garantire la continuità aziendale: * Inserire in `VM_PATH` il percorso principale della directory replicata (D:/Repli-Hyper-V) in cui si trovano i file della VM {{ .Get "app" }}. * Inserire in `VM_NAME` il nome della macchina virtuale {{ .Get "app" }} (VM1). Nota: se viene inserita `VM1`, `D:/Repli-Hyper-V/VM1/` verrà replicata e VM1 verrà riavviata automaticamente utilizzando i comandi Hyper-V. Il cluster SafeKit include un [verificatore di split-brain dedicato per risolvere i problemi di isolamento della rete]( "Dettagli tecnici sul heartbeat e sulla prevenzione del split-brain") senza la necessità di una terza macchina witness o di una rete heartbeat aggiuntiva. ### Come monitorare un cluster {{ .Get "app" }} SafeKit ? {#safekit-mirror-cluster-monitoring} ![Console Web SafeKit: monitoraggio in tempo reale di un cluster {{ .Get "app" }} mirror a 2 nodi che mostra gli stati PRIM e SECOND con replica dati attiva.](/wp-content/uploads/2024/03/14-monitoring-prim-second.png "w:604") La **console di gestione SafeKit** offre una visione unificata della tua infrastruttura ad alta disponibilità. Consente agli amministratori di monitorare lo **stato operativo** del cluster e di tracciare la sincronizzazione dei dati in tempo reale. Per un cluster {{ .Get "app" }} a 2 nodi, la console mostra chiaramente i ruoli di ciascun server: * **PRIM (primario):** il nodo attivo che attualmente esegue la VM e l’applicazione. Esegue scritture sui file della VM nell’archiviazione locale e la replica in tempo reale sul nodo secondario. * **SECOND:** il nodo di standby riceve aggiornamenti sincroni a livello di byte. È pronto a subentrare immediatamente in caso di errore del nodo primario. * **Stato ALONE:** avvisa visivamente quando il cluster è in esecuzione su un singolo nodo (ad esempio, durante la manutenzione o dopo un errore), indicando che la ridondanza è temporaneamente persa. * **Avanzamento della risincronizzazione:** quando un nodo guasto si riprende, il suo stato diventa arancione durante la reintegrazione dei dati in background, garantendo l’assenza di tempi di inattività durante la fase di "ritorno alla normalità". Oltre alle semplici icone di stato, l’interfaccia fornisce **un’orchestrazione di failover con un solo clic**, consentendo di riassegnare manualmente il ruolo primario per la manutenzione pianificata, garantendo al contempo la disponibilità continua per l’attività dell’utente. Si noti che se si distribuiscono più VM per la replica e il failover, si avranno più widget PRIM/SECOND.
