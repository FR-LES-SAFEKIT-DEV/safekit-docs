SafeKit offre alta disponibilità a {{ .Get "app" }} tra due server di qualsiasi marca. Questo articolo spiega come implementare rapidamente un cluster {{ .Get "app" }} senza storage condiviso su un SAN e senza competenze specifiche.. Hai la possibilità di migrare ogni macchina virtuale tra entrambi i server con la console SafeKit e quindi bilanciare il carico in un **cluster attivo-attivo**. ### Devo scegliere l'alta disponibilità a livello di applicazione o a livello di macchina virtuale (VM)?? Con SafeKit, hai la flessibilità di scegliere il modello di ridondanza più adatto alle tue esigenze.. **Ridondanza di livello VM** (per {{ .Get "app" }} o Hyper-V) è il più semplice da implementare poiché replica l'intera macchina virtuale, senza richiedere alcuna conoscenza dell'applicazione interna. Alternativa, **ridondanza a livello di applicazione** è più granulare; replica solo cartelle di dati specifiche e riavvia i servizi dell'applicazione anziché l'intero sistema operativo.. MentreVM-livelloHAè più facile da configurare, a livello di applicazioneHAè indipendente dall'hypervisor e può essere eseguito in ambienti fisici, virtuali o cloud.. ### Quali sono i vantaggi distintivi di SafeKit per l'elevata disponibilità di {{ .Get "app" }} rispetto ai concorrenti?? SafeKit si differenzia dalle tradizionali soluzioni di clustering {{ .Get "app" }} attraverso il suo **architettura shared-nothing** e una gestione semplificata. Mentre la maggior parte dei concorrenti richiede complessi file system distribuiti (come Ceph) o un SAN centrale per gestire il failover di VM, SafeKit fornisce: * **Replica integrata in tempo reale:** La sincronizzazione dei dati è integrata direttamente nella soluzione, garantendo che le macchine virtuali {{ .Get "app" }} vengano replicate in modo sincrono senza la necessità di gestire un livello di archiviazione separato.. * **Clustering semplificato a 2 nodi:** A differenza delle soluzioni enterprise che raccomandano un quorum "witness" a 3 nodi, SafeKit offre la massima alta disponibilità con soli due server ridondanti.. [Scopri di più sul nostro heartbeat e sul meccanismo di quorum.](/it/best-practises/heartbeat-failover-quorum-windows-linux-cluster/). * **Gestione unificata:** Gli amministratori possono gestire il failover, la replica e il bilanciamento del carico di VM tramite un'unica console SafeKit, rendendola accessibile anche ai team privi di competenze specialistiche in materia di clustering.. * **Controllori personalizzati:** SafeKit va oltre il monitoraggio hardware; utilizza **dama di controllo personalizzata** Il sistema rileva se un VM si è bloccato, attivando automaticamente un riavvio locale o un failover sul nodo ridondante. Il sistema è inoltre altamente estensibile, consentendo la facile integrazione di nuovi controlli personalizzati definiti dall'utente e adattati al vostro specifico ambiente.. ### In che modo SafeKit riduce il TCO (Costo totale di proprietà) rispetto alle soluzioni di tipo VMware?? Ogni macchina virtuale replicata viene eseguita in un modulo mirror indipendente (con un massimo di 32 macchine virtuali) con un server primario che può essere il server {{ .Get "app" }} 1 o il server {{ .Get "app" }} 2.. ### 1. Come funziona la replica in tempo reale per {{ .Get "app" }}?? Il server 1 (PRIM) esegue {{ .Get "app" }} e VM (macchine virtuali). SafeKit replica in tempo reale i file di VM (disco rigido virtuale, configurazione VM). Solo le modifiche apportate ai file vengono replicate nella rete.. ![Replicazione dei file a livello di byte in un cluster mirror {{ .Get "app" }}](/wp-content/uploads/2023/02/safekit-prim-second-300.png "w:300") La replica è [sincrono](/it/best-practises/synchronous-replication-vs-asynchronous-replication/) senza perdita di dati in caso di errore, a differenza della replica asincrona. È sufficiente configurare il nome della directory VM in SafeKit. Non ci sono prerequisiti sull'organizzazione del disco. La directory può trovarsi nel disco di sistema.. ### 2. Cosa succede durante un failover automatico {{ .Get "app" }}?? Quando il Server 1 si guasta, il Server 2 subentra. SafeKit riavvia {{ .Get "app" }} e VM sul Server 2. {{ .Get "app" }} trova i file replicati da SafeKit aggiornati sul Server 2.. Il dispositivo VM continua a funzionare sul Server 2 modificando localmente i suoi file, che non vengono più replicati sul Server 1.. ![Failover di {{ .Get "app" }} in un cluster mirror](/wp-content/uploads/2023/02/safekit-stop-alone-300.png "w:300") Il tempo di failover è pari al tempo di rilevamento dei guasti (impostato a 30 secondi per impostazione predefinita) più il tempo di riavvio di VM.. ### 3. Come vengono sincronizzati i dati dopo un errore {{ .Get "app" }}?? Il failback prevede il riavvio del Server 1 dopo aver risolto il problema che ne ha causato il malfunzionamento. SafeKit risincronizza automaticamente i file VM.. ![Failback in un cluster mirror {{ .Get "app" }}](/wp-content/uploads/2023/02/safekit-resynchro-alone-300.png "w:300") Il failback avviene senza interrompere {{ .Get "app" }} VM, che possono continuare a funzionare sul Server 2. ### 4. Come viene ripristinato il normale funzionamento di {{ .Get "app" }}?? Dopo la reintegrazione, i file VM sono nuovamente in modalità mirror, come nel passaggio 1. Il sistema è tornato in modalità ad alta disponibilità, con {{ .Get "app" }} e VM in esecuzione sul Server 2 e SafeKit che replica gli aggiornamenti dei file sul Server 1.. ![Ritorno al normale funzionamento nel cluster mirror {{ .Get "app" }}](/wp-content/uploads/2023/02/safekit-second-prim-300.png "w:300") Se l'amministratore desidera che lo VM venga eseguito sul Server 1, può farlo manualmente tramite la console web in un momento opportuno, oppure automaticamente tramite la configurazione.. ### Come configurare un cluster SafeKit {{ .Get "app" }}? {#safekit-mirror-cluster-configure} ![Console Web SafeKit: dashboard del cluster {{ .Get "app" }} a 2 nodi per la replica VM e il failover automatico.](/wp-content/uploads/2024/03/21-module-kvm-edit-config-1.png "w:694") IL **SafeKitconsole web** fornisce un'interfaccia intuitiva per configurare l'alta disponibilità delle tue applicazioni critiche. In pochi passaggi, puoi configurare un **SafeKit {{ .Get "app" }}grappolo** per garantire la continuità aziendale: * Metti dentro `VM_PATH`, il percorso radice della directory replicata (/var/lib/libvirt/images) in cui risiedono i file {{ .Get "app" }} e VM. * Inserisci `VM_NAME`, il nome della macchina virtuale {{ .Get "app" }} (VM1). Il cluster SafeKit include un dedicato [Strumento di verifica split-brain per risolvere i problemi di isolamento di rete.]( "Technical details on heartbeat and split-brain prevention") senza la necessità di una terza macchina testimone o di una rete heartbeat aggiuntiva. ### Come monitorare un cluster SafeKit {{ .Get "app" }}? {#safekit-mirror-cluster-monitoring} ![Console Web SafeKit: Monitoraggio in tempo reale di un cluster mirror a 2 nodi {{ .Get "app" }} che mostra gli stati di PRIM e SECOND con replica dei dati attiva.](/wp-content/uploads/2024/03/14-monitoring-prim-second.png "w:604") IL **Console di gestione SafeKit** offre una visione unificata della tua infrastruttura ad alta disponibilità. Consente agli amministratori di monitorare l' **stato operativo** della sincronizzazione dei dati del cluster e della traccia in tempo reale. Per un cluster {{ .Get "app" }} a 2 nodi, la console visualizza chiaramente i ruoli di ciascun server.: * **PRIM (Primario):** Il nodo attivo attualmente esegue l'applicazione e gestisce il Virtual IP. Esegue scritture nella memoria locale e la replica in tempo reale sul nodo secondario.. * **SECOND (Secondario):** Il nodo di standby riceve aggiornamenti sincroni a livello di byte. È pronto a subentrare immediatamente in caso di guasto del nodo primario.. * **ALONEStato:** Ti avvisa visivamente quando il cluster è in esecuzione su un singolo nodo (ad esempio, durante la manutenzione o dopo un guasto), indicando che la ridondanza è temporaneamente persa.. * **Avanzamento della risincronizzazione:** Quando un nodo guasto si ripristina, il suo stato diventa arancione durante la reintegrazione dei dati in background, garantendo l'assenza di tempi di inattività durante la fase di "ritorno alla normalità".. Oltre alle semplici icone di stato, l'interfaccia fornisce **orchestrazione del failover con un solo clic** , consentendo di riassegnare manualmente il ruolo principale per la manutenzione programmata, garantendo al contempo la disponibilità continua per l'attività degli utenti.. Si noti che se si distribuiscono più macchine virtuali per la replica e il failover, si avranno più widget PRIM/SECOND.
