SafeKit proporciona alta disponibilidade ao {{ .Get "app" }} entre dois servidores de qualquer marca.. Este artigo explica como implementar rapidamente um cluster {{ .Get "app" }} sem armazenamento partilhado num SAN e sem competências específicas.. O princípio da solução é colocar a aplicação crítica numa máquina virtual sob {{ .Get "app" }}. SafeKit implementa **replicação em tempo real e failover automático da máquina virtual**. Note que o {{ .Get "app" }} é o hipervisor gratuito incluído em todas as versões do Linux.. ### Como posso executar várias aplicações num cluster {{ .Get "app" }} de alta disponibilidade sem um SAN?? Diversas aplicações podem ser inseridas em **várias máquinas virtuais replicadas e reiniciadas por SafeKit**. Tem a possibilidade de migrar cada máquina virtual entre os dois servidores com a consola SafeKit e, assim, equilibrar a carga num **cluster ativo-ativo**. ### Devo escolher a alta disponibilidade ao nível da aplicação ou ao nível da máquina virtual (VM)?? Com o SafeKit, tem a flexibilidade de escolher o modelo de redundância que melhor se adapta às suas necessidades.. **Redundância de nível VM** (para {{ .Get "app" }} ou Hyper-V) é o mais simples de implementar, pois replica toda a máquina virtual, não necessitando de conhecimento da aplicação interna.. Alternativamente, **redundância ao nível de aplicação** É mais granular; replica apenas pastas de dados específicas e reinicia os serviços da aplicação, em vez de todo o sistema operativo.. Embora o VM ao nível da aplicação (HA) seja mais fácil de configurar, o HA ao nível da aplicação é independente do hipervisor e pode ser executado em ambientes físicos, virtuais ou na nuvem.. ### Quais são as vantagens distintivas do SafeKit para a elevada disponibilidade do {{ .Get "app" }} em comparação com os concorrentes?? Cada máquina virtual replicada é executada num módulo de espelhamento independente (com um máximo de 32 máquinas virtuais) com um servidor primário que pode ser o servidor {{ .Get "app" }} 1 ou o servidor {{ .Get "app" }} 2.. ### 1. Como funciona a replicação em tempo real para o {{ .Get "app" }}?? O servidor 1 (PRIM) executa as máquinas virtuais {{ .Get "app" }} e VM. O servidor SafeKit replica em tempo real os ficheiros do servidor VM (disco rígido virtual, configuração VM). Apenas as alterações efetuadas nesses ficheiros são replicadas pela rede.. ![Replicação de ficheiros ao nível de byte num cluster espelho {{ .Get "app" }}](/wp-content/uploads/2023/02/safekit-prim-second-300.png "w:300") A replicação é [síncrono](/best-practises/synchronous-replication-vs-asynchronous-replication/) sem perda de dados em caso de falha, ao contrário da replicação assíncrona.. Basta configurar o nome do diretório VM em SafeKit. Não existem pré-requisitos quanto à organização do disco. O diretório pode estar localizado no disco do sistema.. ### 2.º O que acontece durante uma avaria automática do {{ .Get "app" }}?? Quando o Servidor 1 falha, o Servidor 2 assume o controlo. SafeKit reinicia {{ .Get "app" }} e VM no Servidor 2. {{ .Get "app" }} verifica se os ficheiros replicados por SafeKit estão atualizados no Servidor 2.. O sistema VM continua a ser executado no Servidor 2, modificando localmente os seus ficheiros, que deixam de ser replicados para o Servidor 1.. ![Failover de {{ .Get "app" }} num cluster espelho](/wp-content/uploads/2023/02/safekit-stop-alone-300.png "w:300") O tempo de failover é igual ao tempo de deteção de falhas (definido como 30 segundos por defeito) mais o tempo de reinicialização do VM.. ### 3.De que forma os dados são sincronizados após uma falha {{ .Get "app" }}?? O failback envolve reiniciar o Servidor 1 após corrigir o problema que causou a falha. SafeKit ressincroniza automaticamente os ficheiros VM.. ![Failback num cluster espelho {{ .Get "app" }}](/wp-content/uploads/2023/02/safekit-resynchro-alone-300.png "w:300") O failback ocorre sem interromper o {{ .Get "app" }} VM, que pode continuar a ser executado no Servidor 2.. ### 4.De que forma é restaurado o funcionamento normal do {{ .Get "app" }}?? Após a reintegração, os ficheiros VM voltam a estar em modo espelho, tal como no passo 1. O sistema regressa ao modo de alta disponibilidade, com os ficheiros {{ .Get "app" }} e VM a correr no Servidor 2 e o ficheiro SafeKit a replicar as atualizações para o Servidor 1.. ![Retorno ao funcionamento normal num cluster espelho {{ .Get "app" }}](/wp-content/uploads/2023/02/safekit-second-prim-300.png "w:300") Se o administrador desejar que o VM seja executado no Servidor 1, tal pode ser feito manualmente através da consola web num momento apropriado ou automaticamente através da configuração.. ### Como configurar um cluster SafeKit {{ .Get "app" }}? {#safekit-mirror-cluster-configure} ![Consola Web SafeKit: painel de controlo do cluster {{ .Get "app" }} de 2 nós para replicação VM e failover automático.](/wp-content/uploads/2024/03/21-module-kvm-edit-config-1.png "w:694") O **Consola web SafeKit** Oferece uma interface intuitiva para configurar a alta disponibilidade das suas aplicações críticas. Em apenas alguns passos, pode configurar um **Cluster SafeKit {{ .Get "app" }}** para garantir a continuidade do negócio: * Insira `VM_PATH`, o caminho raiz do directório replicado (/var/lib/libvirt/images) onde residem os ficheiros {{ .Get "app" }} e VM. * Insira `VM_NAME`, o nome da máquina virtual {{ .Get "app" }} (VM1). O cluster SafeKit inclui um dedicado [Verificador split-brain para resolver problemas de isolamento de rede]( "Technical details on heartbeat and split-brain prevention") sem necessidade de uma terceira máquina testemunha ou de uma rede heartbeat adicional.. ### Como monitorizar um cluster SafeKit {{ .Get "app" }}? {#safekit-mirror-cluster-monitoring} ![Consola Web SafeKit: Monitorização em tempo real de um cluster espelho {{ .Get "app" }} de 2 nós, mostrando os estados PRIM e SECOND com replicação de dados ativa.](/wp-content/uploads/2024/03/14-monitoring-prim-second.png "w:604") O **Consola de gestão SafeKit** Oferece uma visão unificada da sua infraestrutura de alta disponibilidade. Permite que os administradores monitorizem a **estado operacional** do cluster e rastrear a sincronização de dados em tempo real. Para um cluster {{ .Get "app" }} de 2 nós, a consola apresenta claramente as funções de cada servidor.: * **PRIM (Primário):** O nó ativo está atualmente a executar a aplicação e a gerir o nó virtual IP. Realiza gravações no armazenamento local e replicação em tempo real para o nó secundário.. * **SECOND (Secundário):** O nó de espera recebe atualizações síncronas ao nível do byte. Está pronto para assumir o controlo instantaneamente caso o nó primário falhe.. * **Estado ALONE:** Alerta visualmente quando o cluster está a ser executado num único nó (por exemplo, durante a manutenção ou após uma falha), indicando que a redundância foi temporariamente perdida.. * **Progresso da ressincronização:** Quando um nó com falha recupera, o seu estado fica laranja durante a reintegração de dados em segundo plano, garantindo que não há tempo de inatividade durante a fase de "regresso ao normal".. Além de simples ícones de estado, a interface fornece **orquestração de failover com um clique** , permitindo reatribuir manualmente a função principal para a manutenção planeada, garantindo ao mesmo tempo a disponibilidade contínua para a atividade do utilizador.. Note que se implementar várias VMs para replicação e failover, terá vários widgets PRIM/SECOND.
