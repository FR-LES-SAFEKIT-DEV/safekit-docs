{{/* translation: translate_md 2026-11-07.15 | glossaire 2026-11-07.12 | Translation LLM | 24 expressions */}} {{/* Shortcode: insert-safekit-mirror-en — 21 instances in 21 files */}} {{/* Parameters: app */}} {{/* Source: content\_index.md */}} ## Wie funktioniert der SafeKit Mirror-Cluster mit {{ .Get "app" }} ? {#safekit-mirror-cluster} ### Schritt 1. Replikation in Echtzeit {#step1} Server 1 (PRIM) führt die {{ .Get "app" }} Anwendung aus. Clients sind mit einer [virtuellen IP-Adresse](/de/best-practises/how-a-virtual-ip-address-works/) verbunden. SafeKit repliziert Änderungen, die an Dateien vorgenommen werden, in Echtzeit über das Netzwerk. ![Dateireplikation auf Byte-Ebene in einem mirror {{ .Get "app" }} Cluster](/wp-content/uploads/2023/02/safekit-prim-second-300.png "w:300") Die Replikation ist [synchron](/de/best-practises/synchronous-replication-vs-asynchronous-replication/) und es kommt im Gegensatz zur asynchronen Replikation bei einem Fehler nicht zu Datenverlust. Sie müssen lediglich die Namen der zu replizierenden Verzeichnisse in SafeKit konfigurieren. Es gibt keine Voraussetzungen für die Festplattenorganisation. Verzeichnisse können sich auf der Systemfestplatte befinden. ### Schritt 2. Automatische Failover-Funktion {#step2} Wenn Server 1 ausfällt, übernimmt Server 2. SafeKit wechselt die virtuelle IP-Adresse und startet die {{ .Get "app" }} Anwendung automatisch auf Server 2. Die Anwendung findet die von SafeKit replizierten Dateien auf Server 2 auf dem neuesten Stand. Die Anwendung läuft weiterhin auf Server 2, indem sie ihre Dateien, die nicht mehr auf Server 1 repliziert werden, lokal ändert. ![Failover der {{ .Get "app" }} in einem Mirror-Cluster](/wp-content/uploads/2023/02/safekit-stop-alone-300.png "w:300") Die Failover-Zeit entspricht der Fehlererkennungszeit (standardmäßig 30 Sekunden) zuzüglich der Anwendungsstartzeit. ### Schritt 3. automatischer Failback {#step3} Failback beinhaltet das Neustarten von Server 1, nachdem das Problem behoben wurde, das zu seinem Ausfall geführt hat. SafeKit synchronisiert die Dateien automatisch neu und aktualisiert dabei nur die Dateien, die auf Server 2 geändert wurden, während Server 1 angehalten war. ![Failback in einem mirror {{ .Get "app" }} Cluster](/wp-content/uploads/2023/02/safekit-resynchro-alone-300.png "w:300") Das Failback erfolgt, ohne die {{ .Get "app" }} Anwendung zu stören, die weiterhin auf Server 2 ausgeführt werden kann. ### Schritt 4. Zurück zum Normalzustand {#step-4-back-to-normal} Nach der Reintegration befinden sich die Dateien wieder im mirror, wie in Schritt 1. Das System ist wieder im Hochverfügbarkeitsmodus, wobei die {{ .Get "app" }} Anwendung auf Server 2 läuft und SafeKit die Dateiaktualisierungen auf Server 1 repliziert. ![Rückkehr zum Normalbetrieb in einem mirror {{ .Get "app" }} Cluster](/wp-content/uploads/2023/02/safekit-second-prim-300.png "w:300") Wenn der Administrator möchte, dass die Anwendung auf Server 1 ausgeführt wird, kann dies manuell über die Webkonsole zu einem geeigneten Zeitpunkt oder automatisch über die Konfiguration erfolgen. ### Wie konfiguriert man einen SafeKit Mirror-Cluster für {{ .Get "app" }} ? {#safekit-mirror-cluster-configure} ![SafeKit Web Console: Dashboard für die Hochverfügbarkeitskonfiguration für {{ .Get "app" }}, das Heartbeat-Netzwerke, die Einrichtung virtueller IPs und die Echtzeit-Verzeichnisreplikation für einen Mirror-Cluster anzeigt.](/wp-content/uploads/2026/01/safekit-mirror-cluster-config.png "w:763") Die **SafeKit Webkonsole** bietet eine intuitive Schnittstelle zur Orchestrierung der Hochverfügbarkeit für Ihre kritischen Anwendungen. In nur wenigen Schritten können Sie einen **SafeKit Mirror-Cluster** konfigurieren, um die Geschäftskontinuität zu gewährleisten: * **Anwendungsfailover (Registerkarte „Makros“):** Definieren Sie die spezifischen Anwendungsdienste, die im Falle eines Ausfalls automatisch neu gestartet werden sollen. * **Heartbeat-Netzwerk(e):** Dedizierte Kommunikationspfade, die von Clusterknoten verwendet werden, um den Zustand und die Verfügbarkeit der anderen Knoten kontinuierlich zu überwachen und Failover-Entscheidungen zu synchronisieren. * **Virtuelles IP-Management:** Richten Sie die virtuelle IP (VIP) für eine transparente Client-Wiederverbindung nach einem Failover ein. * **Echtzeit-Replikation:** Wählen Sie die kritischen Verzeichnisse für die hostbasierte, synchrone Replikation auf Byteebene aus. * **Checkers:** Überwachen Sie den Zustand der Anwendung und lösen Sie eine automatische Wiederherstellung aus, wenn ein Prozessfehler erkannt wird. Das SafeKit Cluster verfügt über eine spezielle Split-Brain-Prüfung, um Probleme mit der Netzwerktrennung zu lösen, ohne dass ein dritter Witness-Computer oder ein zusätzliches Heartbeat-Netzwerk erforderlich ist. Erfahren Sie mehr über [Heartbeat, Failover und Quorum in einem Cluster](/de/best-practises/heartbeat-failover-quorum-windows-linux-cluster/). ### Wie kann man einen SafeKit Mirror-Cluster für {{ .Get "app" }} überwachen? {#safekit-mirror-cluster-monitoring} ![SafeKit Web Console: Echtzeitüberwachung eines 2-Knoten Mirror-Cluster für {{ .Get "app" }}, die PRIM und SECOND Zustände mit aktiver Datenreplikation anzeigt.](/wp-content/uploads/2026/05/mirror-monitoring-prim-second.png "w:604") Die **SafeKit Managementkonsole** bietet eine einheitliche Ansicht Ihrer Hochverfügbarkeitsinfrastruktur. Sie ermöglicht es Administratoren, den **Betriebsstatus** des Clusters zu überwachen und die Datensynchronisierung in Echtzeit zu verfolgen. Bei einem Mirror-Cluster mit zwei Knoten zeigt die Konsole die Rollen der einzelnen Server deutlich an: * **PRIM (Primär):** Der aktive Knoten, auf dem die Anwendung derzeit ausgeführt wird und der die virtuelle IP-Adresse verwaltet. Er führt Schreibvorgänge in den lokalen Speicher und die Echtzeitreplikation auf den sekundären Knoten durch. * **SECOND (Sekundär):** Der Standby-Knoten empfängt synchrone Updates auf Byte-Ebene. Er ist bereit, sofort die Übernahme zu übernehmen, falls der primäre Knoten ausfällt. * **ALONE Status:** Warnt Sie visuell, wenn der Cluster auf einem einzelnen Knoten läuft (z. B. während der Wartung oder nach einem Fehler), was darauf hinweist, dass die Redundanz vorübergehend verloren gegangen ist. * **Resynchronisierungsfortschritt:** Wenn sich ein ausgefallener Knoten erholt, wird sein Status während der Hintergrunddatenneuintegration orange, um sicherzustellen, dass es während der „Rückkehr zum Normalzustand“-Phase keine Ausfallzeiten gibt. Über einfache Status-Symbole hinaus bietet die Schnittstelle **eine Failover-Orchestrierung mit einem Klick**, mit der Sie die primäre Rolle für geplante Wartungsarbeiten manuell neu zuweisen und gleichzeitig die kontinuierliche Verfügbarkeit für Benutzeraktivitäten gewährleisten können.
