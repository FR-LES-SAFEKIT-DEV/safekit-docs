Réplication en temps réel {#step1} Le serveur 1 (PRIM) exécute l’application {{ .Get "app" }}. Les clients sont connectés à une [adresse IP virtuelle](/fr/best-practises/how-a-virtual-ip-address-works/). SafeKit réplique en temps réel les modifications apportées aux fichiers via le réseau. ![Réplication de fichiers au niveau de l’octet dans un cluster {{ .Get "app" }} mirror](/wp-content/uploads/2023/02/safekit-prim-second-300.png "w:300") La réplication est [synchrone](/fr/best-practises/synchronous-replication-vs-asynchronous-replication/) et n’entraîne aucune perte de données en cas de défaillance, contrairement à la réplication asynchrone. Il vous suffit de configurer les noms des répertoires à répliquer dans SafeKit. Il n’y a pas de prérequis sur l’organisation du disque. Les répertoires peuvent être situés sur le disque système. ### Étape 2. Basculement automatique {#step2} Lorsque le serveur 1 tombe en panne, le serveur 2 prend le relais. SafeKit bascule l’adresse IP virtuelle et redémarre automatiquement l’application {{ .Get "app" }} sur le serveur 2. L’application trouve les fichiers répliqués par SafeKit à jour sur le serveur 2. L’application continue de s’exécuter sur le serveur 2 en modifiant localement ses fichiers qui ne sont plus répliqués sur le serveur 1. ![Basculement de {{ .Get "app" }} dans un cluster mirror](/wp-content/uploads/2023/02/safekit-stop-alone-300.png "w:300") Le temps de basculement est égal au temps de détection des pannes (30 secondes par défaut) plus le temps de démarrage de l’application. ### Étape 3. failback automatique {#step3} Le rétablissement après défaillance consiste à redémarrer le serveur 1 après avoir corrigé le problème qui a provoqué sa défaillance. SafeKit resynchronise automatiquement les fichiers, en ne mettant à jour que les fichiers modifiés sur le serveur 2 pendant que le serveur 1 était arrêté. ![Rétablissement après défaillance dans un cluster {{ .Get "app" }} mirror](/wp-content/uploads/2023/02/safekit-resynchro-alone-300.png "w:300") Le basculement s’effectue sans perturber l’application {{ .Get "app" }}, qui peut continuer à s’exécuter sur le serveur 2. ### Étape 4. Retour à la normale {#step-4-back-to-normal} Après la réintégration, les fichiers sont à nouveau en mode mirror, comme à l’étape 1. Le système est de nouveau en mode haute disponibilité, avec l’application {{ .Get "app" }} s’exécutant sur le serveur 2 et SafeKit répliquant les mises à jour de fichiers sur le serveur 1. ![Retour au fonctionnement normal dans un cluster {{ .Get "app" }} mirror](/wp-content/uploads/2023/02/safekit-second-prim-300.png "w:300") Si l’administrateur souhaite que l’application s’exécute sur le serveur 1, cela peut être fait manuellement via la console Web à un moment opportun, ou automatiquement via la configuration. ### Comment configurer un cluster mirror SafeKit pour {{ .Get "app" }} ? {#safekit-mirror-cluster-configure} ![Console Web SafeKit : tableau de bord de configuration de haute disponibilité pour {{ .Get "app" }} montrant les réseaux de pulsation, la configuration IP virtuelle et la réplication de répertoire en temps réel pour un cluster mirror.](/wp-content/uploads/2026/01/safekit-mirror-cluster-config.png "w:763") La **console Web SafeKit** fournit une interface intuitive pour orchestrer la haute disponibilité de vos applications critiques. En quelques étapes seulement, vous pouvez configurer un **cluster mirror SafeKit** pour assurer la continuité des activités : * **Basculement d’application (onglet Macros) :** Définissez les services d’application spécifiques à redémarrer automatiquement en cas de défaillance. * **Réseau(x) de pulsation :** Chemin(s) de communication dédié(s) utilisé(s) par les nœuds du cluster pour surveiller en permanence l’état de santé et la disponibilité de chacun et pour synchroniser les décisions de basculement. * **Gestion de l’adresse IP virtuelle :** configurez l’adresse IP virtuelle (VIP) pour une reconnexion transparente du client après un basculement. * **Réplication en temps réel :** sélectionnez les répertoires critiques pour la réplication synchrone au niveau de l’octet, basée sur l’hôte. * **Checkers :** surveillez l’état de l’application et déclenchez une récupération automatique si une défaillance de processus est détectée. Le cluster SafeKit inclut un vérificateur de split-brain dédié pour résoudre les problèmes d’isolement du réseau sans avoir besoin d’une troisième machine témoin ou d’un réseau de pulsation supplémentaire. En savoir plus sur [la pulsation, le basculement et le quorum dans un cluster](/fr/best-practises/heartbeat-failover-quorum-windows-linux-cluster/). ### Comment surveiller un cluster mirror SafeKit pour {{ .Get "app" }} ? {#safekit-mirror-cluster-monitoring} ![Console Web SafeKit : Surveillance en temps réel d’un cluster mirror 2 nœuds pour {{ .Get "app" }} affichant les états PRIM et SECOND avec réplication de données active.](/wp-content/uploads/2026/05/mirror-monitoring-prim-second.png "w:604") La **console de gestion SafeKit** offre une vue unifiée de votre infrastructure de haute disponibilité. Elle permet aux administrateurs de surveiller l’**état opérationnel** du cluster et de suivre la synchronisation des données en temps réel. Pour un cluster mirror à 2 nœuds, la console affiche clairement les rôles de chaque serveur : * **PRIM (primaire) :** le nœud actif exécutant actuellement l’application et gérant l’adresse IP virtuelle. Il effectue des écritures sur le stockage local et la réplication en temps réel vers le nœud secondaire. * **SECOND (Secondaire) :** Le nœud de secours reçoit des mises à jour synchrones au niveau de l’octet. Il est prêt à prendre le relais instantanément en cas de défaillance du nœud principal. * **État ALONE :** vous avertit visuellement lorsque le cluster s’exécute sur un seul nœud (par exemple, pendant la maintenance ou après une panne), indiquant que la redondance est temporairement perdue. * **Progression de la resynchronisation :** lorsqu’un nœud défaillant se rétablit, son statut devient orange pendant la réintégration des données en arrière-plan, garantissant l’absence d’interruption pendant la phase de « retour à la normale ». Au-delà des simples icônes d’état, l’interface fournit **une orchestration de basculement en un clic**, vous permettant de réaffecter manuellement le rôle principal pour la maintenance planifiée tout en assurant la disponibilité continue de l’activité des utilisateurs.
