app */}} {{/* Source: content\_index.md */}} ## SafeKit mirror クラスター、どのように {{ .Get "app" }} と連携しますか？ {#safekit-mirror-cluster} ### ステップ 1. リアルタイムレプリケーション {#step1} サーバー 1（PRIM）は {{ .Get "app" }} アプリケーションを実行します。クライアントは[仮想 IP アドレス](/ja/best-practises/how-a-virtual-ip-address-works/)に接続されます。SafeKit は、ファイル内で行われた変更をネットワーク経由でリアルタイムに複製します。 ![mirror {{ .Get "app" }} クラスターにおけるバイトレベルでのファイルレプリケーション](/wp-content/uploads/2023/02/safekit-prim-second-300.png "w:300") 非同期レプリケーションとは異なり、レプリケーションは[同期式](/ja/best-practises/synchronous-replication-vs-asynchronous-replication/)であり、障害が発生してもデータ損失はありません。 SafeKit で複製するディレクトリの名前を設定するだけです。ディスクの構成に関する前提条件はありません。ディレクトリはシステムディスクに配置できます。 ### ステップ 2. 自動フェイルオーバー {#step2} サーバー 1 に障害が発生すると、サーバー 2 が引き継ぎます。SafeKit 仮想 IP アドレスを切り替え、サーバー 2 で {{ .Get "app" }} アプリケーションを自動的に再起動します。 アプリケーションは、SafeKit によって Server 2 に最新の状態にレプリケートされたファイルを見つけます。アプリケーションは、Server 1 にレプリケートされなくなったファイルをローカルで変更することにより、Server 2 で実行を継続します。 ![mirror クラスター内の {{ .Get "app" }} のフェイルオーバー](/wp-content/uploads/2023/02/safekit-stop-alone-300.png "w:300") フェイルオーバー時間は、障害検出時間（デフォルトでは 30 秒）とアプリケーションの起動時間を合計した時間です。 ### ステップ 3.自動フェイルバック {#step3} フェイルバックとは、サーバー 1 に障害が発生した原因を修正した後、サーバー 1 を再起動することです。 SafeKit ファイルを自動的に再同期し、サーバー 1 が停止している間にサーバー 2 で変更されたファイルのみを更新します。 ![mirror {{ .Get "app" }} クラスターでのフェイルバック](/wp-content/uploads/2023/02/safekit-resynchro-alone-300.png "w:300") フェイルバックは {{ .Get "app" }} アプリケーションを中断することなく行われ、アプリケーションはサーバー 2 で引き続き実行されます。 ### ステップ 4. 通常の状態に戻す {#step-4-back-to-normal} 再統合後、ファイルはステップ 1 と同様に mirror モードに戻ります。システムは高可用性モードに戻り、{{ .Get "app" }} アプリケーションはサーバー 2 で実行され、SafeKit ファイル更新をサーバー 1 にレプリケートします。 ![mirror {{ .Get "app" }} クラスターで通常運用に復帰する](/wp-content/uploads/2023/02/safekit-second-prim-300.png "w:300") 管理者がアプリケーションをサーバー 1 で実行したい場合、適切なタイミングで Web コンソールから手動で実行するか、または設定によって自動的に実行することができます。 ### SafeKit mirror クラスター{{ .Get "app" }} 用に構成する方法 {#safekit-mirror-cluster-configure} ![SafeKit Web Console: {{ .Get "app" }} のハートビートネットワーク、仮想 IP 設定、mirror クラスターのリアルタイムディレクトリレプリケーションを表示する高可用性構成ダッシュボード。](/wp-content/uploads/2026/01/safekit-mirror-cluster-config.png "w:763") **SafeKit ウェブコンソールは**、重要なアプリケーションの可用性を高めるための直感的なインターフェースを提供します。**数ステップで SafeKit mirror クラスター**を設定し、事業継続性を確保できます * **アプリケーションフェイルオーバー（マクロタブ）：** 障害発生時に自動的に再起動する特定のアプリケーションサービスを定義します。 * **ハートビートネットワーク：** クラスターノードが互いの正常性と可用性を継続的に監視し、フェイルオーバーの決定を同期するために使用する専用の通信パス。 * **仮想 IP 管理：** フェイルオーバー後にクライアントが透過的に再接続できるように、仮想 IP（VIP）を設定します。 * **リアルタイムレプリケーション：** ホストベースの同期バイトレベルレプリケーションの対象となる重要なディレクトリを選択します。 * **チェッカー：** アプリケーションの正常性を監視し、プロセスの障害が検出された場合は自動復旧をトリガーします。 SafeKit クラスターには、専用のスプリットブレインチェッカーが搭載されており、サードパーティのウィットネスマシンや追加のハートビートネットワークを必要とせずに、ネットワーク分離の問題を解決します。[クラスターにおけるハートビート、フェイルオーバー、クォーラム](/ja/best-practises/heartbeat-failover-quorum-windows-linux-cluster/)の詳細については、こちらをご覧ください。 ### {{ .Get "app" }} 用 SafeKit mirror クラスターを監視する方法 {#safekit-mirror-cluster-monitoring} ![SafeKit Web Console: 2 ノード mirror クラスターのリアルタイム監視。PRIM および SECOND 状態とアクティブ PRIM データレプリケーションを伴う {{ .Get "app" }} を表示します。](/wp-content/uploads/2026/05/mirror-monitoring-prim-second.png "w:604") **SafeKit 管理コンソールは**、高可用性インフラストラクチャの統合ビューを提供します。**これにより、管理者はクラスターの動作状態**を監視し、データ同期をリアルタイムで追跡できます。 2 ノード mirror クラスターの場合、コンソールには各サーバーの役割が明確に表示されます * **PRIM (プライマリ):** アプリケーションを実行し、仮想 IP を管理しているアクティブなノード。ローカルストレージへの書き込みと、セカンダリノードへのリアルタイムレプリケーションを実行します。 * **SECOND：** 同期バイトレベルの更新を受信するスタンバイノード。プライマリに障害が発生した場合、即座に引き継ぐ準備ができています。 * **ALONE 状態：** クラスターが単一ノードで実行されている場合（メンテナンス中や障害発生後など）、冗長性が一時的に失われていることを視覚的に警告します。 * **再同期の進捗状況：** 障害が発生したノードが復旧すると、バックグラウンドでのデータ再統合中にそのステータスがオレンジ色に変わり、「通常状態に戻る」フェーズ中にダウンタイムが発生しないようにします。 シンプルなステータスアイコンに加え、このインターフェースは**ワンクリックのフェイルオーバーオーケストレーション**を提供し、計画メンテナンス中にプライマリの役割を手動で再割り当てしながら、ユーザーアクティビティの継続的な可用性を確保します。
