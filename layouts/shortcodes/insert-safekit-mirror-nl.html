Realtime replicatie {#step1} Server 1 (PRIM) draait de {{ .Get "app" }} applicatie. Clients zijn verbonden met een [virtueel IP-adres](/nl/best-practises/how-a-virtual-ip-address-works/). SafeKit repliceert in realtime wijzigingen die in bestanden zijn aangebracht via het netwerk. ![Bestandsreplicatie op byteniveau in een mirror {{ .Get "app" }} cluster](/wp-content/uploads/2023/02/safekit-prim-second-300.png "w:300") De replicatie is [synchroon](/nl/best-practises/synchronous-replication-vs-asynchronous-replication/) en er gaat geen data verloren bij een storing, in tegenstelling tot asynchrone replicatie. U hoeft alleen de namen van de te repliceren mappen in SafeKit te configureren. Er zijn geen vereisten voor de schijforganisatie. Mappen kunnen zich op de systeemdisk bevinden. ### Stap 2. Automatische failover {#step2} Wanneer Server 1 uitvalt, neemt Server 2 het over. SafeKit schakelt het virtuele IP-adres over en start de {{ .Get "app" }} applicatie automatisch opnieuw op Server 2. De toepassing vindt de bestanden die door SafeKit zijn gerepliceerd op Server 2. De toepassing blijft draaien op Server 2 door lokaal de bestanden te wijzigen die niet langer naar Server 1 worden gerepliceerd. ![Failover van {{ .Get "app" }} in een mirror-cluster](/wp-content/uploads/2023/02/safekit-stop-alone-300.png "w:300") De failovertijd is gelijk aan de foutdetectietijd (standaard 30 seconden) plus de opstarttijd van de toepassing. ### Stap 3. automatische failback {#step3} Failback houdt in dat server 1 opnieuw wordt opgestart nadat het probleem dat de storing veroorzaakte, is opgelost. SafeKit synchroniseert de bestanden automatisch opnieuw, waarbij alleen de bestanden worden bijgewerkt die op Server 2 zijn gewijzigd terwijl Server 1 was gestopt. ![Failback in een mirror {{ .Get "app" }}](/wp-content/uploads/2023/02/safekit-resynchro-alone-300.png "w:300") De failback vindt plaats zonder de {{ .Get "app" }} toepassing te verstoren, die kan blijven draaien op Server 2. ### Stap 4. Terug naar normaal {#step-4-back-to-normal} Na de reintegratie zijn de bestanden weer in mirror, zoals in stap 1. Het systeem is weer in de hoge beschikbaarheidsmodus, met de {{ .Get "app" }} applicatie die op Server 2 draait en SafeKit die bestandswijzigingen repliceert naar Server 1. ![Terugkeer naar normale werking in een mirror {{ .Get "app" }} cluster](/wp-content/uploads/2023/02/safekit-second-prim-300.png "w:300") Als de beheerder wil dat de toepassing op Server 1 wordt uitgevoerd, kan dit handmatig via de webconsole op een geschikt moment, of automatisch via configuratie. ### Hoe configureer ik een SafeKit mirror-cluster voor {{ .Get "app" }} ? {#safekit-mirror-cluster-configure} ![SafeKit Web Console: dashboard voor hoge beschikbaarheid voor {{ .Get "app" }} met hartslagnetwerken, virtuele IP-instellingen en realtime directoryreplicatie voor een mirror-cluster.](/wp-content/uploads/2026/01/safekit-mirror-cluster-config.png "w:763") De **SafeKit webconsole** biedt een intuïtieve interface om hoge beschikbaarheid voor uw bedrijfskritische applicaties te orkestreren. In slechts een paar stappen kunt u een **SafeKit mirror-cluster** configureren om bedrijfscontinuïteit te garanderen: * **Failover van applicaties (tabblad Macro's):** Definieer de specifieke applicatiediensten die automatisch opnieuw moeten worden gestart in geval van een storing. * **Heartbeatnetwerk(en):** Toegewezen communicatiepad(en) die door clusterknooppunten worden gebruikt om de status en beschikbaarheid van elkaar continu te controleren en failoverbeslissingen te synchroniseren. * **Virtueel IP-beheer:** Stel het virtuele IP-adres (VIP) in voor een transparante herverbinding van de client na een failover. * **Realtime replicatie:** Selecteer de kritieke mappen voor hostgebaseerde, synchrone replicatie op byteniveau. * **Checkers:** controleer de status van de toepassing en activeer automatisch herstel als er een procesfout wordt gedetecteerd. Het SafeKit cluster bevat een speciale split-brain-checker om netwerkisolatieproblemen op te lossen zonder dat er een derde 'witness'-machine of een extra 'heartbeat'-netwerk nodig is. Lees meer over ['heartbeat', 'failover' en 'quorum' in een cluster](/nl/best-practises/heartbeat-failover-quorum-windows-linux-cluster/). ### Hoe kan ik een SafeKit mirror-cluster voor {{ .Get "app" }} monitoren? {#safekit-mirror-cluster-monitoring} ![SafeKit Web Console: real-time monitoring van een mirror-cluster met 2 knooppunten voor {{ .Get "app" }} die de statussen PRIM en SECOND weergeeft met actieve datareplicatie.](/wp-content/uploads/2026/05/mirror-monitoring-prim-second.png "w:604") De **SafeKit beheerconsole** biedt een uniform overzicht van uw hoge beschikbaarheidsinfrastructuur. Hiermee kunnen beheerders de **operationele status** van het cluster controleren en de gegevenssynchronisatie in realtime volgen. Voor een mirror-cluster met 2 knooppunten geeft de console duidelijk de rollen van elke server weer: * **PRIM (primair):** de actieve node die momenteel de toepassing uitvoert en het virtuele IP-adres beheert. Deze voert schrijfbewerkingen uit naar de lokale opslag en realtime-replicatie naar de secundaire node. * **SECOND:** Het stand-byknooppunt ontvangt synchrone updates op byteniveau. Het is direct klaar om het over te nemen als het primaire knooppunt uitvalt. * **ALONE status:** Geeft een visuele waarschuwing wanneer het cluster op één knooppunt draait (bijv. tijdens onderhoud of na een storing), wat aangeeft dat de redundantie tijdelijk verloren is gegaan. * **Voortgang van de resynchronisatie:** Wanneer een defecte node herstelt, wordt de status oranje tijdens de achtergrondgegevensreïntegratie, zodat er geen downtime is tijdens de fase 'terug naar normaal'. Naast eenvoudige statuspictogrammen biedt de interface **failover-orkestratie met één klik**, zodat u de primaire rol handmatig kunt toewijzen voor gepland onderhoud, terwijl u de continue beschikbaarheid voor gebruikersactiviteiten waarborgt.
