Replicação em tempo real {#step1} O Servidor 1 (PRIM) executa o aplicativo {{ .Get "app" }}. Os clientes estão conectados a um [endereço IP virtual](/pt-br/best-practises/how-a-virtual-ip-address-works/). SafeKit replica em tempo real as modificações feitas nos arquivos através da rede. ![Replicação de arquivos em nível de byte em um cluster {{ .Get "app" }} mirror](/wp-content/uploads/2023/02/safekit-prim-second-300.png "w:300") A replicação é [síncrona](/pt-br/best-practises/synchronous-replication-vs-asynchronous-replication/), sem perda de dados em caso de falha, ao contrário da replicação assíncrona. Você só precisa configurar os nomes dos diretórios a serem replicados no SafeKit. Não há pré-requisitos quanto à organização do disco. Os diretórios podem estar localizados no disco do sistema. ### Passo 2. Failover automático {#step2} Quando o Servidor 1 falha, o Servidor 2 assume o controle. SafeKit alterna o endereço IP virtual e reinicia o aplicativo {{ .Get "app" }} automaticamente no Servidor 2. O aplicativo encontra os arquivos replicados pelo SafeKit atualizados no Servidor 2. O aplicativo continua a ser executado no Servidor 2, modificando localmente seus arquivos que não são mais replicados para o Servidor 1. ![Failover do {{ .Get "app" }} em um cluster mirror](/wp-content/uploads/2023/02/safekit-stop-alone-300.png "w:300") O tempo de failover é igual ao tempo de deteção de falhas (30 segundos por predefinição) mais o tempo de inicialização da aplicação. ### Etapa 3. failback automático {#step3} A recuperação de falhas envolve reiniciar o Servidor 1 após corrigir o problema que causou a falha. SafeKit resincroniza automaticamente os arquivos, atualizando apenas os arquivos modificados no Servidor 2 enquanto o Servidor 1 estava parado. ![Recuperação de falha em um cluster {{ .Get "app" }} mirror](/wp-content/uploads/2023/02/safekit-resynchro-alone-300.png "w:300") O failback ocorre sem interromper a {{ .Get "app" }}, que pode continuar a ser executada no Servidor 2. ### Passo 4. Voltar ao normal {#step-4-back-to-normal} Após a reintegração, os arquivos ficam novamente no modo mirror, como na etapa 1. O sistema volta ao modo de alta disponibilidade, com o aplicativo {{ .Get "app" }} em execução no Servidor 2 e SafeKit replicando as atualizações de arquivos para o Servidor 1. ![Retornar à operação normal em um cluster {{ .Get "app" }} mirror](/wp-content/uploads/2023/02/safekit-second-prim-300.png "w:300") Se o administrador desejar que o aplicativo seja executado no Servidor 1, isso pode ser feito manualmente através do console da web em um momento apropriado ou automaticamente através da configuração. ### Como configurar um cluster mirror SafeKit para {{ .Get "app" }} ? {#safekit-mirror-cluster-configure} ![Console Web SafeKit: Painel de configuração de alta disponibilidade para {{ .Get "app" }}, mostrando redes de pulsações, configuração de IP virtual e replicação de diretório em tempo real para um cluster mirror.](/wp-content/uploads/2026/01/safekit-mirror-cluster-config.png "w:763") O **console da web SafeKit** fornece uma interface intuitiva para orquestrar alta disponibilidade para seus aplicativos críticos. Em apenas algumas etapas, você pode configurar um **cluster mirror SafeKit** para garantir a continuidade dos negócios: * **Failover de Aplicativo (Guia Macros):** Defina os serviços de aplicativo específicos a serem reiniciados automaticamente em caso de falha. * **Rede(s) de pulsações:** Caminho(s) de comunicação dedicado(s) usado(s) pelos nós do cluster para monitorar continuamente a integridade e a disponibilidade um do outro e sincronizar as decisões de failover. * **Gerenciamento de IP Virtual:** configure o IP Virtual (VIP) para reconexão transparente do cliente após uma falha. * **Replicação em tempo real:** selecione os diretórios críticos para replicação síncrona em nível de byte baseada no host. * **Verificadores:** Monitore a integridade do aplicativo e acione a recuperação automática se for detectada uma falha no processo. O cluster SafeKit inclui um verificador de divisão de rede dedicado para resolver problemas de isolamento de rede sem a necessidade de uma terceira máquina testemunha ou de uma rede de pulsações adicional. Saiba mais sobre [pulsações, failover e quórum em um cluster](/pt-br/best-practises/heartbeat-failover-quorum-windows-linux-cluster/). ### Como monitorar um cluster mirror SafeKit para {{ .Get "app" }} ? {#safekit-mirror-cluster-monitoring} ![Console Web SafeKit: Monitoramento em tempo real de um cluster mirror 2 nós para {{ .Get "app" }}, mostrando os estados PRIM e SECOND com replicação de dados ativa.](/wp-content/uploads/2026/05/mirror-monitoring-prim-second.png "w:604") O **console de gerenciamento SafeKit** oferece uma visão unificada da sua infraestrutura de alta disponibilidade. Ele permite que os administradores monitorem o **estado operacional** do cluster e acompanhem a sincronização de dados em tempo real. Para um cluster mirror de 2 nós, o console exibe claramente as funções de cada servidor: * **PRIM (Primário):** O nó ativo que executa atualmente o aplicativo e gerencia o IP virtual. Ele executa gravações no armazenamento local e replicação em tempo real para o nó secundário. * **SECOND:** O nó de espera recebe atualizações síncronas em nível de byte. Ele está pronto para assumir o controle instantaneamente se o primário falhar. * **ALONE Estado:** Alerta visualmente quando o cluster está sendo executado em um único nó (por exemplo, durante a manutenção ou após uma falha), indicando que a redundância foi temporariamente perdida. * **Progresso da resincronização:** quando um nó com falha é recuperado, seu status fica laranja durante a reintegração de dados em segundo plano, garantindo que não haja tempo de inatividade durante a fase de "retorno ao normal". Além de ícones de status simples, a interface fornece **orquestração de failover com um clique**, permitindo que você reatribua manualmente a função primária para manutenção planejada, garantindo a disponibilidade contínua para a atividade do usuário.
