Replicação em tempo real {#step1} O Servidor 1 (PRIM) executa a aplicação {{ .Get "app" }}. Os clientes estão ligados a um [endereço IP virtual](/pt-pt/best-practises/how-a-virtual-ip-address-works/). SafeKit replica em tempo real as modificações feitas nos ficheiros através da rede. ![Replicação de ficheiros ao nível de byte num cluster {{ .Get "app" }} mirror](/wp-content/uploads/2023/02/safekit-prim-second-300.png "w:300") A replicação é [síncrona](/pt-pt/best-practises/synchronous-replication-vs-asynchronous-replication/), sem perda de dados em caso de falha, ao contrário da replicação assíncrona. Basta configurar os nomes dos diretórios a replicar no SafeKit. Não existem pré-requisitos quanto à organização do disco. Os diretórios podem estar localizados no disco do sistema. ### Passo 2. Reposição automática em caso de falha {#step2} Quando o Servidor 1 falha, o Servidor 2 assume o controlo. SafeKit muda o endereço IP virtual e reinicia a aplicação {{ .Get "app" }} automaticamente no Servidor 2. A aplicação encontra os ficheiros replicados pelo SafeKit atualizados no Servidor 2. A aplicação continua a ser executada no Servidor 2, modificando localmente os seus ficheiros que já não são replicados para o Servidor 1. ![Failover da {{ .Get "app" }} num cluster mirror](/wp-content/uploads/2023/02/safekit-stop-alone-300.png "w:300") O tempo de failover é igual ao tempo de deteção de falhas (30 segundos por predefinição) mais o tempo de arranque da aplicação. ### Passo 3. failback automático {#step3} A recuperação de falhas envolve reiniciar o Servidor 1 após a resolução do problema que causou a sua falha. SafeKit resincroniza automaticamente os ficheiros, atualizando apenas os ficheiros modificados no Servidor 2 enquanto o Servidor 1 estava parado. ![Recuperação de falhas num cluster {{ .Get "app" }} mirror](/wp-content/uploads/2023/02/safekit-resynchro-alone-300.png "w:300") A recuperação de falhas ocorre sem perturbar a {{ .Get "app" }}, que pode continuar a ser executada no Servidor 2. ### Passo 4. De volta ao normal {#step-4-back-to-normal} Após a reintegração, os ficheiros voltam a estar em modo mirror, como no passo 1. O sistema volta ao modo de alta disponibilidade, com a aplicação {{ .Get "app" }} a ser executada no Servidor 2 e SafeKit a replicar as atualizações dos ficheiros para o Servidor 1. ![Regresso ao funcionamento normal num cluster {{ .Get "app" }} mirror](/wp-content/uploads/2023/02/safekit-second-prim-300.png "w:300") Se o administrador desejar que a aplicação seja executada no Servidor 1, isso pode ser feito manualmente através da consola web num momento apropriado, ou automaticamente através da configuração. ### Como configurar um cluster mirror SafeKit para {{ .Get "app" }} ? {#safekit-mirror-cluster-configure} ![Consola Web SafeKit: Painel de configuração de alta disponibilidade para {{ .Get "app" }}, mostrando redes de pulsações, configuração de IP virtual e replicação de diretórios em tempo real para um cluster mirror.](/wp-content/uploads/2026/01/safekit-mirror-cluster-config.png "w:763") A **consola web SafeKit** oferece uma interface intuitiva para orquestrar a alta disponibilidade das suas aplicações críticas. Em apenas alguns passos, pode configurar um **cluster mirror SafeKit** para garantir a continuidade do negócio: * **Failover da Aplicação (Separador Macros):** Defina os serviços específicos da aplicação a serem reiniciados automaticamente em caso de falha. * **Rede(s) de pulsações:** Caminho(s) de comunicação dedicado(s) utilizado(s) pelos nós do cluster para monitorizar continuamente a integridade e a disponibilidade uns dos outros e para sincronizar as decisões de failover. * **Gestão de IP Virtual:** Configure o IP Virtual (VIP) para uma reconexão transparente do cliente após uma falha. * **Replicação em Tempo Real:** Selecione os diretórios críticos para replicação síncrona ao nível de byte, baseada no anfitrião. * **Verificadores:** Monitorize o estado da aplicação e acione a recuperação automática se for detetada uma falha no processo. O cluster SafeKit inclui um verificador dedicado de "split-brain" para resolver problemas de isolamento de rede sem a necessidade de uma terceira máquina testemunha ou de uma rede adicional de "heartbeat". Saiba mais sobre ["heartbeat", "failover" e "quorum" num cluster](/pt-pt/best-practises/heartbeat-failover-quorum-windows-linux-cluster/). ### Como monitorizar um cluster mirror SafeKit para {{ .Get "app" }} ? {#safekit-mirror-cluster-monitoring} ![Consola Web SafeKit: Monitorização em tempo real de um cluster mirror 2 nós para {{ .Get "app" }}, mostrando os estados PRIM e SECOND com replicação de dados ativa.](/wp-content/uploads/2026/05/mirror-monitoring-prim-second.png "w:604") A **consola de gestão SafeKit** oferece uma visão unificada da sua infraestrutura de alta disponibilidade. Permite aos administradores monitorizar o **estado operacional** do cluster e acompanhar a sincronização de dados em tempo real. Para um cluster mirror de 2 nós, a consola exibe claramente as funções de cada servidor: * **PRIM (Primário):** O nó ativo que executa atualmente a aplicação e gere o IP Virtual. Executa escritas no armazenamento local e replicação em tempo real para o nó secundário. * **SECOND:** O nó de reserva recebe atualizações síncronas ao nível de byte. Está pronto para assumir o controlo instantaneamente se o Primário falhar. * **ALONE Estado:** Alerta visualmente quando o cluster está a ser executado num único nó (por exemplo, durante a manutenção ou após uma falha), indicando que a redundância foi temporariamente perdida. * **Progresso da Ressincronização:** Quando um nó que falhou recupera, o seu estado fica laranja durante a reintegração de dados em segundo plano, garantindo que não haja tempo de inatividade durante a fase de "regresso ao normal". Além de simples ícones de estado, a interface oferece **orquestração de failover com um clique**, permitindo reatribuir manualmente a função primária para manutenção planeada, garantindo simultaneamente a disponibilidade contínua para a atividade do utilizador.
