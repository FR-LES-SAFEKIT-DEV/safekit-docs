{{/* Shortcode: insert-safekit-shared-nothing-vs-shared-disk-table-en — 1 instance in 1 file */}} {{/* Parameters: none */}} {{/* Source: content\best-practises\shared-nothing-architecture-vs-shared-disk-architecture.md */}} Choosing the right high availability architecture is critical to balance cost, complexity, and reliability. The two main approaches are the **shared nothing architecture** and the **shared disk architecture**. They are fundamentally different in how they handle data redundancy and failover. SafeKit implements a shared nothing architecture. It replicates data between independent servers, and each server has its own local storage. A shared disk architecture relies on a centralized disk array (SAN) that is accessed by several servers. The following table compares these two approaches on key criteria. Criteria | Shared Nothing Architecture | Shared Disk Architecture ---|---|--- Product | [SafeKit on Windows and Linux](/) | A clustering toolkit designed for shared disks Extra hardware | No extra hardware is needed. The servers use their own internal disks. | Extra hardware is needed. A shared disk array (SAN) adds extra cost. Application data organization | There is no impact on the organization of application data. [You only define the directories to replicate in real time](/architectures/file-replication-byte-level-with-failover-mirror-cluster/). Directories on the system disk can also be replicated. | The application must be specially configured to store its data on the shared disk. Data on the system disk is not protected by failover. Complexity of deployment | Deployment is simple. Only the SafeKit software needs to be installed on two servers. | Deployment is complex. Specific IT skills are required to configure the operating system and the shared disk. Failover | The application is restarted on the second server. | The shared disk is moved to the second server. The file system is mounted again. The file system recovery procedure is run. Then the application is restarted. Disaster recovery | The two servers are placed on two remote sites that are connected by an extended LAN. | A second disk array adds extra cost. Specific IT skills are required to configure mirroring between the two disk arrays across the SAN. Quorum and split brain | After a network isolation (split brain), the application runs on only one server. Data consistency is guaranteed. No additional server, no quorum disk, and no special heartbeat line are needed. [More information on heartbeat, failover and quorum](/best-practises/heartbeat-failover-quorum-windows-linux-cluster/) | A special quorum disk or an additional quorum server is required to avoid data corruption in case of split brain. Best suited for | [Software vendors who want to add a simple high availability option to their application](/use-cases/application-clustering-software/) | Large companies with IT teams skilled in clustering and with large database applications **In summary**, the shared nothing architecture of SafeKit is better for **simplicity**, **cost**, and **deployment speed**. No extra hardware is required. No specialized IT skills are required. The organization of application data does not change. Failover is simple, disaster recovery is built in, and split brain is handled without additional infrastructure. The shared disk architecture is still relevant for large companies that already have a SAN infrastructure and dedicated IT teams that manage very large databases. However, for most application high availability needs, the shared nothing architecture of SafeKit is the simpler and more cost-effective choice. This is especially true for software vendors, OT and edge environments, and distributed sites.
