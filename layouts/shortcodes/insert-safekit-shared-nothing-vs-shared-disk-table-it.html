I due approcci principali sono l’**architettura shared-nothing** e l’**architettura a disco condiviso**. Sono fondamentalmente diversi nel modo in cui gestiscono la ridondanza dei dati e il failover. SafeKit implementa un’architettura shared-nothing. Replica i dati tra server indipendenti e ogni server ha il proprio storage locale. Un’architettura a disco condiviso si basa su un array di dischi centralizzato (SAN) a cui accedono più server. La tabella seguente confronta questi due approcci in base a criteri chiave. Criteri | Architettura shared-nothing | Architettura a disco condiviso ---|---|--- Prodotto | [SafeKit su Windows e Linux](/it/) | Un toolkit di clustering progettato per dischi condivisi Hardware aggiuntivo | Non è necessario alcun hardware aggiuntivo. I server utilizzano i propri dischi interni. | È necessario hardware aggiuntivo. Un array di dischi condivisi (SAN) comporta un costo aggiuntivo. Organizzazione dei dati dell’applicazione | Non c’è alcun impatto sull’organizzazione dei dati dell’applicazione. [È sufficiente definire le directory da replicare in tempo reale](/it/architectures/file-replication-byte-level-with-failover-mirror-cluster/). È possibile replicare anche le directory sul disco di sistema. | L’applicazione deve essere configurata in modo specifico per archiviare i dati sul disco condiviso. I dati sul disco di sistema non sono protetti dal failover. Complessità dell’implementazione | L’implementazione è semplice. È sufficiente installare il software SafeKit su due server. | L’implementazione è complessa. Sono richieste competenze informatiche specifiche per configurare il sistema operativo e il disco condiviso. Failover | L’applicazione viene riavviata sul secondo server. | Il disco condiviso viene spostato sul secondo server. Il file system viene montato di nuovo. Viene eseguita la procedura di ripristino del file system. Quindi l’applicazione viene riavviata. Ripristino di emergenza | I due server sono collocati in due siti remoti collegati da una LAN estesa. | Un secondo array di dischi comporta un costo aggiuntivo. Sono necessarie competenze informatiche specifiche per configurare il mirroring tra i due array di dischi sulla SAN. Quorum e split brain | Dopo un isolamento della rete (split brain), l’applicazione viene eseguita su un solo server. La coerenza dei dati è garantita. Non sono necessari server aggiuntivi, né un disco di quorum, né una linea heartbeat speciale. [Maggiori informazioni su heartbeat, failover e quorum](/it/best-practises/heartbeat-failover-quorum-windows-linux-cluster/) | Per evitare il danneggiamento dei dati in caso di split brain, è necessario un disco di quorum speciale o un server di quorum aggiuntivo. Ideale per | [Fornitori di software che desiderano aggiungere una semplice opzione di alta disponibilità alla propria applicazione](/it/use-cases/application-clustering-software/) | Grandi aziende con team IT esperti nel clustering e con applicazioni di database di grandi dimensioni **In sintesi**, l’architettura shared-nothing di SafeKit è migliore in termini di **semplicità**, **costi** e **velocità di implementazione**. Non è necessario alcun hardware aggiuntivo. Non sono richieste competenze IT specializzate. L’organizzazione dei dati dell’applicazione non cambia. Il failover è semplice, il disaster recovery è integrato e lo split brain viene gestito senza infrastrutture aggiuntive. L’architettura a disco condiviso è ancora rilevante per le grandi aziende che dispongono già di un’infrastruttura SAN e di team IT dedicati che gestiscono database di grandi dimensioni. Tuttavia, per la maggior parte delle esigenze di alta disponibilità delle applicazioni, l’architettura shared-nothing di SafeKit è la scelta più semplice ed economica. Ciò è particolarmente vero per i fornitori di software, gli ambienti OT ed edge e i siti distribuiti.
