As duas abordagens principais são a **arquitetura sem compartilhamento** e a **arquitetura de disco compartilhado**. Elas são fundamentalmente diferentes na forma como lidam com a redundância de dados e o failover. SafeKit implementa uma arquitetura sem compartilhamento. Ele replica dados entre servidores independentes, e cada servidor tem seu próprio armazenamento local. Uma arquitetura de disco compartilhado depende de um array de discos centralizado (SAN) que é acessado por vários servidores. A tabela a seguir compara essas duas abordagens em critérios-chave. Critérios | Arquitetura sem compartilhamento | Arquitetura de disco compartilhado ---|---|--- Produto | [SafeKit no Windows e Linux](/pt-br/) | Um kit de ferramentas de cluster projetado para discos compartilhados Hardware adicional | Não é necessário nenhum hardware adicional. Os servidores usam seus próprios discos internos. | É necessário hardware adicional. Um array de discos compartilhado (SAN) gera um custo extra. Organização dos dados da aplicação | Não há impacto na organização dos dados do aplicativo. [Você só define os diretórios a serem replicados em tempo real](/pt-br/architectures/file-replication-byte-level-with-failover-mirror-cluster/). Os diretórios no disco do sistema também podem ser replicados. | O aplicativo deve ser configurado especificamente para armazenar seus dados no disco compartilhado. Os dados no disco do sistema não são protegidos por failover. Complexidade da implementação | A implementação é simples. Apenas o software SafeKit precisa ser instalado em dois servidores. | A implementação é complexa. São necessárias competências específicas de TI para configurar o sistema operativo e o disco partilhado. Failover | O aplicativo é reiniciado no segundo servidor. | O disco compartilhado é movido para o segundo servidor. O sistema de arquivos é montado novamente. O procedimento de recuperação do sistema de arquivos é executado. Em seguida, o aplicativo é reiniciado. Recuperação de desastres | Os dois servidores são instalados em dois locais remotos que estão conectados por uma LAN estendida. | Um segundo array de discos adiciona um custo extra. São necessárias competências específicas de TI para configurar o espelhamento entre os dois arrays de discos através da SAN. Quórum e split brain | Após um isolamento de rede (split brain), a aplicação é executada em apenas um servidor. A consistência dos dados é garantida. Não são necessários servidores adicionais, disco de quórum ou linha de heartbeat especial. [Mais informações sobre heartbeat, failover e quórum](/pt-br/best-practises/heartbeat-failover-quorum-windows-linux-cluster/) | Um disco de quórum especial ou um servidor de quórum adicional é necessário para evitar a corrupção de dados em caso de split brain. Mais adequado para | [Fornecedores de software que desejam adicionar uma opção simples de alta disponibilidade ao seu aplicativo](/pt-br/use-cases/application-clustering-software/) | Grandes empresas com equipes de TI especializadas em clustering e com aplicações de banco de dados de grande porte **Em resumo**, a arquitetura sem compartilhamento do SafeKit é melhor em termos de **simplicidade**, **custo** e **velocidade de implantação**. Não é necessário hardware adicional. Não são necessárias habilidades de TI especializadas. A organização dos dados do aplicativo não muda. O failover é simples, a recuperação de desastres é integrada e o split brain é tratado sem infraestrutura adicional. A arquitetura de disco compartilhado ainda é relevante para grandes empresas que já possuem uma infraestrutura SAN e equipes de TI dedicadas que gerenciam bancos de dados muito grandes. No entanto, para a maioria das necessidades de alta disponibilidade de aplicativos, a arquitetura sem compartilhamento do SafeKit é a escolha mais simples e econômica. Isso é especialmente verdadeiro para fornecedores de software, ambientes de TO e de borda, e locais distribuídos.
