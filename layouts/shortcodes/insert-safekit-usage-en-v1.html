• 1 Gb/s network ≈ 3 hours / TB
• 10 Gb/s network ≈ 1 hour / TB (depending on disk write performances) | • Use [external shared storage](/best-practises/san-vs-nas-shared-storage-for-a-failover-cluster/) (more expensive, more complex). File count: < 1,000,000 files | • Resynchronization time performance after a failure ([step 3](/architectures/file-replication-byte-level-with-failover-mirror-cluster/#safekit-mirror-cluster)).
• Time needed to compare each file between both nodes. | • Put the many files to replicate in a virtual hard disk / virtual machine.
• Only the files representing the virtual hard disk / virtual machine will be replicated and resynchronized in this case. Failover capacity: ≤ 32 VMs | • Each VM runs in an independent mirror module.
• Maximum of 32 mirror modules running on the same cluster. | • Use an external shared storage and another VM clustering solution (more expensive, more complex). Network architecture: LAN/VLAN network between remote sites | • Automatic failover of the [virtual IP address](/best-practises/how-a-virtual-ip-address-works/) with 2 nodes in the same subnet.
• Good bandwidth for resynchronization ([step 3](/architectures/file-replication-byte-level-with-failover-mirror-cluster/#safekit-mirror-cluster)).
• Low latency for [synchronous replication](/best-practises/synchronous-replication-vs-asynchronous-replication/): typically < 5 ms RTT; higher values should be validated against the application's write rate. | • • If the two nodes are in different subnets, which is common in the cloud, use one of the [other IP rerouting solutions](/best-practises/how-a-virtual-ip-address-works/#safekit-virtual-ip-implementation): a load balancer, the command-line tools of the cloud provider, BGP routing or DNS redirection.
• Use [backup solutions](/best-practises/high-availability-disaster-recovery-hadr/) with asynchronous replication for high latency network.
