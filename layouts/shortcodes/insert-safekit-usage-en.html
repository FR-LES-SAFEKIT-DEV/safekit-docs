• 1 Gb/s network ≈ 3 hours / TB
• 10 Gb/s network ≈ 1 hour / TB (depending on disk write performance) | • Use [external shared storage](/best-practises/san-vs-nas-shared-storage-for-a-failover-cluster/). This solution is more expensive and more complex. File count: < 1,000,000 files | • Long resynchronization time after a failure ([step 3](/architectures/file-replication-byte-level-with-failover-mirror-cluster/#safekit-mirror-cluster)).
• Time needed to compare each file on both nodes. | • Put the files to replicate in a virtual hard disk or in a virtual machine.
• In this case, only the files of the virtual hard disk or of the virtual machine are replicated and resynchronized. Failover capacity: ≤ 32 VMs | • Each VM runs in an independent mirror module.
• A cluster can run a maximum of 32 mirror modules. | • Use external shared storage and another VM clustering solution. This solution is more expensive and more complex. Network architecture: LAN or VLAN between remote sites | • Automatic failover of the [virtual IP address](/best-practises/how-a-virtual-ip-address-works/) when both nodes are in the same subnet.
• Good bandwidth for resynchronization ([step 3](/architectures/file-replication-byte-level-with-failover-mirror-cluster/#safekit-mirror-cluster)).
• Low latency for [synchronous replication](/best-practises/synchronous-replication-vs-asynchronous-replication/): typically an RTT below 5 ms. Validate higher values against the write rate of the application. | • If the two nodes are in different subnets, which is common in the cloud, use one of the [other IP rerouting solutions](/best-practises/how-a-virtual-ip-address-works/#safekit-virtual-ip-implementation): a load balancer, the command-line tools of the cloud provider, BGP routing or DNS redirection.
• Use [backup solutions](/best-practises/high-availability-disaster-recovery-hadr/) with asynchronous replication for high-latency networks.
