• Rede de 1 Gb/s ≈ 3 horas / TB
• Rede de 10 Gb/s ≈ 1 hora / TB (dependendo do desempenho de gravação em disco) | • Usar [armazenamento compartilhado externo](/pt-br/best-practises/san-vs-nas-shared-storage-for-a-failover-cluster/) (mais caro, mais complexo). Contagem de arquivos: < 1.000.000 arquivos | • Desempenho do tempo de ressynchronização após uma falha ([etapa 3](/pt-br/architectures/file-replication-byte-level-with-failover-mirror-cluster/#safekit-mirror-cluster)).
• Tempo necessário para verificar cada arquivo entre ambos os nós. | • Colocar os vários arquivos a serem replicados em um disco rígido virtual / máquina virtual.
• Nesse caso, apenas os arquivos que representam o disco rígido virtual / a máquina virtual serão replicados e ressynchronizados. Capacidade de failover: ≤ 32 VMs | • Cada VM é executada em um módulo de espelhamento independente.
• Máximo de 32 módulos de espelhamento em execução no mesmo cluster. | • Usar um armazenamento compartilhado externo e outra solução de clustering de VMs (mais caro, mais complexo). Arquitetura de rede: Rede LAN/VLAN entre sites remotos | • Failover automático do [endereço IP virtual](/pt-br/best-practises/how-a-virtual-ip-address-works/) com 2 nós na mesma sub-rede.
• Boa largura de banda para ressynchronização ([etapa 3](/pt-br/architectures/file-replication-byte-level-with-failover-mirror-cluster/#safekit-mirror-cluster)).
• Baixa latência para [replicação síncrona](/pt-br/best-practises/synchronous-replication-vs-asynchronous-replication/): tipicamente < 5 ms de RTT; valores superiores devem ser validados em relação à taxa de gravação da aplicação. | • Usar um [balanceador de carga para o endereço IP virtual](/pt-br/best-practises/how-a-virtual-ip-address-works/) se os 2 nós estiverem em 2 sub-redes diferentes (suportado pelo SafeKit, especialmente na nuvem).
• Usar soluções de backup com replicação assíncrona para redes de alta latência.
